# UTF-8 折行读取审查

## 已修复的包内问题

原解析器在展开物理折行之前对整个输入调用 `xrtUtf8Valid`，因此会拒绝
在 UTF-8 多字节序列中间折行、展开后完全有效的内容。
[RFC 5545 §3.1](https://www.rfc-editor.org/rfc/rfc5545#section-3.1)
要求先展开内容行，并指出读取端需要正确恢复这种字符序列。发送端仍应
在完整字符之间折行；本包写出器不改变原有的 75 字节/完整字符规则。

修复仅在 `ical_parse.c` 把 UTF-8 校验放到已展开的完整逻辑行，连同
未知属性、未知参数和嵌套组件一起校验。原始长度上限、NUL/CR 检查、
字段映射、错误类别和资源所有权保持不变；没有新模式、兼容回退或
运行时封装，未修改 XRT/编译器。错误文字改为描述实际输入/UTF-8 失败。

没有新增正文复制或缓冲；每个非空逻辑行调用一次 UTF-8 校验，替代原来
整段输入的一次校验。调用次数改变，总扫描仍为线性；未测吞吐或体积，
不声称性能没有变化。

## 防回归

- C 回归对 PRODID、SUMMARY、DESCRIPTION、CATEGORIES、未知属性、
  引号内未知参数、VALARM 中忽略字段七种位置检查 SP/HTAB、2/3/4 字节
  字符各切点与逐字节连续折行：147 个合法场景正确恢复并可规范写回。
- 140 个非法逻辑 UTF-8/控制字符场景继续报告 VALUE，不能借未知字段
  或折行绕过检查。每次失败清理后核对活动分配数/字节数、非法释放、
  重复释放和 UAF 计数，覆盖现在会较晚失败的部分对象清理。
- 七位置共 236 个实际分配失败点保留 MEMORY、释放半成品并立即恢复；
  C 夹具分别通过 GCC、TCC JIT/AOT，Linux GCC 还启用 ASan/UBSan。
- XLang 源字面量本身要求有效 UTF-8，不能用断开的字节直接写成源
  字面量。测试 companion `utf8_folding.c` 用普通 C 借用字符串提供真实
  折行输入；`utf8_folding.xl` 验证 C→XLang→ical、非法输入与 OOM，
  JIT/AOT 均通过。没有为测试放宽语言规则或增加产品私有适配 API。
- 使用实际 cgen 的两个公开函数原型与 C 头做严格 GCC 对照；错改
  parse 返回类型的负例必须拒绝。
- 新 `folded_calendar.xl` / `folded_calendar_c.c` 展示读取、TEXT 恢复与
  规范写回；五条语言/引擎路径的三行输出及完整 `.ics` 黄金字节一致。
  普通运行不创建文件，只有显式提供输出路径时写出。

两平台同一最终 C 回归重放旧解析器均有 **91 条断言失败**，修复后为零；
这是一个顺序错误的多个场景，不是 91 个独立 BUG。旧对照复用未修改的
测试运行库，Linux 同样保留 sanitizer，没有降低边界来换通过。

## 当前验收与阻断

Windows 默认门禁共记录 43 项，前 42 项符合预期（包含一个必须拒绝的
错误原型）；第 43 项原 `allocations.xl` 在语言字典 build 处仍失败。
56 个输入/工具指纹在运行期间未变。Linux 原生文件系统的完整前置检查
和五份正常 AOT 程序通过，随后也在原 allocations 用例失败；54 个复制
源和 GCC/cc1/Python 三工具前后不变。

单独的 `dev/extlib_blockers/ical_build_var_object_projection.xl` 在两平台
JIT/AOT 均先通过原生 parse→build，再在等价语言字典处 ValueError。
因此 **M1 仍未关闭，整包不能签收发布级**。中央 parse/原生往返用例通过
不等于字典创建可用；原字典构造用例未删除、改写或改为预期错误。

门禁统一有界执行、记录命令/原始退出码与输出，失败保留现场。
Windows 静默编译器 raw37/outer1、Linux 37/127 控制通过。
初写 XLang 夹具的换行表达式与非法源字面量已在夹具中修正；Linux 外层
首次误以为会先停在中央用例，实际停在 allocations；最终按真实停点
重新执行整个门禁与对照。上述均不是产品修复计数。
