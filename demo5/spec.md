# xlang 第五版 Demo 实施规范

## 1. 目的

本规范用于约束 `demo5/` 的开发流程、目录结构、阶段目标、调试出口与推进顺序。

`demo5` 不是语法试玩版，也不是第四版 demo 的补丁延续，而是第五版正式路线的首个实现基线。

第五版 demo 的总目标是：

- 以第五版语言设计文档为语义来源，落地一个真实的编译器前端。
- 明确采用 `Flex -> Lemon -> AST -> 语义分析 -> Lowering -> C 代码生成 -> TCC 运行` 的主路线。
- 先把完整功能做通，再进入正式测试阶段。
- 在每个阶段保留充足的数据输出钩子，方便问题定位和人工理解。
- 支持长周期、无人值守式连续推进，避免频繁停在局部决策上。

## 3. 工程原则

### 3.1 功能优先，测试后置

第五版 demo 采用如下规则：

- 先实现阶段目标对应的完整功能。
- 先打通端到端数据流。
- 先保留人工可检查输出。
- 正式自动化测试放到“功能稳定阶段”统一补齐。

这不等于不做验证，而是把验证分成两类：

- 开发期验证：依赖示例输入、调试输出、阶段性 smoke 运行。
- 稳定期验证：统一补自动化测试、回归用例、失败快照。

因此，`demo5` 前中期不以“测试先行”为主策略，而以“可观察、可复现、可解释”为主策略。

### 3.2 每阶段必须可观测

所有阶段都必须提供至少一种稳定的检查出口：

- 命令行子命令
- 文件落盘输出
- 预编译调试开关
- 可序列化的中间结果

没有调试出口的实现，视为未完成。

### 3.3 严格按阶段推进

推进顺序固定为：

1. Spec
2. 词法分析（Flex）
3. 语法分析（Lemon）
4. AST 与错误恢复骨架
5. 语义分析与类型注册
6. Lowering
7. C 后端
8. TCC 运行链路
9. 模块 / native / 异常 / async / yield / task
10. 功能稳定后统一补测

任何阶段中发现后续需求，不允许逆向污染前面阶段的边界。需要扩展时，应先更新 spec，再继续开发。

### 3.4 默认无人值守推进

除以下情况外，开发默认连续推进，不等待人工确认：

- 设计文档之间存在真实冲突
- 本地依赖缺失，无法合理替代
- 需要在两个代价差异很大的方案中择一
- 发现用户已有代码改动与当前目标直接冲突

其余情况一律按本规范自行推进，并在阶段结束时留下：

- 当前完成状态
- 下一阶段入口
- 已知问题与不阻塞原因

### 3.5 代码风格默认对齐 xrt

`demo5` 的代码风格默认尽可能接近 xrt，避免在长期实现过程中逐步偏离。

执行规则如下：

- 若本规范未单独覆盖某条风格细节，则默认遵循 xrt 风格文件。
- 新增代码优先向 xrt 靠拢，不以个人即时习惯为准。
- 对已存在的 `demo5` 代码做修改时，也应尽量向 xrt 风格收敛。
- 除非存在明确技术理由，否则不引入与 xrt 风格明显冲突的新写法。

## 6. 统一命令入口

`demo5` 使用一个统一可执行程序承载所有检查模式，不拆成多个独立小工具。

建议命令形式：

```bat
xl5 lex <file>
xl5 parse <file>
xl5 sem <file>
xl5 lower <file>
xl5 cgen <file>
xl5 run <file>
xl5 test [selector]
```

统一附加参数：

```bat
--dump-token
--dump-ast
--dump-sem
--dump-hir
--dump-json
--dump-c
--trace-lex
--trace-parse
--trace-sem
--trace-lower
--stop-after=<phase>
--emit=<path>
```

说明：

- 所有阶段性数据输出都通过同一驱动层暴露。
- `--stop-after` 用于精确截断流水线，避免调试时反复改代码。
- `--emit` 用于把中间结果或最终 C 代码稳定落盘。

## 7. 统一调试开关

建议保留如下预编译调试宏：

```c
XL_TRACE_LEX
XL_TRACE_PARSE
XL_TRACE_SEM
XL_TRACE_LOWER
XL_TRACE_CGEN
XL_TRACE_RUN
```

规则：

- 所有 trace 输出都要能统一开关，不允许散落不可控的 `printf`。
- 宏输出应包含最少的定位字段：源文件、行号、阶段、节点种类或符号。
- 文本 trace 优先；必要时再补结构化 JSON。

## 9. 实施阶段

本项目采用“功能阶段”而不是“测试阶段”驱动。每个阶段完成标准以功能打通和调试出口完整为准。

### 阶段 0：工程建线

目标：

- 建立目录结构
- 接入 `flex/lemon/lempar`
- 建立统一 CLI
- 建立统一诊断与 dump 基础设施

完成标准：

- `xl5 --help` 可运行
- `xl5 <phase> <file>` 命令框架可解析
- `release/` 输出目录可自动创建

### 阶段 1：词法分析（Flex）

目标：

- 用 Flex 实现第五版核心词法
- 保留完整 token 位置信息

要求：

- 类型名在词法阶段只识别为标识符或保留关键字，不在此阶段引入语义判定
- 保留 `stop-after=lex` 出口

完成标准：

- `xl5 lex <file>` 输出稳定 token 序列
- 错误 token 和诊断对象可打印

### 阶段 2：语法分析（Lemon）

目标：

- 用 Lemon 建立第五版核心语法
- 构建完整 AST
- 支持错误恢复的基本骨架

要求：

- 先完成核心语法闭包，再考虑语法糖
- `break 2` / `continue 2` 作为语句结构解析，不走函数调用形式
- 保留 `stop-after=parse` 出口

完成标准：

- `xl5 parse <file>` 可输出 AST
- 语法错误可继续收集
- AST 节点均带源位置

### 阶段 3：AST 与诊断整合

目标：

- 统一 AST 工厂
- 给节点补齐来源区间、父子关系、节点种类
- 统一错误对象、警告对象、note 对象格式

完成标准：

- AST dump 稳定
- 诊断输出格式统一

### 阶段 4：语义与类型

目标：

- 建立符号表、类型表、作用域树
- 实现类型引用解析、变量声明检查、函数签名注册、重载决议骨架
- 明确软关键字类型名与普通标识符的区分时机

要求：

- 类型必须走“注册表/查表”路线
- 不把类型系统写死到 parser 分支
- 所有语义检查结果都必须可 dump

完成标准：

- `xl5 sem <file>` 可输出符号表、类型表、语义诊断
- 可完成基础声明绑定与重载候选筛选

### 阶段 5：Lowering

目标：

- 从 AST 进入 HIR
- 从 HIR 进入 MIR
- 建立控制流切分
- 为异常、async、generator 预留 lowering 接口

完成标准：

- `xl5 lower <file>` 可输出 HIR/MIR
- async 与 generator 状态机结果可观察

### 阶段 6：同步 C 后端与 TCC 路径

目标：

- 先打通同步表达式、语句、函数、模块初始化的 C 生成
- 打通 TCC 运行链路

要求：

- 执行上下文统一接到 `XL_ExecCtx`
- 先打通同步路径，不在此阶段混入 async 状态机

完成标准：

- `xl5 cgen <file>` 可输出 C 代码
- `xl5 run <file>` 可运行同步程序

### 阶段 7：异常、模块、native

目标：

- 接入异常传播主路径
- 恢复模块 `import/export`
- 建立 native 模块绑定骨架

完成标准：

- 模块导出表可见
- 同步异常传播可用
- 基础标准模块可加载

### 阶段 8：async / await

目标：

- 完成 async lowering
- 建立 await 运行时绑定
- 接入 `future/task` 运行时接口

完成标准：

- `await` 语义可跑
- async 函数的中间表示和调度日志可 dump

### 阶段 9：generator

目标：

- 完成 generator lowering 与状态机生成
- 建立 generator 的运行时主路径
- 支持 `for in` 消费 generator

完成标准：

- generator 可驱动
- `yield` 切分点可观察
- `for in make_values()` 可运行

### 阶段 10：task 编排与 XLP 接口预留

目标：

- 接入 `task.spawn / all / race / cancel`

完成标准：

- 任务编排基本路径可运行
- runtime / module / binding 结构可承接 XLP

### 阶段 11：功能稳定后统一补测

目标：

- 把前面各阶段的 `examples/` 升格为测试资产
- 按类 xrt 项目的统一测试框架组织回归测试
- 使用单文件入口驱动全部测试
- 固化快照输出

完成标准：

- lexer / parser / sem / lower / codegen / runtime 均有自动化回归
- 稳定快照纳入测试基线

## 10. 词法阶段专项规则

- 一次覆盖核心词法，不做试验版词法器
- 必须覆盖中文标识符、数字、字符串、模板字符串、关键字、运算符、分隔符、注释
- 必须保留原始字面量文本、解码后文本、token 起止字节位置
- 词法输出格式必须稳定，因为 parser、错误恢复、后期测试都会依赖它

## 11. 语法阶段专项规则

- Lemon 的目标不是只“能 parse”，而是形成后续语义层可消费的稳定 AST
- 所有节点记录来源区间
- 节点构造集中在 AST 工厂
- 语法动作不直接掺入复杂语义判定
- 错误恢复至少支持继续收集后续错误
- 解析 trace 输出必须始终可开

## 12. 语义与类型阶段专项规则

- 类型系统必须严格按第五版设计执行
- parser 只构建类型引用节点
- sem 层负责把类型引用绑定到类型表
- 必须可导出：全局符号表、作用域树、类型注册表、函数声明表、重载候选集合、模块导出表、协议实现关系

禁止事项：

- 把“是否为类型名”的最终判定写死在 lexer 阶段
- 把本应在 sem 阶段完成的绑定工作拖到 codegen

## 13. Lowering 与后端专项规则

- Lowering 层必须作为正式层存在，不允许直接把 AST 硬翻译成 C
- AST -> HIR：去语法糖、显式化控制结构
- HIR -> MIR：准备生成状态机、模块初始化和统一调用协议
- async / yield 必须通过 lowering 切分，不允许在 C 后端硬拼
- 同步路径先行，异步路径后补，但接口要在第一轮 lowering 中预留

## 14. 测试资产规则

- 项目前中期不以自动化测试为阻塞门槛，但必须保留测试资产素材
- 每完成一个阶段，至少补一份 `examples/` 输入文件
- 稳定输出默认进入 `release/dump/` 与 `release/trace/`

测试框架规则：

- 使用统一 runner，不为每个用例单独创建构建脚本
- lexer / parser / sem / lower / codegen / runtime 都通过同一套 runner 执行
- CLI 层保留 `xl5 test` 作为统一测试入口

## 15. 无人值守开发协议

为了支持长周期连续开发，后续实现默认遵守以下协议：

- 按冻结 spec 推进，不自行扩项
- 不为了一个边界案例阻塞整个阶段
- 每完成一段工作，都同步更新完成状态和下一入口
- dump 输出先给文本版，JSON 版稍后补
- 某复杂分支先给“未实现诊断”，后续再补语义

以下情况必须暂停：

- 结构设计与 spec 明显偏离
- 把后续阶段责任偷偷塞进当前阶段

## 16. 里程碑定义

为避免无限拉长，实现上定义 5 个里程碑：

- M1：`lex` 可用
- M2：`parse` 可用，AST 可见
- M3：`sem` 可用，符号 / 类型 / 诊断可输出
- M4：`cgen` 与同步 `run` 可用
- M5：异常、模块、async、yield、task 主链路贯通

只有在 M5 后，项目才进入“系统化补测试”阶段。

## 17. 维护规则

- 先更新 spec，再做重大结构调整
- 每次提交围绕一个明确阶段目标
- 实现优先服从流水线完整性和可调试性
- 不为早期测试洁癖牺牲主干推进速度
- 未经用户批准，不向本 spec 追加新需求条目，只更新既有进度勾选与状态

本规范是 `demo5` 的第一份实施基线，后续若要新增 phase spec，应以本文件为总纲拆分。

## 18. 代码风格规则

本节根据 xrt 风格文件整理，作为 `demo5` 的正式编码规范。

### 18.1 缩进与换行

- 使用 Tab 缩进。
- 默认使用 CRLF 换行。
- `#if / #ifdef / #else / #endif` 内部代码块同样使用 Tab 缩进。
- `if`、`for`、`while` 的圆括号内外保留空格，采用 `if ( condition ) {` 风格。

### 18.2 花括号

- 函数定义的 `{` 独占下一行。
- `if / else / for / while` 的 `{` 与控制语句同行。
- 单行分支也必须保留 `{}`，不省略大括号。

### 18.3 表达式

- 组合条件使用冗余括号，避免依赖运算符优先级猜测。
- 类型转换必须显式书写，不依赖隐式转换。
- 涉及长度、容量、索引、内存分配的加法和乘法，先做溢出检查再分配或访问。

### 18.4 注释

- 结构体、重要函数前必须有用途说明。
- 简单函数可使用单行 `//` 注释放在函数前。
- 复杂函数优先使用块注释，至少说明函数说明、参数、返回值。
- 算法密集、位运算、状态机切分、lowering 过程必须补充必要注释。

### 18.5 空行

- 同一功能组的函数之间保留 1 个空行。
- 不同功能组之间保留更明显的空行分隔。
- 文件较大时，通过空行把模块边界切清楚。

### 18.6 命名

- 结构体、类型、枚举、函数名尽量贴近 xrt 风格。
- 字符串变量使用 `s` 前缀。
- 调试变体可使用 `Dbg` 后缀。

### 18.7 防御式编程

- 函数入口优先检查空指针、非法长度、非法状态。
- 内存分配、数组扩容、偏移访问前必须先做边界与溢出检查。
- 出错路径必须返回清晰的错误结果，并尽可能通过统一诊断系统输出上下文。

### 18.8 跨平台

- 跨平台分支中使用 `// windows 方案` 与 `// 其他平台方案` 注释。
- 预处理分支内部同样保持正常缩进和风格一致。

### 18.9 总原则

- `demo5` 的 CLI、diagnostic、AST、semantic、lowering、codegen 模块都按同一风格书写。
- 生成器、状态机、语义绑定这类复杂逻辑优先写清楚，不追求过度“短小”。
- 新增代码时，以“尽可能接近 xrt”作为默认裁决标准。
