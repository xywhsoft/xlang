# 普通扩展库门禁的 GCC 选择（2026-10-28）

## 已确认的问题

gettext 的失败留档自测在 PATH 前放置一个返回 37 的 C 测试夹具，后面仍保留
机器原有 GCC。旧写法直接读取全部命令结果的 `.Source`：

```powershell
$gcc = (Get-Command gcc -CommandType Application -ErrorAction Stop).Source
```

多应用命中时会得到路径数组；部分门禁把它转换成一个带空格的字符串再执行，
形成 `first/gcc.exe second/gcc.exe` 这样的无效文件名。单 GCC 环境无法暴露。
不是库的 ABI 或编译失败，也不能靠换编译器、忽略退出码解决。

统一写法只取 PATH 优先匹配的**一个本机应用**：

```powershell
$gcc = (Get-Command gcc -CommandType Application -ErrorAction Stop | Select-Object -First 1).Source
```

不试运行后续编译器，不添加其他编译后端回退；没有 GCC 就明确失败。
UIA 另有未限定命令类型的写法，同名 PowerShell 函数会使 `.Source` 为空；
函数遮蔽红例确认后也统一使用上述规则。

## 聚焦门禁

从 `demo6` 运行：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tools/test_extlib_compiler_resolution.ps1 -ScopeFile docs/普通扩展库开发优先级_2026-10-12.md
pwsh -NoProfile -File tools/test_extlib_compiler_resolution.ps1 -ScopeFile docs/普通扩展库开发优先级_2026-10-12.md
```

若 `pwsh` 不在 PATH，可从 PowerShell 7 使用 `& ./tools/test_extlib_compiler_resolution.ps1`
并传相同 `-ScopeFile`。脚本是 Windows 门禁，源文件明确采用带 BOM 的 UTF-8，
保证 Windows PowerShell 5.1 正确读取中文注释；被检查脚本则显式按 UTF-8 读取。

门禁使用 PowerShell AST 提取真实绑定表达式，只执行这些表达式，不运行包测试主体。
复用已有 `test/cases/c_run_exit_code.c`，临时编译两个路径带空格的可执行夹具；
验证选择结果确实可以执行并返回 37，没有额外的伪编译器实现。

每个宿主均检查 74 处绑定的五组条件：

1. 只有一个编译器。
2. 多个编译器与机器原有 PATH 并存。
3. 反转两个目录顺序，必须跟随新的优先级。
4. 存在同名 PowerShell 函数，仍只能选择本机应用。
5. 没有本机编译器，即使同名函数存在也必须报找不到命令。

修改前多编译器用例为红；修正 65 份同类脚本后，前三组通过，函数遮蔽在
UIA 再次为红；最后统一该入口后，两种宿主五组全通过，共 740 次绑定核对。
成功或失败都恢复本进程 PATH，并在检查绝对目录仍位于 `build/test` 后清理
本次独占夹具。不修改系统 PATH、全局函数、机器 GCC 或主线测试源码。

这项门禁可以快速防止共同设置问题复发，不能替代每个库的 C/XLang 功能、
资源生命周期、格式互通、设备/网络及 JIT/AOT 验收；本阶段没有重复运行 100 包回归。
