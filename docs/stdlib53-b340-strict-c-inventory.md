# 完整标准库清单的严格 C 验收

系统、文本和容器夹具增加完整清单的当前产品严格 C 检查。此前完整清单已有
JIT、模块和独立 AOT 执行记录，严格 C 检查则分散在各专项。现在每份正向
夹具都由同一普通构建的真实 CLI 生成 C，再分别编译为 GCC O0／O2 对象。

## 输入与隔离

人口来自完整独立 AOT 报告，必须与冻结源码发现的清单及显式新增夹具完全
一致。检查器拒绝子集报告、不同构建产品和改动过的断言源码；不会仅挑选
能够通过的用例。预期语义拒绝仍须报出原有诊断，且不留下生成 C。

编译器在独立目录运行，使用真实 CLI／DLL／SO 和内嵌 VFS，不读取工作区
编译器源码作为替代实现。GCC 使用单独的检查 SDK：公开头来自该构建，私有
声明头来自同一 VFS 清单固定的输入。没有 src／lib／res／include 兜底目录，
不替换原生提供方，也不把检查对象注入实际运行产品。

GCC 使用 C11、Wall、Wextra、Werror；沿用现有生成代码门对未使用实体、
未完整初始化字段及 pointer-sign 的明确告警豁免。不屏蔽隐式函数声明、
错误类型转换等实质诊断。所有独立失败集中收集，不因首个失败停止整批。

## 检查对象与运行条件

专用宿主和平台条件夹具也必须生成有效 C 并通过两级对象编译。不过它们的
运行条件原样保留：Windows 的 DST gap／fold 不能由一次编译证明，专用
对象图／线程宿主也不能由普通程序入口替代。

语法错误、错误指针返回及未声明调用三个 C 反例，在 O0／O2 均须由相同
编译命令拒绝，且不能留下有效对象。这六项检查防止门禁接受失败的编译。
生成 C、真实对象、源输入、命令、退出码和日志均保留指纹。

## 双端结果

Windows、Linux 各 327 项完整人口通过：326 项正向生成 C，并各取得 O0／O2
对象，共 652 个实际对象；另 1 项为预期语义拒绝。每端六项错误 C 反例均
被拒绝，合计各 985 个阶段，输入前后指纹一致。本轮没有发现新的生产缺陷，
没有修改编译器、运行时、XRT 快照或工作区 release 产品。

报告分别在 `D:/xlang-validation/stdlib53-b340-strict-win/results.json` 和
`/var/tmp/xlang-stdlib53-b340-strict-linux/results.json`。实际产品仍来自固定
普通构建，断言人口与完整独立 AOT 报告相同，不能把编译次数解释为函数
或运行分支覆盖率。Windows DST 及其余功能完成审计继续单独处理。

只读复核证书 `/var/tmp/xlang-stdlib53-b340-certificate.json` 重新计算了
14,812 项关联文件指纹，并核对两端人口、逐项断言源码、生成 C、对象命令与
六项拒绝控制一致。证书记录严格 C 清单通过，完整功能结项未宣告。

## 复测

完整产品与独立 AOT 验收之后运行：

```text
python tools/check_stdlib_strict_c_shipping.py --root <frozen-demo6> --build-report <ordinary-build.json> --aot-report <complete-aot-results.json> --out <fresh-directory> --jobs 2
```

此门验证生成代码的严格 C 编译，不再次执行程序、不证明全部运行分支，
也不替代功能、生命周期、真实 OOM 或平台验收。原生模块定位与裁剪另外见
[标准库模块定位与当前产品裁剪](stdlib53-b339-module-pruning.md)。
