## 核心结论

生态已有实质进展，尤其是 CSV、graph、chardet、LZ4，以及 HTTP、邮件、SSH、
AI 和 GUI 的真实后端。当前最主要的短板不是缺少库名，而是：

1. C 后端、xlang 声明、运行库符号和编译器还没有在同一正式构建上一起验收。
2. 部分库已经完成范围明确的专项，但官网或旧计划把这种通过扩大为整体可用。
3. 仍有一些包只公开名称查询、格式辅助或小算法，不能按同名完整产品推荐。
4. 测试、双语范例和页面生成的登记机制还未完全闭合。

应从“有多少目录”转向“哪些能力在指定构建上可以可靠交付”。不把源码已修复
写成正式程序已修复，也不把集成失败误判为原生后端不存在。

## 还有哪些质量缺口

1. **C ABI 横向验证。** 例如 [ONNX 的 XL 声明](../release/extlibs/onnxruntime/src/onnxruntime.xl:2)
   使用 XL int，而 [C 实现](../release/extlibs/onnxruntime/src/onnxruntime_artifact.c:390) 返回 C int；
   HTTP 对象析构的 long long/无返回值冲突已在本批修正，六个包完成两平台
   实际生成原型和负控制验证。同一门禁仍需覆盖 Client、XWS、AI 等其他对象族，
   不能靠关闭检查解决，也不能把严格语法检查等同于原型匹配。
2. **返回文本所有权。** color 已去共享环形缓存；semver、units 等仍有共享可变结果缓冲。
   需要统一 C 调用者保留结果、语言复制/接管、并发与回调重入合同。
3. **标准压缩互操作。** LZ4 已使用标准 Frame；LZMA/miniz/Snappy 的流仍含自定义外层块格式。
   自压自解通过不代表可与同名常用工具交换文件。Zstd 仍需完整独立互操作专项。
4. **真实网络边界。** memcached 的 get 使用单次 recv 当完整应答；应补分包、截断、空值与未命中区别。
5. **Agent 边界。** [工作区解析](../release/extlibs/xbot.agent/src/agent.xl:131) 只比较字符串前缀，
   [读取限额](../release/extlibs/xbot.agent/src/agent.xl:364) 在整文件读取后按字符截断。
   这不是可靠的路径边界或字节资源限额，须单独压实。
6. **验收入口。** `run_phase1_extlibs.ps1` 只消费 case/example/cSmoke，不消费 cExamples；
   color/CSV 的新专项也不能仅因工具脚本存在就算进入日常总门禁。
7. **页面和 API 清点。** 本地 ONNX/CSS 等生成页仍标 phase1-verified，与本次失败不符；
   自动 API 正则仅覆盖部分 export 形态，漏掉 export extern 等。应复用导出元数据，
   用带构建、时间、范围的测试证据更新状态，不能靠目录存在生成“已通过”。
8. **AI 后端缺失合同。** [RapidOCR 原生创建](../release/extlibs/rapidocr/src/rapidocr_artifact.c:608)
   在后端不可用时仍分配占位句柄；调用还会分配带空数组的占位结果。即使 output.ok
   为 false，也不能用“结果为空”替代明确的后端不可用错误。应统一创建/调用/释放
   的后端归属，增加缺库、缺符号、后端重新可用及失败恢复测试，再用固定模型验真。

本轮仅确认本地官网；color 正文已生成且哈希一致，没有据此声称线上已部署。

## 建议顺序

1. **先收共同阻塞点**：批量核对 C ABI、所有权和错误分类；修复缺符号、NUL/迭代器等共享边界。
2. **把已验证源码纳入正式构建**：固定 XRT 快照，重建并在同一份 CLI/DLL 上复验，避免源码/发布状态长期分裂。
3. **先交付高收益基础组合**：21 个有专项基础的库优先完成正式验收，补完 color 和两个新 CRT 模块的资料/登记。
4. **接通已有重型后端**：网络用受控回环/TLS，AI 用固定模型，GUI 用真实交互；补成功路径和失败恢复。
5. **最后扩展占位方向**：按实际能力和新增成本评估；先补可用 API，不用名称表或演示输出充当完整生态。

每个准入库至少保留明确的 API/所有权合同、成功和失败测试、双语范例（适用时）、
当前构建证据及已知限制。最终官网只展示真实通过的范围。
