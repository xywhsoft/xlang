# 扩展库开发问题清单

> 来源：扩展库生态六轮批次（82 → 116 个压实库）开发过程中发现并逐项验证的语言/编译器/运行时问题。
> 每项均附最小复现、根因分析与当前规避方案。修复后请同步更新本清单状态。
> 更新日期：2026-08-17
> 审计记录：2026-08-17 对 8/15 14:17 构建全量复核——**修复 3 项**（P1-1、P2-1、P3-4），
> **仍存在 9 项**（P0-1/2/3、P2-5/7、P3-1/3、P4-1），其余为设计约定类不适用修复判定。
> 27 个新库测试 + gzip 在新构建上全部通过，无回归。

## 分级说明

- **P0**：运行时崩溃或数据丢失，无语言层规避以外的保护
- **P1**：功能缺失或链接失败，阻塞正常开发路径
- **P2**：ABI/封送语义陷阱，有稳定规避但与直觉相反
- **P3**：语言锐边（保留字、严格类型等），一次学习后可绕开
- **P4**：C 库兼容性问题（TCC / MSVCRT），影响扩展库 C 代码编写

## P0-1 var 动态值 `.length()` 方法调用崩溃

**状态**：仍存在（2026-08-17 审计确认）

**现象**：
```xlang
var x = [1, 2, 3]
int n = x.length()   // 运行时段错误
```

**证据**：gdb 栈为 `xrtValueGetCallable → xrtValueType`（xlc.dll 内），即运行时把
`.length` 当可调用值做方法分发时对非 callable 值解引用崩溃。属性形式
`x.length`（无括号）工作正常。

**波及**：任何在 var 上误写方法调用形式的代码直接段错误而非报编译错。

**规避**：一律使用属性形式 `.length`。所有 27 个新库的测试与范例已按此编写。

**修复建议**：
1. 语义阶段检测"var 动态值 + 方法调用语法"直接报编译错误（最低成本）；
2. 或运行时 `xrtValueGetCallable` 前置类型检查，非 callable 抛 TypeError。

## P0-2 链式 var 上的方法调用触发运行时致命错误

**状态**：仍存在（2026-08-17 审计确认）

**现象**：
```xlang
var d = {"note": "hello"}
assert d["note"].contains("ell")
// xlang runtime fatal: function value ABI violation (code 3)
```

**证据**：批次 3 ical 测试中 `e1["description"].contains(...)` 首次触发，与 P0-1
同族——对 var 索引链的结果做方法调用，方法分发走到非法值。

**规避**：先绑定 typed 变量再调用：
```xlang
string note = string(d["note"])
assert note.contains("ell")
```

**修复建议**：与 P0-1 同源，可一并处理。

## P0-3 var 嵌套子树经中间变量绑定后内容丢失（顺序相关）

**状态**：仍存在（2026-08-17 审计确认：外层 3 / 内层 0 的半丢失形态不变）

**现象**：对 extern 返回的嵌套 var 结构，经"逐层属性访问 + 中间变量绑定"路径
取出的子树为空；同一路径直接深层链式书写则正确。**且仅在前面有若干次 extern
调用后出现**（顺序相关，单次调用不触发）：

```xlang
import redis

func main(...) as int
    var a = redis.decode("+OK\r\n")                       // 预热调用
    var b = redis.decode(":9\r\n")
    var c = redis.decode("$2\r\nhi\r\n")
    var d = redis.decode("*3\r\n:1\r\n*2\r\n$3\r\nabc\r\n$-1\r\n$3\r\nxyz\r\n")
    var outer = d["value"]
    var nested = outer["value"]     // [1, ["a","b"], "x"]，长度 3 正确
    var one = nested[1]
    var two = one["value"]
    var inner = two["value"]        // 期望 ["abc", null]，实际长度 0！
    println(inner.length)           // 输出 0
    return 0
end
```

对照：`var direct = d["value"]["value"][1]["value"]["value"]` 可取到正确内容。
批次 4 redis 测试因此把嵌套断言改写为直接深层链式形式。

**根因推断**：var 槽位重赋值/move 时对嵌套容器子树的引用计数或所有权处理有
缺陷；中间绑定路径把子树移出后原结构被提前释放。深层链式路径可能因表达式
临时值生命周期不同而幸免。

**波及**：所有从 extern 消费嵌套 var（多层数组/对象）的代码，是当前对扩展库
开发影响最大的问题。

**规避**：
- 嵌套取值用直接深层链式表达式，不落中间变量；
- 或在外层一次性 `string(...)` / `int(...)` 收敛为标量。

**修复建议**：最高优先级。定位点在 var 赋值的 move/lowering 路径
（`src/sem` 或 `src/cgen` 的 var 槽位写回），建议以本清单的复现脚本作为
回归用例（外层长度 3 正确、内层为 0 的"半丢失"形态是关键线索）。

## P1-1 `file.writeBytes` / `file.readBytes` 运行时助手未发射

**状态**：✅ 已修复（2026-08-17 审计确认：读写往返正常，gzip 包恢复通过，
phase1 全量套件解除阻塞）

**现象**：任何使用 `file.writeBytes(path, buffer)` 或 `file.readBytes(path)`
的代码，TCC 链接阶段报：
```
tcc: error: unresolved reference to 'xl6_xrt_buffer_file_write_bytes'
```

**证据**：助手声明见 `src/stdlib/xl6_stdlib_data.c:7462`（映射
`__xl_runtime.fileWriteBytes`），发射逻辑在 `src/cgen/xl6_cgen_buffer.c:255`。
gzip 包的未提交 WIP 因此无法链接，**完整 phase1 套件（86 个库）在 gzip 处
中断**；gettext/epub 的二进制读写测试也被迫改走 C 侧 XRT 文件 API。

**规避**：扩展库 C 层直接用 `xrtFileReadAll` / `xrtFileWriteAll`
（需 `#define XRT_MODULE_FILE_WHOLE`）。

**修复建议**：修 gzip WIP 后核对 `xl6_cgen_buffer.c` 的发射条件；恢复后全量跑
`tools/run_phase1_extlibs.ps1` 收口。

## P2-1 extern 返回裸 C `NULL` 被封送为空数组而非 var null

**状态**：✅ 已修复（2026-08-17 审计确认：探针包返回裸 NULL，var 侧
`r == null` 正确命中）

**现象**：C 函数 `return NULL;` 在 extern `as var` 下变成空 `array`，
包装层的 `if r == null` 永不命中。

**证据**：批次 2 shellwords 的 split、批次 3 srt 解析均踩中。

**规避**：C 错误路径一律 `return xrtValueNull();`。

**修复建议**：编译器对 extern `as var` 返回的裸 NULL 做规范化（或文档化为
硬性约定）。

## P2-2 `xrtValueClone` 对容器是共享 backing 的浅拷贝

**现象**：克隆体与原件共享存储，修改克隆体等于修改原件。

**证据**：json.patch 开发中发现（批次 1），`__xrtValueContainerClone` 仅
retain backing。

**规避**：纯函数式 API 一律 `xrtValueDeepClone`。

---

## P2-3 `xrtValueGetFloat` 只接受真浮点存储

**现象**：int xvalue 经 GetFloat 返回 false。

**证据**：statistics 直方图计数在批次 1 期间因此恒零。

**规避**：先试 GetFloat，失败回退 GetInt 转 double。

---

## P2-4 xlang `int` 为 64 位，C 桥接必须 `long long`

**现象**：C 返回 32 位 `int` 的 extern `as int`，-1 被零扩展成 4294967295。

**证据**：semver 的 `major("bad")`（批次 1）。

**规避**：全部数值返回 `long long`（参考 crontab 既有约定）。

## P2-5 `Buffer` 以 HANDLE(8) 跨 ABI，非 bytes
n**状态**：仍存在（2026-08-17 审计确认：typeId=8、GetBytes 失败、HandleView 空，三探针不变）

**现象**：extern `as var` 收到 Buffer 时 `xrtValueGetBytes` 失败；
`xrtValueGetHandle` 得到的指针上也读不到缓冲内容。

**证据**：gettext 的 parseMo（批次 3）探针确认 typeId=8 且 BufferView 为空。

**规避**：二进制数据不走 var-Buffer。模式 A（hex 字符串跨 ABI，redis/ntp/
socks/modbus/mqtt 采用）；模式 B（`point` + `c_size` 传裸指针，
modbus 的 hexToFrame/frameToHex 采用，配合 `Buffer(point)` 包装与
`buf.data()` / `buf.len()` 取参）。

## P2-7 异常位置报告指向内联包源码行号

**状态**：仍存在（2026-08-17 审计确认：用户第 15 行调用报为 14:9，仍指内联坐标）

**现象**：测试文件里第 62 行抛出的 ValueError 报告为"64:9"——实际是
import 展开后**内联包源码**里 throw 语句的行号，与用户代码行号无关。

**证据**：graph（批次 3）与 mqtt（批次 6）排查时多次被误导。

**规避**：定位时用二分打印；或对照包源码行号。

**修复建议**：诊断位置应映射回用户源文件（import 内联时保留原始位置信息）。

## P3-1 保留字超直觉
**状态**：仍存在（2026-08-17 审计确认：`func f(int end)` 仍报 parse 语法错误）

`end`、`out`、`auto` 均为保留字，不能作参数名/变量名。三者在六轮中各踩中
一次（graph 的 `end` 参数、ntp 的 `out` 变量、mqtt 的 `out` 变量）。
完整表见 `docs/语言基础设计.md` §5。建议：`end`/`out` 这类常用词考虑在
非歧义位置放行，或至少在词法错误信息中提示"保留字"。

## P3-2 严格类型显式转换清单

- float 形参不接受整型字面量（`units.bytes(0)` 需写 `0.0`）
- var 元素参与算术前需 `int(...)` / `string(...)`（`cue["startMs"] + 500` 报 sem 错）
- 多返回值解包只能在声明处 `auto a, b = f()`，预声明后赋值不支持
- `catch` 必须绑定变量（`catch e`），裸 `catch` 语法错
- string 无 `[]` 索引，用 `charAt`/`byteAt`
- stdlib 命名空间不能 `import`（`import file` 报错），直接使用即可
- 嵌套 typed 数组的链式属性（`samples[0].length`）报
  "class field receiver is not a class value"，改用动态 var

## P4-1 TCC 的 `strtod` 接受 FORTRAN `d` 指数
**状态**：仍存在（2026-08-17 审计确认：探针 strtod("1d2") 返回 100）

`strtod("1d2")` 返回 100 而非停在 `d`。units 的时长解析因此把
`"1d2h30m"` 解析错（批次 2）。规避：手写十进制解析器。

## P4-2 MSVCRT `%hhu` 解析错误

`sscanf("%hhu", ...)` 把 127 解析为 0（批次 4 socks 的 IPv4 点分解析）。
规避：手写数字解析。

## P4-3 其余 C 侧注意点

- `strtok` 不可重入，嵌套使用互相破坏（semver 曾踩）
- 注释里出现 `*/`（如 `x/X/*/absent`）会提前终止注释
- XRT 文本值建议经 `xrtValueStringTake`（bson 模式），避免 struct 传参 ABI 风险
