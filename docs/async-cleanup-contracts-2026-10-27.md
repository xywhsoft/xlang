# 异步清理顺序与任务首错

本批修复两个实际缺陷，公开语言及运行时 ABI 不变。

模块同时使用默认 continuation executor 和 TaskPool 时，旧生成代码在第一个
服务返回 BUSY 后立即退出，后续 TaskPool 因而收不到关闭请求。新准备流程先
非阻塞地关闭／探测每个服务；要求等待且没有失败时再进入等待阶段。失败仍
保留首个 checked 结果，BUSY 仍保留模块及服务。独立错误作用域隔离调用者
已经存在的错误，避免其阻止后续退役进展。没有服务的模块保留简单 READY
路径。服务选择继续来自验证后的 XLIR ABI，不读取 AST 或猜测生成文本。

`task.spawn` 的旧适配先调用捕获清理，再取得任务错误；当任务体和析构同时
报错时，错误 88 会被析构错误 77 覆盖。现在在清理前使用现有 checked 清理
事务保存调用结果，随后执行原有释放和异步错误边界。失败位不依赖是否成功
分配诊断对象；取消优先级及输出发布前清理规则不变。

验证使用同一个冻结源配置实际重编译 Cgen，并保留其预处理文件、命令、对象
及 SDK 哈希。Windows 完整 task-storage 工作器的 33 个配置通过，包含 14 次
确定性合同输出及原有拒绝变异。Linux 额外通过 GCC O0/O2、TCC 下的模块清理、
异步结果和回调清理九个配置。Linux 使用相同生成 C 及固定 XRT／驻留源码，
独立原生编译、链接和执行；这不是一次新的 Linux 编译器发布构建。

每个模块清理配置保留 210 次 worker／回调退出、60 次自身退役 BUSY、300 次
禁止嵌套提交，以及完整构造 OOM 前缀。回调配置保留 1,200 次执行、6 次提前
取消、63 次实际分配失败；同时报错时明确验证 AsyncError 的 cause 就是原始
任务错误对象。发布屏障仍在 Future 完成时检查，物理尾段结束后再检查内存。
