# 独立程序循环对象图退役缺陷与验收门

独立 AOT 程序退出存在已复现的语言生命周期缺陷：现有 Stack、
Tree 和并发 Queue 循环图夹具在 Windows／Linux 均构建成功，
但预期的 1／5／6 个析构回调实际全部为零。本批新增明确失败的
验收门，尚未修复该生产实现。此前真实产品 JIT／模块验证仍有效，
不能据此外推独立 AOT 对象图已通过，更不能关闭发布总验收。

## 复现与对照

验收门使用三份现有 ownership 夹具的原始正文，只在开头增加
退出观察注册。原有析构、模块字符串和完整容器字段断言逐字保留。
观察 C 文件不收集对象、不替换所有权适配器，也不释放任何图节点；
它仅统计实际回调、验证字段及拒绝重复析构。

独立程序由新产品 CLI 和内嵌 VFS 编译，搬到不含产品库的目录执行。
每个程序检查 Windows 导入或 Linux 动态依赖；不依赖 xl／xlc 库，
Linux 没有 RPATH／RUNPATH。观察文件另经两端 GCC 严格 C O0／O2
编译。

| 用例 | 预期析构 | Windows 实际 | Linux 实际 | 结果 |
| --- | ---: | ---: | ---: | --- |
| 无环类对照 | 1 | 1 | 1 | 通过，析构可读取模块字符串 |
| Stack 自环 | 1 | 0 | 0 | 失败 |
| Tree 五类循环 | 5 | 0 | 0 | 失败 |
| Queue 六类循环 | 6 | 0 | 0 | 失败 |

每端十二个阶段：四次构建、四次依赖检查、四次独立执行。
三个循环用例均由观察器以 91 退出；工具自身返回失败，
Complete 与 AotGraphRetirementAcceptance 均为 false。
观察对照通过不代表循环图的字段断言已经执行；当前循环析构没有
发生，正是验收失败的原因。程序退出后的 OS 回收也不等于语言析构。

此门已接入当前产品总门，不能只运行较容易通过的子集后跳过。
Linux 整批清单及其他子门通过，总门仅因 AOT 图退役失败；Windows
另复现一次 terminal_session 失败。两端总门均明确失败，输入哈希
保持不变。父门分别记录 625／627 行，不与子门内部步骤混加。

## Windows 终端的新增失败

本次 terminal_session 失败只收到 TTY、stderr 和 line-ready，没有
尺寸与回复；不能归为已经完成的成功验收。另用仅增加诊断的私有
子程序重复 256 次，复现两次模块失败：完整输入已读，原生等待
超时后重新查询仍为 80×24，目标为 96×32，窗口输入模式已启用。
这不是单纯漏掉通知而实际尺寸已经正确的情形。

现有数据尚不能区分早期 resize 与子程序启动阶段的覆盖、平台
行为或实现缺陷。没有修改 XRT、加延时或重发请求来掩盖它；原始
失败、终端字节和诊断代码均保留。此前的尺寸观察修复及成功重跑
不关闭这次新复现，平台归因和实际修复继续。

## 实现断层

当前独立 main 的退出路径调用 xl_script_module_unit_checked，最终
执行生成的全局拥有值释放。循环中的内部强引用仍在，因此普通
引用计数释放不能触发这些析构。真实 JIT 宿主另外驱动驻留
OwnershipPlan 的准备、语义析构、整图提交及物理清理；独立入口
没有等价的驱动。该路径差异与观察结果一致。

修复应补齐共同的驻留生命周期能力，不在 Cgen 中复制收集算法：

1. 独立模块具有真实的拥有记录，初始化前绑定 CodeOwnerGraph；
   类、闭包、Future 和任务持有实际 lease，模块全局环境不能早于
   这些使用者退役。不能以静态代码永不卸载为由忽略模块数据寿命。
2. JIT 与独立入口复用同一对象图协议和策略授权。按已验证 IR／
   原生组件声明提供精确适配器、准备和完成能力，未知节点在
   Count／Trace 前拒绝；不能猜测叶子、虚构引用或折减实际 RC。
3. 驻留驱动在真实静默边界运行准备、析构、提交与完成。析构前
   字段和模块全局保持完整；冻结或宿主锁内不调用可重入语言代码。
4. 首错、无诊断失败、OOM、BUSY、外部强根及持锁恢复保持现有
   checked 合同。失败不能冒充清理成功，也不能丢掉可恢复的记录。
5. 入口退出只输出声明化调用和元数据。纯标量程序不引入对象图
   组件；三类图、Future／闭包、独立程序及双端裁剪须一起验证。

这些是修复方向和必要不变量，不是已实现功能。完整外部根矩阵、
独立图 OOM、worker 故障、模块卸载和发布总门仍待完成。

## 插桩补测的编译预算

动态函数及 float32 补测将 GCC 编译预算与运行预算分开，默认均为
300 秒；显式 compile-timeout 只改变 GCC 编译上限，范围为
30 至 1800 秒。每条命令记录上限、实际耗时、日志及 SHA256。
超时是独立失败状态，不能作为负例的成功拒绝。

Windows／Linux 普通通道各 126 阶段通过，保留原 O0／O2、严格 C、
JIT／模块／AOT、两条各 47 次完整分配前缀和两个错误实现反例。
Linux ASan／UBSan 补充通道重跑的 126 阶段也已完成；其中 Stack
批量用例的 O2 编译实际耗时 609.263 秒，低于本次显式 1200 秒
编译预算，运行上限仍为 300 秒。没有降级 O2 或删除断言，旧的
300 秒失败报告保留。该次补测缺口已闭合，但慢编译仍是吞吐问题。
插桩范围仍限生成 C、宿主及显式选入的 float32 提供方，不代表
全部驻留提供方或 XRT 已插桩。

证据位于 E:/xlang-validation/stdlib53-b300-* 和 Linux 对应目录。
CRT 0、XRT 19 组未决策与对象池最后不变；对象图退役属于已承诺
语言核心的修复，不是等待重新决定标准库外观的事项。
