# 普通扩展库验证中的资源中断记录

本记录只解释本次 miniz 验证的已观察事件，不改变 100 包范围、编译选项或
既有签收标准，也不把已通过的其他包重新判为失败。

## 分开记录代码问题与资源事件

- 新 C 原生入口测试首先暴露桥接头的包含顺序缺陷，以及测试本身漏声明
  目录模块。桥接头改为公开不透明 xvalue 前向声明，两种顺序均经严格 C
  检查；测试显式声明并链接目录模块。这两项有明确代码修复，不归因给内存。
- 随后默认 Windows 门禁在编译共同测试运行时时返回 1：

```text
GCC runtime build: exit 1
cc1.exe: out of memory allocating 35960 bytes
```

现场为 `demo6/build/test/miniz_guard/run_1b43bc3c02584d5ba642c5e2ab9c77bf`，
保留输入指纹、GCC 16.2.0 版本、完整命令和输出。没有把这个失败计成通过。
同期 WSL 调用返回 `Wsl/Service/0x80072746`，随后 `wsl --list --verbose`
显示 Ubuntu Stopped；本任务没有停止 WSL 或修改其配置。

## 系统证据与解释边界

只读查询 Windows System 日志得到来源
`Microsoft-Windows-Resource-Exhaustion-Detector` 的事件 2004：

| 本地时间 | 事件报告 |
| --- | --- |
| 2026-10-28 15:56:35 | Windows 诊断虚拟内存不足，vmmem 占用 12,827,041,792 字节 |
| 2026-10-28 16:10:13 | Windows 诊断虚拟内存不足，vmmem 占用 12,504,444,928 字节 |

这与 GCC 明确报告的分配失败相符，说明不能把这次中断直接认定为 miniz
编解码错误。之后某次系统查询已有空闲虚拟内存，也不能否定失败瞬间的短缺。
日志列出的高占用进程不等于责任归因，没有确定哪个任务或行为触发短缺，
也没有证明 WSL 每一次中断都来自同一原因。

尤其不能据此关闭 INI 的旧 `Illegal instruction` ICE，或 HCL/SQLite 的
历史异常；它们仍遵守各自的风险记录和关闭条件。

## 正常复验

- 没有改变既有优化级别（Windows `-O2`、Linux sanitizer `-O1`），
  更没有更换 GCC、删减断言、放宽限时、借用旧对象或替换 XRT。
- Windows 同一默认包门禁单独执行，完整退出 0，包括新增原生入口和
  头文件顺序、严格 C、Python zlib、语言与双语 JIT/AOT，前后指纹一致。
- 随后建立经目录差分和同步确认的 Linux 原生文件系统新快照，实际 boot id
  为 `2c9ef906-413d-4b4a-88a7-0d6930d36845`。同一默认 Linux 门禁完整
  退出 0，包含 ASan/UBSan、原生入口、Python zlib 和新旧双语 JIT/AOT。
- 发布物保持[验收矩阵](普通扩展库发布验收矩阵_2026-10-28.md)的固定基线，
  没有升级开发中的主线或 XRT。该结果只覆盖正常资源条件下的本包合同，
  不是内存不足下必能构建、所有平台、长期压力或挂载盘耗时问题的认证。

后续若再次出现资源分配失败，继续保留原始状态并核对系统事件。优先错开
本任务自身的重编译峰值，不停止其他任务，不自动修改页面文件或虚拟机设置。
