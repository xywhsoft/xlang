# 扩展库现状复核：2026-09-27 增量

## 结论

扩展库已有大量实质实现，当前主要矛盾已经不只是补功能，而是让已有实现稳定地
穿过 C/XL ABI、运行时符号、对象生命周期和发布资源这几层。不能把 225 个包目录、
116 个测试登记或官网页面数量解释成相同数量的发布级库。

本轮读取全部活动 manifest、集中测试登记、包内测试入口及本地官网，抽查近期
重要实现，并运行 49 个正式发布版 Windows JIT 用例：**30 通过、19 失败、无超时**。
另外使用既有隔离候选复测 12 项：1 通过、11 失败。这是不同选择，不能相加为通过率。

本轮没有修改编译器、扩展库实现、XRT 快照、发布程序或官网正文。新增的 Agent
诊断样例只解析路径，不读写目标文件。所有源代码修补、未构建修改与本轮实际运行
的二进制严格区分；已有源代码不能直接视为发布版已经修复。

## 能力重新分层

### 有明确专项基线的 16 个包

`aho_corasick`、`argon2`、`bloom`、`blake2`、`blake3`、`sqlite`、`xxhash`、
`crc32`、`md5`、`murmur3`、`sha3`、`siphash`、`mqtt`、`gzip`、`brotli`、`bz2`。

本轮这 16 个包的选定正式 JIT 用例全部通过。历史专项另有 C/XL、回调、OOM、
跨平台或文件事务证据，但各包范围不同，本轮没有重跑全部专项。

特别是三个压缩库的完整文件故障收口来自隔离构建，不能用当前基础用例通过掩盖
正式运行库尚未推广的修复。MQTT 的专项也不能自动扩张为完整客户端会话引擎认证。
建议将这 16 个包作为首个固定发布验收批次，而不是宣布整个生态已达到 RC。

### 正则已经取得新的可运行进展

`xregex` 的包内测试在正式程序和隔离候选上均通过，输出 `xregex package ok`。
该入口覆盖捕获、matcher 复用、模板/回调替换、拆分、多模式集合及部分错误分支。

当前 [原生包装](../release/extlibs/xregex/xregex_native.c:359) 持有 matcher 输入副本，
不再让跨调用捕获依赖临时 C 字符串；原生句柄访问也返回底层 matcher，而不是包装对象。
这解决了之前实际复现的输入借用期问题，但不能据一个综合用例宣称全部平台、并发、
回调重入、OOM 与 AOT 都已完整收口。

README 的裁剪段仍写旧 TYPED_ARRAY 及连续数组布局，而 manifest/包装已经采用
VALUE_CONTAINER/xvalue；文档需要跟随验收同步，不能作为当前 ABI 的依据。

### 已有实质实现，不能再按占位计算

| 方向 | 当前可看到的真实能力 | 仍需完成的验收 |
| --- | --- | --- |
| HTTP / WebSocket | xhttp 与子包、xws；URL/query、头/cookie/MIME、正文、流、multipart、表单、客户端对象 | 默认发布链、错误分类、取消/超时、TLS、连接/正文生命周期、真实回环服务 |
| 邮件 | xmail 的 MIME、SMTP/POP3/IMAP 配置、认证、结果及客户端，19 个公开类 | TLS lease 接入、协议状态机、分段输入、认证失败、超时和重复关闭 |
| SSH | C 层有 wire/packet/KEX/auth/connection/session/client；XL 有 5 个公开类 | 当前 XL 接入、完整会话/认证/通道对象及真实会话测试 |
| GUI / 图形 | XUI 有 64 个公开类，XGE 有 9 个；已有控件、事件桥接和对象表层 | 实际窗口、事件回调、销毁期间回调、渲染/输入法和设备条件；import 不够 |
| AI / 图像 | ONNX Runtime、RapidOCR、OpenCV、xfeat、dinov3 等已有后端实现 | 物理 ABI、固定小模型成功样本、结果正确性、重复加载/释放及并发 |

公开类数量仅表示当前 manifest 所列 XL 文件的声明规模，不表示验收覆盖率。
已实现代码不计入占位库新增 10000 行预算；不能因为这些后端较大就直接暂缓。

### 通过用例但公开范围仍有限

- `mysql`：当前入口主要是命令/类型/状态名称、转义、DSN。没有凭此验收连接、

- `faiss`：当前入口主要是类型/度量名称与标量向量距离，不是完整索引构建、

- `nats`：当前入口主要是协议名称、subject 匹配和 URL 辅助，不是完整连接、

- `xbot.agent`：独立的离线 Agent 工具体系，不等于完整 xbot。当前源码注册的是

前四个包的本轮选定测试通过，但不能由此推断同名领域功能完整。

## 当前运行阻断

### 49 项正式程序抽样

两批选择互不重复、使用相同正式程序和稳定的共同输入：重点包 29 项为 21 通过、
8 失败；工具包 20 项为 9 通过、11 失败，总计 30 通过、19 失败。不是随机抽样，
不能将比例推广到 218 个公共包。

工具包通过：`ansi`、`gettext`、`ical`、`memcached`、`money`、`qr`、`rss`、
`shellwords`、`vcard`。这些仅是本轮用例通过，不自动加入上述专项基线名单。

| 阻断类别 | 包/入口 | 当前证据与处理方向 |
| --- | --- | --- |
| 布尔返回 ABI 不一致 | barcode、color、graph、json.patch、semver、sitemap、slugify、units | C 返回 long long，XL extern 声明 bool；全部在生成 C 的原型检查处失败，需整组核对而非放松检查 |
| C int / 语言 int 不一致 | onnxruntime、rapidocr | `ort_available_native`、`rapidocr_vis_image_native` 等原型冲突；需覆盖全部同族声明 |
| 运行时符号缺失 | cli | 找不到 `xl6_xrt_os_args`；正式与隔离候选均失败 |
| 运行时 TypeError | csv、srt、statistics | 当前两个程序均复现；尚不能把三个包统一归因于同一个 bug |
| SDK feature 合同 | xmail、xhttp、xhttp.client、xssh | 正式程序被相关 feature 依赖检查阻断；已有候选能越过其中部分检查，但仍有下一层问题 |
| IR 控制流 | xhttp.body_file | 可达的非空返回函数块未终结，尚未进入正文文件行为测试 |

HTTP client 用例本次允许 100 秒，约 72 秒后返回具体编译错误，因此不再列为
“超时”或网络死锁；本入口没有执行真实 HTTP 请求。

graph 需要特别注意：C 函数有 `-1/0/1` 三态，[XL 包装](../release/extlibs/graph/src/graph.xl:1)
先错误声明成 bool，再试图判断 `< 0`。修正声明时必须保留错误状态，不能仅把
C 返回值改成 bool 来消除原型报错。公开 `isDag` 仍可返回 bool，私有外部声明应
准确表达 C 合同，然后由薄包装处理错误。

### 既有隔离候选并非全部解决

受测程序为 `build/test/extlib-native-20260927/runtime`，不是本轮重建的最新源码。
选择 11 个失败入口和 xregex 正例：xregex 通过，其余 11 项仍失败。

- xmail 越过 feature 检查后，缺少 `xl6ExtlibTlsLeaseRelease`。
- xssh 越过 feature 检查后，暴露 `xssh_code_name` 的 C int/XL int 参数冲突。
- xhttp URL 越过 feature 检查后，遇到 ValueError 与用例 RuntimeError 捕获预期
  不一致。这是错误合同/测试口径问题，不能据此宣布 URL 解析算法错误。
- CSV 仍在字典 writer 路径失败。native-backed XL 字段初始化修补尚不能作为
  端到端已修复的证明，还应核对继承初始化、方法接收者、容器字段与失败回滚。
- cli、graph、srt、statistics、ONNX、RapidOCR、body_file 仍保留上述阻断。

## 用例通过也未覆盖的边界

以下是本轮源代码审查发现的具体问题或待验证风险，不与 49 项测试结果混算。

### Agent 工具系统

[AgentWorkspace.Resolve](../release/extlibs/xbot.agent/src/agent.xl:131) 只比较路径字符串
前缀，没有检查路径分量边界：`.../work-other/file` 具有 `.../work` 前缀，却不在
该工作区内。还需明确 Windows 大小写、符号链接/目录联接及读写权限的合同。

新增的只读探针在正式/候选程序上均先被 `xl6_xrt_time_now_local` 缺失阻断，
没有执行到 Resolve。因此路径问题的证据是源码，不冒充探针已运行成功。

其他源代码缺口：

- `max_command_seconds`、`timeout_seconds` 只有声明与赋值，没有进入实际执行逻辑。
- `fs_read` 先 `file.readText` 全量读取，再按字符数截断；`max_read_bytes` 既不是
  读取阶段的资源上限，也没有按字节计量。
- 文件工具声明的 `start_line/end_line` 和 `recursive` 没有在对应实现中消费。
- `Trace` 拼接 event/name/run_id 等 JSON 字符串，需要统一 JSON 编码。

这些应作为 Agent 库的正式能力缺口处理，不能只补成功路径范例。

### Memcached 客户端

当前集中用例只测试命令构造与完整响应文本解析，没有运行客户端收发。
[语言包装](../release/extlibs/memcached/src/memcached.xl:93) 仍存在以下问题：

- `set` 将 `data.length` 作为协议 bytes；语言 string.length 按 UTF-8 字符计数，
  非 ASCII 文本必须使用字节长度。
- `get/set/del` 都只调用一次 `recv` 就解析响应，没有处理 TCP 分段、合并响应或
  大于默认读取上限的内容，应按协议长度/终止符消费并保存未消费数据。
- `get` 用空串同时表达未命中和命中空值，需要明确结果模型。
- 命令构造函数（历史源码位置：`../release/extlibs/memcached/memcached_native.c:54`） 使用共享静态
  缓冲区，key 验证也不足；需要补并发、重入和控制字符边界。

不应把协议文本用例通过解释成生产客户端已经可用。

### 共享结果缓冲与输入规模

`color`、`semver`、`units` 使用可变的进程级静态字符串环；Memcached 使用静态
结果数组。没有同步或明确的调用者独占约束，C 调用者持有返回指针以及多线程调用
都会受到后续调用影响。应优先复用 XRT 的有所有权结果/调用者输出缓冲合同，
而不是再增加一套隐式缓存兼容层。本轮未运行并发压力测试。

[graph 的 XGraph](../release/extlibs/graph/graph_native.c:43) 含 4096 个节点及 32768 条边
的固定数组，并在多个函数中作为局部变量。x64 下仅该结构约 544 KiB，尚未计入
工作数组；即使小图也付出这份栈开销。建议改用 XRT 堆容器、按需容量与明确资源
上限，随后补大图、OOM、非法权重及算法复杂度测试。本轮未将此宣称为已复现崩溃。

## 官网与文档

目前 35 个公共包没有任何本地官网入口，集中在 20 个小型工具及 xhttp 家族、
xmail、xregex、xssh、xws。已有代码不能被官网遗漏，也不能未验收就标为稳定。

generated 下有 31 个页面不对应当前公共活动包：29 个包名已不在活动集合中，
另 2 个为内部包。应在后续发布时统一迁移、归档或明确标记；本轮未删除页面。
16 份维护型页面与包内源文件相同，说明同步一致，不说明所有 API 已验收。

现有部分文档仍描述旧类型布局、旧包装方式或超出测试范围的能力。官网页建议明确
公开 API、平台/后端依赖、示例、最近验证构建及尚未支持的范围，禁止从测试登记数
自动生成“已压实”标签。

## 下一步优先级

1. **先收共享接入。** 全部 extern 的物理类型/const/析构/容器合同，运行时符号、
   SDK feature 与 VFS，native-backed 初始化及 XLIR 控制流。用生成声明与真实 C
   实现共同编译的门禁覆盖整个函数族，不降低编译器检查，也不添加旧 ABI 回退。
2. **形成固定发布批次。** 16 个基础库加完成后续验证的 xregex，绑定同一组源码、
   XRT 快照和三个程序哈希，执行 C/XL、JIT/AOT、Windows/Linux 与破坏性边界。
3. **优先接通已有高价值实现。** CSV、CLI、小型工具、HTTP 客户端及邮件；再推进
   SSH 完整会话、AI 固定模型成功用例、GUI 实际事件/生命周期。
4. **补真实使用合同。** Agent 路径/权限/资源限制、客户端拆包/超时/取消、线程安全、
   中文与二进制、文件失败事务。不能只修当前报错的第一行。
5. **单独评估有限辅助层与真占位。** MySQL/FAISS/NATS 等按明确的目标 API 估算
   剩余新增成本；10000 行只限制占位库需要新增的实现，不限制已有后端总规模。
6. **验收与交付同步。** 测试、C/XL 范例、包内 README 和官网随同一批次更新，
   测试失败、未执行、后端不可用、功能未实现分别记录。

当前更准确的评价是：**生态能力储备已经丰富，但发布接入的一致性与真实场景
测试仍明显落后于实现广度。先打通现有能力，比继续增加包名更有价值。**
