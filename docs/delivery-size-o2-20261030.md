# 保持 O2 的发布体积优化验收

2026-10-30。机器可读数据见 [统计、哈希与验证摘要](reports/delivery-size-o2-20261030.json)。

本轮保持宿主代码 `-O2`，不启用 `-Oz` 或 LTO，保留双库、自包含 AOT、完整 SDK 和嵌套编译。Windows 的预编译对象仍由 TCC 产生；Linux 的普通 ELF 对象使用 GCC `-O2 -fPIC`，由 TCC 链接。没有加入 Windows COFF 链接器改造。

## 实际产品大小

下表对照相同源码起点的 **O2 基线**，单位均为字节。基线只切换宿主优化等级；最终版再应用本轮的表结构与资源目录优化。CLI 另启用剥除符号和无用节裁剪；调试构建仍保留 `-O0 -g3`。

| 产品 | O2 基线 | 本轮最终版 | 减少 |
| --- | ---: | ---: | ---: |
| Windows xl.exe | 130,175 | 71,168 | 59,007 |
| Windows xl.dll | 16,921,600 | 14,153,728 | 2,767,872 |
| Windows xlc.dll | 22,305,280 | 19,443,712 | 2,861,568 |
| Linux xl | 47,232 | 47,224 | 8 |
| Linux libxl.so | 18,085,424 | 15,550,000 | 2,535,424 |
| Linux libxlc.so | 23,402,320 | 20,965,200 | 2,437,120 |

因此，Windows xlc.dll 在相同 O2 下节省约 **2.73 MiB**，xl.dll 节省约 **2.64 MiB**。此前已经发布到本地的 Os 构建分别为 19,621,888 和 14,268,928 字节；最终版在提升到 O2 后，仍分别比它们少 178,176 和 115,200 字节。不能把 O2 基线的收益直接描述成对旧 Os 产物的净收益。

同一普通 Hash 用例的 Windows AOT 都为 790,016 字节，未引入额外运行时包装。导入 xlang 的嵌套编译样例则从 19,961,856 降到 17,139,200 字节；Linux 对应样例从 20,710,073 降到 14,122,406 字节。

## 已实施的优化与维护方式

### 原生调用合同按实际参数存储

原表为 3,700 条、每条 872 字节，固定保留 16 组参数槽。本轮将声明和存储分开：

- 原始 C 声明保存在 `src/ir/xl6_ir_direct_bridge_declarations.inc`，字段唯一口径是 `xl6_ir_direct_bridge_fields.inc`。
- 构建时由 C 编译器求值，生成紧凑的只读 `xl6_ir_direct_bridge_data.inc`；参数序列和附加合同仅在逐字段相同时共享。
- 7,638 个逻辑参数使用 3,796 个物理参数记录，附加信息共享为 781 条；主记录为 40 字节。
- 记录总量从 **3,226,400 降到 480,160 字节**，减少 **2,746,240 字节**。这是记录数据本身的精确数值，不含字符串、机器码和最终链接重定位，不能再与上表产品总收益相加。
- 按排序名称二分查找，支持原有的普通及带引号名称；查询不分配内存。最大参数数量仍为 16，所有类型、拥有权、效果、回调、原生服务和错误合同均保留。

以后更新声明后运行 `python tools/generate_ir_contract_catalog.py`。Windows/Linux 构建均自动生成；`--check` 可拒绝过期生成文件。`check_ir_contract_catalog.py` 编译并比较全部字段和参数槽，已接入静态 smoke 与 RC0。

### VFS 内部目录改为索引与共享池

内部目录升级为 v3：资源名称改为 UTF-8 字符池偏移，span 使用 blob 下标；完全相同的 span 序列共用一份。文件逻辑长度保留 64 位，读取 API 签名不变。嵌套编译会直接序列化同一格式。

隔离试验使用完全相同的 2,742 项输入和物理打包顺序：

| 项目 | 原目录 | 紧凑目录 |
| --- | ---: | ---: |
| 资源／span／blob 记录 | 158,336 | 93,552 |
| 物理 span 数量 | 2,852 | 2,178 |
| 压缩 payload | 6,674,939 | 6,674,939 |

目录记录精确减少 **64,784 字节**；指针重定位和名称对齐也随之减少，其最终效果计入产品总量。数据内容、别名关系、原有内容去重、差异区间共享及 1 MiB 固实块均保留。

逻辑名称排序供二分查询，物理数据继续按原清单顺序打包。运行时缓存仍为 8 个、每个最多 1 MiB 的解压块，不通过增大缓存换取体积收益。

### Linux 预编译使用 GCC O2

`precompile_builtin.py --native-cc <gcc>` 生成普通 ELF；构建记录编译器、目标、系统头、源文件、参数与对象哈希。GCC 使用自身系统头，不复用 TCC 的 `-B` SDK 搜索路径。Windows 显式拒绝这一入口，继续使用 TCC 对象。

Linux 相同 XRT 实现对象从 6,722,959 降到 4,932,088 字节。GCC 指令与展开信息的压缩效果不同，不能以原始对象减少量推算 DLL 资源收益；同一份最终源码及目录格式的单因素对照，运行库资源从 TCC 的 1,492,471 增到 GCC 的 1,645,419 字节，编译器资源从 6,276,347 增到 6,759,633 字节，分别增加 **152,948 / 483,286 字节**。这项优化减少的是执行代码体积并提高执行性能，不能算作压缩资源节省；总产物仍按上表净减少。

同一个由 TCC 编译的驱动，分别链接两种 XRT 对象；每轮处理 327,680,000 字节，三轮校验和完全一致。中位 CPU 时间：

| 操作 | TCC 对象 | GCC O2 对象 |
| --- | ---: | ---: |
| Hash64 | 0.334941 s | 0.009939 s |
| CRC32 | 1.335415 s | 1.154634 s |

这些是两个本地计算微基准，不代表全部语言程序或编译器的加速比例。

## 试验后未作为发布优化采用的做法

- **ELF 元数据重写**：保留所有符号和重定位，原始唯一对象减少 71,460 字节，但压缩 payload 从 6,674,939 增到 6,694,477 字节。没有将此重写器接入生产构建，也没有剥除所需符号、重定位或展开信息。
- **按同族文件重排固实块**：压缩后少 61,572 字节，但在预编译清单顺序与 8 槽 LRU 的冷读取模拟中，编译器需要解压的字节从 33,930,939 增到 49,322,084。发布默认继续保留清单顺序；生成器的显式试验参数不改变默认行为。

## 性能观察

使用相同 O2 基线及配套 SDK，每条命令启动独立进程，交替运行三轮，操作系统文件缓存未清空。以下为墙钟中位数，包含启动与 I/O：

| 平台／工作负载 | O2 基线 | 最终版 |
| --- | ---: | ---: |
| Windows 数学 check | 0.0853 s | 0.0810 s |
| Windows 随机库 cgen | 0.5029 s | 0.2647 s |
| Windows Hash AOT 构建 | 0.8657 s | 0.5217 s |
| Windows 嵌套编译程序构建 | 0.7016 s | 0.5794 s |
| Linux 数学 check | 0.0559 s | 0.0472 s |
| Linux 随机库 cgen | 0.5423 s | 0.3373 s |
| Linux Hash AOT 构建 | 0.9652 s | 0.6051 s |
| Linux 嵌套编译程序构建 | 0.7373 s | 0.5928 s |

样例未观察到退化；三轮小样本不构成全部负载的性能承诺。合同查询自身另有同一 O2 进程内的 150,000 次查询对照，结果与逐字段验证一并保存。

## 验收与明确边界

- 两端均对 3,700 条合同逐字段比较，包括空槽、空指针、字符串、枚举身份、参数与返回约束；篡改参数及返回合同的实际产物均被拒绝。IR/Cgen 单元测试通过。
- Windows GCC/TCC 各验证 51 项目录夹具，包括 NUL、空文件、中文路径、名称后缀、别名、跨块读取、缓存淘汰、seek、私有对象保护与两代嵌套重建。
- 从实际 DLL 读取核对 Windows 600 + 2,744 项资源；Linux 用独立 Python LZMA 解码器逐项核对 SO 中的 502 + 2,638 项资源，输入哈希保持不变。
- 两端版本、SDK、双库各 1,469 项驻留导出、格式化／argv、分配失败前缀、17 阶段隔离交付，以及原生／嵌套编译 EXE 和共享库交付通过。公开产品版本仍为 0.6.0、版本码 `0x00000600`，嵌入 API ABI 版本仍为 1。
- 两端普通语言验证各 303 阶段，均为 **301 通过、2 失败**，与基线一致。两项仍是 `stdlib_file_async` 的 JIT/AOT 退出清理失败，没有转为通过或放宽断言。
- 原生拥有权发布门禁仍返回 `ready=false`，当前 12 个销毁入口缺少所需合同；本次宿主自动／显式关闭的有界退役检查通过；历史间歇性失败不据此宣告修复。既有 XLIR 静态总守门在基线与最终源码上均停在同一模块清理文本断言。本轮完成体积优化，不代表全部发布阻塞已解决。
- 未运行攻击、网络安全专项测试、外部网络握手或新的 DST 测试。并行 IDE 工作未纳入本轮提交。

外部完整证据目录为 `F:\xlang-validation\size-o2-20261030`，包括冻结源码、构建日志、输入／产物哈希、逐阶段失败记录和试验对象。最终只清除了一个内部头中空宏的五处尾随空格；GCC 与 TCC 对 IR 翻译单元的预处理输出分别逐字节不变，并再次通过全字段合同验证。嵌入资源逐项校验以冻结构建输入为准。
