# List 与 Set 的统一值域配方

List 与 Set 现在共用完整的 XLIR 值域配方，Set 另有独立、可验证的键合同。
目标工厂复用驻留 typed 存储和转换，不在 Cgen 中实现哈希、复制或遍历算法。
本批完成配方和原生目标构造验证，不切换语言 Set 的生产者或消费者。

## 值域与键语义

`collectionValueSchemaType` 指向独立封闭的 Array<T> 值准入 witness。
它描述逻辑元素域、名义身份集、物理槽、转换与所有权，不表示 List 或 Set
采用 Array 存储，也不授予语言源载体权限。List 与 Set 保留各自的 owner 身份。

`XL6_IrValueCollectionRecipe` 一次性提供 owner、值域、元素、身份集、槽、
转换、转移和键合同。验证重新推导这些字段，拒绝缓存伪造、跨族 witness、
未封闭的子域和超出递归预算的类型；失败不发布部分配方。

Set 的 `setKeyAbi` 区分三种规则：

- 基础值按内容，字符串使用精确字节长度，null 与空字符串不同。
- retained Value 域中的基础值仍按内容，可变对象与容器按实例引用身份。
- Future 按控制块身份。

键合同不是所有权合同：引用身份键仍需保留对象、验证其完整准入域并参与
生命周期管理。List 和其他非 Set 类型必须没有 Set 键合同。可变键不调用
用户定义的内容哈希或相等回调，因此插入后修改对象内容不改变其键身份。

## 构造与组件边界

Cgen 使用同一个已验证的值域配方，选择固定的 List 或 Set 驻留工厂。
生成代码只构造 witness、调用 owner 工厂并绑定投影；不从类型名字或旧 AST
恢复语义，也不将失败降级为 ANY 或 wire 集合。目标预检失败时不输出部分代码。

类型表里出现 Set 值域不等于使用 Set 原生操作，不能仅因此引入 SET_NATIVE
或 SET_KEYS。正常语言源工厂保持原状；这批的独立目标验证不是其切换凭证。
现有完整子域可以用于目标构造，尚未支持的嵌套 Set 域保持 pending，不能只凭
相同的物理槽认定可互换。

## 验收与剩余工作

`check_stdlib_set_recipes.py` 从真实语言源码执行语义检查和 XLIR 构建，
对每个完整配方执行 21 个合同变异，并检查后代域、相同物理槽、擦除域和
pending 域。伪造合同必须同时被配方、C/header 输出和原生依赖计划拒绝。
独立生成的目标 C 在严格 O0/O2 下运行向量、完整分配失败前缀和作用域进入
失败前缀；普通源码的生成与 JIT 检查不允许偷偷启用 Set 目标工厂。

Windows 与 Linux 使用最终冻结的选定源码分别重建编译器。相邻 List 配方、
语言路径、持久化、Set 原生方法及按需组件登记共同回归。证据位于
`E:/xlang-validation/stdlib53-b189-*` 和 Linux 对应目录；早期失败尝试保留。
Linux sanitizer 仅覆盖选定原生闭包，不代表整个编译器或发布库已完成验收。

剩余工作包括 Set 的递归域、语言工厂与方法、动态分发、复制、迭代、导入和
持久化的统一迁移，然后完成 Dict 与发布总验收。DEV-XRT-53 继续进行；
CRT 0 项、XRT 19 个未决策组和对象池最后开发的安排不变。
