`c_size(string.len(...))` 向原生接口传长度：`crc32`、`md5`、`murmur3`、`sha3`、
`siphash`、`gzip`、`bz2`、`lz4`、`lzma`、`miniz`、`snappy`。
这是源码发现数量，不是 40 项已执行失败的测试；详细文件/行号进入本次逐包 JSON。

这些接口处理字节，`string.len` 则是 UTF-8 字符数。CRC32 的字符串包装直接将该长度
传给字节哈希，gzip 的字符串包装也直接转交压缩接口，含多字节字符时会截断输入。
应逐库统一文本/Buffer 的字节合同，增加中文、emoji、嵌入 NUL、分块边界与 C/xlang
对照；不能仅修原型到能够编译，就将整包标为完成。本轮没有运行这 11 包的完整
Unicode 矩阵，也没有修改实现。

CRC32 另有首次建表数据竞争风险：`crc32_table_ready` 为普通静态 int，初始化读写
没有同步。slice-by-8 直接将输入 memcpy 到 uint32，计算依赖小端字节序。两项均为
源码审查发现；本轮未执行并发首次调用或大端目标验证，不能伪称已有失败复现。

当前实现定位（CRC32 已修复）：[CRC32 字节长度](../release/extlibs/crc32/src/crc32.xl:18)、
[原生字节入口](../release/extlibs/crc32/crc32_native.c:34)、
[CRC32 建表与字节序](../release/extlibs/crc32/xrt_crc32.c:10)、
[gzip 字符长度](../release/extlibs/gzip/src/gzip.xl:56)。

后续 CRC32 专项已关闭该包三处长度混用、首次建表同步和宿主字节序假设；动态验证

07:19 JSON 是修复前线索，不应继续据此认定当前 CRC32 仍有同样缺陷。

### 能力范围与已有缺陷

源码复查仍确认以下限制：

- MySQL 公开面是命令/类型/状态名称、escape 和 DSN 辅助，没有连接、认证、查询、
  结果集。状态文本的固定 64 字节缓冲仍有越界问题，已有独立 C ASan 证据。
- NATS 公开面是名称表、subjectMatch、URL 与策略辅助，不是完整 PUB/SUB 或 JetStream。
- FAISS 公开面是名称表及 CSV 字符串距离计算，不含真实向量索引。小数解析不能
  推进的问题仍在，点积/余弦也使用同类循环。
- BLAKE2 当前已使用 `string.byteLen`，显式校验密钥和摘要长度，错误获取改用
  `xrtErrorMessage`。上述新增专项已消费 216 条向量并验证回调重入、取消、OOM、
  Unicode 密钥与失败恢复；撤销 01:42 时“边界验收尚未闭环”的当前结论。

更正此前 BLAKE2 分析中“忽略后端返回值”的说法：本仓库后端的 init/update/final
接口本来返回 C `void`，旧问题是没有校验调用前提，不是漏查这些函数的返回状态。

定位入口：[MySQL](../release/extlibs/mysql/mysql_native.c:63)、

### 推理包装的额外交付风险

- ONNX、OpenCV、RapidOCR、xfeat、dinov3 的加载层仍可见 `LoadLibraryExA`；
  RapidOCR 字符集读取还使用 `fopen`。它们没有统一到 XRT 的 UTF-8 文件/加载能力，
  须补非系统代码页字符路径、长路径及外部模型部署测试。这里是源码审查发现的风险，
  不声称本轮已经执行真实模型的中文路径验证。
- RapidOCR 的 `charset_info` 通过 `snprintf` 把 path/first/last 原样拼入 JSON，
  未做 JSON 转义。带反斜杠、引号等输入会造成错误内容或无效 JSON；当前测试只判断
  返回字符串非空，不能发现这一面的问题。应使用结构化 JSON 输出并解析验证内容。
- RapidOCR README 的“四条识别结果”描述落后于源码。当前主路径按最多六项一批
  循环处理检测框，最后调用 list 组装器；不能将旧文档上限当成当前识别上限。
  可视化函数中最多画 16 个框的限制仍存在，应明确范围或补齐。
- 同一包装层有全局错误/字符串缓冲与缓存。应测试并发实例和回调重入的结果寿命，
  不能从单线程 smoke 推断它们可供 Agent、HTTP handler 多线程共享。

## 六、建议的实施顺序

1. **优先统一原生接入合同。** 公共 C 头、xlang extern、实际 cgen 声明做严格编译
   对照；分别处理 bool/整数、const 指针、无返回析构、typed 容器。禁止关闭检查，
   或把 xtarray 与 xvalue* 强转后视为完成。
2. **统一 XRT 模块选择与 SDK 注入。** 包的 xrtModules、编译依赖闭包、预注入声明
   与头文件 feature 检查采用一致合同；独立 C、JIT、AOT 都测试。Brotli 门禁也是
   这类问题的一个样本，不应在每个库中另造一套运行库。
3. **修复已经确认的缺陷并完成交付。** xxhash 的 C JIT 与限定交付缺口已关闭，
   继续处理 MySQL 越界、FAISS 非前进解析，
   保持 BLAKE3、Aho、BLAKE2、Brotli、SQLite 已补齐的限定
   专项范围，不把它们重新列作完全未实现。
4. **按共同边界逐包验收。** 回调、取消、异常、所有权、OOM、空值/超限、Unicode
   与 Buffer 都要覆盖。CRC32 已完成该批边界，继续清理其余 10 包的字符数/字节数混用。
   集中 catalog 未选择的压缩 progress 用例须在各包门禁中
   明确挂接；测试文件存在不等于测试已经被执行。
5. **将真实后端成功路径单列。** HTTP/mail/SSH 做本地协议端点与错误会话；推理库
   用固定模型/样本，补 UTF-8 路径、JSON 内容与并发边界；GUI/设备记录实际环境。
   之后同步 C/xlang 范例和官网能力范围，清除已不适用的旧上限描述。
6. **最后重新评估占位库。** 10000 行预算只用于占位库新增实现。已有 ONNX、
   RapidOCR、xbot 等实现正常压实，不因已有代码量大而跳过；其他候选逐项判断成本，
   不能把旧 budget-review/environment-review 标签当作最终延期决定。

当前不提供一个“生态压实完成百分比”：各包目标范围、测试深度和外部环境差别太大。
更可信的发布清单应逐包记录实现范围、构建哈希、通过平台、测试入口和明确排除项。
