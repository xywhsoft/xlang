================================================================================
xlang 第五版语言设计方案
================================================================================

版本：v5.0-draft1
定位：编译型脚本语言，前端为 xlang，后端为 C，运行时深度绑定 xrt



================================================================================
一、第五版语言设计的总原则
================================================================================

1.1 版本定位
------------
第五版语言标准建立在以下事实上：
	- 第三版更偏可行性验证，语义覆盖广，但机制尚未正式定型
	- 第四版开始转向“编译到 C，再由 tcc 内存编译运行”的脚本编译器路线
	- 第五版继续沿用第四版路线，但恢复第四版因基础设施不足而砍掉的能力

因此，第五版语言的定位是：
	- 一门编译型语言
	- 一门运行时深度依赖 xrt 的语言
	- 一门希望拥有脚本语言动态能力、但又保持编译期机制清晰的语言


1.2 设计目标
------------
第五版语言设计必须同时满足：
	- 语法简洁，沿用第四版风格
	- 编译期机制可见、可解释、可扩展
	- 运行时能力可通过 xrt 稳定承载
	- 动态能力不是“运行时放飞”，而是“编译期可分析、运行时可承载”


1.3 核心原则
------------
	1. 保留第四版的语法风格
		- `func`
		- `if / elseif / else / end`
		- 无分号、按换行分句
		- 类型名即构造/转换入口

	2. 明确编译期与运行时边界
		- 语言标准定义语义
		- 编译器完成绑定、检查、Lowering
		- xrt 承担值、容器、异步、协程、任务、IO 等运行时能力

	3. 机制优先于能力
		- 类型表
		- 函数声明表
		- 协议表
		- 模块导出表
		- native 映射表
	这些机制必须先清晰，能力才能持续增长

	4. 动态能力必须进入静态机制框架
		- async / await
		- yield / generator
		- 动态模块绑定
		- native 扩展类型
	都不能以黑盒方式塞进语言



================================================================================
二、第五版语言的范围
================================================================================

2.1 第五版核心标准
------------------
第五版语言标准核心包括：
	- 基础类型系统
	- 函数与重载
	- 模块系统
	- 错误处理
	- 异步函数与 await
	- yield 生成器
	- 任务编排相关标准库接口
	- 与 xrt 绑定的 native 模块接口


2.2 第五版暂缓项
----------------
以下内容暂不作为第五版核心语言标准：
	- class / custom / object 的完整标准
	- 闭包与匿名函数的完整标准
	- 泛型
	- 宏系统
	- 元编程

说明：
	这些内容不是否定，而是第五版优先先把机制与运行时重能力定稳。



================================================================================
三、词法与基础语法风格
================================================================================

3.1 源文件与编码
----------------
	- 源码编码：UTF-8
	- 标识符允许中文
	- 区分大小写
	- 不允许以数字开头


3.2 语句分隔
------------
	- 以换行作为主要语句分隔
	- 分号不是核心语法
	- 跨行续接仅在语法明确允许的位置成立


3.3 块结构
----------
统一保留第四版块风格：
	- `if ... end`
	- `func ... end`
	- `try ... catch ... finally ... end`
	- `namespace` 暂缓


3.4 保留关键字
--------------
第五版建议的硬关键字：
	- 控制流：
		if, then, else, elseif, end
		for, in, while, do
		break, continue, return

	- 函数与声明：
		func, const, as

	- 异步与协程：
		async, await, yield

	- 错误处理：
		try, catch, finally, throw, assert

	- 模块：
		import, export

	- 逻辑：
		and, or, not

	- 特殊值：
		null, true, false

类型名不建议继续作为硬关键字，而应由类型表识别。



================================================================================
四、类型系统
================================================================================

4.1 设计方向
------------
第五版明确继承第四版思路：
	- 类型不是写死在语法中的特殊分支
	- 类型由编译器启动时注册到类型表
	- Parser 通过类型表判断一个标识符是否为类型名


4.2 核心类型集
--------------
基础值类型：
	- bool
	- int / int8 / uint8 / int16 / uint16 / int32 / uint32 / int64 / uint64
	- float / float32 / float64
	- string
	- time
	- point

容器类型：
	- array
	- list
	- set
	- dict
	- range

特殊类型：
	- var
	- auto
	- type
	- function
	- null

运行时标准类型：
	- error
	- module
	- future
	- task
	- channel
	- generator

补充说明：
	- `type` 是运行时类型对象
	- `int` / `string` / `array` 等类型名可以作为 `type` 值参与传递
	- `Type(expr)` 返回 `type`
	- 运行时需要支持 `t.name`、`t == string` 这类基础反射能力


4.3 值类型与引用类型
--------------------
值类型：
	- null
	- bool
	- 整数系列
	- 浮点系列
	- string（默认 UTF-8，也可承载任意字节序列）
	- time
	- point

引用类型：
	- array
	- list
	- set
	- dict
	- function
	- future
	- task
	- channel
	- generator
	- module
	- error


4.4 类型声明
------------
支持三种基本形式：
	int a = 1
	var v = anyValue
	auto x = expr

规则：
	- 显式类型：右值必须可隐式转换
	- `var`：接受任意值
	- `auto`：推导结果必须唯一
	- `const`：必须初始化


4.5 类型构造与转换
------------------
保留第四版的统一模型：
	- 类型名既可用于声明，也可用于构造/转换

示例：
	int a = int(3.14)
	string s = string(a)
	time t = time("2025-01-01")

规则：
	- 隐式转换只允许安全转换
	- `int(expr)` / `string(expr)` / `time(expr)` 等表示显式构造或转换
	- `Type(expr)` 返回运行时 `type` 对象
	- 有损转换默认必须显式书写


4.6 类型别名
------------
第五版建议保留 `typedef`，但作为二级能力，不阻塞核心标准。

内建数值类型命名约定：
	- `int` 与 `float` 保留为默认整数/浮点类型名
	- 精确位宽类型使用全称：`int8` / `uint8` / `int16` / `uint16` / `int32` / `uint32` / `int64` / `uint64`
	- 浮点精度类型使用全称：`float32` / `float64`
	- 不再采用 `i32` / `u64` / `f64` 这类缩写作为第五版标准命名

建议形式：
	typedef MyInt = int
	typedef BytesMap = dict



================================================================================
五、字面量与表达式
================================================================================

5.1 保留的字面量
----------------
	- 整数
	- 浮点数
	- 布尔
	- null
	- string（默认 UTF-8，也可承载任意字节序列）
	- time
	- array
	- list
	- set
	- dict


5.2 模板字符串
--------------
第五版建议恢复模板字符串，并明确它依赖 xrt 模板能力。

形式：
	`hello {$name}`
	`value = {$a + b}`

规则：
	- 模板表达式在编译期解析
	- 运行时按 string builder / xrt 格式化能力执行


5.3 索引与成员访问
------------------
保留：
	- `obj.member`
	- `obj?.member`
	- `obj[index]`
	- `obj?[index]`

可索引对象通过协议判断，不写死在语法分支中。


5.4 运算符
----------
第五版沿用第四版主运算符体系：
	- 算术：`+ - * / % **`
	- 比较：`== != < > <= >= ~=`
	- 逻辑：`and or not`
	- 位运算：`& | ^ ! << >>`
	- 赋值：`= += -= *= /= %= **=`
	- 特殊：`? :`、`??`、`?=`



================================================================================
六、变量、作用域与声明
================================================================================

6.1 作用域
----------
第五版采用词法作用域：
	- 模块作用域
	- 函数作用域
	- 块作用域


6.2 变量声明
------------
允许：
	int a
	int a = 0
	var a = expr
	auto a = expr


6.3 常量声明
------------
允许：
	const int MAX = 100
	const string NAME = "xlang"

规则：
	- 常量必须初始化
	- 编译器要区分“绑定不可变”与“对象内容不可变”
	- 容器常量默认只保证绑定不可重赋值



================================================================================
七、函数系统
================================================================================

7.1 函数定义
------------
第五版继续使用 `func`：
	func add(int a, int b) as int
		return a + b
	end


7.2 参数
--------
支持：
	- 位置参数
	- 默认参数
	- 数组可变参数 `...`
	- 字典可变参数 `***`

示例：
	func greet(string name, string msg = "Hello")
		println(msg + ", " + name)
	end

	func sum(...)
		return arg.length
	end

	func config(***)
		return arg.length
	end

规则：
	- 第五版首版中，`...` 与 `***` 互斥，一个函数不能同时声明两者
	- `func f(int a, ...)` 中，函数体内自动注入保留变量 `arg`，其静态类型为 `array<var>`
	- `func f(int a, ***)` 中，函数体内自动注入保留变量 `arg`，其静态类型为 `dict<var>`
	- `arg` 为保留名，声明了可变参数的函数内部不得再次声明同名参数或局部变量
	- `...` 用于自动收敛多余位置参数
	- `***` 用于自动收敛多余命名参数
	- 除自动收敛外，也允许显式整包传入：
		- `f(1, arg = [2, 3, 4])`
		- `f(1, arg = {"x": 10, "y": 20})`
	- 自动收敛与显式整包传入不能混用
	- 第五版首版不支持在调用点把已有数组或字典再次展开为 `...arr` / `***map`


7.3 命名参数
------------
第五版正式支持命名参数：
	createUser(name: "Tom", age: 18)

规则：
	- 位置参数必须在前
	- 命名参数必须匹配参数名
	- 命名参数不能重复
	- 命名参数参与重载决议时，先按参数名重排，再进入签名匹配
	- 命名参数名称属于 ABI 元信息的一部分，不能在已发布 API 中随意变更


7.4 返回值
----------
第五版正式支持多返回值。

标准写法：
	func split_name(string s) as string, string
		return "a", "b"
	end

接收写法：
	auto first, second = split_name("x")
	auto first, _ = split_name("x")

规则：
	- 函数声明写法固定为 `func f() as int, string`
	- `return` 直接写作 `return a, b`
	- 调用结果支持解构接收
	- `_` 作为忽略位
	- 多返回值不是一般意义上的一等 tuple 值
	- 但允许在“调用参数位置”展开，如 `g(f())`
	- `auto x = f()` 若 `f()` 返回多个值，则必须报错
	- `cdecl`、`stdcall` 等外部调用约定默认不要求支持多返回值


7.5 重载
--------
第五版保留重载设计，但要求严格受编译期决议机制控制。

规则：
	- 同一作用域允许同名不同签名函数
	- 重载决议必须可解释
	- 多义性必须报错
	- `var` 参数优先级低于精确类型匹配


7.5.1 重载实现原则
------------------
第五版明确：
	- 重载是纯编译期能力，不是运行时按名称动态分派
	- 编译器必须在调用点完成候选收集、匹配、决议
	- 一旦决议完成，后端只面对唯一目标实体

结论：
	- C 后端不保存“按名字模糊调用”的概念
	- 每个具体重载实例都必须有唯一目标映射
	- 导出模块必须提供元信息表
	- xlang 编译器内部调用、跨模块调用、native DLL 调用，都统一走“声明 + 元信息 + 目标符号”的机制


7.5.2 元信息表机制
------------------
第五版正式把“可分发模块元信息表”纳入函数系统设计。

用途至少包括：
	- 重载函数重定向
	- 导出函数声明
	- native 函数映射
	- 后续 class 映射
	- 后续 custom 类型能力描述

也就是说：
	- xlang 编译器自己生成的模块，会自动产出元信息表
	- 其他语言编写的 DLL/so，只要愿意提供符合规范的元信息表，也可以无缝接入 xlang


7.5.3 元信息表示例语义
--------------------
例如一个模块逻辑上导出：
	func foo(int a)
	func foo(string b)

其元信息可表示为：
	- `foo(int)` -> `foo_int(int)`
	- `foo(string)` -> `foo_str(char*)`

未来 class 也可类似映射：
	- `a.b(int)` -> `a_b(ptr obj, int c)`
	- `a(int)` -> `a_create(ptr obj, int c)`

结论：
	重载的本质不是“编译器内部做一次 mangling 就结束”。
	而是：
		- 源语言声明
		- 规范化签名
		- 元信息项
		- 最终目标符号
	之间的一套稳定映射机制。


7.5.4 元信息格式方向
-------------------
第五版建议把元信息表设计成“规范化的结构化数据”，而不是硬编码文本。

建议方向：
	- 编译器内部使用结构化表
	- 发布时可导出为 JSON
	- 运行时加载时也可读取 JSON，或编译进二进制资源段

选择 JSON 作为首版交换格式的理由：
	- 可读
	- 易调试
	- 易被其他语言生成
	- 易和编译期 trace / dump 体系整合

建议一个函数导出项至少包含：
	- 逻辑名
	- 所属模块
	- 参数列表
	- 返回值列表
	- 调用约定
	- 目标符号名
	- 是否 native
	- 是否 async
	- 是否 generator


7.5.5 函数 ABI 草案
------------------
第五版需要提前确定函数 ABI。

第五版实际上需要两层 ABI：

	1. 语言层 ABI
		- 由函数声明 + 元信息表描述
		- 对应 xlang 可见的函数逻辑签名

	2. C 层目标 ABI
		- 对应最终生成或绑定的 C 符号
		- 可是 xlang 编译器生成函数
		- 也可是 native DLL 提供函数

建议统一规则：
	- xlang 编译器内部总是先按语言层 ABI 工作
	- 到 C 后端或 native 绑定阶段，再根据元信息映射到目标 ABI

对 xlang 自生成函数，建议默认目标 ABI：
	- 所有生成函数第一个参数都是 `XL_ExecCtx* pCtx`
	- 后续参数按决议后的静态签名展开
	- 同步普通函数直接返回其逻辑返回值
	- `var`、容器、字符串、future、generator 等运行时对象统一走 xrt/xvalue 或已注册运行时类型

建议的 C 层形态：
	RetType xl_<module>_<mangled_name>(XL_ExecCtx* pCtx, ...)

其中 mangled_name 至少包含：
	- 模块名
	- xlang 函数名
	- overload group id
	- 规范化参数签名

ABI 原则：
	- 运行时绝不再按名字做重载选择
	- 编译器产出的调用点必须已经绑定到具体元信息项
	- 元信息项再绑定到具体 C 符号
	- native 模块、模块导出、调试系统都复用这套“声明 -> 元信息 -> 目标符号”体系
	- 最终 ABI 必须与版本绑定，以支持同名库多版本天然共存

第五版首版已落地的最小双层 ABI 元信息：
	- 每个函数元信息项显式携带 `languageAbi`
	- 当前固定为 `xlang@v1`
	- 每个函数元信息项显式携带 `nativeAbi`
	- 当前固定为 `c@v1`
	- `signatureId` / `dispatchKey` 继续承担语言层签名定位
	- `abiSymbol` 继续承担当前 C 层目标符号定位
	- 首版先稳定“语言层签名 id + ABI 版本 + native 符号名”三者并存
	- 首版先把稳定分发身份固定在元信息层：函数显式输出 `languageAbiId` / `nativeAbiId`，模块导出显式输出 `abiId` / `versionedSymbol`
	- 更激进的“把版本编码继续压进最终 C 导出符号名”可以后续再讨论，但不再作为首版版本绑定 ABI 的阻塞项

第五版首版的版本绑定 ABI：
	- xlp 函数元信息继续保留未绑定版本的 `signatureId` / `abiSymbol`
	- 同时额外显式输出版本绑定后的 `languageAbiId`
	- 格式为：`<moduleAbiId>::<signatureId>#<languageAbi>`
	- 同时额外显式输出版本绑定后的 `nativeAbiId`
	- 格式为：`<moduleAbiId>::<abiSymbol>#<nativeAbi>`
	- 其中 `moduleAbiId` 已绑定包名、包版本、ABI 版本
	- 因此 `languageAbiId` / `nativeAbiId` 可直接作为稳定分发与多版本共存的函数 ABI 身份标识
	- 模块导出表中的每个导出项也显式输出 `abiId`
	- 格式为：`<moduleAbiId>::<exportName>`
	- 同时显式输出 `versionedSymbol`
	- 格式为：`<moduleAbiId>::<symbol>`
	- 这样加载器无需反推即可直接得到“导出名身份”与“版本绑定后的目标符号”
	- 第五版首版先把“版本绑定”稳定在元信息 id 层
	- 是否进一步把版本编码进最终真实 C 导出符号名，可在后续模块 ABI 统一落地时再推进


7.5.6 对未来 custom/class 的设计余量
-----------------------------------
第五版在函数系统中必须为后续能力留出空间：
	- class 的成员方法、构造函数、静态方法，都应能表示为元信息项
	- custom 类型本质上也是元信息驱动类型
	- 类型能力、方法、构造、析构、协议实现，都应能通过元信息描述

结论：
	函数系统的元信息机制不是只为重载服务，
	它其实是未来 custom / class / native bridge 的统一基础设施。


7.6 函数类型
------------
`function` 是标准类型，并支持签名化函数值。

标准形式：
	- `function<int(string)>`
	- `function<void()>`

规则：
	- 函数引用语法使用裸函数名：`foo`
	- `function` 必须携带签名信息
	- `var` 也可存储函数值，但运行时必须同时保存签名信息
	- 重载函数作为值使用时，必须能由目标签名唯一决议，否则报错
	- 第五版首版先支持“无捕获函数值”
	- 闭包与捕获语义后续再补，但底层表示需预留扩展能力



================================================================================
八、流程控制
================================================================================

8.1 if
------
保留：
	if cond
		...
	elseif cond2
		...
	else
		...
	end

单行形式：
	if cond then expr
	if cond then expr else expr


8.2 while
---------
保留：
	while cond do
		...
	end


8.3 do-while
------------
保留第四版已验证形式：
	do
		...
	while cond end


8.4 for
-------
第五版正式取消：
	for i = 1 to 10
	for i = 0 to 100 step 5

统一只保留：
	for v in iterable
		...
	end

	for k, v in iterable
		...
	end

范围循环统一写作：
	for i in range(1, 10)
		...
	end

	for i in range(0, 100, 5)
		...
	end


8.5 break / continue
--------------------
保留：
	break
	continue
	break 2
	continue 2


8.6 控制流实现原则
------------------
第五版要求控制流不但语法无歧义，Lowering 结果也必须无歧义。

编译期原则：
	- `if / elseif / else` 先规范化为单一链式结构
	- `while`、`do-while`、`for in` 在 HIR 阶段仍保持结构化节点
	- 到 MIR 阶段统一降级为显式基本块、跳转和标签
	- `break n` / `continue n` 必须在语义阶段就绑定到目标循环层级

后端原则：
	- 同步函数中，结构化循环优先直接映射为 C 结构化语句
	- 一旦进入 async/generator 状态机，所有控制流统一落为状态号 + switch + label
	- 不允许把控制流歧义留给 C 编译器自然解释



================================================================================
九、错误处理
================================================================================

9.1 设计目标
------------
第五版正式把错误处理纳入核心标准。

错误处理必须支持：
	- 同步错误
	- 异步错误
	- native 绑定错误
	- 模块初始化错误


9.2 try-catch-finally
--------------------
建议形式：
	try
		...
	catch e
		...
	finally
		...
	end

规则：
	- `catch` 最多一个，首版通过 `e.type` 区分类型
	- `finally` 可选
	- `finally` 必须总是执行


9.3 throw
---------
第五版建议从第三版的 `throw(type, message, code)` 收敛为更统一的对象式语义：
	throw Error("message")
	throw IOError("file not found")
	throw e

也就是说：
	- `throw` 接收一个错误对象
	- 标准错误构造函数由标准库/内建类型提供
	- 不再把 `throw(type, message, code)` 作为核心语法形式

原因：
	- 更统一
	- 更利于 native 错误桥接
	- 更利于异步错误传播


9.4 Error 标准类型
------------------
第五版建议把 `error` 作为标准运行时类型，语言层统一暴露为 `Error` 系列。

建议基础字段：
	- type
	- message
	- code
	- data
	- stack
	- cause

建议基础错误分类：
	- Error
	- TypeError
	- ValueError
	- IOError
	- TimeoutError
	- CancelledError
	- NotImplementedError
	- NativeError


9.5 assert
----------
保留：
	assert cond
	assert cond, "message"


9.6 错误处理实现原则
--------------------
第五版必须把错误处理的实现原理提前敲定。

同步函数路径建议：
	- 使用 `XL_ExecCtx` 持有当前错误对象与 jump frame 栈
	- `try/catch/finally` 在 Lowering 后展开为显式的异常帧管理结构
	- C 层使用 `setjmp/longjmp` 或等价跳转机制承载同步异常跳转

异步函数路径建议：
	- 不允许跨挂起点依赖 longjmp
	- async 状态机内部发生错误时，统一把错误写入 output future/task
	- `await` 到 rejected 结果时再把错误重新抛回当前 async 上下文

结论：
	错误处理需要一套同步跳转模型和一套异步结果模型，
	但它们对语言用户呈现为统一的 `Error` 语义。



================================================================================
十、异步函数
================================================================================

10.1 async func
---------------
第五版正式支持：
	async func fetch(url) as string
		var resp = await net.get(url)
		return await resp.text()
	end

规则：
	- `async func` 的声明返回类型仍写逻辑结果类型
	- `async func` 调用结果是 Awaitable / future 语义值
	- 编译期要标记该函数为异步状态机
	- 最终返回值通过 future 运行时值承载


10.2 async 上下文
-----------------
`await` 只能出现在 async 函数体中。

以下不允许：
	func test()
		await foo()
	end


10.3 async 返回值
-----------------
语言层写：
	async func foo() as int

语义上表示：
	- 逻辑返回类型是 `int`
	- 实际调用结果是 `Awaitable<int>` / `future<int>` 语义

这套泛型化表示先作为语义概念，不要求第五版首版一定提供完整泛型语法。


10.4 async 实现原则
-------------------
第五版必须提前固定 async 的 Lowering 原理。

建议模型：
	- 每个 `async func` 降级为一个异步状态机
	- 编译器生成：
		- 状态结构体
		- step 函数
		- 首次启动入口
		- 输出 future/task

状态结构体至少包含：
	- 当前状态号
	- 局部变量快照
	- 当前等待对象
	- 输出结果 future
	- 当前错误

原则：
	- async 语义由 xlang 编译器生成状态机完成
	- xrt 负责提供 future/task/coroutine 调度原语
	- tcc 只负责编译最终 C，不负责理解 async 语义



================================================================================
十一、await 语义
================================================================================

11.1 形式
---------
	await expr

它是表达式，不是语句。


11.2 语义
---------
	- `expr` 必须实现 Awaitable 协议
	- 成功时返回结果值
	- 失败时重新抛出错误


11.3 Awaitable
--------------
第五版建议把 Awaitable 作为语言内建协议，而不是表面语法。

首版满足 Awaitable 的标准类型：
	- future

说明：
	- `future` 是首版主要公开异步值类型
	- `task` 首版更偏标准库编排接口与调度语义层，不强制再引入第二套独立值模型

后续可扩展：
	- native async IO 结果
	- 某些网络请求对象


11.4 await 的错误传播原则
------------------------
第五版需要提前定死：
	- `await` 成功返回结果值
	- `await` 失败重新抛出错误对象
	- `await` 取消则抛出 `CancelledError` 或兼容错误类型

这意味着：
	- Awaitable 协议不只要描述成功结果类型
	- 还必须描述错误结果如何投递到当前函数



================================================================================
十二、yield 与生成器
================================================================================

12.1 设计目标
-------------
第五版正式支持 `yield`，首版已支持 generator 语义，并支持 async generator 的 stage 1 最小版。


12.2 形式
---------
	func count(n)
		for i in range(0, n)
			yield i
		end
	end


12.3 语义
---------
规则：
	- 普通 `func` 中出现 `yield`，该函数即为 generator function
	- 调用结果是 `generator`
	- `yield` 是挂起点
	- generator 可被 `for in` 遍历


12.4 yield 上下文限制
---------------------
	- `yield` 只能出现在 generator 函数中
	- 首版支持在 `async func` 中使用 `yield`（stage 1 最小版）
	- 首版支持把 `yield` 当表达式值回传；stage 1 恢复值类型按 `var` 处理，通过 `generator.next()` / `generator.resume(value)` 驱动


12.5 手动协程控制
-----------------
第五版建议把“手动 resume/coroutine”放在标准库，而不是核心语法。

例如：
	var co = task.coroutine(funcName)
	var r = co.resume()

也就是说：
	- 语言核心负责 `yield`
	- 手动协程调度接口由标准库提供


12.6 generator 实现原则
----------------------
第五版必须提前固定 generator 的实现原理。

建议模型：
	- generator function 降级为独立状态机
	- 编译器生成：
		- generator 状态结构体
		- `next/resume` 函数
		- 当前值槽位
		- 完成标记

`yield` 的 Lowering：
	- 保存局部变量到状态结构体
	- 设置当前产出值
	- 写入下一个状态号
	- 返回给调用方

限制：
	- 第五版首版支持 async generator 的 stage 1 最小版
	- 第五版首版支持 `yield` 作为双向值交换表达式；stage 1 恢复值按 `var` 传递



================================================================================
十三、任务编排
================================================================================

13.1 定位
---------
任务编排属于标准库核心能力，不是单独语法关键字。


13.2 建议标准接口
----------------
	task.spawn(fn, ...)
	task.all(tasks)
	task.race(tasks)
	task.delay(ms)
	task.cancel(t)

首版约定：
	- `spawn` / `all` / `race` / `delay` 的结果按 `future` 语义处理
	- `cancel` 返回 `bool`
	- `task` 是标准库命名空间，不是额外语法关键字
	- 第五版首版同时允许使用 `task` 作为声明类型接收 async / `std.task` 的结果
	- 该声明类型在实现上收敛为具体 `future<T>`，不额外引入第二套独立异步值表示


13.3 与语言语义的关系
--------------------
编译器需要认识这些能力的结果类型，但不需要把它们做成关键字。

例如：
	var results = await task.all([
		fetchA(),
		fetchB(),
		fetchC()
	])

13.4 channel
------------
第五版首版将 `channel` 作为标准运行时类型。

建议构造形式：
	channel()
	channel(16)

建议接口：
	ch.send(v)
	auto ok, v = await ch.recv()
	ch.close()

规则：
	- 第五版首版不强制要求 `channel<T>` 泛型语法
	- channel 首版内部元素统一按 `var` 语义承载
	- `recv()` 在关闭且已读空时返回 `false, null`
	- 不使用 `null` 作为单一结束哨兵，因为 `null` 本身是合法数据
	- `select` 暂不纳入第五版首版核心标准，后续单独扩展



================================================================================
十四、模块系统
================================================================================

14.1 核心定位
-------------
第五版正式把模块系统纳入语言核心。


14.2 import
-----------
建议支持：
	import math
	import math as m
	import math.sin
	import math.sin, math.cos
	import "./utils"


14.3 export
-----------
建议支持：
	export func foo()
		...
	end

	export const PI = 3.14159
	export var config = {}


14.4 模块规则
------------
	- 每个 `.xl` 文件天然是一个模块
	- 顶层定义默认私有
	- 显式 `export` 才能被外部导入
	- 模块首次导入时初始化一次
	- 后续导入使用缓存


14.5 顶层代码
------------
第五版建议允许顶层代码存在。

规则：
	- 顶层代码在模块初始化时执行
	- 模块初始化失败时，导入失败并抛出异常


14.6 include
------------
第五版建议不把 `include` 作为核心语言标准的一部分。

原因：
	- 它更像构建系统或文本预处理能力
	- 容易破坏模块边界


14.7 模块实现原则
----------------
模块系统也必须提前确定实现原理。

建议模型：
	- 每个源文件编译成一个模块单元
	- 编译期生成：
		- 模块描述符
		- 导出表
		- 初始化函数
		- 导入依赖表

运行时模型：
	- 模块对象包含：
		- 模块 ID
		- 初始化状态
		- 导出值表
		- 初始化错误状态

导入规则：
	- `import` 在编译期解析模块路径与导入目标
	- 运行时只负责模块初始化与缓存
	- 模块初始化函数只执行一次


14.8 模块 ABI 草案
-----------------
第五版建议每个模块在 C 层至少生成以下对象：
	- `xl_mod_<name>__init(XL_ExecCtx* pCtx)`
	- `xl_mod_<name>__exports`
	- `xl_mod_<name>__descriptor`

导出项统一进入模块导出表：
	- 导出函数 -> 已决议的 C 符号
	- 导出常量 -> 运行时值或静态值访问器
	- 导出变量 -> 运行时槽位
	- 首版 xlp 元信息中，每个模块额外显式携带 `initSymbol`
	- 首版 xlp 元信息中，每个模块额外显式携带 `exportsSymbol`
	- 首版 xlp 元信息中，每个模块额外显式携带 `descriptorSymbol`
	- 首版 xlp 元信息中，每个导出项额外显式携带 `abiId = <moduleAbiId>::<exportName>`
	- 首版 xlp 元信息中，每个导出项额外显式携带 `versionedSymbol = <moduleAbiId>::<symbol>`

建议首版限制：
	- 模块循环依赖在第五版首版直接视为编译期错误

补充原则：
	- 模块 ABI 必须与包版本和 ABI 版本绑定
	- 最终导出符号应包含足够的版本信息，避免不同版本模块冲突


14.9 模块与扩展分发格式
----------------------
第五版需要明确：
	xlang/xrt 的外部扩展单元，不是单独的 `dll/so/a/c` 文件，
	而是“元信息 + 可接入代码或库”的组合。

基于 xrt 当前分发模型，建议正式承认以下几类扩展产物：

	1. 共享库扩展包
		- 使用 xpack 打包，包扩展名为 `.xlp`
		- 内含：
			- `dll` / `so`
			- 元信息文件

	2. 静态库扩展包
		- 使用 xpack 打包，包扩展名为 `.xlp`
		- 内含：
			- `.a`
			- 元信息文件

	3. 分享库扩展包
		- 使用 xpack 打包，包扩展名为 `.xlp`
		- 内含：
			- `.c`
			- 元信息文件
		- 可选附带：
			- `.h`

结论：
	在第五版语言层面，真正的“扩展模块”概念应理解为：
		元信息 + 可接入实现

而不是：
		某个裸二进制文件

这条规则同时适用于：
	- 函数重载映射
	- native 模块接入
	- 后续 class 映射
	- 后续 custom 类型扩展

并且还适用于：
	- 多版本依赖共存
	- 版本绑定 ABI 的稳定分发



================================================================================
十五、标准协议
================================================================================

第五版建议把以下协议作为语言标准层概念：
	- Callable
	- Indexable
	- Iterable
	- Iterator
	- Awaitable
	- Generator

说明：
	- 这些协议首先服务编译器机制
	- 首版采用“显式注册为标准模型，内建类型自动注册”的方向
	- 后续 class / custom 与基础类型共用同一套协议注册机制
	- 建议保留内部方法名：
		- `Callable -> __call__`
		- `Indexable -> __get_index__ / __set_index__`
		- `Iterable -> __iter__`
		- `Iterator -> __next__`
		- `Awaitable -> __await__`
	- `Iterator.__next__` 与 `channel.recv()` 建议统一采用多返回值 `bool, var`
	- 第五版首版实现采用“显式协议注册表 + 内建类型自动注册”
		- `function -> Callable`
		- `array/list/dict -> Indexable`
		- `array/list/set/dict/range/generator -> Iterable`
		- `generator -> Iterator + Generator`
		- `future -> Awaitable`
	- 首版先让 `call / index / for in / await` 语义检查统一走协议查询
	- 自定义类型协议注册语法后续再补，但模型先与基础类型共用



================================================================================
十六、native 绑定
================================================================================

16.1 定位
---------
第五版语言必须承认：
	xlang 和 xrt 深度绑定，native 绑定不是边缘特性，而是语言能力的一部分。


16.2 设计目标
-------------
native 绑定要支持：
	- 标准库模块绑定
	- xrt 功能映射
	- 后续用户扩展模块


16.3 模块级编译指令
--------------------
第五版将影响当前编译结果的 native 配置统一收敛为模块级编译指令。

标准形式：
	#link user32
	#libpath "c:\\sdk\\lib"
	#incpath "c:\\sdk\\include"
	#loadlib "user32.dll"

设计原则：
	- 这类能力不是运行时代码，而是编译前元信息
	- 编译指令在 lexer / parser 主流程前扫描并提取
	- 编译指令不占用普通关键字，避免污染变量名空间
	- 编译指令只允许出现在模块顶层
	- 编译指令对当前模块及其依赖图生效，不依赖顶层语句执行顺序

各指令职责：
	- `#link <ident>`
		- 声明当前模块依赖一个原生链接库名
		- module-link 汇总全依赖图中的 `#link`，去重后透传给 host / toolchain
	- `#libpath "<path>"`
		- 追加原生链接库搜索路径
		- 相对路径按声明该指令的模块文件目录解释
	- `#incpath "<path>"`
		- 追加 native 头文件搜索路径
		- 首版主要为后续 native include / binding 生成链路预留
	- `#loadlib "<file>"`
		- 声明程序运行前应预加载一个动态库
		- 它不参与静态链接，而是作为运行时符号来源

分层规则：
	- `#link` / `#libpath` / `#incpath` 属于静态编译配置
	- `#loadlib` 属于静态声明的运行前装载配置
	- 这几类能力都不通过顶层代码执行来生效

兼容说明：
	- demo5 已完成源码级 `link foo` 兼容迁移
	- 第五版定稿标准只接受 `#link`
	- `link foo` 不再作为编译指令处理，应按普通源码进入解析并报错


16.4 extern
-----------
第五版保留 `extern`，并将其定位为静态 native 绑定声明。

标准形式：
	extern func foo(int a) as int
	extern "native_symbol" func foo(int a) as int
	extern var errno as int
	extern "native_global" var flag as int
	extern type HWND = point
	extern type DWORD = u32

分工：
	- `extern func`：静态声明 native 函数符号
	- `extern var`：静态声明 native 全局变量符号
	- `extern type`：静态声明 native ABI 对齐的类型别名

规则：
	- `extern` 只能出现在顶层
	- 允许顶层独立声明，不要求一切经由模块包装
	- native 符号名既可默认按 ABI 推导，也可显式绑定
	- 第五版首版暂不支持 `extern async func`
	- 第五版首版暂不支持类型方法形式的 `extern`
	- 第五版首版的 `extern type` 先收敛为 native 类型别名；结构体布局另行扩展
	- 第五版首版固定最小 ABI 版本：
		- 语言层 ABI：`xlang@v1`
		- native C ABI：`c@v1`
	- 每个 native 绑定函数都应同时拥有语言层签名标识与具体 native 符号名


16.5 动态装载与运行时绑定
--------------------------
第五版同时提供与 `extern` 正交的运行时动态绑定能力。

静态声明形式：
	#loadlib "user32.dll"

运行时 API 方向：
	auto lib = sys.loadlib("user32.dll")
	auto msgbox = lib.proc("MessageBoxA") as function<int(point, string, string, u32)>

职责划分：
	- `#loadlib`
		- 在程序启动前由 host / runtime 预加载动态库
		- 预加载的库自动进入 `extern` 的符号搜索域
		- 这是静态声明，不要求 import library，不依赖 `.def` / `.lib` / `.a`
	- `sys.loadlib(path)`
		- 运行时动态加载库并返回库对象
	- `lib.proc(name)`
		- 返回运行时符号句柄或可转换的符号值
	- `as function<...>`
		- 由调用端显式提供签名，将动态符号绑定为函数值

设计原则：
	- `#loadlib` 不等于 `#link`
	- `#link` 走静态链接链路
	- `#loadlib` 走 `LoadLibrary/GetProcAddress` 或 `dlopen/dlsym` 链路
	- `extern` 属于静态绑定模型
	- `sys.loadlib()/lib.proc()` 属于动态绑定模型
	- 两者可以并存，分别适用于稳定系统库与可选插件依赖

================================================================================
十九、第五版语言设计结论
================================================================================

第五版语言设计的主线可以总结为：
	- 语法风格继承第四版
	- 机制设计继续沿第四版深化
	- 能力范围恢复第三版曾提出但未真正落地的运行时能力
	- 通过 xrt 把动态能力放进一门编译型语言中

第五版不是“脚本语言语法加一点编译器壳”。
第五版也不是“静态语言加一点异步语法糖”。

第五版要达成的是：
	- 一门真正编译到 C 的语言
	- 一门拥有清晰编译期机制的语言
	- 一门能稳定承载异步、协程、错误处理、模块、任务编排的语言
