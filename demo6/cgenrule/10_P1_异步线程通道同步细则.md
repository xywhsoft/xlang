## CGEN-ASYNC-011 await typed 结果

| 字段 | 内容 |
| --- | --- |
| xlang 写法 | `int v = await f()`、`array<int> values = await futureItems`、`array<int> values = await makeItemsAsync()` |
| 生成规则描述 | await 有结果类型时，具名 future 的标量结果生成 `*(T*)xl6_future_await_value(future, ..., 1, sizeof(T))`，future 生命周期继续由变量 cleanup 管理并支持 repeated await。具名 future 的 typed container 结果不能直接把 future 内部句柄交给局部变量析构，而是通过 typed container copy helper 复制成本地对象；只有 `await asyncCall()` 这类未绑定直接调用临时 future 才能移动 typed container 句柄并释放 future。基础标量、`function`、class、`var` 与 typed container 临时 future 都必须走专用 release helper；若未来出现没有 helper 的临时 await 类型，生成器应报诊断而不是恢复 statement expression fallback。 |
| 生成器文件名和行号 | await 临时判定 `xl6_cgen_async_func.c:229`，await 分派 `xl6_cgen_async_func.c:369`、`xl6_cgen_async_func.c:377`，release helper 选择 `xl6_cgen_async_func.c:277`、`xl6_cgen_async_func.c:349`；typed container 复制/移动判定 `xl6_cgen_value_object_typed.c:167`、`xl6_cgen_value_object_typed.c:181`，声明初始化分派 `xl6_cgen_stmt_decl_main.c:265`、`xl6_cgen_stmt_decl_main.c:279` |
| 对应生成的 C 代码 | 具名标量 future：`(*(long long*)xl6_future_await_value(f, "", 10, 3, 1, sizeof(long long)))`；具名 typed container future：`xl6_xrt_typed_array_copy_mode(xrtTypeInt(), (*(xtarray*)xl6_future_await_value(itemsFuture, "", 10, 3, 1, sizeof(xtarray))), XRT_OBJMODE_LOCAL)`；临时 typed container async 调用：`xl6_future_await_handle_release(makeItemsAsync(), "", 10, 3)`；临时 function async 调用：`xl6_future_await_function_release(makeAdderAsync(...), "", 10, 3)`；临时 class async 调用：`xl6_future_await_class_makeBoxAsync_release(makeBoxAsync(...), "", 10, 3)` |

数组可变参数补充：`func(int, ...) as int` 函数值经 `task.spawn` 调用时，`task.spawn(variadicJob, 10, 1, 2, 3)` 生成 `argc = 4`，`task.spawn(variadicJob, 10)` 生成 `argc = 1`。后者表示 `...` 尾部为空，由 `xl6_function_call_argv_borrow` 按函数签名构造空 `arg` 数组。语义层对 `task.spawn` 使用 `func` 类型签名的 fixed 参数数量作为必填数量，不把末尾 `array<var>` 计入必填参数。

数组可变参数补充：`func(...) as int` 零固定参数 adapter 也走同一条规则。`func totalDefault(int base = 5, ...) as int` 可赋值给 `func(...) as int variadicDefaultJob`，此时 `task.spawn(variadicDefaultJob)` 生成 `argc = 0`，默认参数由 xcall adapter 补齐，`arg` 为空数组；`task.spawn(variadicDefaultJob, "a", "b")` 生成 `argc = 2`，两个字符串实参分别装箱为 `xvoCreateText(...)` 后交给 adapter 构造 `arg`。这条补充证明 `task.spawn` 不依赖固定参数数量大于 0，也不会把被 adapter 隐藏的默认参数错误计入调用侧必填参数。

标量 bridge 补充：bool/float 已纳入 `task.spawn` 的发布级守门。`func(bool) as bool` 生成 `xl6_task_spawn_values(flipJob, xrtTypeBool(), sizeof(int), ..., xvoCreateBool(...))`，临时 await 使用 `xl6_future_await_i32_release`，命名 `future<bool>` repeated await 通过 `xl6_future_await_value(..., sizeof(int))` 读取；`func(float) as float` 生成 `xl6_task_spawn_values(halfJob, xrtTypeFloat(), sizeof(double), ..., xvoCreateFloat(...))`，临时 await 使用 `xl6_future_await_f64_release`，命名 `future<float>` repeated await 通过 `xl6_future_await_value(..., sizeof(double))` 读取。这里固定的是当前 C 后端的本地存储宽度与 XRT type descriptor 必须同步，不表示 bool/float 走独立 task runtime。

调用形式补充：`task.spawn` 当前 RC0 只接收位置参数。`sem_task_spawn_named_argument.xl` 锁定 `task.spawn does not accept named arguments` 诊断，避免把普通函数的命名参数能力误接入 worker argv 装箱路径。

签名限制补充：`task.spawn` 当前 RC0 只接收单返回 `func` 值。`sem_task_spawn_multi_return.xl` 锁定 `task.spawn currently supports only single-return func values` 诊断，避免多返回结构体结果在没有独立结果对象和 xvalue bridge 规则时进入 worker。

## 补充：task.all/race 源 future retain 规则

`xl6_task_all_values` 与 `xl6_task_race_values` 的字面量输入按 `(xfuture*, owned)` 成对传入。命名 future 使用 `owned = 0`，表达式新建的 future 使用 `owned = 1`。

这条规则依赖 XRT 的聚合 retain 语义，而不是依赖调用方延长临时对象生命周期：

- XRT `xFutureWhenAll` 与 `xFutureRace` 都进入 `__xnetFutureCreateGroup`。
- `__xnetFutureCreateGroup` 对每个源 future 调用 `xFutureAddRef`。
- group context 释放时会释放这些源 future 引用。
- 因此 xlang helper 可以在 `xl6_task_all_start` / `xl6_task_race_start` 返回后释放 owned 输入引用。

对应生成守门：

- `task.all([one, two])` 必须生成 `one, 0, two, 0`。
- `task.all([addAsync(...), addAsync(...)])` 必须生成 `addAsync(...), 1`。
- `task.race([addAsync(...), addAsync(...)])` 必须生成 owned 标记。
- `task.race([task.spawn(...), task.spawn(...)])` 中嵌套 `task.spawn` 结果必须生成 owned 标记。

失败路径补充：`xl6_task_all_values` 与 `xl6_task_race_values` 在内部 `futures` 或 `owned` 数组分配失败时，仍会通过 `va_arg` 消耗所有 `(future, owned)` 对；如果某项 `owned != 0`，立即释放该 future。这样即使 helper 在启动聚合前失败，数组字面量里的临时 async/task.spawn future 也不会泄漏。

## 补充：task.cancel 输入 future 所有权规则

`task.cancel(expr)` 的返回值只表示取消请求结果，不接管命名 future 的生命周期；但如果 `expr` 本身创建 fresh future，则调用表达式持有的原始引用必须在取消请求后释放。

当前生成规则：

- `task.cancel(namedFuture)` 生成 `xl6_task_cancel_value(namedFuture, 0)`。
- `task.cancel(addAsync(...))` 生成 `xl6_task_cancel_value(addAsync(...), 1)`。
- `task.cancel(task.spawn(...))` 生成 `xl6_task_cancel_value(xl6_task_spawn_values(...), 1)`。
- `task.cancel(task.all([...]))` 生成 `xl6_task_cancel_value(xl6_task_all_values(...), 1)`。
- `task.cancel(task.race([...]))` 生成 `xl6_task_cancel_value(xl6_task_race_values(...), 1)`。

runtime helper 规则：

- `pFuture == 0` 时直接返回 `false`，表示没有可取消的任务；该路径不向下调用 XRT，避免空指针语义依赖底层实现。
- `xl6_task_cancel_value` 先调用 `xFutureRequestCancel`。
- `owned != 0` 时释放输入 future。
- `owned == 0` 时保持原局部变量生命周期不变。

这条规则使 `task.cancel` 与 `task.all/race` 的字面量输入所有权口径一致：命名 future borrowed，fresh future owned。

补充边界：如果 fresh future 本身来自 `task.all/race`，外层聚合 future 对 `task.cancel` 是 owned；聚合内部数组字面量中的临时 future 仍由 `task.all/race` helper 按逐项 owned 标记释放。

进一步补充：如果聚合内部数组字面量中的临时 future 来自 `task.spawn(...)`，仍然按 fresh future 处理：

- `task.cancel(task.all([task.spawn(...), task.spawn(...)]))` 中，外层 `task.all(...)` 对 cancel 是 owned，内层两个 `task.spawn(...)` 对 all 也是 owned。
- `task.cancel(task.race([task.spawn(...), task.spawn(...)]))` 同理。

这使 task API 的嵌套组合保持同一口径：每个表达式创建出的 future 引用，都由最近的接收 helper 释放；命名 future 始终由原局部 cleanup 管理。

typed-array 聚合补充：

- `task.cancel(task.all(cancelAllJobs))` 生成 `xl6_task_cancel_value(xl6_task_all_from_array((xtarray)(cancelAllJobs), ...), 1)`。
- `task.cancel(task.race(cancelRaceJobs))` 生成 `xl6_task_cancel_value(xl6_task_race_from_array((xtarray)(cancelRaceJobs), ...), 1)`。

这里 owned 标记作用于聚合 future，而不是 typed array 中的源 future。源 future 仍由 typed array 本地对象和 XRT 聚合 retain 规则管理；聚合 future 的表达式引用由 `task.cancel` helper 释放。

空源 future 补充：

- `task.all` 与 `task.race` 都在启动聚合前检查源 future 指针。
- `futures == 0` 或 `count <= 0` 属于空输入数组，分别抛出 `task.all requires at least one future`、`task.race requires at least one future`。
- 源数组中某一项 future 指针为空时，`task.all` 抛出 `task.all source future is null`，`task.race` 抛出 `task.race source future is null`。
- `[missingFuture]` 这类数组字面量输入仍按命名 future borrowed 规则生成 `missingFuture, 0`，由 task helper 检查空源指针，但不接管局部变量生命周期。
- `[addAsync(...), missingFuture]` 这类混合字面量输入按逐项所有权生成：临时 future 为 `owned=1`，命名空 future 为 `owned=0`。helper 在遇到空源 future 并抛错前，必须释放此前已经接管的 owned future。

这条规则让 task 聚合 API 的输入错误保持两级区分：空集合是参数数量错误，空源 future 是集合内容错误；二者都在 xlang task runtime helper 层显式诊断，不依赖 XRT 聚合函数的底层失败路径。

| RISK-ASYNC-003 | 已收口：`await asyncCall()` 这类直接 async 调用临时 future 会在 await statement expression 内释放；function/class 结果会先 retain 再释放 future，具名 future 仍由变量 cleanup 管理并保持 repeated await 语义。`cgen_async.xl` 和 feature suite `11_concurrency.xl` 覆盖 int、void、function、class 临时 await。 |
| RISK-ASYNC-004 | 已收口：`channel<T>` 语义层只允许 bool/int/float/time/point 等可按值复制元素；string、class、function 等复杂所有权类型由 `sem_channel_string_element.xl`、`sem_channel_class_element.xl`、`sem_channel_function_element.xl` 负例和集中诊断断言锁住，因此不会进入当前 `memcpy` 发送路径。 |

## 补充：失败 future repeated await

本轮不新增 `CGEN-*` 规则编号，只补齐 await/task runtime 的失败状态验证边界。

当前 await helper 规则：

- `xl6_future_await_value` 每次都会先 `xFutureWait(pFuture)`，再读取 `xFutureError(pFuture)`。
- 如果 future 保存了错误字符串，则本次 await 调用重新 `xl6_error_raise("AsyncError", error, ...)`。
- 具名 future await 使用 borrowed 形态，不释放 future 本体；因此同一个 future 可以再次 await。
- 临时 future await 使用 release helper，仍只用于一次性表达式。

本轮覆盖：

- `cgen_async_exception_propagation.xl`：同一个失败 async future `failed` 被 await 两次，两次都捕获 `async boom`。
- `cgen_task_spawn.xl`：同一个失败 `task.spawn` future 被 await 两次，两次都捕获 `spawn boom`。
- `cgen_task_api.xl`：同一个失败 `task.all` future 与同一个失败 `task.race` future 分别 await 两次，两次都捕获 `task boom`。
- `examples/task_api.xl`：同步展示 task.spawn / task.all / task.race 失败 future repeated await 写法。
- `test.bat`：锁定 `secondValue = ... xl6_future_await_value(failed, ...)`、`failedSpawnB = ... xl6_future_await_value(repeatedFailedSpawn, ...)`、`repeatedAllB = ... xl6_future_await_value(repeatedFailedAll, ...)`、`repeatedRaceB = ... xl6_future_await_value(repeatedFailedRace, ...)`。

这条补充使 future 的成功状态和失败状态都具备 repeated await 守门：成功值按类型复制或 retain，失败值每次重新读取 future 内保存的错误并抛出。

## 补充：失败完成态 future cancel

本轮不新增 `CGEN-*` 规则编号，只补齐 `task.cancel` 对失败完成态 future 的边界。

当前 cancel helper 规则：

- `xl6_task_cancel_value(pFuture, owned)` 只向底层 future 请求取消。
- `pFuture == 0` 时返回 `false`，不抛异常。
- future 已经完成时，无论完成结果是成功值还是错误值，取消请求都返回 `false`。
- `owned == 0` 表示命名 future borrowed，cancel 不释放 future 本体。
- `owned != 0` 表示 fresh future 表达式 owned，cancel 完成后释放这一次表达式引用。

本轮覆盖：

- `cgen_async_exception_propagation.xl`：失败 async future `failed` 重复 await 后，`task.cancel(failed)` 返回 `false`。
- `cgen_task_spawn.xl`：失败 `task.spawn` future `repeatedFailedSpawn` 重复 await 后，`task.cancel(repeatedFailedSpawn)` 返回 `false`。
- `cgen_task_api.xl`：失败 `task.all` future `repeatedFailedAll` 和失败 `task.race` future `repeatedFailedRace` 重复 await 后，cancel 均返回 `false`。
- `examples/task_api.xl`：同步展示 task.spawn / task.all / task.race 失败完成态 cancel 写法。
- `test.bat`：锁定 `cancelFailed`、`cancelRepeatedFailedSpawn`、`cancelRepeatedFailedAll`、`cancelRepeatedFailedRace` 都生成 `xl6_task_cancel_value(namedFuture, 0)`。

这条补充使 `task.cancel` 的完成态口径闭合：cancel 不用于清除结果、不用于吞掉错误、不用于释放命名 future；它只表达“请求尚未完成的异步工作取消”。

## 补充：task.all/race 混合空源 future 失败清理

本轮不新增 `CGEN-*` 规则编号，只补齐 task 聚合 varargs helper 的失败清理实证。

当前 varargs helper 规则：

- 每个 future 实参都按 `(xfuture*, owned)` 成对传入。
- 临时 async/task 表达式生成 `owned=1`，命名 future 生成 `owned=0`。
- helper 如果在检查过程中发现某一项 future 为空，会设置 `task.all source future is null` 或 `task.race source future is null`。
- 在返回失败前，helper 必须释放此前已经接管的 owned future，避免“前面创建成功、后面参数无效”造成泄漏。

本轮覆盖：

- `cgen_task_api.xl`：`task.all([addAsync(140, 1), missingFuture])` 先创建 owned 临时 future，再遇到 borrowed 空 future，最终捕获 `task.all source future is null`。
- `cgen_task_api.xl`：`task.race([addAsync(150, 1), missingFuture])` 覆盖同一失败清理规则。
- `examples/task_api.xl`：同步展示未初始化 future 混入聚合 API 时的错误处理。
- `test.bat`：锁定生成形态 `addAsync(140LL, 1LL), 1, missingFuture, 0` 和 `addAsync(150LL, 1LL), 1, missingFuture, 0`。

这条补充让 task 聚合输入的失败路径具备更强证据：不是只验证“第一个参数就是空”，而是验证 helper 在中途失败时能按所有权标记释放已接管资源。
