## CGEN-ASYNC-011 await typed 结果

| 字段 | 内容 |
| --- | --- |
| xlang 写法 | `int v = await f()`、`array<int> values = await futureItems`、`array<int> values = await makeItemsAsync()` |
| 生成规则描述 | await 有结果类型时，具名 future 的标量结果生成 `*(T*)xl6_future_await_value(future, ..., 1, sizeof(T))`，future 生命周期继续由变量 cleanup 管理并支持 repeated await。具名 future 的 typed container 结果不能直接把 future 内部句柄交给局部变量析构，而是通过 typed container copy helper 复制成本地对象；只有 `await asyncCall()` 这类未绑定直接调用临时 future 才能移动 typed container 句柄并释放 future。基础标量、`function`、class、`var` 与 typed container 临时 future 都必须走专用 release helper；若未来出现没有 helper 的临时 await 类型，生成器应报诊断而不是恢复 statement expression fallback。 |

补充：`xl6_task_spawn_values` 在准备 `argv` 数组失败时，仍会通过 `va_arg(ap, xvalue)` 消耗调用方已经创建出的实参，并对非空 `xvalue` 执行 `xvoUnref`。这条规则保证 `task.spawn(job, makeValue())` 这类调用即使在内部临时数组分配失败时，也不会泄漏已经传入的临时 xvalue。

数组可变参数补充：`func(int, ...) as int` 函数值经 `task.spawn` 调用时，`task.spawn(variadicJob, 10, 1, 2, 3)` 生成 `argc = 4`，`task.spawn(variadicJob, 10)` 生成 `argc = 1`。后者表示 `...` 尾部为空，由 `xl6_function_call_argv_borrow` 按函数签名构造空 `arg` 数组。语义层对 `task.spawn` 使用 `func` 类型签名的 fixed 参数数量作为必填数量，不把末尾 `array<var>` 计入必填参数。

数组可变参数补充：`func(...) as int` 零固定参数 adapter 也走同一条规则。`func totalDefault(int base = 5, ...) as int` 可赋值给 `func(...) as int variadicDefaultJob`，此时 `task.spawn(variadicDefaultJob)` 生成 `argc = 0`，默认参数由 xcall adapter 补齐，`arg` 为空数组；`task.spawn(variadicDefaultJob, "a", "b")` 生成 `argc = 2`，两个字符串实参分别装箱为 `xvoCreateText(...)` 后交给 adapter 构造 `arg`。这条补充证明 `task.spawn` 不依赖固定参数数量大于 0，也不会把被 adapter 隐藏的默认参数错误计入调用侧必填参数。

标量 bridge 补充：bool/float 已纳入 `task.spawn` 的发布级守门。`func(bool) as bool` 生成 `xl6_task_spawn_values(flipJob, xrtTypeBool(), sizeof(int), ..., xvoCreateBool(...))`，临时 await 使用 `xl6_future_await_i32_release`，命名 `future<bool>` repeated await 通过 `xl6_future_await_value(..., sizeof(int))` 读取；`func(float) as float` 生成 `xl6_task_spawn_values(halfJob, xrtTypeFloat(), sizeof(double), ..., xvoCreateFloat(...))`，临时 await 使用 `xl6_future_await_f64_release`，命名 `future<float>` repeated await 通过 `xl6_future_await_value(..., sizeof(double))` 读取。这里固定的是当前 C 后端的本地存储宽度与 XRT type descriptor 必须同步，不表示 bool/float 走独立 task runtime。

完成态补充：命名 `task.spawn` future 已经完成后，`task.cancel(namedSpawnFuture)` 返回 `false`，且不消费 future 内保存的完成值或错误。当前 RC0 已覆盖 int/string/bool/float 成功完成值在 cancel 后再次 await 的路径：int/bool/float 继续通过 `xl6_future_await_value(namedFuture, ...)` 借读 raw value，string 继续通过 `xl6_future_await_cstr_copy(namedFuture, ...)` 复制本地字符串。失败完成态 `task.spawn` future 在 cancel 返回 `false` 后再次 await，仍重新抛出原始 worker 错误。该规则与 `task.all/race` 的完成态补充保持一致：cancel 只请求取消未完成工作，不负责清理、消费或改写命名 future 状态。

失败返回类型补充：`task.spawn` 的 worker 错误传播不依赖返回类型。当前 RC0 已覆盖返回类型为 int/string/bool/float 的 worker `throw`：临时 await 分别走 `xl6_future_await_i64_release`、`xl6_future_await_cstr_release`、`xl6_future_await_i32_release`、`xl6_future_await_f64_release`，这些 helper 都必须先保留 future 内的原始错误并抛出，不能退化为默认值或空 future 错误。命名失败 future 的 repeated await 与 cancel 后再次 await 也已覆盖 string/bool/float：string 使用 `xl6_future_await_cstr_copy`，bool/float 使用 `xl6_future_await_value`，每次都应重新抛出同一个 worker 错误。

pending cancel 补充：命名 `task.spawn` future 尚未完成时，`task.cancel(namedSpawnFuture)` 生成 `xl6_task_cancel_value(namedSpawnFuture, 0)`，运行时应返回 true，并把 future 固定为 `future cancel requested.` 取消态。当前 RC0 新增慢函数 `slowAdd`：先 `task.spawn(slowAddJob, 40, 2)`，立刻 cancel，再 await 捕获取消错误；等待 worker 睡醒后再次 await，仍必须捕获取消错误。这条规则防止 worker 晚到完成值覆盖已经取消的 future 状态。

pending string 补充：命名 `future<string>` 的 pending `task.spawn` cancel 也必须走同一取消语义。当前 RC0 新增慢函数 `slowGreet`：`pendingStringSpawn = task.spawn(slowGreetJob, "pending")` 后立刻 cancel，第一次和 worker 晚到后的第二次 await 都生成 `xl6_future_await_cstr_copy(pendingStringSpawn, ...)`，并且都必须抛出 `future cancel requested.`。这条规则专门锁住 string await helper 的取消错误传播，避免 string 结果路径只由完成态或失败态间接证明。

聚合源补充：当 pending `task.spawn` future 作为 `task.all` / `task.race` 源输入时，取消具名 group 必须继续向源 future 传播。当前 RC0 新增 `pendingSpawnAllLeft/pendingSpawnAllRight` 与 `pendingSpawnRaceLeft/pendingSpawnRaceRight`：源 future 通过 `task.spawn(slowAddJob, ...)` 创建，group 使用数组字面量输入生成 `pendingSpawnAllLeft, 0, pendingSpawnAllRight, 0` 和 `pendingSpawnRaceLeft, 0, pendingSpawnRaceRight, 0`，证明具名源 future 以 borrowed 方式进入聚合。`task.cancel(group)` 生成 `xl6_task_cancel_value(group, 0)`，随后 await group 与 source future 都必须抛出 `future cancel requested.`；等待 worker 睡醒后再次 await source future，仍必须保持取消态。

调用形式补充：`task.spawn` 当前 RC0 只接收位置参数。`sem_task_spawn_named_argument.xl` 锁定 `task.spawn does not accept named arguments` 诊断，避免把普通函数的命名参数能力误接入 worker argv 装箱路径。

签名限制补充：`task.spawn` 当前 RC0 只接收单返回 `func` 值。`sem_task_spawn_multi_return.xl` 锁定 `task.spawn currently supports only single-return func values` 诊断，避免多返回结构体结果在没有独立结果对象和 xvalue bridge 规则时进入 worker。

## 补充：task.all/race 源 future retain 规则

`xl6_task_all_values` 与 `xl6_task_race_values` 的字面量输入按 `(xfuture*, owned)` 成对传入。命名 future 使用 `owned = 0`，表达式新建的 future 使用 `owned = 1`。

这条规则依赖 XRT 的聚合 retain 语义，而不是依赖调用方延长临时对象生命周期：

- XRT `xFutureWhenAll` 与 `xFutureRace` 都进入 `__xnetFutureCreateGroup`。
- `__xnetFutureCreateGroup` 对每个源 future 调用 `xFutureAddRef`。
- group context 释放时会释放这些源 future 引用。
- 因此 xlang helper 可以在 `xl6_task_all_start` / `xl6_task_race_start` 返回后释放 owned 输入引用。

对应生成守门：

- `task.all([one, two])` 必须生成 `one, 0, two, 0`。
- `task.all([addAsync(...), addAsync(...)])` 必须生成 `addAsync(...), 1`。
- `task.race([addAsync(...), addAsync(...)])` 必须生成 owned 标记。
- `task.race([task.spawn(...), task.spawn(...)])` 中嵌套 `task.spawn` 结果必须生成 owned 标记。

失败路径补充：`xl6_task_all_values` 与 `xl6_task_race_values` 在内部 `futures` 或 `owned` 数组分配失败时，仍会通过 `va_arg` 消耗所有 `(future, owned)` 对；如果某项 `owned != 0`，立即释放该 future。这样即使 helper 在启动聚合前失败，数组字面量里的临时 async/task.spawn future 也不会泄漏。

## 补充：task.cancel 输入 future 所有权规则

`task.cancel(expr)` 的返回值只表示取消请求结果，不接管命名 future 的生命周期；但如果 `expr` 本身创建 fresh future，则调用表达式持有的原始引用必须在取消请求后释放。

当前生成规则：

- `task.cancel(namedFuture)` 生成 `xl6_task_cancel_value(namedFuture, 0)`。
- `task.cancel(addAsync(...))` 生成 `xl6_task_cancel_value(addAsync(...), 1)`。
- `task.cancel(task.spawn(...))` 生成 `xl6_task_cancel_value(xl6_task_spawn_values(...), 1)`。
- `task.cancel(task.all([...]))` 生成 `xl6_task_cancel_value(xl6_task_all_values(...), 1)`。
- `task.cancel(task.race([...]))` 生成 `xl6_task_cancel_value(xl6_task_race_values(...), 1)`。

runtime helper 规则：

- `pFuture == 0` 时直接返回 `false`，表示没有可取消的任务；该路径不向下调用 XRT，避免空指针语义依赖底层实现。
- `xl6_task_cancel_value` 先调用 `xFutureRequestCancel`。
- `owned != 0` 时释放输入 future。
- `owned == 0` 时保持原局部变量生命周期不变。

这条规则使 `task.cancel` 与 `task.all/race` 的字面量输入所有权口径一致：命名 future borrowed，fresh future owned。

完成态补充：`task.cancel` 不用于清理结果，也不用于清空错误。命名 future 如果已经完成，`task.cancel(namedFuture)` 仍生成 `xl6_task_cancel_value(namedFuture, 0)`，运行时返回 `false`，并保持命名 future 的生命周期由局部 cleanup 管理。当前 RC0 已覆盖成功完成的 `future<array<int/string/bool/float>>` task.all 聚合 future，以及成功完成的 `future<int/string/bool/float>` task.race 聚合 future；这些 future 在 cancel 返回 `false` 后仍可再次 await，并继续返回原成功值。

补充边界：如果 fresh future 本身来自 `task.all/race`，外层聚合 future 对 `task.cancel` 是 owned；聚合内部数组字面量中的临时 future 仍由 `task.all/race` helper 按逐项 owned 标记释放。

进一步补充：如果聚合内部数组字面量中的临时 future 来自 `task.spawn(...)`，仍然按 fresh future 处理：

- `task.cancel(task.all([task.spawn(...), task.spawn(...)]))` 中，外层 `task.all(...)` 对 cancel 是 owned，内层两个 `task.spawn(...)` 对 all 也是 owned。
- `task.cancel(task.race([task.spawn(...), task.spawn(...)]))` 同理。

这使 task API 的嵌套组合保持同一口径：每个表达式创建出的 future 引用，都由最近的接收 helper 释放；命名 future 始终由原局部 cleanup 管理。

typed-array 聚合补充：

- `task.cancel(task.all(cancelAllJobs))` 生成 `xl6_task_cancel_value(xl6_task_all_from_array((xtarray)(cancelAllJobs), ...), 1)`。
- `task.cancel(task.race(cancelRaceJobs))` 生成 `xl6_task_cancel_value(xl6_task_race_from_array((xtarray)(cancelRaceJobs), ...), 1)`。

这里 owned 标记作用于聚合 future，而不是 typed array 中的源 future。源 future 仍由 typed array 本地对象和 XRT 聚合 retain 规则管理；聚合 future 的表达式引用由 `task.cancel` helper 释放。

bool/float 聚合补充：

- `task.cancel(task.all([flipAsync(...), ...]))` 生成 `xl6_task_cancel_value(xl6_task_all_values(xrtTypeBool(), ...), 1)`。
- `task.cancel(task.race([flipAsync(...), ...]))` 生成 `xl6_task_cancel_value(xl6_task_race_values(...), 1)`。
- `task.cancel(task.all(cancelBoolAllJobs))` 生成 `xl6_task_cancel_value(xl6_task_all_from_array((xtarray)(cancelBoolAllJobs), xrtTypeBool(), ...), 1)`。
- `task.cancel(task.race(cancelBoolRaceJobs))` 生成 `xl6_task_cancel_value(xl6_task_race_from_array((xtarray)(cancelBoolRaceJobs), ...), 1)`。
- `task.cancel(task.all([addHalfAsync(...), ...]))` 生成 `xl6_task_cancel_value(xl6_task_all_values(xrtTypeFloat(), ...), 1)`。
- `task.cancel(task.all(cancelFloatAllJobs))` 生成 `xl6_task_cancel_value(xl6_task_all_from_array((xtarray)(cancelFloatAllJobs), xrtTypeFloat(), ...), 1)`。

这条补充不改变 `task.cancel` 的返回语义，只把临时聚合 future 的所有权守门扩展到当前 RC0 已发布的 bool/float 完成值。`task.race` 不需要完成值 type descriptor；其结果类型由外层 await 或语义推断决定，但临时 race future 对 `task.cancel` 仍然是 owned。

空源 future 补充：

- `task.all` 与 `task.race` 都在启动聚合前检查源 future 指针。
- `futures == 0` 或 `count <= 0` 属于空输入数组，分别抛出 `task.all requires at least one future`、`task.race requires at least one future`。
- 源数组中某一项 future 指针为空时，`task.all` 抛出 `task.all source future is null`，`task.race` 抛出 `task.race source future is null`。
- `[missingFuture]` 这类数组字面量输入仍按命名 future borrowed 规则生成 `missingFuture, 0`，由 task helper 检查空源指针，但不接管局部变量生命周期。
- `[addAsync(...), missingFuture]` 这类混合字面量输入按逐项所有权生成：临时 future 为 `owned=1`，命名空 future 为 `owned=0`。helper 在遇到空源 future 并抛错前，必须释放此前已经接管的 owned future。

这条规则让 task 聚合 API 的输入错误保持两级区分：空集合是参数数量错误，空源 future 是集合内容错误；二者都在 xlang task runtime helper 层显式诊断，不依赖 XRT 聚合函数的底层失败路径。

实现审计中发现一处生成器问题：匿名函数已经正确生成 closure 环境字段 `wakeReady`、`wakeMutex`、`wakeCond`，但 sync 方法生成器手写输出 receiver 名称，没有像普通表达式一样把捕获变量改写成 `__env->name`，导致 `thread(wakeWorker)` 中的 `wakeReady.waitTimeout(...)` 生成裸 `wakeReady` 并在 C 编译阶段失败。本轮修复 `xl6CgenSyncReceiver`，使 sync receiver 在匿名函数内先查询 capture 表，命中时输出 `__env->捕获名`。

固定规则：

- sync 方法 receiver 是匿名函数捕获变量时，必须生成 `__env->name`，不能生成裸局部名。
- `wakeReady.waitTimeout(2000)` 在线程闭包内生成 `xrtSemWaitTimeout(__env->wakeReady, 2000LL) == 0`。
- `wakeMutex.lock()` / `wakeMutex.unlock()` 在线程闭包内生成 `xrtMutexLock(__env->wakeMutex)` / `xrtMutexUnlock(__env->wakeMutex)`。
- `wakeCond.signal()` 在线程闭包内生成 `xrtCondSignal(__env->wakeCond)`。
- 主线程持有 `wakeMutex` 后 `wakeReady.post()`，再执行 `wakeCond.waitTimeout(wakeMutex, 2000)`；该等待生成 `xrtCondWaitTimeout(wakeCond, wakeMutex, 2000LL) == 0`，并应被 worker signal 成功唤醒。
- `thread(wakeWorker)` 仍按捕获闭包 borrow/retain 规则生成 `xl6_thread_start(wakeWorker, 1, ...)`。

对应覆盖：

- `src/cgen/xl6_cgen_async_api.c` 修复 sync receiver 的 closure capture 输出。

当前结论：sync 方法在匿名函数/线程闭包中的 receiver 已具备捕获感知生成；cond 不再只覆盖超时和裸 signal/broadcast，也覆盖跨线程 signal 成功唤醒等待者的真实并发路径。

## 补充：sem 容量上限与 postMultiple all-or-none

本轮继续压实 sync 基础原语。此前 `sem` 已覆盖空 `tryWait`、空 `waitTimeout`、`post` 成功、`postMultiple` 成功；但没有覆盖信号量达到最大计数时的 false 返回，也没有证明 `postMultiple` 超过剩余容量时不会部分增加计数。

实现审计中发现 XRT 的跨平台语义差异：Windows `ReleaseSemaphore` 在超过最大计数时整体失败且不改变计数；原 POSIX 分支会尽量部分增加计数，然后返回 false。这会让 xlang 的 `sem.postMultiple()` 在不同平台出现“返回值相同但状态不同”的隐性差异。本轮在 XRT 中将 POSIX 分支收紧为 all-or-none。

固定规则：

- `sem.post()` 在当前计数已达到最大值时返回 false，信号量计数保持不变。
- `sem.postMultiple(n)` 当 `n` 超过剩余容量时返回 false，并且不得部分增加计数。
- `sem.postMultiple(n)` 成功时仍一次性增加 `n` 个计数，并唤醒等待者。
- xlang 生成仍直接使用 XRT：`xrtSemPost(...)`、`xrtSemPostMultiple(...)`、`xrtSemWaitTimeout(...)`、`xrtSemTryWait(...)`。

## 补充：XRT group cancel 传播与 task.race pending cancel

本轮继续压实 task 取消语义。审计发现 XRT `xFutureWhenAll` / `xFutureRace` 输出 future 原本没有 pending cancel hook：对 group future 调用 `xFutureRequestCancel` 只会取消 group 外壳，不会向源 future 传播取消。这会削弱 xlang `task.cancel` 在聚合 future 上的真实含义。

本轮在 XRT 层补齐 group cancel 传播：

- future group 创建成功后，为输出 future 绑定 pending cancel / cleanup hook。
- `xFutureRequestCancel(groupFuture)` 先把 group 标记为 completed/cancelled，再对所有源 future 调用 `xFutureRequestCancel`。
- 正常完成、失败完成、race 赢家完成、显式取消完成时都会 detach pending hook，避免 group、promise、输出 future 形成引用环。
- XRT `future_core` 新增 `xFutureWhenAll` 与 `xFutureRace` 的 group cancel 传播测试：取消 group 后，两个源 future 都必须进入 `XFUTURE_CANCELLED`。

xlang 层本轮压实 `task.race`：

- `task.race([cancelRaceLeft, cancelRaceRight])` 直接落到 XRT race group。
- `task.cancel(cancelRaceGroup)` 生成 `xl6_task_cancel_value(cancelRaceGroup, 0)`，对具名 pending race group 按 borrowed 取消。
- 取消后 `await cancelRaceGroup` 必须抛出 `future cancel requested.`。
- 取消后 `await cancelRaceLeft` 和 `await cancelRaceRight` 也必须抛出 `future cancel requested.`。
- `test.bat` 锁定 `cancelRaceGroup = xl6_task_race_values(...)`、`cancelRaceLeft, 0, cancelRaceRight, 0`、`cancelRaceRequested = xl6_task_cancel_value(cancelRaceGroup, 0)` 以及两个 source await 路径。

当前说明：

- `task.race` 具备 pending group cancel 向 source future 传播的发布级覆盖。
- `task.all` 的同等级取消传播已在后续 `task.all typed-array wrapper cancel forwarding` 小节补齐；当前口径以该后续小节为准。

## 补充：task.all typed-array wrapper cancel forwarding

本轮继续压实 pending 聚合 future 的取消传播。上一轮 XRT 已经让 `xFutureWhenAll` / `xFutureRace` 输出 future 支持 group cancel 向 source future 传播，但 xlang `task.all` 为了把 XRT all-value 转换成 `array<T>`，会额外包一层 worker future。直接取消这层 wrapper 时，取消请求原本不会自动传到内部 `xFutureWhenAll` group。

本轮固定规则：

- XRT 新增 `xFutureForwardCancelTo(xfuture* pFuture, xfuture* pTarget)`，用于把一个 pending future 的取消请求转发到另一个 future。
- `task.all` wrapper 在启动 worker 前先创建内部 `groupFuture = xFutureWhenAll(...)`。
- wrapper future 创建成功后，生成层调用 `xFutureForwardCancelTo(future, arg->groupFuture)`。
- 对 pending `task.all` wrapper 执行 `task.cancel(...)` 时，wrapper 自身进入取消态，并向内部 group 传播取消。
- 内部 `xFutureWhenAll` 收到取消后继续向全部 source future 传播，因此后续 `await` 任一源 future 都应抛出 `future cancel requested.`。
- wrapper 完成、失败、启动失败和释放路径统一通过 `xl6_task_all_arg_release` 释放 `groupFuture` 与源 future 引用，避免 typed-array wrapper 引入新的引用泄漏。

对应生成规则：

- `xl6_task_all_start(...)` 复制源 future 后创建 `arg->groupFuture = xFutureWhenAll(arg->futures, count)`。
- `xl6_task_all_entry(...)` 直接等待 `arg->groupFuture`，再把 all-value 转成 `array<T>`。
- `xl6_task_all_start(...)` 在 `xTaskRunThread(...)` 成功后生成取消转发绑定：`xFutureForwardCancelTo(future, arg->groupFuture)`。
- 绑定失败时取消并释放 wrapper future，再抛出 `TaskError: task.all cancel forwarding setup failed`，避免出现“看似可取消但无法传播”的半状态。

对应覆盖：

- `test/cases/cgen_task_api.xl` 新增 pending `task.all([cancelAllLeft, cancelAllRight])` 后立刻 `task.cancel(cancelAllGroup)` 的行为测试。
- `await cancelAllGroup` 必须抛出 `future cancel requested.`。
- `await cancelAllLeft` 与 `await cancelAllRight` 也必须抛出 `future cancel requested.`，证明取消已穿透 typed-array wrapper。
- `examples/task_api.xl` 同步展示 pending `task.all` group cancel 会取消 source future。
- `test.bat` 锁定 `xFutureForwardCancelTo(future, arg->groupFuture)`、`cancelAllGroup = xl6_task_all_values(...)`、`cancelAllLeft, 0, cancelAllRight, 0`、`cancelAllRequested = xl6_task_cancel_value(cancelAllGroup, 0)` 以及两个 source await 路径。

## 补充：普通 async ownership pending cancel

## 审计：task.spawn ownership 返回值边界

本轮审计 `task.spawn` 的非标量返回值时，确认 `var`、`function`、`class`、`array<T>` 返回值当前不是合法生成规则，而是语义阶段明确拒绝的边界。

当前固定规则：

- `task.spawn` 当前只为第一版 XRT future bridge 支持的单返回值生成运行时调用。
- `func() as var` 作为 `task.spawn` 目标时必须在语义阶段失败，诊断包含 `task.spawn return type cannot be var`。
- `func(...) as func(...)`、`func(...) as ClassType`、`func(...) as array<T>` 作为 `task.spawn` 目标时必须在语义阶段失败，诊断包含 `task.spawn return type must be supported by the current XRT xvalue call bridge`。
- 这些返回类型不进入 `xl6_task_spawn_values(...)` 生成阶段，因此没有 pending cancel 正例生成规则。
- 后续如果扩展 task.spawn 桥接层，必须同时补齐成功完成、repeated await、completed cancel、pending cancel、worker 晚到完成保护、group cancel 传播和失败态 repeated await。

对应守门：

- `test.bat` 对四个负例逐条断言诊断文本。

当前结论：`task.spawn` 当前发布口径不包含 `var/function/class/typed array` 返回值。它们不是漏掉的 pending cancel 规则，而是明确拒绝的未来扩展点。

## 补充：普通 async completed cancel

本轮继续压实普通 `async func` 的完成态取消语义。规则固定为：具名 future 已经完成后，`task.cancel(future)` 必须返回 false；该操作不得释放或破坏 future 的完成结果，后续 `await future` 仍必须按原返回类型重复得到完成值。

本轮固定规则：

- completed cancel 必须按 borrowed 传入：`xl6_task_cancel_value(future, 0)`。
- int/bool/float 的 post-cancel await 继续走 `xl6_future_await_value(...)`。
- void 的 completed cancel 后仍允许再次 `await voidFuture`，用于确认完成态不会被 cancel 破坏。
- string 的 post-cancel await 继续走 `xl6_future_await_cstr_copy(...)`。
- var 的 post-cancel await 继续走 `xl6_xrt_retain((*(xvalue*)xl6_future_await_value(...)))`。
- function 的 post-cancel await 继续从 future 中读取 `XL6_Function`，并执行 `retain(env)`。
- class 的 post-cancel await 继续从 future 中读取 class 值，并保留函数字段的 retain。
- typed array/list/set/dict 的 post-cancel await 继续分别走 `xl6_xrt_typed_*_copy_mode(..., XRT_OBJMODE_LOCAL)`。

对应覆盖：

当前结论：普通 `async func` 的完成态取消语义已覆盖基础标量和主要 ownership-bearing 返回值；它与 pending cancel、failed repeated await 共同构成当前普通 async future 状态机的发布级守门。

## 补充：普通 async failed future 多类型

## 补充：函数体捕获边界

本轮修复一个语义和 C 后端之间的边界缺口：普通顶层变量当前生成在 `xlang_main` 内部，属于脚本入口局部变量；普通函数和 async 函数如果隐式读取它，语义阶段原先会放行，但生成出的 C worker 或 C 函数会访问未声明标识符。

当前结论：typed-array source 校验失败的 cleanup 不再依赖 `memset` 后宽泛释放全部 count。`task.all_start` 的语义是“retain 一个，失败时才能 release 一个”；`task.race_start` 在创建 group 前完成全量校验，不接管任何调用侧 source。

## 补充：默认 typed future array 的 empty-array 语义

本轮补齐默认声明的 typed future array 进入 `task.all/race` 的生成规则。该路径用于区分三类输入错误：

- source array 本身为 null：runtime helper 防御性错误，文本为 `task.all source array is null` / `task.race source array is null`。
- source array 非空但 count 为 0：用户可见 empty-array 错误，文本为 `task.all requires a non-empty future array` / `task.race requires a non-empty future array`。
- source array 中某个 future 元素为 null：用户可见 null-source-future 错误，文本为 `task.all source future is null` / `task.race source future is null`。

固定规则：
- `array<future<int>> defaultJobs` 生成 `xtarray defaultJobs = xrtTypedArrayCreate(xrtTypeFuture(), XRT_OBJMODE_LOCAL);`，默认声明不是 null。
- `array<int> defaultArrayAll = await task.all(defaultJobs)` 生成 `xl6_future_await_handle_release(xl6_task_all_from_array((xtarray)(defaultJobs), xrtTypeInt(), ...), ...)`。
- 因 `defaultJobs` count 为 0，行为层必须捕获 `task.all requires a non-empty future array`。
- `int defaultArrayRace = await task.race(defaultJobs)` 生成 `xl6_future_await_i64_release(xl6_task_race_from_array((xtarray)(defaultJobs), ...), ...)`。
- 因 `defaultJobs` count 为 0，行为层必须捕获 `task.race requires a non-empty future array`。
- 生成 C 中仍必须包含 `task.all source array is null` 与 `task.race source array is null` 防御性 guard，用于保护 helper 被内部或未来 ABI 以空句柄调用的场景。

对应覆盖：
- `test/cases/cgen_task_api.xl` 覆盖 default typed future array all/race。
- `examples/task_api.xl` 展示用户侧默认空容器写法。
- `test.bat` 锁定默认 `xrtTypedArrayCreate`、all/race empty helper、状态断言和 source-array-null 防御性 guard 文本。

当前结论：默认 typed future array 不再只由 `array[]` 字面量间接证明；它作为声明默认值进入 task 聚合时，也明确走 empty-array 语义。

## 补充：task.spawn 空 func 多返回类型错误传播

本轮补齐空函数值进入 `task.spawn` 时的 string/bool/float 生成规则，用于约束不同 await helper 的错误传播。

固定规则：
- `func(string) as string missingStringJob` 生成 `XL6_Function missingStringJob = {0};`。
- `string missingStringJobValue = await task.spawn(missingStringJob, "x")` 生成 `xl6_future_await_cstr_release(xl6_task_spawn_values(missingStringJob, xrtTypeString(), ...), ...)`。
- 因函数值没有 `invoke_var` 或 `invoke_xcall`，`xl6_task_spawn_values` 必须返回携带 `task.spawn requires a callable func value` 的失败 future；string await helper 只能传播该错误，不能返回空字符串。
- `func(bool) as bool missingBoolJob` 生成 `XL6_Function missingBoolJob = {0};`。
- `bool missingBoolJobValue = await task.spawn(missingBoolJob, true)` 生成 `xl6_future_await_i32_release(xl6_task_spawn_values(missingBoolJob, xrtTypeBool(), ...), ...)`，错误必须传播到 catch。
- `func(float) as float missingFloatJob` 生成 `XL6_Function missingFloatJob = {0};`。
- `float missingFloatJobValue = await task.spawn(missingFloatJob, 1.5)` 生成 `xl6_future_await_f64_release(xl6_task_spawn_values(missingFloatJob, xrtTypeFloat(), ...), ...)`，错误必须传播到 catch。
- 三条 catch 状态断言都必须生成 `...State == 42LL`，证明错误落入用户代码的 `catch` 分支。

对应覆盖：
- `test/cases/cgen_task_spawn.xl` 覆盖 string/bool/float 空 func task.spawn。
- `examples/task_api.xl` 展示用户侧写法。
- `test.bat` 锁定三类空函数帧、三类 await helper 和状态断言。

当前结论：`task.spawn` 空 func 诊断已经覆盖 int/string/bool/float 四类基础返回通道。后续修改 `xl6_task_spawn_values`、await helper 或 function value 初始化时，必须保持 callable 错误由 `task.spawn` 产生并穿透到用户 `catch`。

## 补充：空 future await 全返回通道

本轮补齐默认空 future 的直接 await 生成规则。该路径用于固定所有主要返回类型共享同一个空句柄错误入口，而不是在各自外层 helper 中返回默认值。

固定规则：
- 默认声明 `future<T> missingAwaitX` 生成 `xfuture* missingAwaitX = 0;`。
- `await missingAwaitBool` 生成 `(*(int*)xl6_future_await_value(missingAwaitBool, ..., sizeof(int)))`。
- `await missingAwaitFloat` 生成 `(*(double*)xl6_future_await_value(missingAwaitFloat, ..., sizeof(double)))`。
- `await missingAwaitVar` 生成 `xl6_xrt_retain((*(xvalue*)xl6_future_await_value(missingAwaitVar, ..., sizeof(xvalue))))`。
- `await missingAwaitFn` 生成 `(*(XL6_Function*)xl6_future_await_value(missingAwaitFn, ..., sizeof(XL6_Function)))`。
- `await missingAwaitBox` 生成 `(*(XL_Class_AsyncBox*)xl6_future_await_value(missingAwaitBox, ..., sizeof(XL_Class_AsyncBox)))`。
- `await missingAwaitList` / `Set` / `Dict` 分别生成 `xl6_xrt_typed_list_copy_mode`、`xl6_xrt_typed_set_copy_mode`、`xl6_xrt_typed_dict_copy_mode`，但源值仍必须先从 `xl6_future_await_value(...)` 取得。
- `xl6_future_await_value` 在 `pFuture == 0` 时统一抛 `AsyncError: await on null future`；外层 copy/retain helper 不得在 active error 情况下继续制造默认值。

对应覆盖：
- `test/cases/cgen_async.xl` 覆盖 bool/float/var/function/class/typed list/set/dict，加上既有 int/string/typed array。
- `examples/concurrency.xl` 展示常用返回通道的用户侧 `try/catch` 写法。
- `test.bat` 锁定每条路径的默认空 future、await lowering 和 `...State == 42LL` 断言。

当前结论：空 future await 的直接证据已经覆盖所有当前主要 await helper。后续新增 future 完成值类型时，也应先补相同的空句柄 await 守门。
