## 实际观察

从 `demo6` 运行：

```sh
bash tools/check_extlib_sqlite.sh
```

1. 首次在 C sanitizer、分配和线程检查通过后，明确停在黄金文件 CRLF/LF
   对照；按仓库已有 `text eol=lf` 策略规范化本地旧检出，内容与 Git 索引未变。
   这是已定位的夹具行尾问题，不是下述无诊断退出的根因证明。
2. 随后一次完整门禁打印 C 核心、149 个 SQLite 分配故障点、XRT Buffer/
   临时文本故障与四线程通过，之后无额外诊断，外层工具返回 1。
   当时未显式透传原始 WSL 子进程状态，且脚本在失败时也删除临时目录，
   无法确定失败命令、真实退出码或日志内容。**不能据此断定是超时、包错误
   或主线错误，也没有稳定的最小复现。**
3. 补充失败现场保留与 ERR 诊断后，同一默认门禁完整退出 0；原有路径和
   超时上限未放宽。语言中央、边界、文件用例、两份 XLang 范例和公开 C 范例
   的 JIT/AOT 及 GCC 固定输出对照通过，输入前后指纹一致。
4. Windows 最终门禁 37 项全部通过，生成原型 44 个、只读常量 45 个。
   本地结果记录为 `build/test/sqlite_guard/results_0844a82f9bb943bc8b78d2c7c19b11ab.json`；
   该路径是本轮证据，不是仓库运行依赖。

- 原有 stdout 日志、编译器版本、输入指纹和已生成产物均保留。
- 输入指纹补入实际运行的 `release/xl` 与 `release/libxlc.so`。
- 使用已有 `test/cases/c_run_exit_code.c` 生成无输出的退出 37 探针，临时作为
  `CC` 运行本门禁；错误定位到编译器版本查询，原始 37、命令与现场均正确保留。
  这是留档机制验证，不代替 SQLite 功能验收。
