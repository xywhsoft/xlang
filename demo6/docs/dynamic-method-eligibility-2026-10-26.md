# 动态方法资格检查：保留语义的编译性能修复

## 修复内容

动态方法表的构建和完整性检查都会访问类/声明组合。原实现对无关类的方法
也扫描全部节点，寻找覆盖签名；完整标准库参与的程序因而产生大量无效扫描。

现在先用声明身份核对祖先关系，再执行原有的重载隐藏检查。无关组合不再
扫描全部节点；有关组合仍检查同名、同参数签名和 getter/setter 种类。
具体布局共享泛型源声明时仍按声明身份处理，不按类型名称近似。

没有新缓存、可变索引、放宽后的 verifier 或 Cgen 补丁；动态表完整性检查
仍然执行，效果、物理 ABI、拥有权和运行时算法不变。此改动不宣称把整个
算法改成线性复杂度，也不消除其他编译阶段的成本。

## 语义证明与真实产品

- 私有实现单元直接包含当前生产 IR，实现与独立全扫描参考算法逐项比较。
  每次 11,396 个判定；Windows/Linux 的 O0/O2 四次运行均通过。显式断言覆盖
  继承和不同参数重载、属性、访问标志、共享声明、缺失基类及有界循环。
- 五个现有语言用例分别用旧/新真实候选运行。每端 15 对 typed IR、lowered IR
  和 C 文件逐字节相同；并经过 JIT、显式模块、独立 AOT、严格 GCC O0/O2。
- 新候选另行完成五组正常联合业务流：select 与 IOCP/epoll，每端通过
  JIT、模块、独立 AOT、CLI 四条路径，共 8 次完整业务流及 checked 退役。

实际候选使用普通构建脚本重建 TCC、XRT、CLI、两个共享库及 VFS，不覆盖
发布目录，不替换生产源对象。私有单元只复用已校验的依赖对象清单，其本身
不是发布产品证明；真实产品验收另行完成。每端 47 个阶段（41 产品阶段、
6 单元编译/链接/运行阶段），两端合计 94 阶段。

## 配对计时

同一大型联合用例、同一输入路径、同一主机上，分别运行旧/新 CLI 的 `check`：

| 平台 | 旧候选 | 新候选 | 本次观测加速 |
|---|---:|---:|---:|
| Windows | 44.94 s | 1.20 s | 37.35 倍 |
| Linux | 33.69 s | 1.12 s | 30.17 倍 |

这是一次配对实测，不是统计微基准，也不保证每个程序或整个 JIT/AOT 流程
都有同样增幅。多 API 联合宿主仍需数分钟；本批不声称已解决全部编译性能问题。

## 证据与复现

证据根 `F:/xlang-validation/five-groups-20261025/p7-eligibility`，日期跨入
2026-10-26 后沿用原目录。核心回执为 `verified-windows.json`、
`verified-linux.json` 和 `next.json`。

```text
python tools/check_dynamic_method_eligibility_shipping.py --root <新正常构建目录> --build-report <新 build.shipping.json> --previous-root <旧正常构建目录> --previous-build <旧 build.shipping.json> --unit-report <私有单元 results.json> --out <新证据目录>
```

控制器验证输入/产品来源，保存旧/新输出，独立 reader 再复核归档、构建、
日志、产物、输出对照及控制器哈希。此前已独立核验且未变的依赖对象清单
复用；单元控制器在使用前仍逐项核对源、头与对象。

仓库内的私有单元入口可独立复现，不依赖本机证据脚本：

```text
python tools/check_dynamic_method_eligibility_unit.py --root . --dependency-build <源编译器 build.json> --runtime <清单中的对应运行库> --out <新单元目录>
```

依赖清单可由既有 public source driver 构建工具生成。该入口验证清单中的
对象、源、头和运行库身份，直接包含当前 IR，并记录 GCC 实际使用的当前
头文件依赖。它只证明私有实现单元，不声称旧依赖清单代表当前整个编译器。
此入口另在两端完成同一单元的 12 个复现阶段，不混作新增语言功能覆盖。

首次源冻结被并行更新的扩展库台账文档打断；只有该无关文档漂移，生产源码
和构建脚本相同。独立恢复报告明确保留原失败，不把它改写成成功。Windows
首轮 OOM 和 Linux 首轮中断也保留；后续用同一归档、新目录和串行正常构建
完成验收。未更改系统内存、WSL、Defender 或两边时间 ABI。

长期目标仍 active。网络旧生成后端/fixture、相关守卫和最终逐项封板仍待
继续，不以本批替代五组整体完成证明。验证仅离线普通语言材料和自建 loopback，
没有公网、扫描、攻击模拟或网络安全性质专项。

未决策仍为 CRT 0 项、XRT 11 组：核心/错误/所有权、内存、动态值图、
剩余平台信息、HTTP、WebSocket、类型转换、对象图、调用值桥接、typed 容器、
内部支撑。内存池最后处理。
