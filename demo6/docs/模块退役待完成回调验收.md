# 模块退役：待完成回调验收

混合生成代码与原生代码的模块使用同一 V4 退役合同。原生 Promise 槽位通过组合后的只读追踪合同加入实际拥有图，在完成步骤中释放；测试不额外添加代码租约或合成根节点。

Future 的 `finally` 可以由就绪队列执行。准备步骤返回 `BUSY` 后，回调仍属于正在进行的图准备阶段，因此测试在 API 锁下检查以下一致快照：

- 模块仍有实际拥有图计划，阶段为准备阶段，且已通过模块预检。
- 拥有图尚未清除，代码租约仍存在。
- 类终结器按照相应场景在终结阶段执行。

测试不把“当前线程正运行清理驱动”作为异步通知的必要条件。事件顺序、跨线程别名及计数器使用 C11 原子操作，避免观察线程与就绪队列之间的数据竞争。

`xlir_pending_module_preparation` 的完整矩阵保留 8 个场景、O0／O2 两个编译级别：无外部根、保留 Future、回调中保留对象、保留原生生产端，以及生产端显式成功、失败、取消、关闭。

Windows 源码运行时与实际 TCC 通过全部 16 条路径：400 次真实编译／重定位／删除生命周期、800 次有序 finally 通知、400 次类终结、1,200 次跨线程代码驻留与无锁／无冻结探测。每次生命周期均验证实际引用延期、最终 `MEM_FREE` 和严格零存活内存差值。

该结果验证上述模块退役场景。全仓库 74 项检查及 Linux 联合发布验收继续独立执行。
