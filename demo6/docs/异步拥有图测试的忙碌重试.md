## 无结果等待的真实挂起门

同日的整批验收发现 `xlir_async_void_suspension_native.c` 仍假设 async 调用会在调用线程立即运行到第一次 await。固定工作线程模型下，主线程可能先调用完成函数，此时原生 Promise 尚未创建；未同步的全局句柄读写也不成立。

只修改这个原生测试辅助文件：使用共有 freeze 序列化句柄发布和观察，保留真实 Future 引用，并在五秒内等待源图中出现可准入的停放续体 Watch。观察只用公开拥有图接口，不读取私有字段；Promise 完成及句柄释放在离开 freeze 后执行。因此仍是实际挂起，未改成预先完成的 Future，也没有固定 sleep。

语言夹具及其成功、失败、取消、关闭、finally 和析构断言不变。五次 JIT、十次独立 AOT 执行及严格 GCC O0／O2 编译通过，日志和输入独立复核。证据为同一目录下的 `void-gate-r282/results.json` 与 `void-gate-proof-r283/results.json`。这不等于整个 HTTP 扩展测试门通过，相关旧 ABI 与清理问题仍单独保留。

## 模块执行器的分阶段准备合同

模块执行器的 IR 夹具仍搜索旧的 `quiesce(wait)` if 语句，而当前 Cgen 在分阶段准备中用 `quiesce(stage != 0)` 并明确返回 BUSY／READY。实际生成 C 证明其余四个合同条件均存在，只更新这一个精确形态断言；未恢复旧 ABI，也未放宽语义断言。

## 回调余额的物理静止基线与验证工具迁移

回调边界的余额测试在新事务结束时等待了物理静止，却在开始时直接取快照。此前未计量的发布屏障／取消用例可能尚有执行器原生存储待释放，导致后续区间的存活量下降，误报为余额不等。保留原断言的诊断记录确认是计量区间不对称，而非新增分配泄漏。现在五处成对基线均先调用已有的真实执行器静止门，再取快照；总基线、释放计数、取消、错误和分配失败断言不变，没有固定 sleep 或运行时修改。

另将任务池的旧 `quiesce(wait)` 字面形态断言改为实际的 `quiesce(stage != 0)`，并让严格聚合工具使用共有的 GCC 响应文件／重定向助手及发布包含目录，避免过长直接命令尚未启动编译器便失败。
