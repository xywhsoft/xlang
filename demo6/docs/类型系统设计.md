# xlang DEMO6 class 与 custom 设计

本文档记录 DEMO6 当前阶段的 `class` 与 `custom` 设计。

当前阶段不设计动态对象基类，不引入动态字段、缺失字段元方法、反射式成员查找、统一动态 header 或 method table。

## 1. 总原则

`class` 与 `custom` 必须服从 DEMO6 第一绝对原则：xlang 能够和 C 完美混编。

因此：

- `class` 是 xlang 自有结构体类型，用来扩展 C 语言的结构体与方法语义。
- `custom` 是 C 黑盒句柄类型，用来把 C API 零成本映射成 xlang 的 OOP 调用外观。
- 二者都不默认承担动态对象开销。
- 方法调用必须尽量 lowering 到普通 C 函数调用。
- 类型布局、生命周期、C 符号映射都必须显式、稳定、可检查。

## 2. DEMO5 可参考点

DEMO5 中可保留为参考的点：

- `class Name ... end` 与 `custom Name ... end` 是清晰的类型声明入口。
- `extends` 可以表达单继承。
- `create` / `destroy` 能表达构造和析构。
- 方法写在类型体内，调用写成 `value.method(...)`，符合 xlang 预期。
- custom 中的 `extern create`、`extern destroy`、`extern func` 很适合表达 C API 绑定。

DEMO5 中不建议沿用的点：

- custom 与动态对象 runtime 绑定太深。
- custom 暴露 `payload` 字段，导致黑盒 C 句柄变成可随意读写的动态状态。
- class/custom 的方法分发、动态字段、引用计数、弱引用、循环收集混在一起，稳定性成本高。
- DEMO5 中让普通结构体类继承动态对象基类的写法，会把简单 class 也拖入动态对象体系。

DEMO6 的取舍：

- class 回到结构体模型。
- custom 回到黑盒句柄模型。
- 动态对象能力后续单独设计，不进入当前 class/custom 方案。

## 3. class 定位

`class` 表示 xlang 自有结构体类型。

核心能力：

- 字段。
- 方法。
- 单继承。
- 构造函数。
- 析构函数。
- C 兼容布局。

不包含：

- 动态字段。
- 反射式方法查找。
- 运行时 method table。
- 自动装箱。
- 默认引用计数。
- 默认 GC 或循环收集。

示例：

```xlang
class Vec2
    int x = 0
    int y = 0

    create(int x, int y)
        self.x = x
        self.y = y
    end

    func length2() as int
        return self.x * self.x + self.y * self.y
    end
end

auto v = Vec2(3, 4)
auto n = v.length2()
```

## 4. class 字段

字段使用 DEMO6 统一的类型前置声明。

```xlang
class User
    int id = 0
    string name = ""
end
```

规则：

- 字段语法为 `Type name` 或 `Type name = default`。
- 字段名不能与同一 class 内的字段、方法、构造/析构入口冲突。
- 字段默认值必须能赋给字段类型。
- 第一阶段建议默认值只允许静态表达式。
- 没有显式默认值时，使用类型默认值初始化。

不采用 DEMO5 的成员字段写法：

```xlang
var x as int
```

## 5. class 方法

class 方法写在 class 体内。

```xlang
class Counter
    int value = 0

    func add(int step) as int
        self.value += step
        return self.value
    end
end
```

规则：

- 方法声明使用普通 `func` 语法。
- 方法体内自动注入 `self`。
- `self` 表示当前实例。
- `self` 不能重新赋值。
- 方法调用 `a.add(1)` 静态解析为已声明方法。
- 找不到方法时编译期报错，不做动态查找。

期望 lowering：

```xlang
a.add(1)
```

```c
xl_class_Counter__add(&a, 1);
```

其中 C 函数名只是示意，最终名称必须服从 DEMO6 的 C 符号稳定编码规则。

## 6. class 构造

构造函数使用 `create`。

```xlang
class Point
    int x
    int y

    create(int x, int y)
        self.x = x
        self.y = y
    end
end

auto p = Point(1, 2)
```

规则：

- `Type(...)` 表示构造该类型。
- `create(...)` 没有返回类型。
- 可以重载多个 `create`，重载规则与普通函数一致。
- 如果没有声明 `create`，编译器生成默认构造：按字段默认值初始化。
- 字段初始化先执行，再执行用户 `create` 体。

不引入 `new` 作为第一阶段 class 构造方式。

## 7. class 析构

析构函数使用 `destroy`。

```xlang
class Buffer
    point handle

    destroy()
        // 释放 handle
    end
end
```

规则：

- `destroy()` 没有参数，也没有返回类型。
- 拥有 `destroy` 的 class 需要编译器生成离开作用域时的清理调用。
- 清理必须覆盖正常离开、`return`、`break`、`continue` 等路径。
- 错误处理设计完成后，清理规则还必须覆盖异常路径。
- 第一阶段不引入 `delete` 作为用户手写释放语句。

复制规则：

- 没有 `destroy` 且字段都可复制的 class，默认允许按值复制。
- 有 `destroy` 的 class，默认视为不可复制。
- 含有不可复制字段的 class，默认也不可复制。
- 如果后续需要复制资源，必须显式设计 `clone` 或 copy 构造，不做隐式猜测。

## 8. class 继承

DEMO6 第一阶段只支持单继承。

```xlang
class Point2
    int x
    int y
end

class Point3 extends Point2
    int z
end
```

期望 C 布局：

```c
typedef struct XL_Class_Point2 {
    int64_t x;
    int64_t y;
} XL_Class_Point2;

typedef struct XL_Class_Point3 {
    XL_Class_Point2 base;
    int64_t z;
} XL_Class_Point3;
```

规则：

- 父类布局必须是子类布局前缀。
- 子类可以直接访问继承字段，例如 `p.x`。
- 子类构造时，如果父类存在无参 `create`，可自动调用。
- 如果父类构造需要参数，子类 `create` 内必须显式调用 `base(...)`。
- 析构顺序为：先执行子类 `destroy`，再执行父类 `destroy`。
- 第一阶段不设计虚方法和 late dispatch。

示例：

```xlang
class Base
    int seed

    create(int seed)
        self.seed = seed
    end
end

class Child extends Base
    int value

    create(int seed, int value)
        base(seed)
        self.value = value
    end
end
```

## 9. class 与 C

`class` 的生成方向应尽量是可读 C struct。

建议生成：

```c
typedef struct XL_Class_Vec2 {
    int64_t x;
    int64_t y;
} XL_Class_Vec2;

static int xl_class_Vec2__create(XL_Class_Vec2* self, int64_t x, int64_t y);
static int64_t xl_class_Vec2__length2(XL_Class_Vec2* self);
```

规则：

- class 方法 C 侧第一个参数是实例指针。
- class 构造 C 侧第一个参数也是实例指针。
- class 析构 C 侧第一个参数也是实例指针。
- 不默认把 class 作为 C ABI export 类型。
- 如果要暴露给 C，应通过 `export "c_symbol" func ...` 写明确 wrapper。

## 10. custom 定位

`custom` 表示 C 黑盒句柄类型。

它的目标不是实现完整 class，而是把一组 C 函数声明成 xlang 可读的 OOP 形式。

示例 C API：

```c
typedef struct image image;

xptr image_open(const char* path);
int64_t image_close(xptr self);
int64_t image_width(xptr self);
int64_t image_resize(xptr self, int64_t w, int64_t h);
```

对应 xlang：

```xlang
custom Image
    extern "image_open" create(string path)
    extern "image_close" destroy()
    extern "image_width" func width() as int
    extern "image_resize" func resize(int w, int h) as int
end

auto img = Image("a.png")
auto w = img.width()
img.resize(320, 240)
```

期望 lowering：

```c
XL_Custom_Image img;
img.__handle = image_open("a.png");
w = image_width(img.__handle);
image_resize(img.__handle, 320, 240);
image_close(img.__handle);
```

## 11. custom 结构

custom 内部只保存 C 黑盒句柄。

建议生成：

```c
typedef struct XL_Custom_Image {
    xptr handle;
} XL_Custom_Image;
```

规则：

- 句柄字段是编译器内部字段，不作为 xlang 普通字段开放。
- custom 第一阶段不允许声明 xlang 字段。
- custom 第一阶段不允许继承。
- custom 第一阶段不允许动态字段。
- custom 第一阶段不允许把 `payload` 作为公开成员。
- 如果需要额外 xlang 字段，应使用 `class` 包装 `custom`。

包装示例：

```xlang
custom NativeImage
    extern "image_open" create(string path)
    extern "image_close" destroy()
    extern "image_width" func width() as int
end

class ImageInfo
    NativeImage image
    string path

    create(string path)
        self.path = path
        self.image = NativeImage(path)
    end
end
```

## 12. custom create/destroy

custom 的构造和析构由声明决定。

```xlang
custom File
    extern "file_open" create(string path, string mode)
    extern "file_close" destroy()
end
```

C ABI 方向：

```c
xptr file_open(const char* path, const char* mode);
int file_close(xptr self);
```

规则：

- `extern create` 调用 C 函数并接收返回的黑盒句柄。
- `extern destroy` 调用 C 函数并传入黑盒句柄。
- 如果声明了一个或多个 `extern create`，`Type(...)` 只参与 `create` 重载解析。
- 如果完全没有声明 `extern create`，`Type(point_value)` 表示直接绑定一个已有 C 指针，不调用任何 C 构造函数。
- 没有 `extern create` 时，除了 `point` 或明确兼容的 C 指针表达式，不允许用普通参数构造 custom。
- 如果声明了 `extern destroy`，custom 变量离开生命周期时，编译器对非空句柄调用 `destroy`。
- 如果没有声明 `extern destroy`，编译器不释放句柄，也不猜测释放方式。
- 有 `destroy` 的 custom 默认不可复制。
- 无 `destroy` 且句柄只是借用/观察用途的 custom，可以按普通值复制句柄；是否安全由 C API 映射约束保证。

空句柄策略：

- custom 的默认初始化值是空句柄。
- 空句柄可以作为 custom 的可表示值存在。
- 编译器插入 `destroy` 时必须先判断句柄非空。
- 普通方法调用不自动做空句柄检查，编译器只把句柄传给 C 函数。
- 如果某个 C API 不接受空句柄，应该通过映射文档、显式 `valid()` 方法或后续错误处理机制表达，不在 custom 基础模型中暗加运行时检查。

当前边界：

- custom `create` 失败时，如果 C 构造函数返回空句柄，xlang 保存空句柄；语言层不替 C API 猜测错误类型。
- 需要暴露失败原因时，应由映射的 C API 提供 `lastError()`、返回状态码，或在 xlang wrapper 中显式 `throw "message"`。
- 当前不提供通用的提前释放语法。需要提前释放时，应通过 custom 映射提供会释放并清空句柄的显式方法，避免后续自动析构重复释放。
- 编译器自动插入的 `destroy` 仍以生命周期结束为主路径，且必须先判断句柄非空。

## 13. custom 方法

custom 方法通常是 extern 方法。

```xlang
custom Bag
    extern "bag_create" create()
    extern "bag_destroy" destroy()
    extern "bag_add" func add(int value) as int
    extern "bag_count" func count() as int
end
```

C ABI 方向：

```c
xptr bag_create();
int64_t bag_destroy(xptr self);
int64_t bag_add(xptr self, int64_t value);
int64_t bag_count(xptr self);
```

规则：

- xlang 方法参数列表不写隐藏的 `self`。
- C 函数第一个参数固定接收 custom 内部句柄。
- 编译器负责把 `a.add(1)` lowering 为 `bag_add(a.__handle, 1)`。
- 该调用不能发生装箱、动态查找或额外分配。

允许 custom 内部声明 xlang helper 方法，但第一阶段建议谨慎：

```xlang
custom Bag
    extern "bag_create" create()
    extern "bag_destroy" destroy()
    extern "bag_count" func count() as int

    func empty() as bool
        return self.count() == 0
    end
end
```

helper 方法仍然必须静态解析。

## 14. custom 所有权

custom 不内置复杂所有权系统，生命周期完全由 `create` / `destroy` 映射约束决定。

规则：

- 有 `create` 且有 `destroy`：`create` 返回的句柄由当前 custom 实例持有，离开生命周期时自动调用 `destroy`。
- 有 `create` 但没有 `destroy`：xlang 可以创建句柄，但不会自动释放，通常只适合进程级对象、外部统一回收对象或 C API 自身管理生命周期的对象。
- 没有 `create` 但有 `destroy`：custom 通过 `Type(point_value)` 绑定已有指针，离开生命周期时自动调用 `destroy`，这表示映射作者明确把该指针交给 xlang 管理。
- 没有 `create` 且没有 `destroy`：custom 只保存并传递指针，xlang 不额外管理内存。
- custom 可以作为 class 字段；外层 class 的清理必须按字段声明顺序的反序清理拥有 `destroy` 的 custom 字段。
- custom 可以作为局部变量。
- 有 `destroy` 的 custom 不建议第一阶段作为普通函数按值参数或按值返回。
- 无 `destroy` 的 custom 作为参数或返回值，本质上只是指针值传递。

第一阶段不设计主动提前释放语法。

如果 C API 需要手动关闭，应该先把关闭函数声明为普通方法；但编译器不会因为调用了该方法就自动把句柄置空或取消后续 `destroy`。后续如需支持“提前释放且防双释放”，必须设计专门的 `close/detach/move` 规则。

后续再设计：

- borrowed custom。
- attach/detach。
- move。
- raw handle 显式借用。
- 与 `var` 的装箱规则。

## 15. class 与 custom 的边界

建议边界：

- 用 `class` 表达 xlang 自己拥有布局的结构体类型。
- 用 `custom` 表达 C 已经拥有布局、xlang 只持有句柄的黑盒类型。
- 需要字段 + C 句柄时，用 `class` 包一层 `custom` 字段。
- 需要零成本 C API OOP 外观时，用 `custom`。

不要把以下能力塞进 custom：

- 任意 xlang 字段。
- 动态字段。
- 元方法。
- 继承。
- 反射式方法表。

这样能保持 custom 的核心价值：声明即绑定，调用即 C 函数调用。

## 16. 与 var 的关系

`var` 未来可以持有 function/class/custom，但第一阶段先不开放。

第一阶段规则：

- function 不默认装入 `var`。
- class 不默认装入 `var`。
- custom 不默认装入 `var`。
- 当前 XRT 的 class value 只有裸结构体数据块，缺少 xlang 具体类型身份和 typeops。
- 当前 XRT xvalue 没有第一阶段约定好的 function 承载格式。
- 如果后续需要 `var` 持有 function/class/custom，必须先设计完整的 typeops：copy、move、destroy、trace、type id。

这避免为了 `var` 兼容而重新造出动态对象 runtime。

## 17. 暂缓能力

以下能力不进入当前 class/custom 方案：

- 动态对象基类。
- 动态字段。
- 缺失字段读写/call 元方法。
- 虚方法与 late dispatch。
- operator 重载。
- 属性 `get` / `let`。
- 索引分发。
- custom 继承。
- custom 公开 payload。
- `new` / `delete`。
- class/custom 的反射 API。

这些能力后续如果要做，必须单独设计，不能作为 DEMO5 兼容项自动进入。
