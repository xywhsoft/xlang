# xlang DEMO6 标准库设计

XRT 与 xruntime 的语言内核、语言级抽象和显式底层入口边界见 [xruntime 语言桥接契约](xruntime语言桥接契约.md)。

## 总原则

DEMO6 标准库默认进入 xlang 编译环境，用户不需要为基础能力手写 `extern` 或 `import`。

标准库不是另起一套运行库。能够由 XRT 提供的能力，必须优先映射到 XRT；确实属于 CRT 基础设施、没有必要在 XRT 重复实现的能力，可以直接映射到 CRT。典型例子是 `math` 命名空间，它映射到 C 数学函数。

标准库使用短命名空间：

```xlang
math.log(10.0)
string.split("a,b", ",")
time.now()
file.readText("data.txt")
```

不采用 DEMO5 中额外增加一层包命名空间的写法。

带密钥短消息散列使用明确的算法命名空间：默认 `siphash.hash64`
（`string`/`bytes`）与 `siphash.hash64Buffer` 接受恰好 16 字节的 `bytes`
密钥、可选字节上限 `size=-1`；`siphash.hasher(key)` 返回可分块追加的
`SipHasher64`。内嵌 NUL 属于数据，不用 C 零结尾约定推断长度。64 位实现
直接调用 XRT keyed-hash 模块，未使用时不引入该模块；域分离的 128 位
变体仅在显式 `import siphash128` 扩展时编入，输出 16 字节 Buffer。
流式 hasher 是可变对象；跨线程共享时由调用者串行化。同样，传入
`Buffer` 后，调用尚未结束前不得并发修改该 Buffer。

## 编译器实现口径

标准库命名空间在语义检查前展开：

1. 编译器识别 `namespace.name` 或未来的 `namespace.sub.name` 成员访问。
2. 如果命中标准库函数表，将其改写为内部函数名。
3. 编译器只为实际用到的标准库函数注入 `extern` 声明。
4. 后续语义检查、类型推断、C 代码生成继续复用现有 C 混编能力。

示例：

```xlang
auto x = math.sqrt(9.0)
```

会在编译器内部等价展开为：

```xlang
extern "sqrt" func __xl_std_math_sqrt(float x) as float
auto x = __xl_std_math_sqrt(9.0)
```

这保证标准库和 C 混编使用同一条 ABI 路径。

## 字符串所有权

DEMO6 的静态 `string` 已是 XLIR 受管理值，当前 C 表示为 `char*`，并在 IR 中区分 borrowed、owned、retain/copy 与 release。赋值保持值语义；索引写入采用 copy-and-commit，不把共享可变别名暴露给语言层。

2026-09-28 决定：普通 `string` 允许内嵌 U+0000。2026-09-29 又决定将
语言字符串 C ABI 定为两个字段：只读数据指针和实际 UTF-8 字节长度；
不在值结构体中保存容量。`byteLen` 直接读取实际长度，按 Unicode scalar
计数的 `length`/`len` 扫描 UTF-8；容量与重复追加属于 `Buffer`。语言
`string` 的末尾可以额外补零以方便显式 C 互操作，但不能用 `strlen`
推断语言值长度。只有转换到 C 字符串互操作时才检查并拒绝内嵌 NUL；
`cString.length` 则故意只计算首个 NUL 之前的长度。

普通同步函数的只读字符串参数可在 XLIR 中作为调用期借入值，不复制
字节；写入须构造独立的新值并提交，返回、存储、闭包捕获和异步逃逸前
须取得所有权。跨全局/共享存储或未知 C 调用边界不得推测借入安全。
上述双字段 ABI 与完整长度链路仍在迁移中，不是现有实现能力。

标准库仍保留一层 C/XRT 兼容桥：

1. 返回需由 `xrtFree` 释放的旧式 XRT API 可以先以 `point` 接收原始分配。
2. `xl6_xrt_take_cstr` 消费该分配；独立 XLIR 产物生成 owned 副本，旧运行时头中的 inline 版本只作为 borrowed 临时桥。
3. borrowed 结果进入变量、字段、返回值、闭包或异步状态前，XLIR 必须建立自己的 owned 字符串。
4. 用户不手动释放 `string`；所有正常路径和失败路径的释放由 XLIR 所有权合同闭合。

`xrtTempMemory` 因此不是语言字符串的存储模型，只是尚未迁移完的标准库 C helper 的兼容边界。标准库重设计时应优先改为显式 typed bridge，不再新增依赖临时区的接口。

## 命名空间规则

标准库命名空间只在成员访问位置生效，例如 `math.sqrt`。

如果写了已存在标准库命名空间但不存在的符号，例如 `math.unknown()`，编译器报错。

标准库支持命名空间常量，例如 `math.pi`。常量在标准库重写阶段直接改写为字面量，不生成运行时函数调用。

## 第一批已实现函数

全局输出函数默认进入环境，不需要命名空间。`print` / `println` 是值输出：接收任意数量参数，按调用顺序输出，参数之间自动插入一个空格；`print` 不追加换行，`println` 追加换行。`write` / `writeln` 是文本输出：只接收字符串，不做值格式化、不自动插入空格；`write` 不追加换行，`writeln` 追加换行。

`xl6_xrt_print` 的生成代码不使用 C `FILE*`、`stdout`、`fwrite` 或 `fflush`。Windows 下由生成文件自声明最小 WinAPI 原型并通过标准输出句柄写入，不依赖 `windows.h`；POSIX 下通过 `write(1, ...)` 写入。值格式化仍优先使用 XRT 的整数、浮点、时间和 JSON/XLON 转换能力。

`math.divRem(numerator, denominator)` 返回 `(int, int)`，使用 xlang 已有的
受检整数 `/` 与 `%`；零除和最小整数除以 `-1` 沿用语言错误语义，不引入 C
`div_t` 布局或未定义行为。

Windows 内嵌 TCC 默认链接 UCRT 以解析旧 msvcrt 未导出的 C99 数学符号；
Linux 链接 `libm`。`frexp/modf/remQuo` 使用语言现有的 `out` 参数 ABI
组合两个标量结果，不引入 C 结构体布局；生成的 C 仍是普通标量原型和
调用，不含逐函数 Cgen 规则。

Windows 旧 `msvcrt` 对 `frexp(-0)` 的结果与 IEEE Annex F 的符号位
合同不一致，而 TCC 仍可能优先从它导入已有符号。因此零值在 xlang
源包装中直接返回，绕开该 CRT 差异；非零值继续直接调用 CRT。
`signBit/isNormal/isUnordered` 由普通 xlang 表达式实现，不依赖 C 宏的
平台枚举值。`isNormal` 的两个界值是 xlang `float` 固定 binary64 格式的
最小正规数与最大有限数，生成代码无需每次调用 `ldexp` 求阈值。

线程浮点环境不进入默认命名空间。显式 `import floatEnv` 后可使用
`getRounding/setRounding`、`getFlags/clearFlags/raiseFlags`、`capture/hold`
和 `Snapshot.restore()`。`RoundingMode` 的稳定编码为就近偶数、向下、
向上、趋零；异常标志的稳定掩码为 invalid=1、divideByZero=2、
overflow=4、underflow=8、inexact=16，不公开平台 `FE_*` 数值。
快照记录创建线程，只能在同一 OS 线程恢复；析构只释放内存，不自动
恢复环境。尤其不能把快照跨 `await` 搬到可能不同的工作线程。嵌套
快照按调用者的恢复顺序生效，`hold()` 额外清除标志并屏蔽陷阱，直至
显式恢复。该模块在内嵌 Windows TinyCC 上直接同步 x87 与 SSE 环境，
以避开其头文件声明 `fenv` 但未链接实现的 CRT 缺口；正常 C 工具链使用
标准 `<fenv.h>`。`raiseFlags` 保证设置可查询的标志位，但不同平台的
浮点陷阱触发行为不作为语言合同。本轮在 Windows 内嵌运行、独立 build
和严格 C 编译验证。

`ascii` 接收 xlang `char`，只识别 U+0000..U+007F，结果不随 C locale 变化。
当前提供 `isAlpha/isDigit/isAlphaNumeric/isHexDigit/isWhitespace/isBlank/`
`isControl/isPrintable/isGraphical/isPunctuation/isLower/isUpper/toLower/toUpper`；
非 ASCII scalar 的分类结果为 `false`，大小写转换原样返回。

显式 `import cString` 提供 `cString.length(text)`，严格表示 C `strlen`：
计算首个 NUL 前的原始字节数，不是 Unicode 字符数，也不是完整 xlang
字符串的字节长度。生成的 C 直接调用 `strlen`；日常文本应使用
`string.len` 或 `string.byteLen`。该模块不提供任意裸指针读写接口。

数字 `parse/tryParse` 已提供 `int`、`int8/16/32/64`、
`uint8/16/32/64` 和 `float` 的类型命名空间入口。
整数签名为 `T.parse(text, base = 10)` / `T.tryParse(text, base = 10)`，
基数限定 `2..36`；浮点签名只有 `text`。解析器接收 xlang `string` 的
精确字节长度，完整消费输入，内嵌 NUL 不作终止符。整数允许可选正负号
（无符号不允许符号），不接受空白、分隔符或 `0x/0b/0o` 前缀；显式基数下
直接按该基数解释数码。浮点小数点固定为 `.`，接受可选符号、指数及
`inf`、`infinity`、`nan`（ASCII 大小写不敏感），不依赖当前 C locale。
`parse` 将语法与非法基数报为 `ValueError`，范围超限报为 `RangeError`；
`tryParse` 仅把这两种预期解析失败转为 `(false, 0)`，不会发布部分结果。
既有标量字符串构造仍是不同 API，未借此声称它已具备同样的严格语义。

`array.sort::<T>(values, compare)` 原地采用堆排序：最坏时间 `O(n log n)`，
额外空间 `O(1)`，不保证稳定性。`array.sortBy::<T, K>(values, key, compare)`
先对每个元素恰好求一次键，再同步排列元素与键，额外空间 `O(n)`；键提取
失败时原数组尚未开始排序。`array.binarySearch::<T>(values, needle, compare)`
在已排序数组上返回第一个相等元素的下标，未找到返回 `-1`。比较器必须对
元素提供一致的负/零/正顺序且不修改正在排序的数组；比较器抛错会传播，
此时排序中的数组可能已部分重排。这些函数是 xlang 泛型源实现，不通过
`qsort` 的 `void*` 消去类型，也不需要 Cgen 为各元素类型写特例。

2026-09-28 CRT 补充合同：数字 `parse/tryParse` 必须使用显式输入长度，
不接受隐式截断、前后空白或未明确提供的数字前缀；默认十进制，整数
可显式指定合法基数，浮点小数点固定为 `.`，不受进程 C locale 影响。
解析必须完整消费输入；`parse` 的语法错误报 `ValueError`、范围错误
报 `RangeError`。`tryParse` 返回 `(bool, T)`，失败时返回 `(false, 0)`，
不得发布部分结果。`sort/sortBy`
维持上面的非稳定、比较器抛错后可能部分重排的合同；若未来需要稳定
或异常原子性，另设 API。以上解析 API 尚待实现。

新增 CRT 实数数学的公开基础是 binary64 `float`，不为 C `*f/*l`
变体另设名字；已有的 `math.abs` 有符号整数重载不变。定义域、NaN、
无穷和有符号零遵循对应 CRT/IEEE 数值行为，数学函数不把定义域结果
包装成 xlang 异常；`minNumber/maxNumber` 与现有 `min/max` 的 NaN
语义保持区分。浮点环境仅通过显式 `floatEnv` 修改；快照只能在创建
它的 OS 线程恢复，不能跨 `await` 隐式搬运，陷阱触发不是可移植合同。
非 Windows 工具链和跨线程拒绝专项仍待验收。

已决定的 CRT 控制台文本入口为 `console.write/writeLine/`
`error/errorLine/flush/readLine/readChar`，现已全部按精确长度接通。
`console.flush()` 刷新标准输出与标准错误；文本编码为 UTF-8；
`readLine()` 在 EOF 返回 `null`，空行返回 `""`，读取结果不包含行终止符；
`readChar()` 返回 `char?`，在 EOF 返回 `null`。无效 UTF-8 与 I/O
失败报告 `IOError`；`readLine/readChar` 不预读下一字符，并共享输入租约，
与活动的 io.stdin/终端 Session 不可竞争消费。
重定向输出须保留可预测的字节内容，可靠刷新由 `flush` 显式保证。
原始字节 I/O 不塞进这组控制台文本接口。

`io` 合并基础文件、内存流和行读取；高级编码文件能力仍属 `file`。
完整 API、size/所有权、CLI/TUI 原语及平台边界见
[IO与Console标准库设计](IO与Console标准库设计.md)。全局 `exit(code)`
目前没有实现，不属于已验收控制台能力。

环境变量入口为 `env.get/has/set/remove`，底层统一复用 XRT environment。

| 声明 | 合同 |
|---|---|
| `env.get(name: string, size: int = -1) -> string?` | 缺失返回 null；存在时返回独立拥有的 UTF-8 副本 |
| `env.has(name: string, size: int = -1) -> bool` | 是否存在；无效输入、读取/转换或分配失败仍抛出错误 |
| `env.set(name: string, value: string, nameSize: int = -1, valueSize: int = -1)` | 选中名称和值全部准备成功后更新；空值不是删除 |
| `env.remove(name: string, size: int = -1)` | 幂等删除；无效输入和系统失败不是成功 |

size 是字节上限：-1 为完整值，非负值取 min(size, byteLength)，小于 -1
报 RangeError。只验证选中的完整 UTF-8 前缀，切断字符报 ValueError；
选中内容含 NUL 不传入系统 API。名称的空值、`=` 和 NUL 报 ValueError。
底层 OS 的名称大小写规则不被修改：Windows 不区分大小写，POSIX 区分。

`get` 返回 `string?`，缺失为 `null`，已存在但值为空为 `""`；
名称不得为空且不得含 `=` 或 NUL，值不得含 NUL，但空值合法。
读取结果是独立副本；设置空值不得误删变量，删除不存在的变量视为
成功，名称或值无效报 `ValueError`，系统失败报 `IOError`。
环境是进程级共享状态，运行时自身的操作通过 XRT 环境能力协调；
但无法保证外部原生库绕过该入口直接修改环境时的原子性。
公开输入保持指针和显式长度；进入 OS CString API 时只为选中的前缀
建立一次终止副本，不假设借用 view 的尾部可读。只有 OS/XRT 返回的
owned CString 使用 strlen 恢复长度，缺失不被视为分配失败。
四个声明由封闭 typed ABI 校验，使用线程错误载体、保守副作用和可阻塞
边界；它们不应标成 pure/no-raise/nonblocking。Cgen 不包含环境变量算法。
运行时自身的 POSIX 读写由同一 XRT 实例协调，独立 XRT 副本或外部
getenv/setenv/putenv/unsetenv 调用仍需由宿主统一协调。
`os.env(name, defaultValue = "", size = -1)` 只是 `env.get(...) ?? defaultValue`
的语言门面：有空值时不返回默认值，错误也不被默认值吞掉。
验收范围和冻结结果见三组接入任务的 B19 批次，不代表其他系统库完成。

### signal：基础查询与原生处置（B20a）

公开稳定代码保留 `INT/TERM/HUP/BREAK/CLOSE/LOGOFF/SHUTDOWN`，
不得与平台的原始整数信号号混用。基础入口只用声明调用 XRT signal
适配器；此批不包含脚本监听与路由，其整体状态仍为开发中。

| 声明 | 合同 |
|---|---|
| `signal.supported(code: int) -> bool` | 平台是否支持；未知或超出原生 enum 宽度为 false |
| `signal.name(code: int) -> string` | 独立拥有的稳定 ASCII 名称；未知或超宽为 UNKNOWN |
| `signal.ignore(code: int) -> bool` | 忽略信号并退役该代码的原生监听；成功为 true，失败抛错 |
| `signal.restore(code: int) -> bool` | 恢复 XRT 接管前的处置，不强制替换为 SIG_DFL；失败抛错 |
| `signal.restoreAll() -> bool` | 恢复全部受支持代码；保留原生第一个失败错误 |
| `signal.raise(code: int) -> bool` | 向当前进程发送；必须先明确安装监听或忽略，否则可能终止进程 |
| `signal.count(code: int = 0) -> uint64` | 原生调度累计值，0 为全部；总和饱和至 uint64 上限 |
| `signal.received(code: int) -> bool` | 对应累计值是否非零，0 可查询全部 |
| `signal.clear(code: int = 0)` | 清除对应累计值和待处理数，0 为全部 |
| `signal.healthy() -> bool` | 检查调度状态；后端故障抛出结构化错误，不伪装成正常 false |
| `signal.reset()` | 安全停机：等待原生回调、恢复处置、释放调度线程/唤醒资源；可重复调用和停机后惰性启动 |

以上均为 checked、保守副作用、可阻塞声明：查询也可能惰性初始化失败，
名称复制可能 MemoryError，恢复/停机可能等待原生回调，不标注虚假的
pure/no-raise/nonblocking。动作、计数和清零的超宽 int 报 RangeError，
不会先窄化再意外发送另一信号；原生未知/不支持代码保留 XRT 错误语义。
0 只在查询/总计/清零位置有意义，不作为可发送或可忽略信号。

所有处置都是进程全局的，同一进程的宿主/嵌入实例须协调使用；不要把
reset 视为某个监听句柄的私有清理。native handler 只计数和唤醒；XRT
回调运行于原生调度线程，不能在其上执行脚本。B20a 的原生回调测试
仅是 XRT 退役边界证据，不是 xlang 监听已经接通的证据。
POSIX 标准信号可合并，不承诺发送次数与事件数逐次对应。Windows INT
在已监听时是私有逻辑发送，不广播到控制台组；部分系统控制信号不能
程序化发送。公开接口沿用这些平台能力，绝不模拟成成功。

组件 `xl6_signal_core.c` 的根为 SIGNAL/STRING；它不启动脚本执行器，
查询本身不创建调度线程或安装 handler。Cgen 无信号算法和补丁分支。

CRT 进程生命周期只新纳入全局 `exit(code: int)`，其他 `abort/system/`
`atexit/_Exit/quick_exit` 等不加入本组。`exit` 不能直连 C `exit()`：
无论从哪层调用，它都应触发不能被普通 `catch` 吞掉的语言退出流程，完成沿途
`finally`、作用域析构、模块终结及宿主清理后才交付退出码。
若清理失败，必须报告诊断并以失败状态覆盖请求的退出码。
独立可执行程序从其 `main` 返回最终状态；嵌入式 `xlRunScript*`
把状态交还宿主，不允许终止宿主进程。既有模块退役若报告仍忙，
不能跳过清理或提前宣称退出成功。
这也是待开发合同，不能用现有 `os.env` 或 `process.*` 功能代替。

字符串迭代规则：

```xlang
for c in "1234你好"
    print(c)
end

for b in string.bytes("A你")
    print(b)
end
```

默认 `for ... in string` 按 UTF-8 Unicode scalar 迭代，循环值类型为 `char`；双目标写法 `for i, c in text` 中 `i` 为 0 基 scalar 索引。需要逐字节处理时优先转换为 `bytes`；旧 `string.bytes(text)` helper 仍返回每个字节的整数值，等待标准库重设计。

`time` 是绝对 Unix Epoch 微秒，`now()` 和 `nowUTC()` 都返回同一坐标系；
字段函数默认 UTC，不把当地民用时间伪装为另一个绝对时间。`DateTime` 是
受管理的只读日历快照，具有 year/month/day/hour/minute/second/microsecond/
offset/weekday/dayOfYear/isDST 属性。offset 是 UTC 以东的秒数（-86399..86399）；
weekday 为 Sunday=0..Saturday=6，dayOfYear 从 1 开始。isDST 是 -1 未知、
0 标准时间、1 夏令时；Windows 原生分解可能返回未知，不假装得到 DST 信息。

`DateTime(year,month,day,hour=0,minute=0,second=0,microsecond=0,offset=0)`
严格验证字段；`DateTime(value,offset=0)` 是固定偏移分解，`DateTime(value,true)`
按系统历史时区规则分解，false 则 UTC。`toTime()` 只按快照 offset 重建绝对
时间，环境时区变化不会改写快照。`time.fromLocal(fields,fold=TimeFold.reject)`
则把年月日时分秒当作当前系统时区的民用字段：不使用输入 offset/isDST
作为提示；gap 抛 ValueError，fold 默认拒绝，可明确选择 earlier 或 later。
这是有意区分的两种操作。受宿主系统的可表示年份/时区数据约束，失败不能
退化为 UTC；不提供通过该 API 修改系统时区的能力。

日历字段/范围/local 已通过专项验收；时间文本已迁移到精确长度 typed
桥接，协议/格式/日历算法全部在 XRT，不在 Cgen 识别库名或翻译格式。

`size/patternSize=-1` 使用完整字节长度，非负值截到实际长度；小于 -1
抛 RangeError，切断 UTF-8 字符抛 ValueError。输入中的 NUL 不会被 strlen
截断；原生日期文本不接受多余 NUL，格式 DSL 明确拒绝 NUL，调用者可显式
选取 NUL 前的长度。try 仅将 XRT 的输入解析不匹配转为 `(false,time(0))`；
原生格式错误、UTF-8/长度错误、诊断分配失败继续抛错，不吞 MemoryError。
一般 try 的失败诊断可能分配，不承诺零分配；HTTP try 的原生解析不分配。

旧 `time.relative` 只有指向退役原生函数的不可运行占位声明，已移除。
本轮不在核心库重新引入硬编码中文、本地化或近似月份算法；相对时间文本
不属于已批准的 time_text 基础/协议范围。

`lastDayOfMonth/Year/Week` 返回最后一天的 UTC 午夜，不是区间的最后一微秒。
范围的 C ABI 是无堆分配的双 time 值 carrier；纯字段/getter 带准确
pure + no-raise + nonblocking，构造/范围/local 保留 checked 错误。正常
字段与范围调用没有算法转接、字符串复制或 dynamic value 装箱。

密码学随机数使用 `crypto.randomBytes(count) -> bytes`、
`crypto.fillRandomBytes(Buffer)`、`crypto.randomHex(byteCount)` 和
`crypto.randomString(length = 22, alphabet = URL-safe, alphabetSize = -1)`。
这些函数只使用系统安全随机源，不会回退到伪随机状态；失败会抛错。
`randomHex` 的参数是原始字节数，输出长度为两倍。自定义字母表必须是
1 到 94 个互不重复的可见 ASCII 字节；负长度和 `alphabetSize < -1`
报错，过大的 `alphabetSize` 截断到实际长度。`bytes` 是普通值类型，
并非锁页或保证销毁时擦除的密钥容器。

`encoding` 使用精确长度的 `string ↔ bytes` 与 `bytes ↔ bytes` 转码，
只支持真实的 UTF-8/16LE/16BE/32LE/32BE。编码 ID 为 1/2/3/4/5，
unknown=0，不是 Windows code page；BOM 与严格/替换策略独立。
公开签名、默认参数、错误、BOM 歧义与生成代码合同见
[文本标准库接入的 B8/B9](文本标准库接入.md)。

`encode(text,encoding=1,bom=false,policy=0,size=-1)` 返回拥有 bytes；
`decode(data,encoding=1,policy=0,bom=1,size=-1)` 返回拥有 string；
`transcode(data,source,target,policy=0,bom=1,size=-1)` 返回拥有 bytes。
有五种编码的具名 encode/decode、bom/bomSize/bomBytes、unitSize/name、
string/bytes isUtf8，以及 unicode.decode/repair。size 全部按实际字节计，
支持 NUL，过大夹紧；strict=0，replaceInvalid=1。旧 point/Buffer/code-page
外观退役，不兼容保留。`detect(string|bytes,size=-1)` 返回
`(encoding,bomSize,confidence)` 三个值；只猜测字节，BOM 100 分不验证
正文。正常调用无分配，与转码/元信息按需组件独立。

```xlang
bytes utf16 = encoding.encode("A\0你好", encoding.utf16LE, true)
string text = encoding.decode(utf16, encoding.utf16LE)
assert text == "A\0你好"
```

`file.*Async` 面向 xlang 返回类型化 `future<T>`，避免把 XRT 的 `xasyncfilebuf` / `xasyncfileio` 结构直接泄漏到语言层。C 代码仍可直接调用 XRT 原生 `xrtFile*Async` API，并按 `xFutureWait` / `xFutureValue` 读取 `xasyncfilebuf` 或 `xasyncfileio`。

`file.openAsync(path, flags, shareFlags)` 返回 `AsyncFile` native-backed class，用于随机偏移异步读写。公开主入口为 `readAt(offset, size)`、`writeAt(offset, buffer)`、`flush()`、`size()`、`setSize(size)` 和 `close()`；底层分别映射 `xrtAsyncFileReadAt`、`xrtAsyncFileWriteAt`、`xrtAsyncFileFlush`、`xrtAsyncFileGetSize`、`xrtAsyncFileSetSize`、`xrtAsyncFileClose`。`read/write/resize` 保留为简写别名。

`File` 是基于 XRT `xfile` 的 native-backed class，用于需要明确游标的流式文件读写。`file.seekSet`、`file.seekCur`、`file.seekEnd` 分别对应 XRT 的 `XRT_SEEK_SET`、`XRT_SEEK_CUR`、`XRT_SEEK_END`。

`json` 命名空间映射 XRT JSON 与 `xvalue` 能力，公开 API 使用 xlang `var` 表达动态 JSON 值，不额外引入独立 JSON 对象模型。四个结构化格式的当前配置重载、回调写出与 XLON 命名口径见《结构化数据标准库.md》；下表保留基础简写入口。

| xlang 写法 | 底层能力 | 说明 |
| --- | --- | --- |
| `json.parse(text)` | `xrtJsonParse` | 从 JSON 字符串解析为 `var`，解析失败返回 `null` |
| `json.valid(text)` | `xrtJsonValid` | 验证 JSON 文本是否合法，不构造 `var`，适合配置、网络输入和工具参数预检 |

| `json.write(path, value, pretty = false)` | `xrtJsonStringifyFile` | 将 `var` 序列化并写入文件，写入失败返回 `false` |
| `json.writer(pretty = false)` | `xrtJsonWriterCreate` | 创建流式 JSON 写入器对象 `JsonWriter` |

`json.visit` 返回 `json.visitComplete`、`json.visitStopped`、`json.visitInvalid`。事件表包含 `type`、`depth`、`key`、`index`、`value` 字段；回调返回 `true` 继续遍历，返回 `false` 停止遍历。`JsonWriter` 支持 `beginObject/beginArray`、对应 `end*`、`writeNull/writeBool/writeInt/writeFloat/writeString/writeValue` 与 `finish()`。无参数写入用于根和数组；`string key` 重载用于对象字段。writer 只允许一个根值，未闭合容器或写入非法 key 时 `finish()` 返回空字符串。

`xlon` 命名空间映射 XRT XLON 能力。XLON 与 JSON 保持兼容，并允许 XRT 表达更多 `xvalue` 类型。常规 API 不暴露底层 flags；`xlon.valid` 只保留 `ignoreUnsupported` 这一项验证开关，用于检查包含 XRT 扩展值的文本是否可按“跳过不支持项”策略读取。

| xlang 写法 | 底层能力 | 说明 |
| --- | --- | --- |
| `xlon.parse(text)` | `xrtXlonParse` | 从 XLON/JSON 字符串解析为 `var`，解析失败返回 `null` |
| `xlon.valid(text, ignoreUnsupported = false)` | `xrtXlonValid` | 验证 XLON 文本是否合法；默认严格，`ignoreUnsupported = true` 时允许跳过无法进入 xlang `var` 的扩展值 |
| `xlon.stringify(value, pretty = false)` | `xrtXlonStringify` | 将 `var` 序列化为 XLON 字符串，返回临时字符串 |
| `xlon.read(path)` | `xrtXlonParseFile` | 从文件读取并解析 XLON，路径处理由 XRT 负责，读取或解析失败返回 `null` |
| `xlon.write(path, value, pretty = false)` | `xrtXlonStringifyFile` | 将 `var` 序列化为 XLON 并写入文件，写入失败返回 `false` |
| `xlon.writer(pretty = false)` | `xrtXlonWriterCreate` | 创建流式 XLON 写入器对象 `XlonWriter` |
| `xlon.writer(options)` | `xrtXlonWriterCreate` | 将 `XlonOptions` 转换为 `xxlonwriterconfig` 后创建流式写入器，使 writer 与 stringify/write/visit 共用同一组选项口径 |

`xlon.visit` 返回值常量与 `json.visit` 一致：`xlon.visitComplete` 为完整遍历，`xlon.visitStopped` 为回调主动停止，`xlon.visitInvalid` 为输入或参数错误。事件表包含 `type`、`depth`、`key`、`index`、`value` 字段；其中 `index` 用于数组下标和 list 稀疏索引，`type` 包含 `arrayBegin`、`listBegin`、`dictBegin`、`setBegin`、`time` 等 XLON 专有事件。

`XlonWriter` 支持 `beginArray/beginList/beginDict/beginSet`、对应 `end*`、`writeNull/writeBool/writeInt/writeFloat/writeString/writeTime/writeValue` 与 `finish()`。xlang 的 `dict/list` 分别映射到 XLON 的 `object/intmap`，线格式使用 `{...}` 与 `intmap{...}`；无参数写入用于根、数组和集合，`string key` 重载用于字典字段，`int index` 重载用于稀疏列表项。时间值可通过 `writeTime(value)`、`writeTime(key, value)`、`writeTime(index, value)` 或 `writeValue(varTime)` 写入。writer 只允许一个根值，未闭合容器或写入非法 key/index 时 `finish()` 返回空字符串。需要让 writer 与其他 XLON API 使用同一组 print/visitor 选项时，应使用 `xlon.writer(XlonOptions)`。

`hash` 命名空间映射 XRT 的确定性、非加密哈希能力，适合哈希表和缓存键。它不是密码学摘要：普通 `seed` 不是密钥，结果不能用于认证、完整性校验或生成安全令牌。

`size = -1` 处理完整的实际字节长度；非负值只处理前 `min(size, 实际字节长度)` 个字节，超长自动截断，`0` 处理空输入，小于 `-1` 抛 `RangeError`。字符串按 UTF-8 原始字节而非字符数计算；内嵌 NUL 不截断。`Buffer` 单独命名，避免只调用 `hash.u32(string)` 时把整个 `Buffer` 类注入生成模块。

`Stack<T>` 提供 `push(value)`、`popInto(outValue)`、`peekInto(outValue)`、`peekAtInto(depth, outValue)`、`clone()`、`equals(other)`、`count()`、`capacity()`、`reserve(capacity)`、`trim()` 和 `clear()`。赋值共享语言句柄，`clone()` 才调用 `xrtTypedStackClone` 深复制元素；`equals` 直接映射 xruntime 的精确类型、深度和顺序比较。深度 `0` 表示栈顶；负深度和负容量直接失败，不进入无界整数转换。

`AvlTree<K, V>` 提供 `set`、`getInto`、`takeInto`、`contains`、`remove`、`firstInto`、`lastInto`、`lowerBoundInto`、`upperBoundInto`、`keys`、`values`、`clone`、`equals`、`merge(other, replace = true)`、`count`、`clear`、`trim` 和 `trimTo(retainEmpty)`。所有 `...Into` 方法都写入调用方已有变量，避免用空值表示查找失败；`takeInto` 把值的所有权移出树，边界方法同时返回规范键和值。复制、比较和合并分别直接映射 `xrtTypedTreeClone`、`xrtTypedTreeEquals`、`xrtTypedTreeMerge`，合并保持 xruntime 的失败原子性。`trim()` 释放全部空节点池，`trimTo(n)` 保留至多 `n` 个空节点，两者返回实际释放数量。

typed queue 统一支持 `tryPush(value)`、`tryPopInto(outValue)`、`count()`、`capacity()`、`close()`、`isClosed()` 和 `isDrained()`；SPSC、MPSC、MPMC 还提供直接映射 xruntime 连续值接口的 `pushBatch(array<T>)` 与 `popBatchInto(array<T>, capacity)`，返回实际处理数量，错误返回 `-1`，并可复用输出数组而不重复分配。这三类队列在独占且排空后可用 `reset()` 重新开放。`WaitQueue` 额外提供 `popInto(outValue)` 和 `popTimeoutInto(outValue, timeoutMs)`，但不开放 `reset()` 或无锁批量接口，避免等待者跨队列生命周期滞留并保持阻塞语义单一。输出参数用于避免泛型值复制和失败值哨兵之间产生歧义；负超时或负批量容量直接失败。

`channel<T>` 是语言级线程通信通道，继续使用 XRT `xchannel`。当前支持 `send(value)`、`trySend(value)`、`recvInto(outValue)`、`tryRecvInto(outValue)`、`recvTimeoutInto(outValue, timeoutMs)`、`count()`、`close()`、`isClosed()`。`recvTimeoutInto` 直接映射 `xrtChannelRecvTimeout`；`timeoutMs < 0` 等价阻塞接收，`timeoutMs == 0` 表示立即检查。`recvInto` / `tryRecvInto` / `recvTimeoutInto` 的第一个参数必须是可写具名变量，不进入普通命名参数调用体系。

`template` 命名空间映射 XRT `xte` 模板引擎。模板层只负责把 `xvalue` 数据渲染为文本，不承担业务计算；xlang 的 `var`、`array`、`dict` 会直接落到 XRT `xvalue`，因此可以零额外数据模型进入 `xteMake`。`Template` 是 native-backed class，`template.compile` 返回预编译模板对象，适合 Web 页面、代码生成、Agent prompt 等需要重复渲染的场景；`template.render` / `template.renderFile` 是脚本便捷路径。

模板默认使用 `{}` 定界符，例如 `{$title}`。需要嵌入 JSON/HTML/其他模板片段时，可以通过 `bracket` 改为 `"<>"`、`"{{}}"`、`"(())"` 等偶数字符串，其中前半段为开始定界符，后半段为结束定界符。模板语法由 XRT 统一实现，当前支持文本输出、数字/时间格式化、行内布尔分支、`if/elseif/else`、`for`、`foreach`、`break/continue`、`define`、`script` 和 `include`。

常见写法：

```xlang

```

`http` 命名空间映射 XRT 的 HTTP/1.1 client 与共享 HTTP 语义层。当前稳定范围明确不包含 HTTP/2、HTTP/3 和 QUIC。快捷函数提供阻塞式请求；`HttpClientRequest`、`HttpClientResponse`、`HttpClient` 则同时覆盖同步执行、typed Future、增量响应回调、连接池、CookieJar、取消上下文和诊断。

`HttpClientRequest` 支持动态 header、流式或缓冲请求体、FormData、总超时、空闲超时、Context、proxy 与 TLS peer 校验。`execute()` 返回同步响应，`executeAsync()` 返回 `future<HttpClientResponse>`，`stream()` 以 Future 交付最终响应并把 header/body 分片增量送给回调。传入长期存活的 `HttpClient` 时，请求共享其有界 keep-alive 池和 CookieJar；`closeIdle()` 只关闭空闲连接。

`HttpClientResponse` 提供状态、版本、reason、动态 header 枚举、正文文本/字节与 `HttpCallInfo`。通过 `callInfo()` 取得请求状态、阶段、错误码、时间与传输统计；`ok()` 对 400 以下状态返回 `true`；`bodyData/bodySize` 是响应对象生命周期内的借用视图，`bodyBytes()` 返回独立 `Buffer`。生成代码只调用 XRT 公开构造器和访问器，不复制或访问 XRT 私有结构；HTTP/HTTPS client 的 XRT 裁剪会保留 `xhttp`、`xurl`、`http_util`、`xcodec`、`nettls`、`crypto`、网络层和 coroutine 依赖。

`http.server` 命名空间映射 XRT `xweb` 高层 HTTP 服务基座。当前采用“服务句柄 + 路由注册”模型：`create` 返回 `point` 句柄，调用者注册 `get`、`post`、`any`、`getRequest`、`postRequest`、`anyRequest` 或静态目录，再显式 `start`、读取端口、最后 `destroy`。server 默认绑定 `127.0.0.1`，`port = 0` 表示由系统分配空闲端口。

xlang 标准库创建的 server 默认使用 XRT owned engine：`http.server.create/createTls` 内部让 XRT 创建并持有独立网络 engine，`workerCount` 对该 engine 生效，`http.server.destroy` 会释放 server 和对应 engine。`http.server.create(engine, ...)` 与 `createTls(engine, ...)` 使用调用方的 `NetEngine`，用于 HTTP client/server、WebSocket 和其他网络对象共享同一事件循环；此时调用方必须保证 engine 比 server 活得更久，`destroy` 不会停止或释放该 engine。

`recvLimit` 控制单连接接收缓冲上限，`bodyLimit` 控制单个 HTTP 请求 body 上限，`headerLimit` 控制请求头数量上限，`headerBytesLimit` 控制请求头总字节上限，`multipartPartLimit` 控制 multipart part 数量上限，`multipartPartSizeLimit` 控制单个 multipart part body 字节上限。`multipartPartLimit = 0` 或 `multipartPartSizeLimit = 0` 表示关闭对应限制。`headerTimeoutMs` 控制请求头读完前的最长等待时间，`bodyTimeoutMs` 控制固定长度 body 读完前的最长等待时间，`idleTimeoutMs` 控制 keep-alive 空闲连接保留时间，`writeTimeoutMs` 控制响应提交后发送队列排空的最长等待时间。超过 body/multipart/header limit 分别返回 `413 Payload Too Large` / `413 Payload Too Large` / `431 Request Header Fields Too Large`；header/body 超时返回 `408 Request Timeout`；idle 超时只关闭空闲连接；write 超时直接关闭连接。

`get`、`post`、`any` 是简化路由 API，handler 固定为 `func(string, string, string, string) as string`，四个参数依次为 `method`、`path`、`query`、`body`，返回值作为 `text/plain; charset=utf-8` 响应正文。`getRequest`、`postRequest`、`anyRequest` 是对象化路由 API，handler 固定为 `func(point, point) as bool`，两个参数分别是借用的 request/response 句柄，函数体内应构造 `HttpRequest` 和 `HttpResponse` 对象访问请求、设置状态码、响应头和响应体。`postStreamRequest`、`routeStreamRequest` 和 `anyStreamRequest` 是流式请求体路由 API，适合上传、大体积 body 或边收边处理场景，不把请求体完整缓冲到 `HttpRequest.body*()`。路由 pattern 由 XRT `xweb` 解析，支持静态段、变量段 `{id}` 和尾通配符 `*`，匹配优先级为静态段 > 变量段 > 通配符。

流式请求体 handler 由三段组成：`beginHandler` 签名为 `func(point) as bool`，收到请求头并匹配路由后调用；`chunkHandler` 签名为 `func(point, point, int) as bool`，每个 body 分片调用，参数依次为 request 句柄、分片指针和分片字节数；`endHandler` 签名为 `func(point, point) as bool`，body 读取完成后调用，参数为 request/response 句柄。分片指针只在当前 `chunkHandler` 调用期间有效，需要保存时必须立即用 `http.server.chunkText(data, size)` 或 `http.server.chunkBytes(data, size)` 复制。当前流式请求体 end handler 必须同步完成响应，暂不支持返回异步动作。

app 模型额外支持 `http.server.appError(app, handler)`，用于给待挂载或热替换的 app 设置错误处理器。错误 handler 参数依次为 HTTP 状态码、默认错误文本、`HttpRequest` 原始句柄和 `HttpResponse` 原始句柄；返回 `true` 表示已处理，返回 `false` 时由 XRT 回退到默认文本错误响应。

app 模型同样支持通用方法注册：`http.server.appRoute(app, method, pattern, handler)` 和 `http.server.appRouteRequest(app, method, pattern, handler)`。`method` 使用 HTTP 大小写敏感 token，可传单个扩展方法、用 `|` 分隔的多个方法，或独占使用 `ANY` / `*`。流式请求体在 app 上使用 `http.server.appPostStreamRequest(app, pattern, beginHandler, chunkHandler, endHandler)`、`http.server.appAnyStreamRequest(...)` 或 `http.server.appRouteStreamRequest(app, method, pattern, ...)` 注册；这些 route 会随 app/router 生命周期托管闭包引用。静态文件可使用 `http.server.appStatic(app, mount, root)` 快捷挂载，也可使用 `http.server.appStaticEx(app, mount, root, index = "index.html", cacheControl = "", chunkSize = 65536, flags = 0)` 设置首页、缓存头、发送块大小和路径策略。`flags` 可组合 `http.server.staticPortable` 与 `http.server.staticAllowHidden`。

Cookie 响应常量直接映射 XRT：`http.server.sameSiteUnspecified`、`http.server.sameSiteLax`、`http.server.sameSiteStrict`、`http.server.sameSiteNone` 分别对应 `0..3`；`http.server.cookieSecure`、`http.server.cookieHttpOnly`、`http.server.cookiePartitioned` 分别对应 XRT `Set-Cookie` 布尔属性 flag。xlang 层只提供常用 Cookie 输出能力；需要 Domain、Expires、Priority 等更细粒度属性时，优先补 XRT 的结构化 helper，再向 xlang 暴露。

示例：

```xlang
func hello(string method, string path, string query, string body) as string
    if path == "/users/42" then
        return "user-42"
    end
    return "hello"
end

func(string, string, string, string) as string handler = hello
point server = http.server.create(8080)
http.server.get(server, "/users/{id}", handler)
http.server.post(server, "/echo", handler)
http.server.static(server, "/public", "public")
http.server.start(server)
http.server.destroy(server)
```

## WebSocket

`WebSocketClient` 与 `WebSocketServer` 是 XRT RFC 6455 主线的薄封装，支持 `ws/wss`、握手策略、Origin/path/subprotocol、permessage-deflate、Ping/Pong、分片消息 writer、关闭元数据、结构化错误和硬发送队列上限。当前范围不包含基于 HTTP/2 的 extended CONNECT、HTTP/3 或 QUIC。

`WebSocketClientOptions` 与 `WebSocketServerOptions` 持有配置的深拷贝；由 `tls(config)` 传入的动态证书、CA、CRL、ALPN、host 和验证回调通过 TLS lease 保活，因此源 `TlsConfig` 可以在 client/server 建立后离开作用域。事件回调必须在 `start()` 或第一次共享 HTTP Upgrade 前注册；投入使用后回调表被冻结，避免 worker 与配置线程并发修改。

| xlang 写法 | 底层能力 | 说明 |
| --- | --- | --- |
| `options.client(engine)` / `options.server(engine)` | `xrtWsClientCreate` / `xrtWsServerCreate` | 使用调用方 engine 创建客户端或服务端协议管理器 |
| `client.startAsync()` | `xrtWsClientStartFuture` | 握手完成后解析为 typed Future |
| `client.writableAsync()` / `drainAsync()` / `closeAsync()` | XWS wait Future | 观察背压、排空和关闭终态 |
| `client.waitOpen()` / `waitWritable()` / `waitDrain()` / `waitClose()` | XWS 同步等待 | 不得在同一网络 worker 中阻塞调用 |
| `send(string/Buffer)` / `ping(Buffer)` | XWS bytes-first send | 返回 XRT 网络结果；`AGAIN` 时等待 writable 后重试 |
| `beginText()` / `beginBinary()` | `xwswriter` | 跨多个 frame 发送一条消息，writer 存活期间独占数据消息发送槽 |
| `closeInfo()` / `lastError()` | `xwscloseinfo` / `xwserrorinfo` | 获取稳定的关闭 code/reason、错误分类、阶段和 HTTP/协议状态 |
| `response.upgradeWebSocket(server)` | `xrtWebResponseUpgradeWebSocket` | 在 xweb route 中把当前 HTTP/1.1 请求移交给 XWS |

共享端口 Upgrade 必须让 HTTP server 和 WebSocket 管理器使用同一个 `NetEngine`：

```xlang
NetEngine engine = NetEngine(2, 0)
engine.start()
point httpServer = http.server.create(engine, 8080)

WebSocketServerOptions options = WebSocketServerOptions(0, "127.0.0.1")
options.path("/ws")
WebSocketServer ws = options.server(engine)

func upgrade(point requestHandle, point responseHandle) as bool
    HttpResponse response = HttpResponse(responseHandle)
    return response.upgradeWebSocket(ws)
end

func(point, point) as bool handler = upgrade
http.server.getRequest(httpServer, "/ws", handler)
http.server.start(httpServer)
```

成功 Upgrade 后，HTTP 连接从 xweb 连接集合移除，由 XWS 管理帧、背压和关闭状态。`WebSocketServer` 必须活到所有已升级连接结束；销毁顺序应为 client/connection、WebSocket manager、HTTP server，最后才是共享 `NetEngine`。回调中的 payload 指针只在当前回调期间有效，需要跨 task 保存时应立即复制为 `string` 或 `Buffer`；`WebSocketConnection` 构造器会 retain 原生连接，适合跨异步边界持有。

## tcc / xlang 脚本嵌入

`tcc` 命名空间暴露内嵌 TCC 的脚本运行和低层 Context 能力；`xlang` 命名空间暴露内嵌 xlang 运行能力。`xl.dll` 只提供内存运行能力，不输出 exe/dll/obj；`xlc.dll` 和 `xl.exe` 才提供发布编译能力。动态 VFS 用于本次运行临时挂载 C 源文件，优先级高于外部文件系统，调用结束后可用 `tcc.vfsClear()` 清空。

| xlang 写法 | 底层能力 | 说明 |
| --- | --- | --- |
| `tcc.run(source)` | `TccContext` + `tcc_run` | 编译并运行 C 源字符串，返回 C `main` 的退出码 |
| `tcc.runFile(path)` | `TccContext.addFile` + `tcc_run` | 编译并运行 C 文件或动态 VFS 文件 |
| `tcc.compile(source, output, outputType = tcc.EXE)` | `tcc_output_file` | 编译 C 源字符串到指定产物，仅编译器模式可输出外部文件 |
| `tcc.compileFile(path, output, outputType = tcc.EXE)` | `tcc_add_file` + `tcc_output_file` | 编译 C 文件或动态 VFS 文件到指定产物 |
| `tcc.vfsMount(path, text)` | `tcc_vfs_mount_memory` | 将文本挂载到动态 VFS 路径，例如 `__xlvfs__/main.c` |
| `tcc.vfsClear()` | `tcc_vfs_clear_dynamic` | 清空当前动态 VFS 挂载 |
| `tcc.Context(outputType = tcc.MEMORY)` | `tcc_new` | 创建可精细控制的 TCC 上下文 |
| `TccHandler(path)` / `TccHandler(handle)` | 常驻 TCC handler | 从源码文件创建 handler，或显式接管已有原生句柄 |
| `xlang.run(source)` | `xlRunScriptString` | 运行 xlang 源字符串，返回是否成功 |
| `xlang.runFile(path)` | `xlRunScriptFile` | 运行 xlang 源文件 |
| `xlang.Context()` | `xlCreateContext` | 创建独立 xlang 运行上下文，可设置工作目录和读取 `lastError` |
| `XLangHandler(path, workDir)` / `XLangHandler(handle)` | 常驻 xlang handler | 从脚本文件创建 handler，或显式接管已有原生句柄 |

TCC 输出类型常量：`tcc.MEMORY`、`tcc.EXE`、`tcc.OBJ`、`tcc.DLL`、`tcc.PREPROCESS`。

`TccHandler(point)` 与 `XLangHandler(point)` 采用所有权接管语义：对象析构时会释放传入句柄。临时借用池中句柄时，调用方必须在对象离开作用域前把 `handle` 设为 `null`；真正移交销毁责任时则保留句柄，由对象统一释放。禁止通过未构造的空 class 变量写入 `handle`。

## 暂缓能力与后续扩展

以下能力已明确暂缓，不属于当前标准库缺失。后续进入新批次时，应先补齐底层类型或运行时模型，再进入标准库公开 API：

- `codec`：基于 `Buffer` 补充二进制安全的 encode/decode API。
- `crypto`：基于 `Buffer` 补充二进制安全摘要、HMAC、HKDF、AEAD、随机字节和密钥交换接口。
- `process`：配置与同步捕获已进入 B21，合同见 `Process配置与运行设计.md`；流式句柄、pipeline、Future、文件重定向和 PTY 仍按三组长期任务继续，不再因旧占位声明就视为实现。
- `xlon`：后续如需暴露 XRT flags，应设计为稳定枚举或选项对象，而不是直接泄漏裸整数标志位。

## C ABI 类型要求

标准库公开 API 应尽量使用 xlang 推荐类型，例如 `int`、`float`、`bool`、`string`、`time`、`point`。

标准库内部桥接 XRT/CRT 函数时，必须使用 `c_*` 类型对齐真实 C 原型。例如：
- `size_t` 使用 `c_size`。
- C `int` / `unsigned int` 使用 `c_int` / `c_uint`。
- C `bool` 使用 `c_bool`。
- `ptrdiff_t` / `intptr_t` / `uintptr_t` 使用对应 `c_ptrdiff` / `c_intptr` / `c_uintptr`。

不要为了方便把平台相关 C 类型猜成 `int32`、`uint64` 等固定宽度类型；这会破坏和 XRT 头文件或用户 C 头文件的 ABI 一致性。

## Buffer Hex/Base64 声明式接口（B41）

- `Buffer.fromHex(text, flags=0, size=-1) as Buffer`、
  `buffer.hex(flags=0, size=-1) as string`。
- `Buffer.fromBase64(text, flags=0, alphabet="", size=-1, alphabetSize=-1) as Buffer`、
  `buffer.base64(flags=0, alphabet="", size=-1, alphabetSize=-1) as string`。
- `HexFlags as int`：None=0、Upper=1（仅编码）、IgnoreSpace=2（仅解码）。
- `Base64Flags as int`：None=0、Url=1、NoPadding=2、IgnoreSpace=4（仅解码）、
  OptionalPadding=8（改变解码接受规则；编码仍输出 padding）；
  NoPadding 与 OptionalPadding 冲突。

延续现有 Number flags 的显式转换约定，例如
`raw.hex(int(HexFlags.Upper))`。`size`/`alphabetSize` 是字节前缀，-1
表示完整输入，非负长度超过实际长度截断，低于-1报 RangeError。
不使用 strlen，不忽略内嵌 NUL；编码读取全部任意 bytes，解码严格
验证所选字符。空 alphabet 使用原生默认表；自定义表必须恰好64个
唯一的可见ASCII字节，不含`=`，不能与Url组合。通过固定65字节栈
空间给真实 XRT config ABI 补哨兵，既不截断也不复制一份算法。

配置错误为 ValueError，格式错误延续真实 XRT 的 XERR_PROTOCOL→
IOError 映射（Hex code902、Base64 code1002），分配失败为 MemoryError。
这些函数不是 pure/no-raise；使用现有 checked may-raise 合同。
返回 Buffer 为原生 owned 工厂结果；返回 string 持有精确长度和唯一
输出分配。实例方法只借用 Buffer payload，不复制源数据或修改它。
`codec.hexDecodeBytes/base64DecodeBytes` 改为调用上述静态工厂，旧私有
原始指针解码桥及其 Cgen 实现已移除。旧 Buffer core 与其余 codec
功能不因本节接口完成而宣布全部迁移完成。

## Buffer 核心直接 ABI（B42）

`Buffer()` 创建空对象；`Buffer(capacity)` 预留非负容量，不改变长度。
`len/capacity/reserve/clear/appendByte/byteAt/setByte` 使用独立原生
BUFFER_CORE；`byteAt` 和索引返回 uint8（物理调用仍为固定 int64 ABI）。
清空保留容量，预留失败不改变原数据。byte 值超出0..255报 ValueError。

- `copyFrom(offset, source, sourceOffset=0, count=-1)`：count=-1取源剩余
  字节；显式范围必须有效，不截断；目标可扩展，间隙填零。
- `copyWithin(offset, sourceOffset, count)`：两端必须在现有有效区间内，
  count必须非负；支持重叠，不改变长度或分配。
- `fill(value, offset=0, count=-1)`：只填现有有效区间；非法范围或
  非字节value报 RangeError；不扩展。
- `compare(other, size=-1, otherSize=-1)`、
  `indexOf(needle, start=0, size=-1, needleSize=-1)`：前缀长度-1表示
  全部，非负值超出实际长度截断，低于-1报 RangeError。按无符号字节
  比较/查找，支持NUL，不解释UTF-8。空needle在合法start处匹配；
  start负数报错，超过选定前缀长度返回-1。

查询独立在BUFFER_QUERY，复用真实 XRT xrtStrCompare/xrtStrFind 的
精确字节视图。复制复用真实 xrtBufferWrite 的自引用/扩容事务；
固定区间只使用memmove/memset，不新增一份搜索或分配算法。

所有 Buffer 工厂和消费方统一登记 `xl6BufferDestroyV1` 所有权身份；
析构不抛语言错误，并保留正在传播的原始XRT错误。普通操作仍为
checked may-raise，不能虚假声明pure/no-raise来掩盖失败。
public Buffer不再通过旧私有名称matcher恢复ABI，也不生成核心实现。

`Buffer(point)`、`data/nativeHandle`、原始point append/insert属于显式
可信C互操作。采用point成功即转移真实XRT payload所有权；不能重复
采用或释放。data只借用底层字节，扩容或销毁后不得使用。描述符校验
无法证明任意外国指针有效，语言层不因此新增引用或借用语法。
仍保留的旧file/network转换帮助函数是独立待迁移范围，不作为本节
公共Buffer安全合同或“全部容器已完成”的证据。
