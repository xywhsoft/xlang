# xlang DEMO6 第二阶段功能清单

本文档记录 DEMO6 第二阶段准备实现的功能边界，供最终审阅使用。

第二阶段的目标不是扩张高级语法，而是把第一阶段已经确定的基础语义压实，使 xlang 已经声明支持的数据类型、函数模型、容器模型、C 混编模型具备成熟、稳定、可解释的实现。

本文档经审阅确认后，作为第二阶段开发边界。

## 1. 阶段定位

阶段名称：

```text
DEMO6 第二阶段：基础语义夯实阶段
```

核心目标：

- 让 xlang 已经承认的数据类型成为真正的一等公民。
- 让 `var`、`function`、`class`、`custom`、静态泛型容器具备统一运行时基础。
- 让 XRT 成为 xlang 基础语义的主要承载层，而不是在 xlang 中堆临时运行时代码。
- 让 xcall 成为 XRT 的通用动态调用模型，同时保留 native entry 作为高性能静态调用面。
- 让 C 使用 XRT 也自然、舒服，而不是把 XRT 变成 xlang 私有后端。

## 2. 硬约束

### 2.1 XRT 优先

能够使用 XRT 实现的功能，必须优先使用 XRT。

如果 XRT 不满足需求，应优先改造 XRT：

1. 在 `D:\GIT\xrt\lib` 中实现或改造能力。
2. 在 `D:\GIT\xrt\test` 中补充测试。
3. 运行 XRT 测试。
4. 运行 `D:\GIT\xrt\singlehead\single_head_maker.exe`。
5. 将生成后的单头文件同步到 xlang 对应目录。
6. 再在 xlang 中优雅接入。

禁止为了短期方便，在 xlang 中重复制造 XRT 应该提供的运行时能力。

### 2.2 XRT 不和 xlang 过度耦合

XRT 是 xlang 的官方标准库和运行时基础，但 XRT 不假设自己只能运行在 xlang 中。

XRT 新增能力必须满足：

- 可被纯 C 项目直接使用。
- 不依赖 xlang 语法、AST、编译器内部结构。
- API 命名和语义在 C 层也能合理解释。
- 能作为 C 与 xlang 的桥梁。
- 未来可供其他语言绑定使用。

XRT 不应出现这些概念：

- `func` 语法。
- xlang 专用 AST。
- xlang 模块系统。
- xlang 泛型语法。
- `self`、`base`、`create`、`destroy` 等语言关键字依赖。

XRT 应建模这些通用概念：

- type desc。
- type ops。
- value。
- callable。
- record。
- handle。
- container。
- method。
- call frame。

### 2.3 xvalue 结构保持稳定

`xvalue_struct` 应保持小而稳定，适合池化内存优化。

复杂能力不要直接塞进 `xvalue_struct` 字段，而应让 `xvalue` 指向独立对象：

- `function` 指向 callable 对象。
- `class` 指向 record/class box。
- `custom` 指向 handle/custom box。
- typed container 指向 typed container 对象。

`xvalue.Type` 只表达粗分类，精确类型由 `type_desc` 表达。

## 3. 非目标

第二阶段暂不主动扩张以下高级功能：

- 模块系统。
- 异常系统。
- async/await。
- yield/generator。
- object 动态对象。
- 完整元编程。
- 模板字符串完整插值。
- 完整运算符重载系统。
- C varargs 的通用自动桥接。

如实现过程中必须预留结构，可以做轻量占位，但不得引入未设计完成的语言表面能力。

## 4. XRT 类型系统改造

### 4.1 type desc

新增或完善 XRT 通用类型描述。

目标能力：

- 表示类型 id。
- 表示类型名。
- 表示类型 kind。
- 表示 C ABI 名称。
- 表示大小与对齐。
- 绑定 type ops。
- 绑定方法表。
- 表示泛型实例。
- 表示 callable 签名。
- 表示 record/class 类型。
- 表示 custom/handle 类型。
- 表示 typed container 类型。

`type_desc` 是 XRT 运行期/ABI 类型系统，不是 xlang 编译期类型系统。

xlang 编译期类型系统可以映射到 XRT `type_desc`，但 XRT 不依赖 xlang 类型语法。

### 4.2 type ops

新增或完善统一类型操作表。

目标操作：

- `init`。
- `copy`。
- `move`。
- `drop`。
- `compare`。
- `hash`。
- `to_string`。
- `box`。
- `unbox`。
- `method lookup`。

第一版不要求所有类型全部完整实现所有操作，但结构必须稳定，缺失能力要能明确表达。

### 4.3 type(value)

`type(var)` 应返回精确类型，而不是只返回粗分类。

示例：

```text
var 保存 int              -> type(v) == int
var 保存 Point            -> type(v) == Point
var 保存 File custom      -> type(v) == File
var 保存 add 函数          -> type(v) == func(int, int) as int
var 保存 array<Point>     -> type(v) == array<Point>
```

## 5. xvalue 改造

### 5.1 粗类型与精确类型分离

`xvalue.Type` 继续保留粗分类：

- null。
- bool。
- int。
- float。
- text/string。
- time。
- point。
- func。
- array。
- list。
- set。
- dict。
- class/record。
- custom/handle。

精确类型由 `type_desc` 或复杂对象内部描述承担。

### 5.2 function 进入 var

`var` 保存 `function` 时，必须保存签名和调用入口。

目标信息：

- 函数精确签名。
- 参数类型。
- 参数名。
- 默认值信息。
- 返回值数量与类型。
- 是否支持 `...`。
- 是否支持 `***`。
- native entry。
- xcall entry。
- env。
- env 生命周期。

动态调用：

```xlang
var f = add
f(1, 2)
```

必须通过签名完成参数检查、转换、调用和返回值处理。

### 5.3 class 进入 var

`var` 保存 `class` 时，不能只保存栈地址。

目标策略：

- 创建 heap box。
- box 内保存真实 class 数据。
- box 绑定 class `type_desc`。
- 复制时调用 type ops `copy`。
- 释放时调用 type ops `drop`。
- 支持 `type(v) == Point`。

### 5.4 custom 进入 var

`var` 保存 `custom` 时，不能只保存裸指针。

目标信息：

- custom `type_desc`。
- 黑盒 handle。
- 所有权标记。
- 是否允许 null handle。
- retain/release 或 destroy 函数。
- 是否可复制。
- 是否可移动。

策略：

- 有 destroy 映射时，可以拥有资源并自动释放。
- 没有 destroy 映射时，只能保存 borrowed handle。
- 调用 custom 方法时直接传递 handle，不额外包装。

## 6. 静态泛型容器

### 6.1 动态容器与静态容器分层

动态容器继续基于 `xvalue`：

```xlang
var a = [1, 2, 3]
array a = [1, 2, 3]
```

静态泛型容器必须落到 XRT typed container：

```xlang
array<int>
array<string>
array<Point>
list<T>
set<T>
dict<T>
```

### 6.2 XRT typed container

XRT 应提供或改造 typed container 能力：

- typed array。
- typed list。
- typed set。
- typed dict。

typed container 依赖元素类型的 `type_ops`：

- 初始化元素。
- 复制元素。
- 移动元素。
- 释放元素。
- 比较元素。
- 哈希元素。

### 6.3 set 独立实现

XRT 应补齐真正的 set 能力。

目标：

- 不再让 xlang 代码生成直接理解 `avltree` 细节。
- `xvalue` set 接入新的 XRT set。
- 静态 `set<T>` 接入 typed set。
- set 依赖元素类型的 hash/compare。

### 6.4 dict 策略

第一阶段延续方向：

- `dict<T>` 的 key 固定为 string。
- value 类型为 T。

后续如需支持 `dict<K, V>`，另行设计，不在本阶段扩张。

## 7. 隐性类方法

隐性类方法应绑定到 XRT，而不是在 xlang 编译器里堆特殊逻辑。

目标：

- XRT 提供基础类型方法表。
- XRT 提供容器方法表。
- xlang 类型注册系统绑定这些方法。
- 静态类型方法调用优先解析为直接 C/XRT 调用。
- `var` 方法调用走 type desc / method lookup。

示例：

```xlang
auto s = 123.toString()
auto parts = "1,2".split(",")
auto a = [1, 2, 3]
a.append(4)
a.clear()
```

实现原则：

- 方法实现优先来自 XRT。
- xlang 只做解析、绑定和代码生成。
- 不复制一套 xlang 专用标准库。

## 8. xcall 调用约定

### 8.1 xcall 定位

`xcall` 是 XRT 的统一动态调用模型，不是 CPU/平台 ABI。

它类似轻量、跨平台、C 友好的 `IDispatch::Invoke`。

它支持：

- 运行时参数数量。
- 参数名。
- 可选参数。
- `...`。
- `***`。
- 多返回值。
- `self`。
- `env`。
- 动态类型检查。
- 动态类型转换。
- function/class/custom 方法调用。

### 8.2 native entry 定位

native entry 是高性能静态调用面。

它类似固定接口或固定函数表调用面。

特点：

- 函数地址确定。
- 参数类型确定。
- 返回值布局确定。
- 按 C ABI 直接调用。
- 不构造 call frame。

同一个函数可以同时拥有：

- native entry。
- xcall entry。

静态调用走 native entry。

动态调用、`var` 调用、反射调用、脚本嵌入调用走 xcall entry。

### 8.3 call frame

XRT 应提供通用调用帧。

建议模型：

```c
typedef struct xrt_call_frame {
    xvalue self;
    xvalue env;

    uint32 argc;
    xvalue* argv;

    xvalue kwargs;
    xvalue varargs;

    const xrt_func_sig* sig;
} xrt_call_frame;
```

说明：

- `kwargs` 为 dict，没有则为 null。
- `varargs` 为 array，没有则为 null。
- `...` 和 `***` 对 C 兼容性较好，本质是额外传递一个 `xvalue` 参数。

### 8.4 call result

XRT 应区分“返回一个 array”和“多返回值”。

建议模型：

```c
typedef struct xrt_call_result {
    uint32 count;
    xvalue values[4];
    xvalue overflow;
} xrt_call_result;
```

规则：

- 无返回：`count = 0`。
- 单返回：`count = 1`。
- 多返回：`count > 1`。
- 返回 array：`count = 1`，第一个值是 array。
- 超过 4 个返回值时使用 `overflow`。

### 8.5 callable 对象

XRT callable 应表达：

- 函数签名。
- native entry。
- native ABI。
- xcall entry。
- env。
- env 生命周期。

建议模型：

```c
typedef struct xrt_callable {
    const xrt_func_sig* sig;
    void* native_entry;
    uint32 native_abi;
    bool (*xcall_entry)(xrt_call_frame* frame, xrt_call_result* result);
    void* env;
    void (*drop_env)(void* env);
} xrt_callable;
```

## 9. cdecl/stdcall 兼容

### 9.1 ABI 分层

cdecl/stdcall 是 native ABI。

xcall 是 XRT 动态调用约定。

两者不互相替代，通过 adapter 连接。

### 9.2 C 函数进入 xcall

C 函数注册到 XRT/xlang 时，生成或手写 xcall adapter。

示例：

```c
int add(int a, int b);
```

映射为：

```c
bool add_xcall(xrt_call_frame* frame, xrt_call_result* result);
```

adapter 负责：

- 读取参数。
- 处理默认值。
- 处理 `...`。
- 处理 `***`。
- 调用真实 C 函数。
- 打包返回值。

### 9.3 xlang 函数导出给 C

xlang 函数导出给 C 时，必须生成 native wrapper。

规则：

- 普通单返回、定长参数函数可以直接导出。
- 多返回需要 out 参数或返回结构体映射。
- 可选参数不直接暴露给 C ABI，由 wrapper 提供固定签名。
- `...` 可以映射为额外 `xvalue array` 参数。
- `***` 可以映射为额外 `xvalue dict` 参数。
- 闭包函数不能直接作为普通 C 函数导出，必须导出 callable/xcall 或生成上下文 wrapper。

### 9.4 C varargs

C 的 `...` 与 xlang 的 `...` 不是同一概念。

规则：

- xlang `...` 是 `xvalue array`。
- xlang `***` 是 `xvalue dict`。
- C varargs 不做通用自动桥接。
- `printf` 等函数应通过 XRT/CRT 专用 wrapper 使用。

## 10. 函数模型完善

目标：

- 每个函数具备稳定签名描述。
- 支持 optional 参数的签名与默认值表达。
- 支持 `...` 和 `***` 的签名表达。
- 支持多返回的签名表达。
- 支持 function value 保存签名。
- 支持 function value 动态调用。
- 支持 xcall adapter 生成。
- 支持 native direct call 优化。

xlang 编译器应为需要动态调用的函数生成：

1. native 函数体入口。
2. xcall adapter。
3. XRT `func_sig`。
4. callable 对象描述。
5. 必要的 C ABI wrapper。

## 11. class/custom 完善

### 11.1 class

第二阶段 class 目标：

- class 有精确 type desc。
- class 有 type ops。
- class 可以作为变量类型。
- class 可以作为参数。
- class 可以作为返回值。
- class 可以进入 `var`。
- class 可以进入静态泛型容器。
- class 方法可通过隐性类/方法表解析。
- class 仍保持 C 兼容结构体模型。

### 11.2 custom

第二阶段 custom 目标：

- custom 有精确 type desc。
- custom 有 handle box。
- custom 有所有权策略。
- custom 可作为变量类型。
- custom 可作为参数。
- custom 可作为返回值。
- custom 可进入 `var`。
- custom 可进入静态泛型容器。
- custom 方法直接降级为 C 函数调用。

custom 仍然保持“零成本 C 到 OOP 抽象”的方向。

## 12. 类型注册系统升级

DEMO6 类型注册系统应统一管理：

- 类型名。
- type id。
- kind。
- ABI 名称。
- C 类型名称。
- 默认值。
- type desc。
- type ops。
- 方法表。
- 构造函数。
- 转换函数。
- 泛型实例。
- func 签名。
- 是否可 box 到 `var`。
- 是否可 unbox。
- 是否可比较。
- 是否可哈希。
- 是否可进入 set。
- 是否可作为 dict key。

编译器不应把这些信息散落在语义分析和代码生成的多处特判中。

## 13. 真实 IR 与调用归一化

第二阶段应继续推进真实 typed IR。

目标：

- AST 不再直接驱动大部分代码生成。
- 语义分析后生成带类型的 IR。
- 函数调用在 IR 中归一化。
- optional 参数在 IR 中补齐。
- 命名参数在 IR 中重排。
- `...` 在 IR 中收集为 array。
- `***` 在 IR 中收集为 dict。
- 多返回在 IR 中明确表示。
- 静态调用和动态调用在 IR 中明确区分。
- C ABI wrapper 和 xcall adapter 从 IR 生成。

这可以降低代码生成器复杂度，并为后续模块、异常、异步打基础。

## 14. 标准库与隐性类接入

第二阶段标准库目标：

- 标准库主要是 XRT 函数声明和绑定。
- 不另写一套 xlang runtime 标准库。
- 隐性类方法优先绑定 XRT。
- 容器方法优先绑定 XRT。
- 类型转换优先绑定 XRT。
- 字符串、时间、路径、文件等能力优先绑定 XRT。

需要补充 XRT 缺口时，应按 XRT 风格实现，并优先推动合并回 XRT。

第二阶段完成时，应至少满足：

- `var` 可以可靠保存并调用 function。
- `var` 保存 function 时保留精确签名。
- `var` 可以可靠保存 class。
- `var` 可以可靠保存 custom。
- `type(var)` 返回精确类型。
- `array<T>` 是真实静态泛型容器。
- `list<T>` 是真实静态泛型容器。
- `set<T>` 是真实静态泛型容器。
- `dict<T>` 是真实静态泛型容器。
- XRT 拥有独立 set 能力。
- xvalue set 接入新的 XRT set。
- class/custom/function 可以作为一等公民参与变量、参数、返回值、容器、泛型。
- 隐性类方法绑定到 XRT。
- xcall frame 可独立由 C 使用。
- native entry 可用于静态高性能调用。

## 16. 已固定的默认口径与后续深化项

以下内容已经采用默认建议作为第二阶段实现口径。后续如果要修改，需要作为新的设计变更单独讨论，不能在实现中临时分叉。

- call frame 使用 `kwargs` / `varargs` 两个 `xvalue`，保持结构简单，便于 C 侧直接使用。
- call result 使用 `values[4] + overflow` 小数组优化，覆盖常见 0 到 4 个返回值路径。
- `xvalue_struct` 保持稳定，不直接塞签名、class、custom 等大字段；复杂数据通过对象指针和 type desc 间接表达。
- typed set 优先 hash set，依赖 type ops 的 hash/compare。
- `dict<T>` 第二阶段固定 string key。
- class 进入 `var` 默认拥有独立副本。
- custom 进入 `var` 由 type desc 的 ownership 策略决定。
- xlang 函数多返回导出给 C 时，第一版优先 out 参数。

后续深化项：

- 更细的 borrowed/owned 语法是否进入语言层。
- call result 小数组容量是否需要根据真实场景调整。
- type desc 的跨 DLL 边界稳定性和版本兼容策略。
- typed set 在 hash 稳定性、顺序稳定性和性能之间的最终取舍。
