# DEMO6 扩展库生态压实计划

## 目标

本计划把 `release/extlibs` 中的目录分成可验证的生态状态，而不是把“存在
目录”误写成“已经发布”。每一个第一期扩展库都必须同时具备：

- 可构建的 xlang 包清单和真实的底层实现；
- 明确、简短并适合 xlang 的公开 API；
- 正常路径、错误路径、资源释放和取消/回调边界测试；
- 可运行的 xlang 范例；可稳定独立编译时再提供对应 C 范例；
- 由元数据生成的官网详情页。

`tools/audit_extlib_ecosystem.ps1` 从包目录、包清单、测试和示例生成机器可读的
`test/extlib_ecosystem.json` 和审计报告。当前工具的标签包含名单推断，不能作为发布证明。
实际验收必须附带当前源文件/构建哈希、测试时间、命令、输出、退出状态与未验证范围。

## 状态定义

| 状态 | 含义 | 官网展示 |
| --- | --- | --- |
| `featured-rc` | 已通过重点库 RC 门禁 | 正式详情页 |
| `phase1-candidate` | 有真实实现，适合本轮补齐后纳入第一期 | 候选详情页 |
| `phase1-rebuild-candidate` | 当前仅有简化表层，但完整边界可在 10000 行新增预算内实现 | 重建候选详情页 |
| `existing-hardening` | 已有实质实现，需针对真实后端补齐稳定性、测试、范例与平台边界 | 压实中详情页 |
| `needs-xrt-migration` | 仍引用已移除的 XRT ABI（例如 `xvo`），当前构建不可视为可用 | 阻塞，先迁移底层所有权与错误模型 |
| `blocked-dependency` | 包本身有实现，但关键依赖仍被 ABI 迁移或构建链阻塞 | 阻塞，先修复依赖，不把上层误报为待压实 |
| `placeholder` | 只有包装层、演示算法或未连接真实后端 | 不作为首期能力宣传 |
| `deferred-large` | 占位库的完整新增实现预计超过 10000 行，或需要大型第三方/平台 SDK | 暂缓，并说明依赖条件 |
| `deferred-platform` | 强依赖平台、服务、设备、凭据或商业运行时 | 暂缓，并说明运行条件 |
| `internal` | 仅供其他包使用的私有依赖 | 不生成公共详情页 |

## 第一期开源生态准入规则

1. 不以目录数量作为生态规模，不以 `extern` 声明数量作为功能完整度。
2. 新实现优先下沉到 XRT；扩展库只承担 XRT/C 库到 xlang 的薄包装、对象
   生命周期、错误映射和易用 API。
3. 只有占位库在补齐真实能力时预计需要新增超过 10000 行的自研算法、协议栈或
   大型依赖移植，才记录为 `deferred-large`。已有实质实现的库不受总代码量限制，
   必须进入 `existing-hardening`，按真实后端完成迁移、测试、范例和边界压实。
4. 网络服务、数据库、GPU、模型推理、GUI、硬件和云服务库必须有可重复的
   本地或容器测试环境；没有环境时不宣称生产可用。
5. `native` 类必须有明确的 create/destroy、所有权和失败约定；错误必须进入
   当前 XRT error 模型，禁止复用废弃的局部错误/缓冲区 ABI。
6. C 范例只在库本身拥有稳定 C 表面时提供。依赖 xlang 运行时内部私有模块的
   包，不伪造独立 C 可用性。

## 本轮批次

### A. 已有 RC 基线

`aho_corasick`、`argon2`、`blake2`、`blake3`、`bloom`、`brotli`、`bson`、
`bz2`、`crc32`、`lz4`、`lzma`、`md5`、`miniz`、`murmur3`、`sha3`、
`siphash`、`snappy`、`xxhash`、`zstd`。

这些是历史重点名单，不凭名单维持当前 `featured-rc` 结论。默认后端或运行库改变后，
必须在相应构建上复验；仍以破坏性测试、性能回归和 API 一致性改进为主，不以兼容旧接口扩张。

### B. 首期优先补强候选

- 数据与配置：`cbor`、`csv`、`ini`、`toml`、`plist`、`yaml`、`xml.sax`、
  `xml.etree`、`xml.dom`、`zip`、`tar`、`gzip`、`md4c`、`netrc`。
- 算法与本地工具：`chardet`、`consistent_hash`、`crontab`、`diff`、`dotenv`、
  `fuzzy`、`geohash`、`hyperloglog`、`lru`、`progress`、`tabulate`、`trie`。
- 具备明确平台条件的小型能力：`clipboard`、`com`、`daemon`、`sysinfo`、
  `watch`、`singleinstance`、`sharedmem`、`serial`、`process` 类近邻能力。

候选不等于已发布。每个库需通过本计划的门禁后才能变成 `phase1`。

## 当前验证基线

状态区分目录事实、历史标签和实际验收结果。清单能解析、源文件存在、登记了用例，
都不能代替运行结果；`tools/run_phase1_extlibs.ps1` 与 `tools/run_platform_extlibs.ps1`
分别承担无副作用包与平台集成包的门禁。平台功能的回环、模拟或负例不替代真实后端验收。

历史 smoke 结果保留对应构建和时间，不改写旧结果，也不能作为当前发布依据。
最新状态应明确指向新的验收批次，不将不同构建、不同范围的结果合并成一个通过率。
当前完整复核见 [2026-09-05 状态报告](扩展库当前状态_2026-09-05.md)；
后续独立修复见 [serial 边界批次](扩展库串口边界收口_2026-09-05.md)。

### C. 既有实现压实与暂缓评估

`onnxruntime`、`dinov3`、`rapidocr`、`xfeat`、`opencv`、`xbot`、`sqlite`、
`md4c` 与图像基础库已有可审计实现，不因总代码量大而暂缓。它们先进入
`existing-hardening`：确认后端真实可调用、资源生命周期、错误映射、可重复测试、
C/xlang 范例和平台依赖，再决定是否纳入第一期。

下列类别通常不能以轻量自研代码达到第一期质量：

- 尚无真实后端的大型推理/视觉/音频栈：`llama`、`libtorch`、`tensorrt`、
  `openvino`、`whisper`、`stablediffusion` 等。
- 大型数据库和消息系统：`mysql`、`postgresql`、`mongodb`、`kafka`、`pulsar`、
  `rabbitmq`、`clickhouse`、`tdengine` 等。
- 大型协议/基础设施：`grpc`、`quic`、`webrtc`、`ssh`、`kubernetes`、`docker`、
  `terraform_state` 等。

审计工具会保留这些目录和真实依赖信息，但不会将其列为第一期可用库。

### D. 当前 ABI 迁移队列

以下项目已有实质实现，因此不按 10000 行新增预算暂缓；但在完成当前 XRT
所有权、错误和调用 ABI 迁移以前，必须保持 `needs-xrt-migration` 或
`blocked-dependency`，不得以 dry-run 或占位成功结果宣传为可用：

- `_xge_native`：核心绘制、XUI workflow/dock 面板和回调 bridge 仍大量依赖
  旧动态值 ABI。应先迁移独立的回调 bridge 到当前 `xrtcallable`/`xrtValueInvoke`
  模型，再把 workflow、dock、inventory、flow graph 按模块迁移为当前
  `xvalue` 容器与明确的释放规则。`xge`、`xge_shape_ex`、`xui` 必须保持由该
  私有依赖阻塞，不能用局部 typedef 或宏映射伪造兼容。

## 验收门禁

每一包补强完成时至少运行：

```powershell
release\xl.exe check test\cases\extlib_<package>.xl
release\xl.exe run test\cases\extlib_<package>.xl
release\xl.exe run release\examples\extlibs\<package>.xl
```

随后执行：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tools\audit_extlib_ecosystem.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File tools\generate_extlib_site.ps1
```

重点库还必须通过 `tools\run_featured_extlibs_rc.ps1`。新加入第一期的库会被加入
相应分组套件，不把全部两百余包塞进单个慢速批处理。
