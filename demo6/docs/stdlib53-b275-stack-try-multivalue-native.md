# Stack try 的双结果拥有底座

2026-10-14。Stack 动态 try 的原生提供方已实现两个独立的拥有返回值，
使用 XRT 的 `xrtcallresult`，不把 `(found, item)` 包装成 Array。
提供方已登记为独立按需组件；语言多值接收与 product IR 尚未接通。

## 原生合同

`xl6StackErasedTryCallV1` 借用 Stack，接收 depth、是否 pop 和已初始化
的空结果向量。返回 bool 表示整项操作是否成功，不表示是否找到元素。
成功的结果向量恰有两项：Bool found 和拥有的动态 item。未找到返回
`false, null`；找到可空 null 返回 `true, null`，不通过 item 的空值
判断存在性。成功投影保留 char、精确文本长度及元素身份。

负 depth 报 RangeError；pop 的 depth 必须为零。错误角色、未绑定
投影、BUSY 及非空输出向量均拒绝。提供方不消费借用源，失败不发布
部分结果，非空输出拒绝时保留调用方原值。真正的读取、复制和资源
失败不能转成“未找到”。

读取投影和两个 inline 结果槽均在移除元素前准备。没有额外结果容器
分配；正常空栈 try 的零分配预算通过。移除后的发布使用原生完整向量
move。准备失败保留栈内容；晚来的析构或发布失败可能发生在移除
提交之后，但必须报告失败、释放两个结果并保持输出为空。

独立失败状态即使没有错误对象也会传播。晚来的错误不替换首个无
诊断失败；投影回调释放源的最后引用时，原生操作 pin 保持存储活跃。
代码没有公开 byref 语法，也不生成标准库函数体。

## 当前验收范围

Windows 和 Linux 原生专项各 84 项检查、18 条闭合分配前缀及八份
实际错误实现对照通过。覆盖 int 零值／边界、NUL 文本、char、bytes、
可空 null、空栈、超大 depth、错误角色、BUSY、拥有结果、无诊断
失败、回调释放最后引用和发布失败。Linux 对所选实现启用 ASan/UBSan。
错误实现必须通过编译并在运行期被拒绝，不能以编译失败充数。

源码构建为 Windows 331、Linux 330 个翻译单元。原生依赖闭包专项
核对符号提供方、唯一源文件、Sequence／错误依赖和 runtime-call
模块。既有语言回归仍只覆盖已接通的核心和批量方法，不据此标记
动态 try 语法完成。纯 typed Stack 的 AOT 不携带新增 try 提供方。

原生证据为 `E:/xlang-validation/stdlib53-b275-native-win-final1/results.json`
和 `/var/tmp/xlang-stdlib53-b275-native-linux-final1/results.json`。当前
源码及头文件须与构建摘要一致；旧 TCC 仅提供真实 C 编译前置。

## 多返回值接入的剩余要求

当前动态表达式合同只投影返回值零，语义检查的多值接收要求静态
返回列表，动态方法登记又拒绝两个及以上返回值。因此不能只新增
try 方法名、偷偷丢弃 item，或由 Cgen 根据方法名称补造结果类型。

下一阶段需贯通同一个通用合同：

- 多值接收上下文给出精确结果数量，统一 IR 登记拥有的 product 与
  字段 ABI；运行时先核对实际数量，再移交每个结果。
- 立即调用和保留后的绑定方法都返回完整原生向量。只有外层单值
  表达式选择返回值零，其余结果仍完整释放。
- class 方法保留优先分派，Stack try 是精确原生角色的 fallback；
  同名自定义方法的多返回值不能因名字或物理布局被误判为 Stack。
- 声明、赋值、丢弃字段、nullable item、正常缺失、真实错误和 OOM
  都须验证；独立成功状态不能被 product 零值或错误指针代替。

`stdlib_stack_dynamic_try.pending.xl` 保留立即调用、赋值及绑定方法的
最小端到端目标，当前仍因动态返回列表缺失被语义检查拒绝，不能转为
通过夹具或把待实现诊断当成成功验收。

完整容器转换、Native 编码、工作线程／对象图故障、模块组合和发布
总门仍继续。本批不更新发布 CLI/DLL/VFS，不宣告 53 模块完整封板。
WaitQueue 保持已批准的 MPMC；CRT 未决策 0、XRT 19 组及对象池最后不变。
