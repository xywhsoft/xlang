## 核心结论

真实实现已经远超早期占位层，但当前构建的扩展库集成明显落后于代码规模。
最应优先做的是恢复已有实现的精确 C ABI、模块依赖与语言运行合同，而不是继续增加包名。

- 活动目录仍为 **225**：**218 公共包、7 内部包**。不能称为 225 个成熟库。
- featured/phase1/platform 分别登记 **19/87/10** 个包，合计 **116**。
  登记不是测试结果，更不能直接写为“116 个已压实”。
- 首次固定输入的 136 个 JIT 用例：**20 通过、111 失败、5 项超过 30 秒预算**。
  79 项外显为 C 原型冲突，16 项为功能依赖检查失败；不能解释为 116 个独立实现 BUG。
  对 5 项延长到 120 秒后，4 项给出编译失败、1 项仍超时；合并观察为
  **20 通过、115 失败、1 超时**，原始两批记录分别保留。
- 与 9 月 5 日重叠的 132 个用例，从 94 通过变为 19 通过，75 个由通过转为非通过，
  未观察到失败转通过。编译链与 XRT 快照都已变化，这证明集成结果退步，
  不证明 75 个底层算法分别出现了新错误；更严格的原型检查也可能暴露原有不一致。
- MQTT 本日的独立限定范围验收有完整证据。serial 的核心复测通过，但当前范例
  有语法迁移遗漏，因此不能把此前的整包验收结果自动外推到本构建。
- 后续 Argon2/Bloom 批次新增 44 项通过的 Windows 检查、44 个精确生成原型、

### 模块与声明 SDK 边界

HTTP 等包已经在 manifest 写明 `artifact.xrtModules`，不能把这些错误简单归因于“清单没写依赖”。
当前入口在 [xl_api.c](../src/api/xl_api.c:2067) 设置模块宏；
声明 SDK 又会恢复未提前存在的 feature 宏，例如 [codec_percent](../release/include/xrt_decl.h:44339)。
包内头仍按 feature 宏验证依赖，实际编译时出现 codec/query、HTTP、mail deflate、
SSH secure-random、WS spin/TCP 等检查失败。
应核实预注入头、模块闭包和 feature 条件的合同；这不是新增一份运行库能合理解决的问题。
本次确认外显和相关路径，不声称已经完成全部预处理顺序的根因定位。

30 秒超时不直接判定死循环。HTTP client request 和 volc.core 单独 `check` 分别约
12.8/13.0 秒通过，说明至少这两个不是解析/语义阶段立即失败；对全部 5 项另跑
120 秒预算，结果单独记录，不改写原始基线。

| 补查项 | 120 秒预算结果 |
| --- | --- |
| HTTP client exchange | 73.3 秒后在 form-urlencoded 功能依赖检查失败 |
| HTTP client request | 75.8 秒后在相同功能依赖检查失败 |
| HTTP client transport | 79.6 秒后报 async suspension result ABI is not admitted |
| volc.core | 70.7 秒后在所依赖 HTTP 头的功能检查失败 |

CSS/HCL/PKCS 等测试包含预期失败返回。应区分原生函数的 last-error 与语言异常合同，
逐项决定错误效果标注和调用方处理，不允许无条件清空错误槽来使门禁变绿。

## 独立 C 探针发现

这两项不依赖 xlang 代码生成，证明尚未纳入正式验收的简化包本身也需要边界审查。

1. **MySQL 状态字符串越界**：`xmysql_status_str(0x017b)` 连续向 64 字节静态数组
   `sprintf` 多个状态名称。Ubuntu GCC 的 ASan 确认 `global-buffer-overflow`，
   首次越界位于 [mysql_native.c](../release/extlibs/mysql/mysql_native.c:75)。
   应使用有明确拥有权的动态字符串/缓冲区，并消除共享静态返回缓冲的覆盖和并发问题。
2. **FAISS 小数输入不前进**：`xfaiss_l2_distance("1,2", "4,6")` 正常返回 5；
   `xfaiss_l2_distance("1.5,2.5", "4.5,6.5")` 在 2 秒预算内不返回。
   [解析循环](../release/extlibs/faiss/faiss_native.c:38) 只消费整数数字及逗号，停在小数点后
   外层循环不推进。点积/余弦还有相同结构，需一起审查负数、空白、非法 token、维度不等。
   不能把这套简化算法修到能算小数就宣称已经接入 FAISS。

本次仅记录问题，不修改生产实现。探针程序、命令、退出码、输出与源码哈希有独立证据；
所有超时子进程已由测试工具结束。

### 实际修复

- **精确 ABI**：两包原生整数/布尔/尺寸声明与真实 C 函数一致，公开语言 bool 显式

### 下一步顺序

1. **先恢复已有包的接入合同**：用真实公共 C 头核对生成原型，分清 bool/整数、
   指针限定、无返回析构、typed 容器；补正模块 feature 闭包、返回块和辅助符号。
   不关闭检查、不加旧 ABI 回退，也不把不兼容容器指针强转后视为完成。
2. **同时收口正在修改的包**：Brotli 的回调、标准流互操作、范例和错误原子性，
   BLAKE2 的字节/密钥/摘要/错误对象；随后按同类边界审查其他压缩与哈希包。
3. **建立真正逐包的验收入口**：将回调、取消、范例、C/xlang、JIT/AOT、分配故障、
   所有权和必要的跨平台验证绑定到同一包。网络/推理/GUI/设备成功路径单列证据。
4. **最后补新后端并同步官网**：对已确认占位包估算新增实现成本；10000 行预算不
   适用于已有 ONNX、RapidOCR、xbot 等后端。只对通过范围发布对应能力说明。

总体判断：实现广度已经大幅提升，但当前生态的主要短板是公共接入稳定性和逐包交付闭环。
现在不宜用目录数或历史通过数量估算“压实完成百分比”；必须先恢复可重复的当前构建基线。
