# 进程终端：PTY / ConPTY

终端能力属于 `process`；不增加框架、模拟终端或第二套进程对象。
普通 `ProcessCommand` / `Process` 不选入终端原生组件，显式使用
`terminal`、`terminalSize` 或 `resize` 才选入。能力查询本身不是启动前置条件。

```xlang
auto command = process.cmd("my-cli", ["--interactive"])
command.terminal()
command.terminalSize(80, 24)
auto handle = command.start()
assert handle.resize(96, 32)
auto input = handle.stdinWriter()
auto output = handle.stdoutReader()
// 应用持续读取 output，按子程序的协议向 input 写入 bytes。
// 子程序正常结束后，wait 返回独立的 ProcessExitStatus。
```

## 公开合同

- `process.terminalSupported() as bool`：平台能力探测，false 不是错误；
  非 pure，不承诺不可变平台状态。不自动创建终端。
- `command.terminal(enabled = true)`：创建线程上的配置操作，true 禁止
  已绑定的 File 标准流，关闭 HideWindow / NewConsole。无普通管道降级。
- `command.terminalSize(columns, rows)`：启动时的尺寸；两个值均须
  为 1..32767，否则 RangeError，保留原配置。尺寸为列/行，不是像素。
- `handle.resize(columns, rows) as bool`：调整存活终端，使用同一范围；
  非终端、已关闭或系统调用失败通过 checked 错误边界传递，不伪造成功。
  XRT 同步 resize / native close；调用者须持有有效 Process 引用。
- `stdinWriter()` / `stdoutReader()`：独立拥有的 IoWriter / IoReader。
  stderr 合流到 stdout，`stderrReader()` 报 StateError，不给出空假流。
  唯一流租约、调用方串行操作和拥有对象寿命延续均沿用普通 Process 合同。

输出为原始 `bytes`，不自动猜测编码，也不剥离 ANSI/VT 控制序列。
“原始 bytes”指传输/表示，不承诺终端处于 raw mode：POSIX 默认行纪律
和 Windows 控制台处理可能产生回显、换行转换、控制序列。普通精确二进制
IPC 应使用 pipe。输入、输出应持续服务；大输出时不得先无限 wait 再读。

closeStdin 并不在所有 PTY 上承诺普通 pipe 的 EOF；若协议要求退出，应
发送协议退出消息或使用显式 interrupt/terminate/kill。最后一个流/Process
引用释放会关闭父端，终端后端可能因此向子程序发出系统关闭事件；不能把
对象释放当作无影响的子程序后台化。Windows 自然结束后的 waiter 也会关闭
ConPTY，附着的后代进程可能收到关闭事件。没有语言借用句柄、自动 VFS pump
或生成代码回调。File / pipeline / capture-run 的范围见《进程文件重定向.md》。

## 声明与裁剪

`resize` 的封闭物理 ABI 为 `bool(void*, int64_t, int64_t)`，接收者
owner 为 `xl6ProcessDestroyV1`。效果保守、可能报错、可能等待原生锁；不能
声明 pure / no-raise / nonblocking。尺寸配置同样严格签名并校验 creator。
Cgen 只打印已校验的调用、拥有关系和错误分支，不包含终端算法。

查询、配置、存活 resize 分为三个 resident 组件，分别对应
`xl6_process_terminal.c`、`xl6_process_terminal_config.c`、
`xl6_process_terminal_live.c`。均声明原生 PROCESS_TERMINAL 依赖，普通
command-only 不承担终端体积。不得依赖“碰巧先调用能力查询”来接通 AOT。

## 验收边界与 Windows 系统限制

专项测试使用真实私有 child，报告三个流的 tty 属性，回显一行并回读
调整后的尺寸；既测 JIT，也测没有先调用 terminalSupported 的独立 AOT。
公开 API 不增加测试专用 waiter join；账本 fixture 持有实际原生引用，
私下 join 其 waiter 尾部以区分逻辑完成和物理释放。

当前 Windows 10 19045.6466 的 inbox ConPTY：不链接 XRT 的最小 Win32
CreatePseudoConsole / ClosePseudoConsole 对照循环，每轮仍多保留一个已退出
conhost 的 Process 句柄。XRT 会话显示相同增长，自有 child/输入/输出句柄
均已关闭，堆账本平衡。不能宣称 Windows 全进程 OS 句柄零增长。正式 fixture
保留双次原生 API 对照，校验实际会话没有额外增长；Linux 校验零 descriptor
增长。此为当前宿主平台限制，不通过解读/关闭 opaque HPCON 内部句柄补丁解决。
连续、大量创建 Windows 终端的发布级零增长验收仍待其他系统/后端验证。

平台 API 的生命周期和同步关闭风险可参照
[Microsoft 的伪控制台生命周期文档](https://learn.microsoft.com/en-us/windows/console/creating-a-pseudoconsole-session)。
该文档不作为本机句柄问题的归因证据，归因以独立原生对照为准。
