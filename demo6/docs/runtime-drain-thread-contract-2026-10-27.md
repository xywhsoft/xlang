# 运行时跨线程退役排空修复（2026-10-27）

## 已确认的问题

`xlRuntimeDrainRetiringChecked` 的合同区分本线程回调重入和其他线程正在进行的清理：前者应立即返回 BUSY，后者应遵循调用者给出的期限等待。

旧实现只看进程级 `collectingRetirements` / `ownershipDriverRunning` 标记，把两种情况混为重入。Windows 和 Linux 的未修改普通 r6 产物均可用纯公开 API 稳定复现：另一线程停在合法 V4 退役预检时，20 毫秒调用实际仅耗时 0–1 微秒；`-1` 调用也立即返回 `ready=0, ok=1`。

Windows r6 的五组联合 CLI 曾在完成业务断言后报告退役未完成。同一用例后续普通重复运行未再复现，因此不能仅凭通用缺陷就断言那次失败的精确原因；原始联合失败报告保留，修复产物仍需重新验收。

## 实现

两个已有驱动标记同时记录执行线程身份，所有读写由原有 API 互斥量保护。排空只将当前驱动线程的回调识别为重入；其他线程正在清理时，零期限返回 BUSY、正期限等待到期、`-1` 等待清理完成。

直接模块退役的 typed step 也采用同一执行身份保护，确保它不依赖先经过集合驱动才能正确识别重入。没有待退役模块时，收集器直接返回，避免普通 API 边界新增线程身份查询。

没有修改公开 ABI、XRT 时间单位、生成 C 或拥有图协议。成本是 16 字节私有静态状态，以及实际退役驱动入口/排空调用的线程身份查询；不分配新的堆对象。

## 验证与后续

新增 `xlir_runtime_drain_threads.c`，通过真实公开 API 编译、激活和清理合法 V4 模块，不构造假的宿主模块记录，不使用网络。

三个阶段覆盖直接预检、集合驱动中的 typed step、直接 typed step。每阶段验证本线程回调的 `0 / 1 / -1` 三种重入立即 BUSY，以及另一线程的零期限、20 毫秒期限、无限等待和最终真实回收。
