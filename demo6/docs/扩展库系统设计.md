# DEMO6 扩展库系统设计

本文档记录 DEMO6 对模块化、import/package、XAPI 接口元数据和扩展库系统的统一设计口径。后续实现扩展库系统时，以本文档为准。

## 设计目标

xlang 的扩展库系统不是简单的源码 include，也不是 Python 风格的全局环境包系统。它的目标是：

- import 能精确找到一个可验证的能力单元。
- package 能同时承载源码包、C 混合源码包、静态库、动态库。
- XAPI 作为机器生成的接口元数据，成为 xlang、C、扩展库之间的稳定桥梁。
- 同一个项目中允许同一个扩展库的多个版本同时存在。
- 函数、类型、模块、ABI、native artifact 都有明确身份，避免 Python 式依赖地狱。

## 三层结构

扩展库系统分为三层。

### 1. 源码声明层

源码声明层是开发者主要接触的层。

来源包括：

- `.xl` 中的 `export`。
- `.xl` 中的 `extern`。
- `class`。
- native-backed class。
- 未来的 `#doc ... #end`。

开发者应优先通过 xlang 声明表达接口，而不是手写复杂接口文件。

### 2. XAPI 接口元数据层

XAPI 是 xl 生成的权威接口元数据。

XAPI 记录：

- compiler 信息。
- target 信息。
- package instance 身份。
- module 身份。
- exported functions。
- exported vars。
- exported types。
- class/native-backed class 元数据。
- 函数签名。
- 参数、可选参数、可变参数。
- 多返回值。
- C symbol。
- calling convention。
- init/unit 生命周期。
- imports。
- links/loadlibs/cSources。
- docs。

XAPI 默认不由用户手写。开发期可以使用 `.xapi.json` 作为调试产物；分发期可以使用 `.xapi` 或 `.xapi.json` 作为接口事实来源。

### 3. package manifest 层

package manifest 是轻量包清单，不承担完整接口声明职责。

它只描述：

- package name。
- package version。
- package ABI version。
- XAPI 文件位置。
- artifact 类型。
- source 文件。
- C source 文件。
- static/shared native artifact。
- links。
- loadlibs。
- dependencies。
- assets。

函数签名、类型信息、导出符号不应在 manifest 中重复维护，应由 XAPI 提供。

## Package Instance Identity

DEMO6 采用 package instance identity 解决多版本共存问题。

同一个包的不同版本、不同 ABI 版本，是不同 package instance。

建议身份格式：

```text
packageId = name@version#abi
moduleId  = packageId::module
exportId  = moduleId::symbol(signature)
typeId    = moduleId::typeName
```

示例：

```text
C@1.0.0#abi1::math::add(int,int)
C@2.0.0#abi1::math::add(int,int)
C@1.0.0#abi1::Image
C@2.0.0#abi1::Image
```

这些身份互不相同，不能因为名字相同而合并。

## 多版本依赖模型

目标场景：

```text
App
  -> A
      -> C@1.0.0
  -> B
      -> C@2.0.0
```

规则：

- `C@1.0.0` 和 `C@2.0.0` 可以在同一项目中共存。
- A 内部绑定到 `C@1.0.0`。
- B 内部绑定到 `C@2.0.0`。
- App 不会自动看到 A/B 的私有依赖。
- 依赖默认私有，只有显式 export/re-export 的符号才暴露给上层。
- 如果 App 同时需要直接使用两个版本，必须显式 alias。

未来可设计：

```xlang
import C1 = C@1.0.0
import C2 = C@2.0.0
```

第一版不急于实现版本语法，但内部模型必须按 package instance identity 设计。

## 类型身份

类型必须携带 package instance 身份。

如果两个版本都导出：

```xlang
class Image
```

内部身份必须不同：

```text
opencv@1.0.0#abi1::Image
opencv@2.0.0#abi1::Image
```

规则：

- 不同 package instance 中的同名类型默认不兼容。
- `C@1::Image` 不能传给要求 `C@2::Image` 的函数。
- 只有显式声明 ABI 兼容或提供转换函数时，才能跨版本转换。
- 类型别名不能抹掉 package identity。

## 函数导出身份

函数导出必须强绑定 package、module、version、ABI 和签名。

函数身份不应只由函数名决定。

建议 XAPI 中记录：

```json
{
  "packageId": "C@1.0.0#abi1",
  "moduleId": "C@1.0.0#abi1::math",
  "name": "add",
  "signature": "func(int,int) as int",
  "exportId": "C@1.0.0#abi1::math::add(func(int,int) as int)",
  "cSymbol": "..."
}
```

重载函数必须记录可稳定比较的 signature key。

## 命名空间与可见性

import 不应污染全局命名空间。

规则：

- `import counter` 后符号进入 `counter.xxx` 命名空间。
- 依赖包默认不向上层暴露。
- package 可以显式 re-export 符号。
- 同一作用域导入两个同名 package instance 时必须 alias。
- 未 alias 的命名冲突应在编译期报错。

## XAPI 必须承载的身份字段

XAPI 应逐步扩展以下字段：

```json
{
  "format": "xlang-xapi-1",
  "package": {
    "name": "C",
    "version": "1.0.0",
    "abiVersion": "1",
    "packageId": "C@1.0.0#abi1"
  },
  "module": {
    "name": "math",
    "moduleId": "C@1.0.0#abi1::math"
  },
  "exports": [],
  "types": [],
  "imports": [],
  "links": [],
  "loadlibs": [],
  "cSources": [],
  "docs": []
}
```

第一版可以保留现有字段，但新增实现必须向 package identity 方向收敛。

## package manifest 建议格式

manifest 不重复接口细节，只指向 XAPI 和 artifact。

建议格式：

```json
{
  "format": "xlang-package-1",
  "name": "counter",
  "version": "1.0.0",
  "abiVersion": "1",
  "xapi": "package.xapi.json",
  "artifact": {
    "kind": "source",
    "entry": "src/counter.xl",
    "cSources": ["src/counter_native.c"]
  },
  "links": [],
  "loadlibs": [],
  "dependencies": [
    {
      "name": "C",
      "version": "1.0.0",
      "abiVersion": "1"
    }
  ],
  "native": {
    "singleton": false
  }
}
```

## Native Artifact 冲突规则

纯 xlang 包和大多数源码包可以多版本共存。

native 动态库需要额外规则，因为一个进程内某些 DLL 可能不能加载多个版本。

manifest 应允许声明：

```json
{
  "native": {
    "singleton": true,
    "loadName": "xxx.dll",
    "version": "1.0.0"
  }
}
```

规则：

- `singleton=false` 时，按 package instance 独立处理。
- `singleton=true` 时，同一进程中只能有一个兼容实例。
- 两个 singleton native artifact 的 `loadName` 相同但版本或 ABI 不兼容时，编译期报错。
- 编译器不能静默选择其中一个版本。

## Lock 文件

为保证构建可重复，扩展库系统需要 lock 文件。

建议名称：

```text
xlang.lock
```

lock 文件记录：

- package name。
- version。
- abiVersion。
- packageId。
- resolved path。
- artifact hash。
- XAPI hash。
- dependency graph。
- target。
- native artifact。
- links/loadlibs/cSources。

原则：

- import resolver 每次解析出的结果应能写入 lock。
- 有 lock 时，构建优先按 lock 复现。
- 依赖解析结果变化时，必须显式更新 lock。

## Resolver 规则

第一阶段 resolver 保持简单确定：

1. 显式路径。
2. 当前项目 `packages`。
3. 项目配置中的 package path。
4. xlang home packages。
5. 标准库 packages。

第一阶段不做远程下载，不做完整包管理器。

解析结果必须包含 package instance identity。

## 与 demo5 的关系

demo5 的 XLE/package 设计有重要参考价值：

- package manifest。
- source/shared artifact。
- dependencies。
- modules。
- exports。
- functions。
- ABI id。
- native binding。

DEMO6 继承这些方向，但不照搬 demo5 的职责混合模型。

DEMO6 的调整：

- package manifest 只做轻量索引和构建信息。
- XAPI 成为机器生成的接口事实来源。
- package instance identity 成为依赖隔离核心。
- 用户不需要手写完整接口 JSON。
- 多版本共存是默认设计，而不是事后修补策略。

## 第一阶段实现边界

第一阶段应实现：

- package manifest 读取。
- XAPI 读取。
- packageId/moduleId/exportId/typeId 内部建模。
- import 注入导出函数和变量。
- package 私有依赖不污染上层。
- 基础 alias 设计预留。
- native singleton 冲突检查预留。
- lock 文件格式设计预留。

第一阶段暂不实现：

- 远程包下载。
- 完整版本求解器。
- 复杂 semver range。
- 自动升级。
- 包仓库。
- 用户手写完整 XAPI。

## 设计原则

- import 绑定的是确定 package instance，不是模糊包名。
- 函数、类型、模块都必须带 ABI 身份。
- 多版本共存优先于全局唯一版本。
- 冲突必须显式报错，不能静默选择。
- XAPI 是接口事实，manifest 是索引清单。
- 用户使用应简单，复杂度留在 xl 内部。
