# xlang DEMO6 设计理念

本文档用于记录用户对 xlang DEMO6 的基础设计理念叙述。

记录原则：

- 只记录用户明确表达或后续确认的设计理念。
- 不混入 DEMO3、DEMO4、DEMO5 的历史口径。
- 如果需要引用旧版本，只作为“历史对照”单独标注，不作为 DEMO6 默认标准。
- 对尚未决定的内容标记为“待定”，不提前替用户做结论。

## 1. 项目定位

xlang 是一种基于 XRT 和 TCC 的新型编程语言。

- XRT 是 xlang 的运行时与标准库基础，全称可理解为 `x runtime library`。
- TCC 是 xlang 当前重要的底层编译/执行支撑。
- xlang 的语言设计、标准库设计、运行时稳定性与 XRT 的演进是相互促进的关系。

## 2. XRT 与 xlang 的关系

XRT 也是用户开发的独立项目，仓库位置为：

```text
D:\GIT\xrt
```

开发 DEMO6 时，如果遇到属于 XRT 的 BUG，不应在 xlang 仓库里绕过或临时掩盖，而应该进入 XRT 仓库修复。

XRT 修复完成后，再将更新后的单头文件库同步回 xlang 对应目录。

## 3. XRT 开发与同步流程

XRT 的开发方式：

1. 在 XRT 仓库的 `lib` 目录下编写或修改库代码。
2. 在 XRT 仓库的 `test` 目录下编写测试用例。
3. 运行测试，确认 XRT 侧修复稳定。
4. 运行 XRT 仓库 `singlehead` 目录下的 `single_head_maker.exe`。
5. 由 `single_head_maker.exe` 生成单头文件库。
6. 将生成后的单头文件库更新到 xlang 仓库对应目录，完成 XRT 与 xlang 的同步。

## 4. TCC 承担的核心设计指标

TCC 负责支撑 xlang 的三个核心设计指标：

1. xlang 编写的程序可以编译为 native 程序。
2. xlang 也可以作为脚本语言，嵌入到程序中运行，例如通过 `xl.exe`、`xl.dll`。
3. xlang 可以和 C 语言无缝混编，包括访问 C 变量、调用 C 函数等。

这三个指标是 DEMO6 设计时必须保持清晰的基础目标。

## 5. 第一绝对原则：与 C 完美混编

xlang 能够和 C 完美混编，是 DEMO6 的第一绝对原则。

后续所有语言设计都必须持续检查这一点：

- 新语法是否能清晰映射到 C 或 TCC 可接受的 C 代码。
- 新类型是否有明确、稳定、简单的 C ABI 表达。
- 函数调用、返回值、错误处理、模块初始化是否能生成清晰的 C wrapper。
- xlang 符号导出给 C 时，是否能生成普通 C 头文件和普通 C ABI 符号。
- C 符号导入 xlang 时，是否能通过声明完成，不依赖复杂运行时魔法。
- 标准库是否能通过声明 XRT 函数实现，而不是重新开发一套 xlang 专用标准库。
- 如果某个语言特性会严重破坏 C 混编，应优先调整该语言特性，而不是牺牲 C 混编原则。

后续讨论语言设计时，需要主动提醒：该设计如何践行“与 C 完美混编”。

## 6. 标准库设计方向

DEMO6 的标准库设计不应沿用 DEMO5 “为 xlang 专门重新开发一套标准库”的方向。

用户期望的设计是：

- xlang 的标准库不需要单独重新开发实现。
- 标准库应尽量直接声明 XRT 中已有的对应函数。
- xlang 层只负责把 XRT 函数暴露为 xlang 中的符号名。
- 标准库的真实实现应沉淀在 XRT 中，由 XRT 负责稳定性、测试与演进。

DEMO5 出现专门开发标准库的原因是历史阶段限制：当时还没有成熟的 C + xlang 混编机制，因此只能先在 xlang 侧实现一套标准库桥接/封装。

在 DEMO6 中，C 与 xlang 的混编机制应成为标准库设计的基础能力，而不是补丁式能力。

## 7. XRT 优先硬约束

能够使用 XRT 实现的功能，必须使用 XRT 对应功能。

严格要求：

- 不在 xlang 仓库里重复制造 XRT 已经存在的功能。
- 实现 runtime、标准库、隐性类方法或基础转换前，必须先查询 XRT 是否已有对应能力。
- XRT 已有能力时，xlang 侧只做声明、绑定、类型映射或极薄适配。
- XRT 缺少能力时，允许在 xlang 侧建立单独的临时补全层。
- 临时补全层必须使用 XRT 风格命名，为后续合并回 XRT 做准备。
- 类型隐式转换和强制转换是当前已知重点缺口，需要按该原则处理。

详细规则见 `XRT集成原则.md`。

## 8. 统一方案优先原则

DEMO6 后续设计与实现应尽可能使用一套清晰方案，而不是为了兼容历史版本引入多套兼容回退。

具体原则：

- 优先做统一设计，不优先做历史兼容。
- 不因为 DEMO3、DEMO4、DEMO5 曾经存在某种写法，就自动保留该写法。
- 如果旧方案与 DEMO6 新口径冲突，应以 DEMO6 新口径为准。
- 兼容层只有在用户明确要求、收益明显、且不会污染主实现时才考虑。
- 命令行、语法、标准库、C 混编、运行时绑定都应遵守这个原则。

## 9. 代码实现风格原则

DEMO6 编写代码时，最重要的原则是：使用最简单直接的实现方式，尽量编写更少的代码。

代码风格要求：

- 实现应直接、清晰、可调试，避免提前抽象。
- 能用简单函数解决的问题，不引入复杂框架或多层封装。
- 尽量减少代码量，但不能牺牲可读性和稳定性。
- 多写注释，注释使用中文。
- 注释要说明功能段落、设计意图、关键分支和不明显的边界条件。
- 多用空行和分行标识不同功能段落，让代码结构肉眼可见。
- 平台差异、阶段切换、错误处理、资源释放等地方要用短中文注释标明。
- 代码风格可参考 XRT 库中 `lib/time.h`、`lib/string.h` 等文件：函数前用中文说明功能，函数内部按平台/步骤分段，逻辑保持直接。

这条原则优先级很高。后续如果“通用抽象”和“简单直接”冲突，默认选择简单直接。
