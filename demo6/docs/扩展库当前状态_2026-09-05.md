## 本轮重点确认的问题

### 1. 静态容器的外部 C ABI 不一致

完整 [xregex_test.xl](../release/extlibs/xregex/test/xregex_test.xl:88) 调用：

```xlang
RegexSet set = xregex.compileSet(["error", "warn(ing)?", "[0-9]+"])
```

生成的 C 将 `xregex_set_compile_native` 第一参数声明为 `xvalue*`。
实际 [xregex_native.c](../release/extlibs/xregex/xregex_native.c:680) 的第一参数是 `xtarray`，并读取其 Kind/Value 布局。
`xtarray` 在 [公开 ABI](../release/include/xl_extlib_abi.h:189) 中是 `xl6_typed_container*`，不是 xvalue。

这是已确认的物理表示不一致，不是用户传错了字符串数组。
应在 typed/XLIR 的外部参数合同中处理真实表示与拥有权，并以 C 原型一致性测试防止漂移；不能靠强制转换指针或修改报错文本解决。

### 2. 原生错误槽与未捕获语言异常混用

[CSS 用例](../test/cases/extlib_css.xl) 故意验证无效 CSS 应返回 false，最后正常 return 0。
对应语言 API 没有 throw，但原生验证留下 XRT 错误后，程序退出仍被判为 uncaught IOError。

[当前入口生成](../src/cgen/xl6_ir_cgen_function_shell.c:70) 直接用 `xrtGetError() != NULL` 判断脚本是否有未捕获异常。
这没有区分“供 C API 调用方读取的最近错误”与“逃逸出语言调用边界的异常”。
应统一该边界及 `xl6ExtlibErrorPending/PublishXrt/Clear`，保留真实错误，不应通过无条件清空错误槽让测试变绿。
HCL、PKCS、md4c 等有相似外显结果，仍需逐项核对，不能只凭输出相似就认定全部同源。

### 3. serial 的独立实现缺陷（后续批次已修复）

复核时 serial_native.c 的 read 使用固定 4096 字节全局缓冲：

- loopback 读满时写入下标 4096 的终止符，越界。
- 真实 ReadFile 对 max_len 未按缓冲容量限制，负数、0 和过大长度不安全。
- loopback 写满后仍返回请求长度，而非实际写入量。
- 读缓冲和错误缓冲为全局共享，缺少对象/线程隔离。
- serial.xl 使用字符数量作为字节长度，UTF-8 文本可能被截断。

本轮未触发危险越界或操作真实串口。这些来自源码审查，现有 loopback 测试不能证明设备和并发边界安全。
后续已替换为 XRT buffer / file / mutex 并补故障、并发、双语与跨平台测试，见上方批次报告；真实硬件仍待验收。

### 4. MQTT 接收仍假定一次读完

[mqtt.handshake](../release/extlibs/mqtt/src/mqtt.xl:81) 发送 CONNECT 后只调用一次 recvBytes，再直接解析 CONNACK。
应补增量接收、分段输入、额外帧与超时用例。当前支持范围也应如实写为已有的 QoS 0/1，而不是完整 MQTT 客户端。

已建立 [MQTT 边界计划](扩展库MQTT边界计划.md)，目录中也已出现新的二进制帧构造和头部检查模块。
但当前 manifest 仍只编入 `mqtt_native.c` 与 `src/mqtt.xl`；新模块尚未接入完整包和门禁。
因此不能把这些新增文件作为上述问题已修复的证据。
