# Windows PowerShell 5 源码部署前置：2026-10-26

正常 XLIR 守卫会构建当前源码编译器。旧构建器部署内嵌编译器源码时使用
`Path.GetRelativePath`，该方法在 Windows PowerShell 5 的 .NET 环境不存在，
因此尚未进入合同检查便失败；这不是 TCP／TLS 行为失败。

本批只有一行构建实现变更：改用缓存助手已经加载的
`Get-XlirContainedRelativePath`，不添加第二套路径算法或平台分支。
它规范化绝对路径并要求目标位于明确根目录内；不会以任意 `..` 逃逸路径
代替规范映射，不改变实际部署文件、目录布局或内容。

## 验证

- 从实际生产脚本 AST 提取同一部署循环，在两版 PowerShell 执行真实映射，
  均得到 2,268 个文件。PowerShell 7 另与原 .NET 实现比较，全部相对路径和
  文件 SHA256 一致；PowerShell 5 也完整执行，不模拟缺失的方法。
- 四个正常路径案例及三个兄弟目录／父目录／跨盘逃逸拒绝通过。首轮测试
  控制器的 AST 选择和子作用域数组问题保留，修正的是控制器，不是生产循环。
- Windows PowerShell 5 完成当前源码 1,272 个 O2 翻译单元的完整构建，没有
  替换对象；随后两版 PowerShell 的正常 XLIR 守卫均通过。每版各包含实际
  GCC O0／O2 的四个编译／执行阶段，不只执行静态文字检查。
- 实际静态守卫另通过 38 个反例，以及 81 个 Cgen 片段的递归／防环检查。

证据根 `F:/xlang-validation/five-groups-20261026/p7-tls-close/`，包括两版
部署结果、完整源码构建收据、正常守卫日志、编译合同证据和哈希复核。
本提交只修复源码工具前置，不包含正在验收的 TLS 生命周期修改；不代表
普通 CLI／DLL／SO／VFS 或整个五组长期任务已封板。
