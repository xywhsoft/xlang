# 扩展库现状复核：2026-09-28

## 结论

当前扩展库已经有相当多的真实实现，主要矛盾不是包数量不足，而是已有能力与当前
编译链、运行时、测试和交付文档没有一起收口。**不能把 227 个活动包或 116 个测试登记
解释为已完成的生产级扩展库数量。**

相较 [9 月 27 日 23:11 快照](扩展库现状复核_2026-09-27_2311.md)，新增
`cString`、`floatEnv` 两个包；graph 的实现与测试有实质重构，主路径恢复通过。
更早已经完成的 HTTP、邮件、SSH、GUI、AI 等后端仍应按“已有实现、待接入验收”处理，
不能继续按占位库评估全部重写成本。

本次只清点、审查、复测和保存报告；没有修改编译器或扩展库实现，没有升级 XRT，
没有替换正式发布程序，没有更新或部署官网。现有 graph/CSV 开发内容作为受测输入，
不归为本次审计实现的修改。

## 范围和证据

- 重新解析所有活动包 manifest，核对声明源码、includeDirs、依赖、coverage.tests 路径。
- 核对集中测试登记、范例、README、包内官网正文与本地官网页面。
- 阅读新增包与重点包的语言声明、原生实现、所有权和错误处理路径。
- 固定本次 CLI/DLL/include，运行 147 个 Windows JIT 入口，涉及 126 个公共包。
- 重新运行 graph 独立 C 门禁，另跑四个共享边界探针。
- 对 CSV 既有 C 测试记录逐个核验输入哈希，没有将其冒充本次重新执行的测试。

未逐行审计全部 227 个包；未执行全量 API、全部 C/AOT/DLL/Linux、设备、模型和真实服务场景。
未选择不等于失败，某个入口通过不等于整包发布准入。

## 新增与推进

### cString

当前只有一个明确功能：`cString.length(string) as c_size`，直接声明 CRT `strlen`。
其语义是第一个 NUL 前的字节数，不是 UTF-8 字符数，也不是允许任意 NUL 的二进制长度。
这是显式 C 互操作入口，不应替代普通文本的 `string.len`/`string.byteLen`。

本轮 `stdlib_crt_c_string.xl` 通过，覆盖空串、ASCII、中文的字节计数及与字符数量的区别。
尚未在本轮验证嵌入 NUL、全部平台及发布产物模式。

源码：[cString.xl](../release/extlibs/cString/src/cString.xl:1)。

### floatEnv

已有实际浮点环境对象和操作，不是名称表占位：

- 舍入方向：nearest、downward、upward、towardZero。
- 浮点异常标记：invalid、divideByZero、overflow、underflow、inexact。
- 查询、设置、清除/引发标记，capture、hold、Snapshot.restore。
- 快照记录创建线程，恢复时检查线程身份；文档注释禁止跨 await 携带恢复。
- 普通环境使用 CRT fenv；Windows x64 TCC 补齐 x87/SSE 状态操作。

本轮 `stdlib_crt_float_env.xl` 通过，覆盖标记、非法 mask、舍入、嵌套快照和恢复。
还需要跨线程拒绝、异常退出恢复、优化构建、Linux/其他架构和反复创建释放测试。
原生层仍手写 `xrtThreadCurrentId` 声明并使用 malloc/free，宜改为正式 XRT 头及内存接口，
以进入统一的 ABI 和 OOM 检查；本次没有修改实现。

源码：[语言对象](../release/extlibs/floatEnv/src/floatEnv.xl:1)、
[原生实现](../release/extlibs/floatEnv/float_env_native.c:1)。

这两个包的现有测试名均为 `stdlib_*`，而非 `extlib_*`，且尚未登记扩展库套件或
manifest coverage。因此不能说“没有测试”，但应补登记，避免生态门禁漏检。

### graph

当前已经从单文件、固定大数组改为模型/遍历/分量/最短路四个 C 编译单元：

- 邻接表和 XRT map/array 管理图；按实际规模分配。
- SCC 改为显式栈 Kosaraju，不再使用旧的 `int[4096][520]` 共享桶。
- Dijkstra 使用索引堆，校验负权、非有限权重和距离溢出。
- 明确 4096 节点、32768 边上限，统一失败清理和结果所有权。
- C 名称接口带显式长度；语言包装返回 array/dict，布尔 ABI 与 C 定义对齐。

本次通过：集中 XL 用例、新边界 XL 用例、新基础范例；独立 C 的边界/容量/所有权测试，
128 组独立参照算法图验证，以及全部 9 个 API 的 218 个分配失败点检查。

**旧的静态桶越界和装载泄漏记录不能继续直接标为当前复现。** 但 graph 还不能标整包完成：
多线程 C 测试因缺少 `XRT_MODULE_ATOMIC` 声明而编译失败，专项因此尚未走到后续
生成原型核验、双语/AOT/Linux 和交付检查。含 NUL 的语言名称边界仍失败，见共享问题。

源码：[分量算法](../release/extlibs/graph/graph_components.c:43)、
[公开 C 合同](../release/extlibs/graph/include/graph.h:17)、
[未通过的线程测试](../release/extlibs/graph/test/test_graph_threads.c:1)。

### CSV

目前已有流式 reader/writer、短读短写、BOM/CRLF、严格文本检查、资源限制、错误位置、
借用/拥有流，以及显式关闭才提交的文件事务实现。集中 XL 用例本轮通过。

前一批 5 个独立 C 测试程序全部通过，包含 143+47 个分配失败点；本轮核对其记录的
16 个输入未变，保留为既有证据，而不是宣称本次重跑。
语言完整边界、AOT/Linux、双语同输出范例、互操作和官网仍需完成整包交付。
单独的 class 字段迭代探针仍失败，不能因为 CSV 采用索引遍历就认为编译器已修复。

### 有专项验收基础的候选

`aho_corasick`、`argon2`、`bloom`、`blake2`、`blake3`、`sqlite`、`xxhash`、
`crc32`、`md5`、`murmur3`、`sha3`、`siphash`、`mqtt`、`gzip`、`brotli`、`bz2`、`xregex`。

这 17 个库已有范围明确的专项记录，本轮所选入口也通过。其测试涉及不同程度的
C/XL 原型、所有权、错误、回调取消、OOM、流、文件事务和双语范例。
本轮没有重跑全部专项，不把不同构建、平台和范围拼成“17 个全平台生产级”。
例如 MQTT 的范围是报文/TCP 帧/握手，不等于完整自动重连、持久会话与 QoS 交付引擎。

## 本轮运行结果

同范围的 56 项从前一批 32 通过/24 失败变为 **33 通过/23 失败**，graph 恢复。
另补跑 91 项，扩展后的原始 147 项结果如下：

| 首个外显结果 | 入口数 | 说明 |
| --- | ---: | --- |
| 通过 | 51 | 只代表该入口 |
| C 声明冲突 | 75 | 涉及 67 个包；含依赖触发，不是 75 个独立根因 |
| 未解析符号 | 5 | cli、bson、xbot.agent、xmail（两个入口） |
| 异常/行为合同不符 | 8 | css、dns、fix、hcl、pkcs、srt、statistics、xhttp |
| XLIR 检查拒绝 | 5 | 四个可达未终结块、一个 async suspension result ABI |
| 其他 C 生成错误 | 1 | dotenv：identifier expected |
| 初始 45 秒超时 | 2 | volc.core、xui；不能仅凭超时认定运行死锁 |

合计 51 通过、94 失败、2 超时。按公共包去重：126 个受测，41 个所测入口全部通过，
85 个至少有一项失败或超时；另有 94 个公共包未选择。

扩大测试范围得到更多失败，不能直接说成与 56 项相比“又新增了 71 个回归”。
也不能把该选择集的通过比例外推为整个生态的完成率。
两个超时另以 180 秒复测，结果单独保存，不覆盖原始记录：

- volc.core 在约 66 秒后报 `x_volc_core_available` C 声明冲突，不能再记为原因不明超时。
- xui 的 import 入口仍超过 180 秒，没有诊断；尚未区分编译慢、编译器卡住或其他原因，
  不据此认定 GUI 运行死锁，也没有进行真实窗口交互验收。

因此按每个入口的最新观察，147 项为 **51 通过、95 失败、1 超时**，声明冲突为
76 个入口、68 个包。下面的逐项 JSON 保留初测，复测另有记录，未把同一入口重复计数。

### 需要整面修复，而非逐个关掉报错

1. **C/XL 原型一致性。** 不只是 bool/int，还有 C 整数宽度、const、句柄和返回类型。
   例如 `xcolor_valid` 的 C 返回 long long，XL 声明 bool。生成声明应与真实 C 头共同编译验证，
   不关闭类型检查，也不通过强转把 ABI/所有权问题藏起来。
2. **原生返回值所有权。** `chardet` 的 C detect_name 返回静态字符串，XL 却声明为 point
   并交给 takeCstr；该桥会调用 xrtFree。当前先被声明冲突挡住，但源码已显示借用/拥有合同错误。
   应和原型一起修，不能只将返回类型改到可编译。尚未将其计作本轮端到端崩溃复现。
3. **错误传播统一。** CSS/HCL validate 的正常“不合法”结果带出 XRT error，导致 false 变异常；
   FIX/PKCS 等原生错误被归为 IOError，而语言包装/测试期待 ValueError。
   当前生成桥把 XERR_PROTOCOL 归入 IO 路径，需统一规范和适配，而不是 catch 全部异常。
   同时不能把 OOM、资源超限等错误吞成 false。
4. **共享符号与 XLIR。** 缺 `xl6_xrt_os_args`、time now/fromUnix、TLS lease 等；
   HTTP async/try 等路径还有控制流与挂起结果 ABI 拒绝。应作为编译器/运行库联动任务，
   不能都记为包未实现。
5. **文本与字节。** 独立复现 string.byteLen 对含 NUL 文本截短、graph 名称混同、
   string.join 桥缺失。LZ4/LZMA/miniz/Snappy 仍把 string.len 传给 C 字节数参数，
   修声明时必须一起补中文、二进制、Buffer 和流式分块测试。

源码指针：[color C](../release/extlibs/color/color_native.c:78)、
[color XL](../release/extlibs/color/src/color.xl:1)、
[chardet C](../release/extlibs/chardet/chardet_native.c:29)、
[chardet XL](../release/extlibs/chardet/src/chardet.xl:8)、
[takeCstr](../src/cgen/xl6_ir_cgen_emit_async_support.c:526)、
[异常映射](../src/cgen/xl6_ir_cgen_emit_prelude.c:172)、
[长度桥](../src/cgen/xl6_ir_cgen_emit_string_bridges.c:14)。

还保留两个源码层面的场景风险：Memcached 客户端一次 recv 当完整应答，且空值/未命中不区分；
Agent 工作区只做文本前缀判断，读限额在读完整文件后按字符截断，部分公开参数未进入实际行为。
它们的辅助函数通过不构成完整客户端或 Agent 验收。

## 建议推进顺序

1. 先做一次**全生态 C/XL 声明、所有权、错误与运行库桥接一致性收口**。这是目前收益最大的横向工作。
2. 完成 CSV/graph 的专项、双语范例和官网；补 cString/floatEnv 的测试登记与线程/平台边界。
3. 恢复 BSON、LZ4、LZMA、miniz、Snappy、Zstd 六个历史重点库，连同字节长度、回调取消、OOM 和文件事务验收。
4. HTTP/邮件/SSH/Agent 按真实产品场景推进；AI 用固定小模型与结果，GUI 用真实交互和生命周期，不停在 import。
5. 在同一发布构建上统一跑首期候选；补 36 个缺页入口，核对 31 个旧生成页，页面标明真实能力与验证范围。

现阶段最合适的路线是把已完成的实现变为可重复交付的能力，而不是继续按包数量扩张。
