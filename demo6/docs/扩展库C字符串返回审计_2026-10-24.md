# 扩展库 C 字符串返回审计（2026-10-24）

## 2026-10-28 SQLite 返回链补查

生成 C 证实旧 `@owned string?` 只在接管点复用原生指针，随后
`__sqlite_take_owned` 的借用参数返回仍调用 `xlir_string_copy`。
因此此前“原生结果已接管”的证据不足以证明完整返回路径没有重复复制。
现删除该辅助函数，六个公开文本函数直接返回 `@owned string`；C 已
将 SQL NULL 规范化为空字符串，真正的 NULL 返回伴随 XRT 错误，
没有改变用户 string 类型、C ABI 或业务结果。

16 条薄接口/对象路径的 32 组分配预算先红后绿，明确约束原生结果
只需一次 XRT 分配；首个分配失败仍抛 MemoryError。SQL NULL、空串、
UTF-8、诊断、元数据、rowid 和连接关闭后持有结果均覆盖，Windows/Linux
八份语言用例/范例的 JIT/AOT 通过，44 个生成原型与 C 头一致。
同一基础范例 cgen 文件从 621789 缩至 611811 字节，只作源码对照，
不冒充最终 EXE/性能基准。C 实现未变，未重复刚通过的完整 C 故障矩阵。

必要的 SQLite 借用数据到 XRT 拥有内存副本、strlen、错误作用域和
释放检查仍存在；本项消除的是后续不必要的第二份正文副本，不是
“SQLite/XLang 全调用链零开销”认证。旧 Linux 偶发无诊断退出仍未关闭。

## 历史编译器边界（已被当前发布版覆盖）

以下记录保留首次审计时的失败证据，不描述当前编译器能力；现行口径
以文首“发布编译器同步后的状态”为准。

当时的源码版编译器已支持普通同步函数以 `cstring.take(pointer, releaser)`
接管 C 分配，调用方静态读取可共享 owner，避免复制正文。
但当时的 `xl6_sem_c_owned.c` 禁止 `export func ... as cstring`。
用 `md4c.html` 的实际包导出试编译，得到：

```text
[sem] C result markers require a synchronous language function with an explicit take adapter
```

因此只把包的公开 `as string` 改为 `as cstring` 会直接破坏导入；
这只约束 `cstring` marker 的公开签名，不等于 `takeCstr` 会复制。
对 XRT 分配的 NUL 结尾文本，当前 `takeCstr` 生成 `{pointer, strlen(pointer)}`，
普通 `string` 返回可直接转移该分配，失败清理也调用 `xrtFree`。
该实验性包修改已经撤销，未留下不兼容 API。
当时发布目录的 `xl.exe` 也早于源码版 `cstring`，不能作为新语法门禁。

`md4c` 的三个 HTML 结果是 `xrtBufferTake` 产生的独立 XRT 分配，
可由 `xrtFree` 释放；`version` 和 `last_error` 则是借用字符串，
不能接管。`argon2` 的一部分结果来自 `xrtTemp`，同样不能交给
`cstring.take` 释放。这个差异说明改造必须按 C 端所有权，而非按
XLang 的返回类型做全局替换。

## 历史实施条件（导出限制已解除）

1. 先明确导出 ABI：保留对 C 可用的普通 `string` 导出函数，编译器可为
   同模块静态调用生成私有拥有型结果路径；或者正式定义可从 C 安全使用、
   可释放的拥有型导出 ABI。不能仅删除语义检查。
2. 对已有 `takeCstr` 入口只核实原生所有权、XRT 分配器、NUL 合同和失败释放；
   不为了新语法重写已零拷贝的入口。`md4c` 的源码版独立 EXE 已能运行，
   但全包发布验收仍按包级门禁进行。
3. 对初始 147 个 `extern ... as string` 从 C 端分类：静态/借用/临时保持复制；
   独立拥有结果才接管。插件 DLL 未提供稳定释放器时不可猜测。
4. Buffer 转文本先确认 UTF-8、NUL 和长度合同；压缩、归档等二进制
   主 API 继续返回 Buffer。仅文本专用接口在证明等价后考虑所有权转移。

当前 `Buffer(handle)` 对原生 `xbuffer*` 调用 `xl6BufferAdoptV1`，直接
转移句柄所有权，**包装本身不复制字节**。`Buffer.text()` 调用
`xl6BufferTextV1`，先按实际长度验证，再由 `xl6TextCopy` 复制正文一次。
因此“Buffer 包装加转 string 固定多复制两次”不符合当前源码；这里
确实存在的一次复制是为了让 `string` 在 Buffer 销毁后仍独立存活，
且必须保留精确长度和内嵌 NUL。要消除这一次复制，需要在共享
Buffer/string 所有权层提供长度明确的移交能力，不能在各压缩包把
原始字节强行改成以 NUL 结尾的 `takeCstr`。本任务不改 xlang 主线。

`takeCstr` 的公开 `string` 返回当前确实可以直接接管 XRT 分配；
`cstring.take` 负责不同 releaser 的拥有型结果与跨静态调用共享 owner，
二者不能混为一谈。不要为了消除一次复制而引入
可悬空指针、双重释放或改变 `string` 公开语义。

## 已落地：BLAKE3 可变长文本结果

原 C 接口的 hex 字符串借用 XRT 临时区，面向 C 的生命周期合同保持不变。
XLang 的一次性普通/keyed/KDF、文件和流式摘要改走新增 `_owned` 原生入口：
摘要仍在临时区计算，但 hex 直接写入一份 XRT 堆分配，`takeCstr` 接管，
不再为 `extern as string` 复制整个可变长 XOF 文本。失败返回 NULL，
原生边界和 XLang 包装保留原来的错误类别。

当前源码版驱动的向量 JIT、独立 EXE、GCC 原生边界和分配故障注入均通过；
保留的生成 C 显示新结果只经过 `xl6_xrt_take_cstr`，`from_cstr` 仅用于
版本号和错误消息等借用文本。完整 `check_extlib_blake3.ps1` 在测试前被
既有 `third_party/blake3_impl.h` 与 vendor 清单 SHA256 不符挡住，
本轮未改动或重锁该第三方文件，因此不宣称整包门禁通过。
发布目录现有 `xl.exe` 还不认识包中此前已有的 `cbytes` 声明，
故此轮 XLang 验证使用当前源码驱动，不能把旧二进制的拒绝误记为本轮回归。

## 新增已完成包的返回路径复核

在 P0-P3 清单之外，继续检查了已有实际能力的 `csv`、`mqtt`，并对照
`extlib-c-owned-optimization.md` 中正在维护的 HTTP 协议构建器。这里的
“零拷贝”仅指 **C 已构造好的文本正文到语言返回值** 不再复制；生成文本
本身、拥有型分配及必要的对象快照不计入这个说法。

| 入口 | 原生内存合同 | 结论 |
| --- | --- | --- |
| `csv.Writer.finishText` | `xcsv_writer_take_text` 在缓冲尾部补 NUL，随后 `xrtBufferTake` 移交 XRT 分配；与 `finish()` 共用一次性结果状态 | `takeCstr` 接管正文，不走 `Buffer.text()`；追加终止字节时容量不足仍可能触发扩容 |
| `csv.Reader.field` | 当前行由 reader 持有；`xcsv_reader_field` 先 `xrtStrDup`，避免下一次 `next()` 后悬空 | 这一份所有权副本必需，语言侧 `takeCstr` 不再复制 |
| `mqtt.frameToHex` 及 hex 便捷入口 | `xmq_frame_to_hex` 使用 `xrtHexEncodeNew` 创建独立分配 | 语言侧 `takeCstr` 接管；原始二进制帧继续保持 `Buffer` |
| HTTP Headers/Cookies/MediaType/QueryParams/form 构建器 | 专项改造增加了直接移交的文本出口，保留 C 侧 Buffer 出口 | 已有专项生成代码与分配计数验收；这些包由独立上下文维护，本清单不重复修改 |

当前 `release/xl.exe run test/cases/extlib_mqtt.xl` 和
`release/xl.exe run release/extlibs/csv/test/boundaries.xl` 均通过。
`mqtt` 的其余网络门禁、`csv` 的全包 AOT 门禁没有因为本次返回路径复核
而重新签收。

`cstring/cbytes` 目前可为普通导出函数生成**私有静态特化**，其公开 ABI
仍是普通值；这不意味着允许把公开签名直接改为 `export func ... as
cstring`，也不意味着已有 `takeCstr` 出口必须重写。借用文本和插件
内部结果无可证明的独立所有权时，不能通过 `cstring.take` 消除复制。
对固定很短的摘要、版本号、状态名新建一套 `_owned` C ABI 往往增加代码、
分配和释放成本，不能只按“少一次 memcpy”判断更快。

本次复核后仍有三类未验收链路或不能在普通包内安全消除的正文复制：

1. `volc.core` 的在线响应已消除语言桥接的额外正文复制，但 XLang 导入
   仍被 HTTP 依赖链阻断；含 NUL 的响应尚无长度安全的公开接口。
2. `onnxruntime`、`opencv`、`rapidocr` 的部分 JSON/文本来自仅有 DLL 的
   桥接层。没有源码或专用释放器，不能将借用指针假定为拥有型结果。
3. 解压文本、归档读取、串口及共享内存等长度敏感入口必须保留内嵌 NUL。
   `Buffer(handle)` 不复制字节，当前 `Buffer.text()` 仅复制正文一次；
   若要消掉这一次，需要运行时提供带长度的安全所有权转移，而不是
   用 `takeCstr` 截断数据。本普通扩展库任务不改动 xlang 主线。

## 清单外已实现包的补查

以同时具有包说明和测试目录的发布包为线索，补查现行 `src/*.xl` 的
`extern ... as string`、`takeCstr` 与 `Buffer.text()` 入口。以下结论只针对
列明的返回路径；这些包由其他上下文维护，且 HTTP、邮件、SSH、WebSocket
目录正在并行修改，因此本轮不改动其源码，也不把静态审计冒充发布验收。

| 包与入口 | 当前内存合同 | 处理结论 |
| --- | --- | --- |
| `xws` 的文本帧 | 原生返回独立 `xbuffer*`，语言以 `Buffer(handle).text()` 按长度构造字符串 | WebSocket 文本帧允许 U+0000；不能用 `strlen`/`takeCstr`。包装 Buffer 不复制，文本转换复制一次。 |
| `xssh` 的文本结果 | 原生返回独立 `xbuffer*`，同样按长度转文本 | 命令输出等不能假定无 NUL；保留精确长度路径。错误名与错误消息是借用短文本，`extern as string` 的稳定副本必要。 |
| `xmail` 的 MIME 报文及 SMTP/POP3/IMAP 文本 | 原生返回 `xbuffer*`，公开 `compose` 和客户端便捷入口使用 `Buffer(...).text()` | 当前每次文本转换复制正文一次；可作为将来“带长度接管 Buffer 为 string”的候选，但不能单凭协议名称假定每个结果均为 NUL 结尾且无内嵌 NUL。错误文本仍按借用处理。 |
| `xhttp.body`、`xhttp.client`、`xhttp.multipart`、`xhttp.form_data` 的正文/表单文本 | 主要按 `Buffer.text()` 转换，原始 HTTP 字节仍有 Buffer 入口 | HTTP 正文和表单值可能含 NUL；保留长度语义。正在并行修改，不在普通包任务中穿插重写。 |
| `xhttp`、`xhttp.protocol`、`xregex`、`aho_corasick` 的文本构建路径 | 已有“无 NUL 且尾部可终止时直接移交，否则按 Buffer 长度复制”的分支 | 该分支避免普通文本再复制，同时不截断含 NUL 的合法结果；不应机械改写。 |

此轮没有发现可在**不修改主线、又不破坏长度/生命周期合同**的前提下
继续消除正文复制的普通包入口。若要统一优化上述长度敏感结果，应在
语言运行时提供 `xbuffer*` 到带长度 `string` 的安全所有权转移，并测试
空值、NUL、UTF-8 校验、失败清理和原 Buffer 析构；不能在每个扩展包
各造一个只适用于 C 字符串的替代接口。

## 2026-10-24 再次逐类核验

本次从 214 份 `xlang.package.json` 对应的 `src/**/*.xl` 重新扫描：
158 包、690 行命中单行 `extern ... as string`；69 包、211 行命中
`__xl_runtime.takeCstr`；25 包、47 行命中 `.text()`。这些是源码
候选数，不是 memcpy 次数，也不把尚未完成的占位包计为发布能力。
此前快照的声明数与本次不同，HTTP 等目录正由独立任务并行改动，
因此以本次扫描作为这一时点的入口清单，不推断差异全部来自优化。

当前源码版 `ini` 独立 EXE 的生成 C 中，`xl6_xrt_take_cstr` 构造的
