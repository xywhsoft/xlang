# DEMO6 扩展库生态重整（2026-10-12）

本文件确定首期生态的投入次序，不把包目录数、import 成功、名称表查询或历史单项测试当作完整可用证明。旧的 162 包建设 Spec 和 2026-09-28 状态报告是历史计划与限定证据；后续推进以本文件的优先级为准，实际可用范围仍以当次构建的测试记录为准。

## 判断标准

对标的是 Python 和 Go 的日常开发覆盖面，不是照抄它们的包名或总包数。两者官方标准库均优先覆盖文件/进程、文本和数据格式、网络、并发、测试、日志等基础工作；数据库或大型专业能力再由独立驱动/生态承担。参考：[Python 标准库目录](https://docs.python.org/3/library/index.html)、[Go 标准库目录](https://pkg.go.dev/std)。

按以下顺序决定投入：实际使用频率与复用面、是否填补开发闭环、现有实现与 XRT 复用程度、跨平台和测试成本、长期维护与安全成本。已经有真实后端的包不按总代码行数淘汰；只有辅助常量或格式片段的包，不因名称响亮获得优先级。默认标准库已提供的能力不再另造同名扩展库。

## 新的开发优先级

**P0：完成日常开发闭环，优先修好而非增加名字。** `cli`、`dotenv`、`ini`、`toml`、`yaml`、`csv`、`sqlite`、`zip`、`tar`、`xregex`，加上已在标准库的 file/path/dir/process/json/HTTP/TCP/TLS/任务/日志。目标是单文件 CLI、数据导入、Web 服务、配置与测试任务可直接完成。重点是当前正式构建上的端到端运行、UTF-8/二进制边界、错误合同、生命周期与跨平台回归；`xhttp.client` 仍有编译耗时/集成缺口，不能称为已经稳定的 HTTP 客户端。

**P1：应用交付必需的互操作。** `redis`、`xws`、`xmail`、`xssh`、`jwt`、`argon2`、`oauth2`、`watch`、`xml.etree`、`md4c`、`gettext`、`opentelemetry`。数据库重点选择一个经过真实服务测试的远端驱动（优先在 `postgresql` 与 `mysql` 中基于现有实现核定），避免同时维护多个只有 DSN/类型名的“驱动”。消息系统先把已有 MQTT 的完整客户端合同厘清，再决定 NATS/Kafka 等后续投入。网络和认证必须包含失败恢复、TLS、超时与取消测试。

**P2：有真实后端的垂直能力，独立交付，不拖累基础发布。** `onnxruntime`、`rapidocr`、`opencv`、`xfeat`、`dinov3`、`xui`、`xge`、`xbot` 以及设备/平台包。它们不是占位库，但依赖模型、设备、GUI 或平台环境；按各自实际公开范围与可重复环境验收，必要时做可选生态包，不要求进入每个 xl 发布包。

**P3：需求驱动的专用库。** 地理、金融、音视频、Kubernetes、GPU、大型科学计算和多种数据库引擎暂不并行扩张。尤其旧 `deferred-large` 名单是预算候选，不自动等于“确定超 10000 行”或“没有后端”。先确认真实能力、调用方和外部依赖，再决定保留、退出版目录或独立仓库。`mysql`、`faiss` 等目录有正在进行的修改，本次不移动；仍不得把它们的辅助 API 宣称为完整驱动/索引。

## 继续清理的规则

1. 每个包写明一个可运行的用户任务、实际后端、支持平台、外部依赖和未实现边界。只有名称、常量、状态枚举或 helper 的包不得进入发布目录；若确有通用价值，先评估并入现有标准库或工具包，而不是保留误导性的产品名。
2. 当前包有真实后端、已有用户工程依赖或未提交的并行修改时，不按旧文档直接移动。先查 manifest 和源码 import 依赖，再查测试、范例、网站页面与二进制资产；迁移必须让发布索引、测试门禁及文档一致。
3. 首期准入必须在同一构建上通过 XL JIT/AOT、C ABI/示例、正常与失败路径、资源释放、目标平台集成、可重复的功能演示；官网只展示已核定范围。专项通过不能被扩成全 API 认证。
4. 从本次起生态指标是“能可靠完成的开发任务”与“合格包数”，不是活动目录总数。新增包先证明需求和验收环境，再写代码。
