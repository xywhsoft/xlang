# xlang DEMO6 异常处理与文档注释设计

本文档记录 DEMO6 对异常处理、断言、高级错误模型和 `#doc ... #end` 文档注释的正式设计口径。

本设计必须服从以下原则：

- 用户侧写法保持简单直接。
- 运行时错误模型保持统一、可诊断、可跨 C/XRT 传递。
- 能由 XRT 承担的错误对象、内存管理、字符串处理和错误状态，应优先进入 XRT。
- `#doc ... #end` 是 ABI 元数据来源，不是普通注释，也不是运行时代码。

## 1. 异常处理目标

异常处理用于表达程序运行期的非正常路径。

DEMO6 采用一套统一模型：

- xlang 源码中抛出异常时，只允许抛出字符串描述。
- 编译器和运行时内部将字符串包装为统一的 `error` 对象。
- `catch` 捕获到的是 `error` 对象，不是裸字符串。
- XRT/native/C 侧错误也应转换为同一种 `error` 对象。

这样可以同时满足：

- 用户写法简单。
- 运行时信息完整。
- C 混编边界稳定。
- ABI 元数据 可以描述函数是否可能抛错。
- 扩展库可以长期复用同一套错误模型。

## 2. try/catch/finally

基础语法：

```xlang
try
    work()
catch e
    print(e.message)
finally
    cleanup()
end
```

允许形式：

```xlang
try
    work()
catch e
    handle(e)
end

try
    work()
finally
    cleanup()
end

try
    work()
catch e
    handle(e)
finally
    cleanup()
end
```

规则：

- `try` 块内发生异常时，优先进入 `catch`。
- `catch name` 声明一个只在 catch 块内有效的局部变量。
- catch 变量类型为 `error`。
- 长期目标：`finally` 无论正常结束、异常、return、break、continue 都必须执行。
- 当前 RC 实现边界：为了避免控制流穿过异常边界时破坏清理顺序，`try/catch/finally` 内暂不允许 `return`、`break`、`continue`，编译期直接报错。后续只有在引入统一控制流帧后，才放开这一限制。
- 如果 `finally` 中抛出新异常，新异常优先传播，原异常不得丢失，应进入新异常的 `cause` 或 `suppressed` 信息。
- `catch` 和 `finally` 至少存在一个。

当前阶段不设计多个 catch 分支和 typed catch。后续如果需要按错误种类过滤，应基于 `error.kind` 或 XRT error kind 继续扩展。

## 3. throw

DEMO6 去掉用户侧 `Error("boom")` 写法。

标准写法：

```xlang
throw "boom"
```

也允许字符串表达式：

```xlang
string message = "file not found"
throw message
```

规则：

- `throw expr` 中的 `expr` 必须是 `string`。
- 如果静态类型明确不是 `string`，编译期报错。
- 当前 RC 实现要求表达式能静态确认为 `string`；`var` 动态字符串暂不进入 `throw`，避免异常边界携带不确定类型。
- `throw string` 内部创建 `error` 对象。
- 默认错误种类为 `Error`。
- 错误对象必须记录源码位置：file、line、column。
- 错误对象应尽量记录 function、module、package，用于堆栈和 ABI 元数据 诊断。

示例：

```xlang
func readConfig(string path)
    if path == "" then
        throw "config path is empty"
    end
end
```

### 3.1 rethrow

为了保留原始错误信息，catch 块内允许空 `throw` 表示重新抛出当前异常：

```xlang
try
    work()
catch e
    log(e.message)
    throw
end
```

规则：

- 空 `throw` 只允许出现在存在当前异常的上下文中。
- 空 `throw` 不创建新错误。
- 空 `throw` 必须保留原错误的 kind、message、source、cause、stack。
- 在普通代码块中使用空 `throw` 是编译期错误。

## 4. assert

断言语法：

```xlang
assert condition
assert condition, "message"
```

示例：

```xlang
assert count > 0
assert path != "", "path is empty"
```

规则：

- `condition` 必须是 bool 表达式，或能明确转换为 bool 的表达式。
- message 必须是能静态确认为 `string` 的表达式；`var` 动态字符串暂不作为断言消息。
- 断言失败时抛出 `AssertError`。
- 没有 message 时，运行时错误信息使用默认文本，并尽量包含断言表达式原文。
- 断言失败产生的错误对象必须记录源码位置。

推荐内部降低形式：

```xlang
if not condition then
    throw "assert failed"
end
```

但实际生成的错误种类应为 `AssertError`，不能退化为普通 `Error`。

## 5. error 对象

`error` 是运行期错误对象类型，由类型注册系统预声明，不作为词法保留字。

建议字段：

```text
kind        错误种类，例如 Error、AssertError、IOError
message     面向用户的错误描述
code        可选错误码
data        可选附加数据
cause       可选原因错误
suppressed  被 finally 等控制流覆盖但不应丢失的错误列表
stack       调用栈或轻量栈信息
source      源码位置
native      native/C/XRT 错误来源信息
```

`source` 建议包含：

```text
file
line
column
function
module
package
```

`native` 建议包含：

```text
library
symbol
message
code
```

设计要求：

- xlang 源码中不直接构造 `error`。
- `throw string` 由编译器和运行时创建 `error`。
- `assert` 创建 `AssertError`。
- XRT/native/C 错误通过桥接函数创建对应 kind 的 `error`。
- error 对象应由 XRT 提供基础实现，xlang 不应长期维护一套重复对象模型。

## 6. C/XRT 错误桥接

XRT 是 xlang 与 C 的共同基础层。

建议方向：

- XRT 提供统一 `xerror` 对象。
- XRT last error 可以转换为 `xerror`。
- xlang 的 `error` 直接映射或包装 XRT `xerror`。
- xcall 调用帧携带 `error` 槽位。
- 普通 C ABI 函数是否检查 XRT last error，由 ABI 元数据 中的 `throws` 声明决定。

示意：

```json
{
  "name": "readText",
  "abi": "cdecl",
  "throws": true
}
```

规则：

- `throws: true` 的 C 函数调用后，编译器生成 XRT 错误捕获代码。
- 捕获到 XRT 错误时，转换为 xlang `error` 并进入异常传播。
- 没有 `throws` 声明的普通 C 调用不强制检查 last error，避免隐藏成本。

## 7. #doc 文档注释

`#doc ... #end` 用于给后续声明附加文档元数据。

它不是普通注释。编译器必须保留它，并写入 AST/ABI 元数据。

基础形式：

````xlang
#doc
desc:
    计算两个整数的最大值。
param left:
    左值。
param right:
    右值。
return value:
    较大的整数。
note:
    参数按普通 int 规则比较。
example:
    ```xlang
    print(max(1, 2))
    ```
#end
export func max(int left, int right) as int
    if left > right then
        return left
    end
    return right
end
````

## 8. #doc 字段格式

文档块采用“顶格字段头 + 缩进正文”的行级格式。

字段头必须从行首开始：

```text
desc:
param name:
return name:
note:
example:
```

字段正文必须缩进至少一个空格或一个 tab。

字段正文可以多行，空行会被保留。

字段正文只作为文档文本处理，不进入 xlang 词法、语法或语义解析。

例如 `example:` 中的 Markdown 代码块：

````text
example:
    ```xlang
    print(max(1, 2))
    ```
````

其中的 Markdown 代码围栏、`print(max(1, 2))` 和代码围栏结束标记都只是 `example` 字段的文本内容，不会被编译器当作 xlang 源码解析。

允许单行短写：

```xlang
#doc
desc: 当前缓存数量。
#end
export int cacheCount
```

单行短写也可以继续追加缩进正文：

```xlang
#doc
desc: 读取文本文件。
    路径使用 UTF-8。
    失败时抛出异常。
#end
func readText(string path) as string
end
```

解析规则：

- `#doc` 开始文档块。
- `#end` 结束文档块。
- 文档块内部只识别顶格字段头。
- 缩进内容全部属于当前字段。
- 字段正文保留换行。
- 编译器必须对字段正文执行公共缩进去除。
- 公共缩进去除只处理字段正文，不处理字段头。
- 未知字段是编译期错误。
- 没有字段头的裸文本是编译期错误。

### 8.1 字段正文缩进处理

字段正文缩进采用按字段独立 dedent 的规则。

处理步骤：

1. 收集同一个字段下的所有物理正文行。
2. 忽略空行和只包含空白的行，计算其余正文行的最小行首空白长度。
3. 从每一行非空正文中移除这个最小行首空白长度。
4. 空行保留为空行。
5. 字段内部的相对缩进必须保留。

示例源码：

````xlang
#doc
example:
    ```xlang
    if ok then
        print("ok")
    end
    ```
#end
func demo()
end
````

写入 ABI 元数据 的 `example` 文本为：

````text
```xlang
if ok then
    print("ok")
end
```
````

说明：

- `example:` 下方每一行前面的 4 个空格只是为了表示这些行属于 `example` 字段。
- dedent 后，文档正文不再携带这 4 个结构性缩进。
- `print("ok")` 前面的 4 个空格是代码块内部的相对缩进，必须保留。

单行短写和后续缩进正文组合时，短写文本作为第一行，不参与公共缩进计算：

```xlang
#doc
desc: 读取文本文件。
    路径使用 UTF-8。
    失败时抛出异常。
#end
func readText(string path) as string
end
```

写入 ABI 元数据 的 `desc` 文本为：

```text
读取文本文件。
路径使用 UTF-8。
失败时抛出异常。
```

## 9. #doc 字段语义

### desc

说明函数、类、native-backed class、变量、常量、typedef、extern、export 等声明的用途。

规则：

- 每个文档块最多一个 `desc`。
- `desc` 推荐放在第一项。

示例：

```xlang
#doc
desc:
    表示一个二维点。
#end
class Point
end
```

### param name

说明参数。

规则：

- `name` 必须对应后续函数、方法、构造、extern 函数或 native-backed class extern 方法中的参数名。
- 可选参数和普通参数一样使用 `param name`。
- 数组可变参数使用 `param ...`。
- 字典可变参数使用 `param ***`。
- 重复描述同一个参数是编译期错误。

示例：

```xlang
#doc
desc: 打印多段文本。
param ...:
    要打印的文本片段。
#end
func printAll(...)
end
```

### return name

说明返回值。

规则：

- 单返回值可以使用 `return:` 或 `return value:`。
- 多返回值建议使用 `return name:`。
- 如果返回值没有名字，可以使用 `return 0:`、`return 1:` 表示位置。
- 无返回值函数不应出现 `return` 字段。

示例：

```xlang
#doc
desc: 拆分用户名和域名。
return name:
    用户名。
return domain:
    域名。
#end
func splitEmail(string email) as (string, string)
end
```

### note

补充说明。

规则：

- `note` 可以出现多次。
- 每个 `note` 作为独立段落写入 ABI 元数据。
- 适合记录边界条件、性能说明、线程安全说明、平台差异。

### example

使用范例。

规则：

- `example` 可以出现多次。
- 正文按原样保留，适合放 Markdown 代码块。
- 示例不参与语义检查，后续可以增加 doctest 能力，但不属于当前阶段。

## 10. #doc 绑定规则

`#doc ... #end` 自动绑定到后续第一个可文档化声明。

可文档化声明包括：

- `func`
- `class`
- native-backed class
- `extern func`
- `extern "c_symbol" Type name`
- `export func`
- `export Type name`
- `const`
- `var`
- `typedef`

规则：

- 文档块和目标声明之间允许空行和普通注释。
- 文档块和目标声明之间不允许出现其他语句。
- 如果后续不是可文档化声明，编译期报错。
- 一个声明最多绑定一个文档块。
- 连续两个未绑定文档块是编译期错误。
- 文档绑定后进入 AST，并由 ABI 元数据 生成器输出。

当前 RC 实现中，`#doc` 只绑定顶层声明以及 `class` / native-backed class 成员声明，不作为函数体内任意局部语句的前缀。这样可以保持“文档块生成ABI 元数据”的定位清晰，并避免与普通语句块产生语法二义性。

## 11. ABI 元数据 表示

当前 RC 实现中，ABI 元数据 文档结构为：

```json
{
  "doc": {
    "raw": "#doc\n...\n#end\n",
    "fields": [
      { "kind": "desc", "text": "计算两个整数的最大值。" },
      { "kind": "param", "name": "left", "text": "左值。" },
      { "kind": "param", "name": "right", "text": "右值。" },
      { "kind": "return", "name": "value", "text": "较大的整数。" },
      { "kind": "note", "text": "参数按普通 int 规则比较。" },
      { "kind": "example", "text": "```xlang\nprint(max(1, 2))\n```" }
    ]
  }
}
```

要求：

- ABI 元数据 是机器生成的接口事实来源。
- 用户不手写 ABI 元数据。
- `#doc` 是源码侧维护文档的主要入口。
- `raw` 保留原始文档块，便于调试和未来重新解释字段。
- `fields` 是稳定的机器字段数组，便于后续生成帮助文档、HTML 文档、C 头文件注释和包文档。

## 12. 词法注意事项

xlang 已有 time literal：

```xlang
#2026-06-18#
```

因此 lexer 必须优先识别语句边界处的 `#doc`。

规则：

- `#doc` 只在语句边界有效。
- `#doc` 必须单独成行，行内不能跟其他 token。
- `#end` 必须单独成行，行内不能跟其他 token。
- 不满足上述规则时，按词法或语法错误处理。
- 普通 `#...#` 仍然按 time literal 处理。

## 13. 当前阶段实现清单

本轮实现异常与文档注释时，应至少完成：

- lexer 支持 `#doc ... #end` 文档块 token。
- parser 支持 doc block 绑定后续声明。
- AST 保存文档元数据。
- ABI 元数据 输出 doc 字段。
- parser/AST 支持 `try/catch/finally`。
- parser/AST 支持 `throw string_expr` 和空 `throw`。
- parser/AST 支持 `assert expr` 和 `assert expr, string_expr`。
- 语义检查 `throw` 表达式类型必须为 string。
- 语义检查 `assert` message 必须为 string。
- catch 变量注册为 `error` 类型。
- C codegen 生成统一异常传播逻辑。
- XRT/native 错误桥接预留 `throws` 路径。
- 正向、负向测试和示例程序覆盖全部写法。
