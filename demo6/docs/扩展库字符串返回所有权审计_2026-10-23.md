# 扩展库字符串返回所有权审计（2026-10-23）

## 范围和判断标准

扫描 `release/extlibs` 的 214 个包目录中 `src/*.xl` 的字符串返回声明、
`takeCstr` 和 `.text()` 路径；对普通维护清单中的 100 个已有实际能力包，
逐项检查可能把原生 Buffer 再转成字符串的调用点。另检查新近完成的
`aho_corasick` 及独立维护包的同类调用点。此处的“扫描”不是对每个 C
函数体完成动态所有权证明；新增原生入口时仍须核对生产者的分配器、
生命周期、长度和释放方法。

- `__xl_runtime.takeCstr` 将 XRT 分配的 NUL 结尾内存直接作为普通
  XLang `string` 接管；现有这种路径不需要改成 `cstring.take`。
- `extern ... as string` 从 C `const char*` 构造独立字符串，适合静态、
  临时或对象借用指针；不能接管或释放这些指针。已核对的 Argon2、
  BLAKE2/BLAKE3 摘要文本来自临时存储，`money.symbol` 来自静态表，
  `watch.path` 借用监视器内部路径。
- `cstring` / `cbytes` 可在同步局部作用域无复制地读取 C 分配，
  但返回普通 `string` / `bytes` 时仍物化一份。不能据此把已有的
  零拷贝 `takeCstr` 改成载体再返回。
- 新的 `cstring.take(pointer, releaser)` 适用于非 XRT 分配器的拥有型
  C 文本，并要求显式的释放函数；它不会让静态表、临时缓存或对象内部
  借用指针变成可接管内存。已使用 `takeCstr` 的 XRT 文本返回不需要
  改写为 `cstring`，否则反而多一个拥有者记录。
- 仅当原生 Buffer **确定包含无嵌入 NUL 的 UTF-8 文本**、使用 XRT
  分配器、且所有权可移交时，才在桥接层补终止字节、`xrtBufferTake`，
  再由 `takeCstr` 接管。补终止字节时容量不足可能引发扩容；优化去掉
  的是随后必然发生的整串 `Buffer.text()` 复制，而非承诺绝无重分配。

## 已优化的文本结果

| 包 | 原路径 | 新路径 |
| --- | --- | --- |
| `csv` | `Writer.finish().text()` | `finishText()` 接管内存写入器缓冲；`stringify` 使用此路径，保留 `finish() as Buffer` |
| `toml` | 原生 `xbuffer*` → `Buffer.text()` | `xtoml_stringify_text` → `takeCstr` |
| `ini` | 原生 `xbuffer*` → `Buffer.text()` | `xini_stringify_text` → `takeCstr` |
| `netrc` | 原生 `xbuffer*` → `Buffer.text()` | `xnetrc_stringify_text` → `takeCstr` |
| `xml.dom` | 原生 `xbuffer*` → `Buffer.text()` | `xdom_stringify_text` → `takeCstr` |
| `xml.etree` | 原生 `xbuffer*` → `Buffer.text()` | `xetree_stringify_text` → `takeCstr` |
| `plist` | XML `dumps(...).text()` | 仅 XML 使用 `xplist_stringify_text` → `takeCstr`；二进制仍使用 Buffer |
| `clipboard` | XRT UTF-8 内存或文本 Buffer → `xrtValueString` 复制 → 释放来源 | 已拥有的 UTF-8 字符串和纯文本 Buffer 改用 `xrtValueStringTake`；借用文本仍独立复制 |
| `clipboard.get_text` | Windows UTF-8 转码 → `xvalue` 接管 → `string(var)` 再复制 | 原有 C `xvalue*` API 复用同一读取核心；XLang 直接接管 XRT UTF-8 内存，保留空结果和错误行为 |
| `clipboard` 其他文本接口 | JSON Buffer、格式名与文件名 → `xvalue` 接管 → `string(var)` 再复制 | `formats_json`、`image_info_json`、`format_name`、`get_file` 共用各自原生生产路径；C 保留 `xvalue*`，XLang 接管 NUL 结尾的 XRT 文本 |
| `json.patch` | `encodePointer` 的 XRT 编码结果 → `xrtValueString` 复制 → 释放来源 | 原生 `xvalue` 路径使用 `xrtValueStringTake`；嵌入 NUL 仍保留精确长度 |
| `vcard` | 解码后的 XRT Buffer → `xrtValueString` 复制 → 释放 Buffer | 解析字段时取走 Buffer 内存，再交给 `xrtValueStringTake` |
| `ical` | 解码后的 XRT Buffer → `xrtValueString` 复制 → 释放 Buffer | 文本属性和普通属性共用 Buffer 接管路径，借用参数仍按需复制 |
| `cbor` | 不定长 bytes/text 分块 Buffer → `xrtValueBytes`/`xrtValueString` 复制 → 释放 Buffer | 完整分块结果改用长度感知的 `xrtValueBytesTake`/`xrtValueStringTake`；定长输入仍复制借用字节 |
| `com` | COM `BSTR` → XRT 分配的 UTF-8 → `xrtValueString` 复制 → 释放 UTF-8；文本属性另复制到复用缓冲 | `invoke` 值由 `xrtValueStringTake` 接管；文本属性直接转换到复用缓冲，保留 NUL 拒绝 |
| `dns.resolve` | `xrtNetAddrString` 分配地址文本 → `xrtValueString` 复制 → 释放文本 | `xrtValueStringTake` 接管地址文本 |
| `dns.encodeName` | XRT 十六进制文本 → 线程本地 Buffer 复制 → `extern string` 再复制 | C 直接交付 XRT 拥有的文本，XLang 通过 `point` ABI 薄桥调用 `takeCstr`；C 调用方使用 `xrtFree` |
| `shellwords` | 每个完成的词从 XRT Buffer 复制成 `xvalue` 字符串，再清空并复用 Buffer | 直接取走词缓冲交给 `xrtValueStringTake`；空词与分配失败仍由原有门禁覆盖 |
| `sitemap` | XML 字段文本先写入 XRT Buffer，再复制成 `xvalue` 字符串 | 完成字段校验后取走缓冲交给 `xrtValueStringTake`；下一字段按需重新分配 |

再次沿普通维护清单核对公开字符串返回：`hcl` 查询、`css` 文本操作、
`semver` 格式化及 `md4c` HTML 已经返回 XRT 拥有的文本并由
`takeCstr` 接管；`watch.poll`、`ini.get` 和 DOM/ElementTree 属性读取
同样在公开 XLang 路径接管独立文本。这些路径无需再包一层 `cstring`
或 `Buffer`。`dotenv.get`、`watch.path` 借用各自对象内部的文本，
返回独立 `string` 必须复制，不能移交对象仍拥有的指针。

`argon2` 的编码结果/盐、`blake2` 的摘要文本以及同类哈希包的十六进制
结果使用临时区或短暂缓存；`extern ... as string` 的复制保障结果在下一次
原生调用后仍有效。它们的典型结果有严格的短长度上界，单为消除这次
短拷贝而改用逐次堆分配，可能增加分配开销和包级桥接代码；没有基准
证明前不将这种改动计为性能优化。静态枚举名称与错误消息也属于借用
指针，不能按拥有型返回释放。

本轮复核了扩展库原生代码中的 `xrtValueString` 构造点：`json5`、`msgpack`、
`bson`、`fix`、`redis`、`mqtt` 等读取借用的输入或解析器窗口，
`graph`、`skiplist`、`plist` 等读取对象内部存储，`sitemap_robots` 读取
输入切片；这些来源不能移交。少数短字段使用可复用解析缓冲，强行取走会
改变其分配策略；没有把“减少一次 memcpy”误记为一定降低总分配成本。

`json.patch` 和 `dns.resolve` 的公开 XLang 包装仍有 `string(var)`，当前代码生成
会把 `xvalue` 字符串复制成 XLang `string`。`clipboard` 的五条文本返回已改成
拥有型文本直通；其他列出的路径**尚不是端到端零复制**。要继续消除最终转换，须使用直接的拥有型
字符串返回路径；其中 `json.patch` 还必须保持嵌入 NUL 的长度语义，不能
直接改用仅接收 NUL 结尾文本的 `takeCstr`。本线程不改动主线转换规则。
`redis.encode` 的 RESP 帧和 `skiplist.get` 的值也都按显式长度保存，
可能含内嵌 NUL；它们的 `string(var)` 不能用 C 字符串出口替换。

## 保留原样的路径

普通维护清单剩余的 `.text()` 调用分为以下几类，不可直接转为
NUL 结尾 C 字符串：

| 类别 | 包 | 原因 |
| --- | --- | --- |
| 解压后的文本便利接口 | `brotli`, `bz2`, `gzip`, `lz4`, `lzma`, `miniz`, `snappy`, `zstd` | 解压结果首先是任意字节，可能含 NUL；`Buffer` 保留精确长度 |
| 原始设备/共享内存读取 | `serial`, `sharedmem` | 内容不保证 UTF-8 或无 NUL |
| 归档条目文本读取 | `tar`, `zip` | 归档数据同样是任意字节 |
| UI 元素 | `ui.auto` | `.text()` 是元素方法，不是 `Buffer.text()` 转换 |

`aho_corasick` 的模式文本保留精确字节长度，底层模式可含 NUL；
目前 `xrtBufferFrom` → `Buffer.text()` 有复制，但 `takeCstr` 会截断，
不能作等价替换。回调式 replace 的输出同理。若要进一步优化，需要
**长度感知的拥有型文本移交**并验证 UTF-8，而不是把二进制指针伪装
为 C 字符串。

`xhttp.*`、`xmail`、`xssh`、`xws` 等 XRT 专门维护包，以及 XUI/XGE、
`xbot.agent`，本次只纳入静态候选扫描，不在普通扩展库线程内修改；
其中 HTTP 正文、Multipart 等同样可能含 NUL，不能批量替换。

## 尚未改动的真实候选

`sqlite` 的文本列、列名、错误消息及行号文本通过 `xsqlite_text` 复制到
XRT 临时区，再由 `extern ... as string` 复制到 XLang。C 借用式 API
必须保留，XLang 可另增拥有型文本入口，从 SQLite 借用值直接复制一次
到最终 XRT 分配，再 `takeCstr`。当前 `xl run examples/extlibs/sqlite_basic.xl`
在包内 `sqlite.xl:550:28` 的 `rows.append(stmt.row())` 处报
`XLIR C emitter runtime operation ABI is unresolved`；已有
`dev/extlib_blockers/sqlite_dynamic_call_abi.md` 记录。主线恢复前不改包，
否则无法验收错误、生命周期及 JIT/AOT 一致性。

`volc.core` 的规范查询、JSON 转义和签名预览先生成 XRT 分配的文本，
再通过 `xvolc_return_text` 复制进线程结果槽；公开 XLang `extern ... as string`
随后再复制一次。C 门禁通过，但当前 `xl run examples/extlibs/volc_core.xl`
在 `xhttp.multipart/src/xlang/xhttp_multipart.xl:352:23` 因未知类字段失败，
无法验证 XLang 接管桥。依照扩展库并行开发边界，暂不修改该包；
导入链修复后，应保留 C 的线程槽返回合同，为 XLang 增加拥有型文本出口，
并分别验证连续调用、错误返回、线程隔离和分配失败。HTTP 响应体目前
从长度化字节视图进入文本槽，可能含 NUL；此路径不能直接套用
`takeCstr`，须先决定长度化结果合同。

`uia` 的 UTF-16 属性文本写入可复用的 UTF-8 缓冲，快照 JSON 也使用
可复用的增长缓冲，随后 `extern ... as string` 复制一次。理论上可拆下
缓冲交给 XLang，但会取消跨调用复用，且 C 当前承诺返回借用指针；
这不是单纯删除 `memcpy` 就能保证更快的路径。Windows UIA 的真实
工作负载和长期分配曲线未测量前，保留现状，不把重分配换来的
“零复制”计作已完成优化。`onnxruntime`、`opencv`、`rapidocr`
桥接 DLL 没有本机源码，按插件调用贯通验收，不对其内部返回实现
声称已完成所有权优化。

## 后续边界

1. 对新增 C 函数的 `extern ... as string` 声明，逐个核对返回的是
   静态/借用/临时指针还是调用方拥有的内存；仅凭返回类型无法判断。
2. 如要消除 `aho_corasick` 等长度感知文本的中间复制，应先在语言
   运行时定义 `(pointer, length, releaser)` 到普通 `string` 的安全
   拥有型入口，包括 UTF-8、嵌入 NUL 和错误路径合同，再修改扩展库。
3. 不为压缩、归档、网络正文和共享内存的任意字节内容使用 C 字符串
   移交；它们的首要正确性是保留长度和二进制内容。
