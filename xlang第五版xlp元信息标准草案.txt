================================================================================
xlang 第五版 XLP 元信息标准草案
================================================================================

版本：v5.0-draft2
适用范围：xlang / xrt 外部扩展包
目标：一次性定义 `.xlp` 包、`xlp.json` 元信息文件、依赖规则、版本绑定 ABI、导出项、类型桥接、协议声明与加载规则



================================================================================
一、定位
================================================================================

1.1 什么是 XLP
---------------
`xlp` = `xlang library package`

它是基于 xpack 的统一分发格式，用于承载：
	- xlang 编译产物
	- xrt 扩展产物
	- native 库桥接产物
	- future custom / class 映射产物


1.2 XLP 的核心原则
-------------------
XLP 的最小单元不是裸库文件，而是：
	元信息 + 可接入实现

可接入实现可以是：
	- 动态库：`dll` / `so`
	- 静态库：`.a`
	- 分享库：`.c`
	- 可选头文件：`.h`


1.3 XLP 的职责
---------------
XLP 至少承担以下职责：
	- 描述包身份与版本
	- 描述 ABI 边界
	- 描述依赖项
	- 描述模块导出
	- 描述函数重载映射
	- 描述调用约定
	- 描述返回值列表
	- 描述类型桥接
	- 描述协议实现
	- 描述 native 符号绑定


1.4 首版设计原则
----------------
	1. 交换格式优先可读
	2. 多版本共存优先于全局统一版本
	3. ABI 与版本绑定
	4. 元信息比物理产物更高优先级
	5. 结构化数据优先于字符串拼接



================================================================================
二、XLP 包结构
================================================================================

2.1 包扩展名
------------
统一扩展名：
	`.xlp`


2.2 推荐包结构
--------------
`.xlp` 是一个 xpack 包，推荐内部结构如下：

	/
		xlp.json
		artifacts/
			win-x64/
				mylib.dll
			linux-x64/
				libmylib.so
			static/
				libmylib.a
			source/
				mylib.c
				mylib.h
		resources/
			...
		docs/
			README.md


2.3 必需文件
------------
每个 `.xlp` 必须包含：
	- `xlp.json`


2.4 包类型
----------
建议支持以下包类型：
	- `shared`
	- `static`
	- `source`
	- `hybrid`

含义：
	- `shared`：以动态库为主
	- `static`：以静态库为主
	- `source`：以 `.c/.h` 形式分享
	- `hybrid`：同时携带多种实现载体



================================================================================
三、xlp.json 顶层结构
================================================================================

3.1 交换格式
------------
首版统一使用 JSON。

文件名固定为：
	`xlp.json`


3.2 顶层结构
------------
建议 `xlp.json` 顶层结构如下：

```json
{
  "schema": "xlp/1",
  "package": { ... },
  "artifacts": [ ... ],
  "dependencies": [ ... ],
  "modules": [ ... ],
  "values": [ ... ],
  "types": [ ... ],
  "functions": [ ... ],
  "protocols": [ ... ],
  "bindings": [ ... ]
}
```


3.3 顶层字段说明
----------------
	- `schema`
		元信息格式版本

	- `package`
		包基础信息

	- `artifacts`
		物理实现载体列表

	- `dependencies`
		依赖项列表

	- `modules`
		逻辑模块列表

	- `values`
		导出常量 / 变量 / 属性访问入口

	- `types`
		本包声明或桥接的类型列表

	- `functions`
		本包导出的函数/方法/构造等条目，同时承载命名参数、
		重载决议、错误语义、async/generator 桥接元信息

	- `protocols`
		协议实现声明

	- `bindings`
		符号级绑定信息


3.4 顶层数组规则
----------------
除 `schema` 与 `package` 外，其余顶层段都建议显式给出数组。

规则：
	- 不存在某类定义时，使用空数组 `[]`
	- 首版不允许把对象与数组混用
	- 读取器不得依赖“字段缺失即为空”的宽松行为



================================================================================
四、package 段
================================================================================

4.1 建议结构
------------
```json
{
  "name": "xrt.net.http",
  "version": "1.2.0",
  "abi_version": "1",
  "abi_id": "xrt.net.http@1.2.0#abi1",
  "kind": "shared",
  "entry_module": "xrt.net.http",
  "description": "HTTP extension for xlang/xrt",
  "author": "OpenX",
  "license": "MIT"
}
```


4.2 必需字段
------------
	- `name`
		包名

	- `version`
		包版本，建议语义版本格式

	- `abi_version`
		ABI 主版本

	- `abi_id`
		包级 ABI 唯一标识

	- `kind`
		`shared` / `static` / `source` / `hybrid`

	- `entry_module`
		默认入口模块名


4.3 可选字段
------------
	- `description`
	- `author`
	- `license`
	- `homepage`
	- `repository`
	- `xlang_version`
		声明该包使用的 xlang 语言标准版本
	- `xlang_abi`
		声明该包遵循的 xlang 语言 ABI 版本
	- `xrt_min_version`
		最小依赖的 xrt 运行时版本
	- `xrt_min_abi`
		最小依赖的 xrt 运行时 ABI 版本
	- `build_tag`
		构建标签，例如 `release` / `debug` / `asan`


4.4 语义版本规则
----------------
首版建议包版本遵循：
	`major.minor.patch`

说明：
	- `version` 是包发布版本
	- `abi_version` 是 ABI 主版本
	- 两者相关但不相同

例如：
	- `1.2.3` 和 `1.2.4` 可能共享 `abi_version = 1`
	- `2.0.0` 可能升级到 `abi_version = 2`


4.5 abi_id 规则
--------------
首版建议：
	`<package-name>@<version>#abi<abi-version>`

例如：
	- `libc@1.0.0#abi1`
	- `libc@2.0.0#abi2`

要求：
	- 同一 `abi_id` 必须语义兼容
	- 不同 `abi_id` 必须视为不同 ABI 实体


4.6 兼容性字段规则
------------------
建议约束：
	- `version` 表示包版本，不参与语言标准判断
	- `xlang_version` 表示语法/语义标准版本
	- `xlang_abi` 表示语言层调用约定版本
	- `xrt_min_version` / `xrt_min_abi` 用于检查运行库最低要求

这意味着：
	- 两个包可以同属 `xlang_version = 5`
	- 但一个使用 `xlang_abi = 1`，另一个使用 `xlang_abi = 2`
	- 编译器必须据此决定是否允许直接互调或要求桥接层



================================================================================
五、dependencies 段
================================================================================

5.1 设计目标
------------
第五版明确避免 Python / JS 常见的依赖地狱问题。

核心原则：
	- ABI 与版本绑定
	- 依赖解析按“边”而不是按“全局唯一库名”处理
	- 不要求整个程序里同名包只能有一个版本
	- 不强制把所有依赖提升到单一版本


5.2 建议结构
------------
```json
[
  {
    "id": "dep-libc-v1",
    "alias": "libc",
    "package": "libc",
    "version": "1.0.0",
    "abi_version": "1",
    "abi_id": "libc@1.0.0#abi1",
    "require": "=1.0.0",
    "visibility": "private",
    "optional": false,
    "artifact_kind": "shared"
  }
]
```


5.3 字段说明
------------
	- `id`
		依赖项唯一 ID

	- `package`
		依赖包名

	- `alias`
		当前包内使用的依赖别名，缺省时等于 `package`

	- `version`
		已解析到的具体版本

	- `abi_version`
		依赖使用的 ABI 主版本

	- `abi_id`
		依赖指向的 ABI 标识

	- `require`
		版本要求，首版建议至少支持：
			- `=1.0.0`
			- `^1.2.0`
			- `~1.2.0`

	- `visibility`
		依赖可见性：
			- `private`
			- `public`

	- `optional`
		是否为可选依赖

	- `artifact_kind`
		期望载体类型：`shared` / `static` / `source`


5.4 依赖解析规则
----------------
	1. 依赖按“父包 -> 子包”边解析
	2. 每条依赖边都绑定到一个具体版本与 ABI
	3. 只有当版本与 ABI 都兼容时，两个依赖节点才可复用
	4. 版本不同或 ABI 不同，则视为两个独立依赖实例

结论：
	- A 依赖 C@1.0.0#abi1
	- B 依赖 C@2.0.0#abi2

则最终构建中两个 C 都存在，且各自保持自己的 ABI 绑定。


5.5 编译期行为
--------------
编译最终程序时，编译器应：
	- 读取所有 `.xlp`
	- 构建依赖图
	- 解析每条依赖边的版本与 ABI
	- 把多版本依赖都纳入最终链接单元
	- 调用点始终绑定到所属父包决议后的具体 ABI


5.6 依赖可见性规则
------------------
	- `private`
		仅当前包内部可见，默认值
	- `public`
		该依赖成为当前包导出 ABI 的一部分，继续向外暴露

规则：
	- 若某导出类型/函数签名直接引用了依赖包类型，则该依赖必须为 `public`
	- `private` 依赖不得出现在对外导出的签名边界中


5.7 可选依赖规则
----------------
	- `optional = false` 时，缺失依赖必须直接报错
	- `optional = true` 时，缺失依赖不会导致包描述失效
	- 但任何引用该依赖的导出项都必须显式标记为条件可用


5.6 首版限制
------------
首版建议：
	- 不做复杂 peer dependency 机制
	- 不做运行时热升级
	- 不做同一 abi_version 下的自动兼容推断
	- 由元信息明确给出最终 `abi_id`



================================================================================
六、artifacts 段
================================================================================

6.1 建议结构
------------
```json
[
  {
    "id": "win64-dll",
    "kind": "dll",
    "path": "artifacts/win-x64/mylib.dll",
    "target": "windows-x64-msvc"
  }
]
```


6.2 必需字段
------------
	- `id`
	- `kind`
	- `path`
	- `target`


6.3 kind 枚举
-------------
建议值：
	- `dll`
	- `so`
	- `a`
	- `c`
	- `h`


6.4 可选字段
------------
	- `hash`
		文件摘要
	- `entry_symbol`
		主入口符号
	- `headers`
		相关头文件 artifact id 列表
	- `os`
		目标操作系统，如 `windows` / `linux`
	- `arch`
		目标架构，如 `x64` / `arm64`
	- `toolchain`
		构建工具链标记，如 `msvc` / `gnu` / `clang`
	- `link_name`
		链接时使用的逻辑库名
	- `runtime`
		附加运行库要求


6.5 artifact 选择规则
--------------------
加载或构建时建议按以下优先级选择：
	1. 与当前目标平台匹配的 `dll/so`
	2. 可链接的 `.a`
	3. 可重新编译的 `.c`



================================================================================
七、modules 段
================================================================================

7.1 建议结构
------------
```json
[
  {
    "id": "mod-http",
    "name": "xrt.net.http",
    "abi_id": "xrt.net.http@1.2.0#abi1",
    "init_symbol": "xl_mod_xrt_net_http__init",
    "exports": [
      "fn-http-get",
      "type-http-client",
      "val-http-version"
    ]
  }
]
```


7.2 字段说明
------------
	- `id`
		模块唯一 ID

	- `name`
		xlang 模块名

	- `abi_id`
		模块所属 ABI 标识

	- `init_symbol`
		模块初始化入口符号

	- `exports`
		导出项 ID 列表，可引用：
			- function
			- type
			- value
		首版实现中，`modules[].exports[]` 建议直接展开为对象数组，每个导出项显式给出：
			- `name`
			- `symbol`
			- `abiId`
			- `versionedSymbol`
			- `kind`
			- `overloadCount`

	- `source`
		可选，声明该模块来自的源单元或文件


7.3 模块规则
------------
	- 同一模块名在不同 `abi_id` 下可并存
	- 导入绑定必须精确到模块名 + abi_id
	- `init_symbol` 只能初始化当前模块 ABI 实例
	- 模块导出的任一项都必须属于同一个模块 ABI 视图
	- `modules[].exports[].abiId` 用于表达“导出名身份”，格式固定为 `<moduleAbiId>::<exportName>`
	- `modules[].exports[].versionedSymbol` 用于表达“版本绑定后的目标符号名”，格式固定为 `<moduleAbiId>::<symbol>`
	- 加载器不应再通过包名/版本/模块名反推导出身份，而应直接消费 `abiId` 与 `versionedSymbol`



================================================================================
八、values 段
================================================================================

8.1 定位
--------
`values` 用于描述导出常量、导出变量、后续属性访问入口。


8.2 建议结构
------------
```json
[
  {
    "id": "val-http-version",
    "module": "xrt.net.http",
    "name": "VERSION",
    "kind": "const",
    "type": { "name": "string" },
    "symbol": "xl_http_version"
  }
]
```


8.3 kind 枚举
-------------
建议值：
	- `const`
	- `var`
	- `getter`
	- `setter`


8.4 value 规则
--------------
	- `const` 必须可读且不可写
	- `var` 可以直接绑定存储位置，也可以绑定 getter/setter 对
	- `getter` / `setter` 用于 future 属性模型和 class/custom 映射



================================================================================
九、types 段
================================================================================

9.1 定位
--------
`types` 不只是给 custom 用，首版就应支持：
	- native 桥接类型
	- future/task/channel/generator 等运行时类型
	- future class/custom


9.2 建议结构
------------
```json
[
  {
    "id": "type-http-client",
    "name": "HttpClient",
    "kind": "native",
    "module": "xrt.net.http",
    "abi_id": "xrt.net.http@1.2.0#abi1",
    "runtime_repr": "pointer",
    "c_type": "xhttpclient*",
    "box": "xl_box_http_client",
    "unbox": "xl_unbox_http_client",
    "destroy": "xl_drop_http_client"
  }
]
```


9.3 必需字段
------------
	- `id`
	- `name`
	- `kind`
	- `module`
	- `abi_id`


9.4 kind 枚举
-------------
建议值：
	- `builtin`
	- `native`
	- `custom`
	- `class`
	- `module`


9.5 可选桥接字段
----------------
	- `runtime_repr`
		建议值：
			- `value`
			- `xvalue`
			- `pointer`
			- `opaque`

	- `c_type`
		C 层表示

	- `box`
		装箱函数

	- `unbox`
		拆箱函数

	- `destroy`
		销毁函数

	- `retain`
		引用增加函数

	- `release`
		引用释放函数

	- `layout`
		未来类型布局信息占位，例如：
			- `opaque`
			- `value`
			- `record`

	- `size`
		若可静态确定，可给出字节大小

	- `align`
		若可静态确定，可给出对齐值

	- `native_name`
		原生实现层名称，可用于 C/C++/Rust 等桥接



================================================================================
十、functions 段
================================================================================

10.1 定位
---------
`functions` 是 XLP 的核心段。

它必须同时支持：
	- 普通导出函数
	- 重载函数
	- native 函数
	- future 方法/构造/析构
	- async / generator 元信息


10.2 建议结构
-------------
```json
[
  {
    "id": "fn-foo-int",
    "module": "demo.math",
    "logical_name": "foo",
    "export_name": "foo",
    "overload_group": "demo.math::foo",
    "signature_id": "foo(int)",
    "dispatch_key": "foo$arity1|a:int",
    "abi_id": "demo.math@1.0.0#abi1",
    "kind": "function",
    "call_conv": "cdecl",
    "params": [
      {
        "index": 0,
        "name": "a",
        "label": "a",
        "type": { "name": "int" },
        "default_kind": "none",
        "default_value": null,
        "accept_positional": true,
        "accept_named": true,
        "variadic": false,
        "by_ref": false,
        "nullable": false
      }
    ],
    "returns": [],
    "symbol": "foo_int",
    "abi_symbol": "xl_demo_math_v1_0_0_abi1__foo_int",
    "artifact": "win64-dll",
    "native": true,
    "throws": false,
    "error_type": null,
    "error_mode": "none",
    "async": false,
    "generator": false,
    "suspend_kind": "none"
  }
]
```


10.3 必需字段
-------------
	- `id`
	- `module`
	- `logical_name`
	- `export_name`
	- `overload_group`
	- `signature_id`
	- `dispatch_key`
	- `abi_id`
	- `kind`
	- `call_conv`
	- `params`
	- `returns`
	- `symbol`
	- `abi_symbol`
	- `artifact`
	- `native`
	- `throws`
	- `error_mode`
	- `async`
	- `generator`
	- `suspend_kind`


10.4 kind 枚举
--------------
建议值：
	- `function`
	- `method`
	- `constructor`
	- `destructor`
	- `getter`
	- `setter`


10.5 call_conv 枚举
------------------
建议值：
	- `xlang`
	- `cdecl`
	- `stdcall`
	- `fastcall`


10.6 参数结构
-------------
建议参数项结构：

```json
{
  "index": 0,
  "name": "a",
  "label": "a",
  "type": { "name": "int" },
  "default_kind": "none",
  "default_value": null,
  "accept_positional": true,
  "accept_named": true,
  "variadic": false,
  "by_ref": false,
  "nullable": false
}
```

补充规则：
	- `index` 是参数槽位序号
	- `name` 用于命名参数匹配
	- `label` 是外部命名参数标签，缺省时等于 `name`
	- `default_kind` 建议值：
		- `none`
		- `literal`
		- `const_ref`
	- `default_value` 在 `default_kind != none` 时必须提供
	- `accept_positional` / `accept_named` 用于控制参数传递模式
	- `variadic = true` 表示当前项是可变参数入口
	- `variadic = true` 只能出现在最后一个参数
	- `by_ref = true` 表示按引用或指针语义传递
	- `nullable = true` 表示允许空值


10.6.1 命名参数规则
-------------------
	- 语言层命名参数匹配基于 `label`
	- `label` 在同一函数中必须唯一
	- `accept_named = false` 的参数不得通过命名方式传递
	- 命名参数重排不影响 ABI，只影响调用点的编译期决议


10.7 返回值结构
---------------
首版虽然先用单返回值，但 XLP 必须从一开始支持返回值列表。

建议结构：

```json
[
  { "slot": 0, "name": null, "type": { "name": "int" } }
]
```

意义：
	- 为 future xlang 调用约定多返回值留空间
	- 即使 `cdecl/stdcall` 不支持多返回值，元信息层也不应限制 xlang 自身扩展


10.7.1 返回值规则
-----------------
	- `slot` 是返回值槽位序号
	- 单返回值函数的首个槽位固定为 `0`
	- `cdecl/stdcall/fastcall` 下若出现多返回值，必须通过桥接或 xlang ABI 封装


10.8 方法/构造的扩展表示
-----------------------
为 future class/custom 留余量，函数项允许这些可选字段：
	- `owner_type`
	- `receiver`
	- `member_name`
	- `static`


10.8.1 方法接收者规则
---------------------
若 `kind = method/constructor/destructor/getter/setter`，建议补充：
	- `owner_type`
		所属类型 ID
	- `receiver`
		接收者参数索引或接收者类型描述
	- `member_name`
		语言层成员名
	- `static`
		是否为静态成员


10.8.2 重载决议元信息
---------------------
XLP 中的重载不依赖 C++ ABI 风格符号推导，而依赖显式元信息。

建议规则：
	- `overload_group` 标识同一逻辑函数组
	- `signature_id` 是规范化签名标识
	- `dispatch_key` 是编译器用于快速建立重载索引的稳定键

`dispatch_key` 建议至少编码：
	- 逻辑函数名
	- 参数个数
	- 参数标签序列
	- 参数类型序列
	- 调用约定

结论：
	- 逻辑调用 `foo(a: 1)` 先匹配重载组
	- 再按 `label/type/arity/default` 规则选定具体函数项
	- 一旦决议完成，直接跳转到对应 `symbol/abi_symbol`


10.8.3 重载唯一性规则
---------------------
	- 同一 `overload_group` 内，`signature_id` 必须唯一
	- 同一 `overload_group` 内，`dispatch_key` 必须唯一
	- 若两个候选仅因返回类型不同而区分，首版视为非法


10.8.4 默认参数与重载关系
------------------------
	- 默认参数参与重载候选筛选
	- 但不得制造二义性
	- 若省略参数后可命中多个候选，编译器必须报歧义错误


10.8.5 错误语义元信息
---------------------
为统一错误处理机制，函数项应显式给出错误语义：
	- `throws`
		是否可能抛出语言层错误
	- `error_type`
		错误类型，通常为 `Error` 或其桥接类型
	- `error_mode`
		建议值：
			- `none`
			- `xlang_error`
			- `errno`
			- `result_code`
			- `custom`

规则：
	- `throws = false` 时，`error_mode` 应为 `none`
	- `throws = true` 时，`error_mode` 不得为 `none`
	- 若 `error_mode != xlang_error`，应通过 `bindings` 提供桥接入口


10.8.6 async / generator 元信息
-------------------------------
为避免实现黑盒，函数项应显式描述挂起语义。

建议字段：
	- `async`
	- `generator`
	- `suspend_kind`
		建议值：
			- `none`
			- `async`
			- `generator`
			- `async_generator` 预留
	- `runtime_type`
		对应的运行时状态对象类型 ID
	- `resume_symbol`
		恢复执行入口
	- `poll_symbol`
		异步轮询入口
	- `cancel_symbol`
		取消入口
	- `next_symbol`
		generator 取下一项入口
	- `close_symbol`
		收尾入口

规则：
	- `async = true` 时，`suspend_kind` 必须为 `async`
	- `generator = true` 时，`suspend_kind` 必须为 `generator`
	- `async` 与 `generator` 在首版不得同时为 `true`
	- 若声明了挂起语义，则必须给出 `runtime_type`


10.9 abi_symbol 规则
-------------------
首版建议最终 ABI 符号至少编码：
	- 包或模块名
	- 版本
	- abi_version
	- 逻辑目标名
	- 规范化签名

例如：
	- `xl_demo_math_v1_0_0_abi1__foo_int`
	- `xl_libc_v2_0_0_abi2__foo_string`

要求：
	- 不同 `abi_id` 下不得复用同一 `abi_symbol`
	- `abi_symbol` 应稳定、可重现、跨编译机一致

建议规范化格式：
	`xl__<package>__v<major>_<minor>_<patch>__abi<abi>__<module>__<export>__<sig>`

其中：
	- 所有名称统一转小写
	- 非字母数字字符归一化为 `_`
	- 连续 `_` 折叠为单个 `_`


10.10 symbol 与 abi_symbol 的职责分离
------------------------------------
	- `symbol`
		物理产物中实际可链接的原始符号名
	- `abi_symbol`
		xlang 语言层稳定符号名

规则：
	- external/native 产物可以只真实存在 `symbol`
	- `abi_symbol` 作为语言层索引和跨包稳定名，允许通过 `bindings` 映射到 `symbol`
	- xlang 自己编译出的产物应尽量使 `symbol == abi_symbol`



================================================================================
十一、protocols 段
================================================================================

11.1 定位
---------
`protocols` 用来声明某个类型实现了哪些标准协议。

首版重点支持：
	- Callable
	- Iterable
	- Iterator
	- Awaitable
	- Generator


11.2 建议结构
-------------
```json
[
  {
    "type": "type-http-task",
    "protocol": "Awaitable",
    "abi_id": "xrt.net.http@1.2.0#abi1",
    "meta": {
      "result_type": { "name": "string" },
      "error_type": { "name": "Error" },
      "poll_symbol": "xl_http_task_poll",
      "cancel_symbol": "xl_http_task_cancel"
    }
  }
]
```


11.3 必需字段
-------------
	- `type`
	- `protocol`
	- `abi_id`


11.4 Awaitable 的最低要求
------------------------
对于 Awaitable，元信息至少要能表达：
	- 成功结果类型
	- 错误类型
	- 运行时桥接入口


11.5 协议桥接规则
-----------------
建议各标准协议最少具备以下桥接信息：
	- `Callable`
		- `invoke_symbol`
	- `Iterable`
		- `iter_symbol`
	- `Iterator`
		- `next_symbol`
		- `done_symbol`
	- `Awaitable`
		- `poll_symbol`
		- `cancel_symbol`
		- `result_symbol`
		- `error_symbol`
	- `Generator`
		- `next_symbol`
		- `close_symbol`

规则：
	- 协议元信息不得只给出“实现了协议”而不给出桥接能力
	- 若协议语义无法桥接到运行时入口，则该声明无效



================================================================================
十二、bindings 段
================================================================================

12.1 定位
---------
`bindings` 负责把语言层声明绑定到物理实现。

作用：
	- 从逻辑函数到 native 符号
	- 从类型到 box/unbox/destroy
	- 从协议到运行时桥接函数


12.2 建议结构
-------------
```json
[
  {
    "id": "bind-foo-int",
    "kind": "function",
    "source": "fn-foo-int",
    "artifact": "win64-dll",
    "symbol": "foo_int",
    "abi_symbol": "xl_demo_math_v1_0_0_abi1__foo_int"
  }
]
```


12.3 kind 枚举
--------------
建议值：
	- `function`
	- `type-bridge`
	- `protocol-bridge`
	- `value`


12.4 binding 规则
-----------------
	- `function`
		用于逻辑函数到物理符号的映射
	- `type-bridge`
		用于 box/unbox/destroy/retain/release 的集合桥接
	- `protocol-bridge`
		用于标准协议的运行时入口映射
	- `value`
		用于常量、变量、getter/setter 入口绑定

建议补充字段：
	- `bridge_symbol`
	- `marshal`
	- `ownership`



================================================================================
十三、类型表示对象
================================================================================

13.1 设计目标
-------------
避免把签名压成难以解析的字符串。


13.2 建议结构
-------------
首版建议：

```json
{ "name": "int" }
```

future 扩展：

```json
{ "name": "array", "args": [ { "name": "int" } ] }
```


13.3 规则
---------
	- 首版不要求开放泛型语法
	- 但元信息层从一开始保留 `args` 扩展位
	- `name` 必须引用已知类型名或包内类型定义
	- 建议允许可选字段：
		- `abi_id`
		- `nullable`
		- `mutable`



================================================================================
十四、校验规则
================================================================================

14.1 顶层校验
-------------
	- `schema` 必须存在
	- `package` 必须存在
	- `modules`、`functions`、`bindings` 缺省可为空数组，但建议显式给出


14.2 ID 校验
------------
以下 ID 在各自命名空间中必须唯一：
	- artifact id
	- dependency id
	- module id
	- value id
	- type id
	- function id
	- binding id


14.3 引用校验
------------
	- `modules.exports` 中的 ID 必须能解析到导出项
	- `functions.artifact` 必须引用存在的 artifact id
	- `bindings.source` 必须引用存在的 function/type/value id
	- `protocols.type` 必须引用存在的 type id
	- `functions.runtime_type` 若存在，必须引用存在的 type id


14.4 ABI 校验
-------------
	- `modules.abi_id` 必须与包 ABI 兼容
	- `functions.abi_id` 必须与所属模块 ABI 一致
	- `bindings.abi_symbol` 若存在，必须对应唯一 ABI 符号


14.5 参数与重载校验
-------------------
	- 同一函数内 `label` 不得重复
	- `variadic` 参数必须位于最后
	- `default_kind = none` 时，`default_value` 必须为 `null`
	- 同一 `overload_group` 内不得出现重复 `signature_id`
	- 同一 `overload_group` 内不得出现重复 `dispatch_key`
	- 仅凭返回值不同区分重载时必须报错


14.6 错误与挂起语义校验
-----------------------
	- `throws = false` 时，`error_type` 应为 `null`
	- `throws = true` 时，`error_mode` 不得为 `none`
	- `async = true` 时，`generator` 必须为 `false`
	- `generator = true` 时，`async` 必须为 `false`
	- `suspend_kind = none` 时，不得声明 `poll_symbol/next_symbol/...` 等挂起桥接入口


14.7 依赖边界校验
-----------------
	- `public` 依赖必须可被最终消费者解析
	- `private` 依赖不得泄露到导出签名
	- `optional` 依赖若被导出项引用，必须在导出项上体现条件约束



================================================================================
十五、加载与解析规则
================================================================================

15.1 包加载顺序
--------------
建议顺序：
	1. 读取 `xlp.json`
	2. 校验 schema
	3. 读取 package 信息
	4. 解析依赖项
	5. 选择 artifact
	6. 解析模块/函数/类型/协议/绑定
	7. 建立包级导入索引
	8. 建立重载分发表
	9. 建立协议桥接表


15.2 artifact 选择
-----------------
按当前目标环境选择：
	- 优先平台匹配动态库
	- 次选静态库
	- 再次选源代码载体


15.3 依赖解析
------------
每个导入边都保留自己的 `abi_id`。

编译器内部应维护：
	- 逻辑导入名
	- 实际包版本
	- 实际 ABI
	- 实际目标符号表
	- 重载组到函数项的分发表
	- 类型到协议桥接的索引表



================================================================================
十六、版本与兼容性
================================================================================

16.1 schema
-----------
首版固定：
	`xlp/1`


16.2 向后兼容
------------
建议规则：
	- 读取器必须拒绝未知主版本
	- 可忽略未知可选字段
	- 必需字段缺失必须报错

================================================================================
十八、首版结论
================================================================================

XLP 首版标准的关键结论：
	1. `.xlp` 是统一扩展包格式
	2. `xlp.json` 是统一元信息文件
	3. 元信息首版使用 JSON
	4. `functions` 段必须显式承载命名参数、重载、错误语义、挂起语义
	5. 重载、native 绑定、模块导出、类型桥接都统一走同一元信息机制
	6. 返回值列表从元信息层首版就必须支持
	7. ABI 必须与版本绑定，支持同名库多版本天然共存
	8. `dependencies` 是正式标准字段，且带 `public/private/optional` 语义
	9. future class/custom 扩展继续复用这套结构

这意味着：
	XLP 不只是“库的说明文件”，
	而是 xlang/xrt 外部扩展体系的基础协议。
