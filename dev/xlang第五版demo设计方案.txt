================================================================================
xlang 第五版 Demo 设计方案
================================================================================

版本：v5.0-draft2
定位：xlang 前端 + C 后端 + tcc 内存编译运行 + xrt 运行时
目标：在第四版编译运行路线之上，恢复并验证异步、协程、任务编排等运行时能力



================================================================================
一、版本定位与设计迁移
================================================================================

1.1 第三版的定位
----------------
第三版更偏向可行性验证：
	- 重点是验证语言结构能否成立
	- 后端本质上是 AST 执行
	- xrt 主要承担基础数据结构与运行时支撑

第三版的价值：
	- 把语言全景基本铺开
	- 提前确认 xrt 作为 xlang 基础运行库是可行的

第三版的问题：
	- 语义、后端、运行时边界没有真正拉开
	- AST 执行适合验证语义，不适合作为正式路线


1.2 第四版的定位
----------------
第四版开始把 xlang 收束为一种“编译运行的脚本语言”：
	- xlang 源码先编译成 C
	- 再依赖 tcc 提供的内存编译/运行能力执行
	- 解释执行感受，本质来自“即时编译后的直接运行”，而不是 AST 解释器

第四版的重要推进：
	- 方向上已经更像“开发一个 C 语言编译器，只是前端语法换成 xlang”
	- 开始认真区分编译期和运行期
	- 类型系统从“硬编码语法”转向“编译期查表构建”

第四版的实际妥协：
	- 当时基础设施薄弱，所以砍掉了大量重功能
	- async / await / yield / 任务编排 / 模块 / 异常等没有进入核心 demo
	- demo4 最终更偏向“前端子集验证”


1.3 第五版的定位
----------------
第五版不是回到解释器优先，也不是回到第三版。

第五版的正确定位是：
	- 继续沿用第四版“编译到 C，再由 tcc 内存编译运行”的主路线
	- 但不再维持第四版那种过度收缩的功能边界
	- 以一个真正的“xlang 编译器 demo”来推进，而不是语法验证器

可以这样理解：
	第五版的 xlang 实现，更像是在开发一个 C 编译器前端。
	区别只在于：
		- 用户写的是 xlang
		- 编译器生成的是 C
		- 最终运行时依托的是 xrt + tcc



================================================================================
二、第五版的核心结论
================================================================================

第五版的主路线：
	源码
	-> Lexer
	-> Parser
	-> AST
	-> 语义分析 / 类型查表 / 绑定
	-> 中间层 Lowering
	-> C 代码生成
	-> tcc 内存编译
	-> 直接运行


第五版必须坚持的原则：
	1. 不走 AST 解释执行主路线
	2. 继续把 C 作为 demo 阶段的统一后端
	3. xrt 是运行时 ABI，不是附属工具库
	4. 类型系统继续走“编译期注册表 / 查表”路线
	5. 把第四版因基础设施不足而砍掉的重功能逐步恢复


第五版的工作重点不是：
	- 做更多语法糖
	- 做类系统全量落地
	- 做优化器

第五版的工作重点是：
	- 把前端语义真正做厚
	- 把编译期和运行时边界真正做清楚
	- 把 xrt 已经成熟的能力稳定映射进语言



================================================================================
三、编译期与运行时的边界
================================================================================

这一条是第五版最重要的设计前提。


3.1 编译期负责的内容
--------------------
编译期必须负责：
	- 词法分析
	- 语法分析
	- AST 构建
	- 模块依赖分析
	- 符号表构建
	- 类型表初始化与类型查询
	- 标识符是否为类型名的判定
	- 重载决议
	- `async` / `yield` / `try` / `import` 等上下文合法性检查
	- 作用域分析
	- 捕获变量分析（如果后续引入闭包）
	- 函数调用签名检查
	- 控制流 Lowering
	- 异步函数与生成器的状态机生成
	- C 代码生成


3.2 运行时负责的内容
--------------------
运行时由 xrt 与生成代码共同承担：
	- 内存管理
	- string（默认 UTF-8，也可承载任意字节序列）/ time / 容器实现
	- var / xvalue 动态值
	- Future / Task / Coroutine / Channel / Mutex 等并发原语
	- 异步文件 / 网络
	- 模块初始化后的对象存活
	- 异常对象与运行期错误传播
	- 调度器与等待唤醒


3.3 边界判定原则
----------------
原则一：
	凡是“写代码时就能决定”的问题，必须放在编译期解决。

原则二：
	凡是“依赖真实运行状态、IO、调度、对象生命周期”的问题，必须放在运行时解决。

原则三：
	编译器不要把本该在运行时由 xrt 处理的事情重新造一遍。



================================================================================
四、类型系统：继续第四版路线，正式定型
================================================================================

4.1 第三版与第四版的根本区别
----------------------------
第三版：
	- 类型更多是写死在语法与分支判断里

第四版：
	- 明确尝试把类型做成编译期查表构建
	- Parser 识别类型名，本质上是“查询编译器当前的类型注册表”

第五版必须明确站在第四版一侧：
	- 类型不是硬编码语法
	- 类型是编译器启动时注册的一张表
	- 语法层只保留极少数硬关键字


4.2 类型名应改为“软关键字”
--------------------------
第五版建议把下面两类东西严格区分：

硬关键字：
	- if / then / else / elseif / end
	- for / in / while / do
	- break / continue / return
	- func / const / as
	- async / await / yield
	- try / catch / finally / throw
	- import / export
	- and / or / not

软关键字（由类型表决定）：
	- bool / int / float / string / time
	- array / list / set / dict / range / type
	- function
	- future / task / channel / error / module
	- 后续 class / custom / object

这样做的好处：
	- Parser 不需要为每个类型写死一套分支
	- 扩展类型系统时，不必同时修改 lexer 关键字表与 parser 结构
	- 与第四版“注册类型”的方向完全一致


4.3 第五版建议的标准类型集
--------------------------
基础值类型：
	- null
	- bool
	- int / int8 / uint8 / int16 / uint16 / int32 / uint32 / int64 / uint64
	- float / float32 / float64
	- string（默认 UTF-8，也可承载任意字节序列）
	- time
	- point

容器类型：
	- array
	- list
	- set
	- dict
	- range

特殊类型：
	- var
	- type
	- function

运行时类型：
	- error
	- module
	- future
	- task
	- channel
	- generator

延后类型：
	- class
	- custom
	- object
	- carray


4.4 类型描述符应扩展的内容
--------------------------
第四版的 `XL_TypeDesc` 方向正确，第五版应在其上补齐：
	- C 层映射类型
	- 默认值生成
	- 构造/转换生成
	- 运算符生成
	- 索引生成
	- 可调用协议
	- 可迭代协议
	- 可等待协议
	- 模块导出元信息

结论：
	第五版里，类型表不只是给 parser 用来“认类型名”。
	它必须成为：
		- 语义分析器的判定中心
		- C 后端的生成中心
		- 标准库 native 绑定的元信息中心


4.5 编译期检查体系必须前置固化
------------------------------
第五版必须明确一条原则：
	编译器最难、也是最关键的部分，不是把 AST 翻译成 C，
	而是把所有语义检查、协议检查、类型绑定、声明绑定做成一套可维护、可扩展、无黑盒的机制。

这也是 xlang 设计的核心要点：
	- 语言形态上希望接近编译型语言
	- 能力形态上希望吸收解释型语言常见的动态能力
	- 因此决定语言长期可维护性的，不是“当前支持了什么语法”，而是“机制是否清晰且能扩展”

结论：
	第五版必须把检查体系、流程、数据结构、产物在设计阶段就固化，而不是边实现边补。


4.5.1 检查体系的总目标
----------------------
编译期检查体系需要同时满足：
	- 看得见：每一类检查都有明确输入、输出、错误产物
	- 可追踪：每个符号、函数、类型、协议实现都能回溯来源
	- 可扩展：未来加入 class/custom/闭包/泛型时不推翻现有机制
	- 可降级：检查结果能直接服务 HIR/MIR/C 后端
	- 可缓存：模块编译结果、声明表、类型表可复用


4.5.2 编译器内部必须固化的核心表
-------------------------------
第五版至少需要以下编译期核心表：

	1. 类型注册表 `XL_TypeTable`
		- 所有已知类型
		- 类型别名
		- 类型分类
		- C 映射
		- 运算符能力
		- 构造/转换能力
		- 协议实现声明

	2. 符号表 `XL_SymbolTable`
		- 模块级符号
		- 函数级局部符号
		- 块级符号
		- 导入符号
		- 捕获符号（为闭包预留）

	3. 函数声明表 `XL_FunctionDeclTable`
		- 每个函数的声明信息
		- 参数列表
		- 返回类型
		- async / generator 标记
		- 导出属性
		- native / xlang 来源
		- overload group 归属

	4. 重载组表 `XL_OverloadGroupTable`
		- 同名函数集合
		- 每个候选签名
		- 签名优先级
		- 转换成本规则

	5. 协议实现表 `XL_ProtocolImplTable`
		- 哪个类型实现了哪个协议
		- 是编译器内建实现、native 注册实现，还是用户类型实现
		- 协议方法签名是否完整

	6. native 映射表 `XL_NativeBindingTable`
		- xlang 模块/函数/类型到 xrt 或 C 符号的映射
		- 参数映射
		- 返回值映射
		- 错误处理策略
		- 所需头文件 / 运行时依赖

	7. 模块声明表 `XL_ModuleTable`
		- 模块路径
		- 导出表
		- 导入依赖
		- 初始化顺序
		- 编译缓存 key

	8. 诊断表 `XL_DiagnosticSet`
		- 错误
		- 警告
		- note
		- 关联符号
		- 关联候选项


4.5.3 建议的数据结构骨架
-----------------------
建议从第五版一开始就把这些结构显式落盘，而不是散落在多个模块里。

类型描述：
	typedef struct XL_TypeDesc {
		str pszName;
		int iTypeId;
		int iCategory;
		bool bValueType;
		bool bBuiltin;
		bool bNative;
		str pszCType;
		str pszCStorageType;
		str pszCDefaultExpr;
		xvalue xOperators;
		xvalue xProtocols;
		xvalue xConversions;
		xvalue xMeta;
	} XL_TypeDesc;

函数声明：
	typedef struct XL_FunctionDecl {
		str pszName;
		str pszModuleName;
		int iFuncId;
		int iOverloadGroupId;
		bool bAsync;
		bool bGenerator;
		bool bExport;
		bool bNative;
		int iCallConv;
		xvalue xParams;
		xvalue xReturns;
		xvalue xDefaults;
		xvalue xAttributes;
		xvalue xSourceLoc;
	} XL_FunctionDecl;

协议实现：
	typedef struct XL_ProtocolImpl {
		int iTypeId;
		int iProtocolId;
		bool bComplete;
		xvalue xRequiredMethods;
		xvalue xResolvedMethods;
		xvalue xMeta;
	} XL_ProtocolImpl;

native 映射：
	typedef struct XL_NativeBinding {
		str pszModuleName;
		str pszSymbolName;
		str pszCName;
		int iBindingKind;
		int iTargetId;
		xvalue xParamMap;
		xvalue xReturnMap;
		xvalue xHeaders;
		xvalue xMeta;
	} XL_NativeBinding;


4.5.4 协议系统必须显式建模
-------------------------
第五版不能把 Awaitable / Iterable / Callable 这些概念写成零散特判。

必须定义正式协议表，例如：
	- Callable
	- Indexable
	- Iterable
	- Iterator
	- Awaitable
	- Generator
	- Stringify

其中 `Awaitable` 至少要固化：
	- await 结果类型
	- 错误类型
	- 挂起后恢复所需的 runtime 支持
	- 是否允许直接 `await`

示例：
	typedef struct XL_ProtocolAwaitableDesc {
		int iResultTypeId;
		int iErrorTypeId;
		str pszAwaitCheckProc;
		str pszAwaitGetResultProc;
		str pszAwaitGetErrorProc;
	} XL_ProtocolAwaitableDesc;

这意味着：
	- `future`
	- `task`
	- 后续某些 native 异步结果对象
都可以通过注册进入 `Awaitable` 协议，而不是写死在 `await` 节点判断里。


4.5.5 编译期检查阶段必须拆开
---------------------------
建议第五版把语义检查拆成固定阶段，每一阶段都有明确输入输出。

阶段 0：编译器启动与注册
	- 注册内置类型
	- 注册协议
	- 注册标准模块声明
	- 注册 native 绑定
	- 冻结基础类型表

阶段 1：模块级预扫描
	- 收集 import/export
	- 收集顶层变量、常量、函数声明
	- 建立模块符号表骨架
	- 建立函数声明表骨架

阶段 2：类型绑定
	- 解析所有显式类型名
	- 检查类型名是否存在
	- 检查 typedef / alias 是否冲突
	- 给 AST 节点绑定类型引用

阶段 3：作用域与符号绑定
	- 绑定局部变量
	- 检查重复声明
	- 检查未定义标识符
	- 标记捕获变量

阶段 4：函数声明检查
	- 参数名唯一性检查
	- 默认参数位置检查
	- 返回值声明检查
	- async/generator 互斥检查
	- native 声明一致性检查

阶段 5：协议与上下文检查
	- `await` 上下文检查
	- Awaitable 协议检查
	- `yield` 上下文检查
	- Iterable / Iterator 协议检查
	- try/catch/finally 结构检查

阶段 6：调用与重载决议
	- 找到候选函数组
	- 计算参数匹配成本
	- 进行最优候选选择
	- 无匹配 / 多义性错误诊断

阶段 7：native/custom 映射检查
	- xlang 类型到 C/xrt 类型映射是否存在
	- 自定义类型桥接函数是否完整
	- async native 返回值是否实现 Awaitable
	- 容器/字符串/错误对象的 ABI 是否一致

阶段 8：Lowering 前验证
	- 所有控制流出口是否完整
	- async 状态机生成前的挂起点检查
	- generator 状态持久化变量检查
	- MIR 所需临时变量与标签预分配


4.5.6 变量类型检查必须固化规则
-----------------------------
变量类型检查不是一句“能不能赋值”。
至少要固定以下规则：
	- 显式声明类型变量：右值必须可隐式转换
	- `const`：必须初始化，且初始化后不可写
	- `auto`：推导结果必须唯一
	- `var`：接受任意运行时值，但仍需记录静态来源类型用于诊断
	- 多返回值或 tuple-like 绑定时，左右数量必须匹配

需要产出的数据：
	- 变量声明节点的最终类型 ID
	- 初始化表达式的静态类型 ID
	- 是否发生隐式转换
	- 转换规则来源


4.5.7 协程/异步接口检查必须前置
------------------------------
以下检查必须在 Lowering 之前完成：
	- `await` 只能出现在 async 函数中
	- `yield` 只能出现在 generator 函数中
	- async 与 generator 不得在 demo5-alpha1 中混用
	- `await expr` 的 `expr` 必须实现 Awaitable
	- `for in expr` 的 `expr` 必须实现 Iterable 或 Generator
	- `task.all/race/spawn` 这类编排函数的参数类型必须可推导

不能接受的实现方式：
	- 到代码生成阶段才临时判断
	- 直接根据名字判断是不是 future
	- 把协议校验交给运行时报错


4.5.8 函数重载检查必须形成稳定算法
---------------------------------
重载是第五版必须提前固化的一块。

至少要固定：
	- 候选收集范围
	- 精确匹配优先
	- 隐式转换匹配次之
	- 有损转换默认不参与普通重载决议
	- `var` 参数优先级低于精确类型参数
	- 多义性必须报错，不能“猜一个”

建议引入转换成本模型：
	- 0：精确匹配
	- 1：类型别名归一后的精确匹配
	- 2：安全隐式转换
	- 3：`var` 吞并匹配
	- 4+：保留给未来扩展

最终每次调用都应产出：
	- 命中的函数 ID
	- 候选列表
	- 每个候选参数成本
	- 是否发生重写/桥接调用


4.5.9 自定义类型映射检查必须独立成表
-----------------------------------
虽然 `class/custom/object` 可以延后完整落地，但“自定义类型映射机制”本身不能晚。

第五版必须提前设计：
	- xlang 类型 ID
	- 对应 C 结构体名
	- 构造函数
	- 析构函数
	- 引用/所有权规则
	- 到 xvalue 的装箱规则
	- 从 xvalue 的拆箱规则
	- 错误时的诊断文本

否则后续接入 custom/native 类型时，编译器会重新变成黑盒拼接器。


4.5.10 函数声明表必须成为编译器主索引
-----------------------------------
第五版建议把函数声明表提升到最高优先级之一。

因为以下能力都依赖它：
	- 调用检查
	- 重载决议
	- async/generator 标记
	- native 绑定
	- 导出表生成
	- C 符号名生成
	- 调用图分析
	- 状态机 Lowering

函数声明表至少需要支持：
	- 按模块查
	- 按名字查
	- 按 overload group 查
	- 按导出名查
	- 按 C 生成符号查


4.5.11 每个检查阶段都要输出可见产物
-----------------------------------
第五版不允许检查逻辑埋在内部不可见。

建议所有阶段支持调试输出：
	- `--dump-types`
	- `--dump-symbols`
	- `--dump-funcs`
	- `--dump-overloads`
	- `--dump-protocols`
	- `--dump-bindings`
	- `--dump-hir`
	- `--dump-mir`

这样做的意义不只是调试。
它直接决定未来这门语言能不能长期维护，以及能不能依靠模型，对出现的各种问题进行排查。


4.5.12 第五版在机制上的最终要求
------------------------------
第五版必须把以下观点落实到工程结构：
	- 能翻译成 C 的部分，不是编译器最难的部分
	- 检查体系、声明体系、协议体系、映射体系，才是编译器的核心资产
	- 机制必须先固化，再扩能力
	- 所有动态能力都必须落在静态可分析的编译期框架内
	- 不允许依赖“运行时碰碰运气”来替代编译期约束


4.6 编译期可跟踪性必须作为正式能力设计
------------------------------------
第五版还必须把“编译过程可跟踪”作为正式设计目标，而不是调试附属品。

原因很明确：
	- 你需要完全理解 xlang 的每一个方面
	- 编译器中最复杂的部分恰恰是各种表、绑定、检查、Lowering 的流转
	- 如果这些过程不可见，编译器就会逐渐变成黑盒
	- 一门强调机制的语言，如果其编译器内部机制不可观测，就无法长期维护

结论：
	第五版必须保证“每一步的数据如何流转、如何变化”都能被查看。


4.6.1 可跟踪性的目标
-------------------
编译器可跟踪性至少要做到：
	- 可定位：知道当前处理的是哪个模块、哪个函数、哪个 AST 节点
	- 可回放：知道每一步之前和之后的数据状态
	- 可比较：知道同一数据结构在不同阶段发生了什么变化
	- 可解释：知道为什么做出某个决议，而不只是知道结果
	- 可导出：所有关键阶段都能 dump 成稳定格式


4.6.2 编译阶段必须细分成可观察流水线
-----------------------------------
第五版不能只暴露：
	分词器 -> 语法分析器 -> C 代码

建议至少拆成下面这些可观测阶段：
	1. Source Load
		- 加载源文件
		- 处理模块路径解析

	2. Lex
		- 产出 token 流

	3. Parse
		- 产出 AST

	4. Predeclare
		- 预扫描顶层声明
		- 建立模块骨架

	5. Type Register
		- 编译器启动注册的类型与协议

	6. Type Bind
		- AST 中的类型名解析到类型 ID

	7. Symbol Bind
		- 标识符绑定到具体声明

	8. Function Build
		- 建立函数声明表、重载组

	9. Protocol Check
		- Awaitable / Iterable / Callable 等协议检查

	10. Call Resolve
		- 调用检查与重载决议

	11. Native Bind
		- native/xrt 符号映射

	12. HIR Build
		- 语义绑定后的高层中间表示

	13. MIR Lower
		- 控制流、async、generator 状态机降级

	14. C Emit
		- 生成 C 代码

	15. TCC Compile
		- 内存编译

	16. Run
		- 加载与执行

每一阶段都应有单独的输入、输出与 dump 能力。


4.6.3 每一阶段都必须定义标准输入输出
-----------------------------------
建议为每个阶段定义统一的记录结构：
	typedef struct XL_StageRecord {
		str pszStageName;
		str pszModuleName;
		str pszUnitName;
		uint64 iStartTime;
		uint64 iEndTime;
		xvalue xInputs;
		xvalue xOutputs;
		xvalue xDiagnostics;
		xvalue xStats;
	} XL_StageRecord;

这样做的意义：
	- 不同阶段统一记录格式
	- CLI/UI/日志文件都可以直接消费
	- 以后做可视化编译器面板也有基础


4.6.4 所有核心表都必须支持“快照”
--------------------------------
以下表不只要能查，还要能在阶段结束时做快照：
	- 类型表快照
	- 协议表快照
	- 模块表快照
	- 符号表快照
	- 函数声明表快照
	- 重载组表快照
	- native 绑定表快照
	- 诊断表快照

快照要求：
	- 稳定顺序
	- 可序列化
	- 带唯一 ID
	- 带来源位置
	- 能和上一阶段快照做 diff


4.6.5 表查看必须是一等能力
-------------------------
第五版建议从一开始就提供表查看命令，而不是后续临时打印。

建议的 CLI 能力：
	- `--dump-types`
	- `--dump-protocols`
	- `--dump-symbols`
	- `--dump-funcs`
	- `--dump-overloads`
	- `--dump-modules`
	- `--dump-bindings`
	- `--dump-diagnostics`
	- `--dump-hir`
	- `--dump-mir`
	- `--dump-c`

建议的阶段限定：
	- `--dump-types=register`
	- `--dump-symbols=bind`
	- `--dump-overloads=resolve`

这样可以直接查看：
	- 某一步之前有什么
	- 某一步之后多了什么、改了什么


4.6.6 所有对象都必须有稳定 ID
-----------------------------
为了实现真正可跟踪，以下对象都建议在编译期分配稳定 ID：
	- TokenId
	- AstNodeId
	- TypeId
	- SymbolId
	- FuncId
	- OverloadGroupId
	- ProtocolId
	- NativeBindingId
	- HirNodeId
	- MirNodeId

这样就可以做到：
	- 从一段 C 代码反查到 MIR 节点
	- 从 MIR 节点反查到 HIR 节点
	- 从 HIR 节点反查到 AST 节点
	- 从 AST 节点反查到源代码位置


4.6.7 必须支持“决议解释”
-----------------------
仅仅显示“命中了哪个函数”“某类型实现了 Awaitable”还不够。

第五版需要支持 explain 模式，告诉用户：
	- 为什么这个标识符被绑定到这个符号
	- 为什么这个调用命中这个重载
	- 为什么另一个候选被淘汰
	- 为什么某个类型被视为 Awaitable
	- 为什么某个 native 映射合法或不合法

建议为关键决议记录解释对象：
	typedef struct XL_ResolutionTrace {
		str pszKind;
		int iSubjectId;
		xvalue xCandidates;
		xvalue xRulesApplied;
		xvalue xChosen;
		xvalue xRejected;
		xvalue xNotes;
	} XL_ResolutionTrace;


4.6.8 HIR/MIR 不只是内部结构，也要能查看
---------------------------------------
第五版既然引入 HIR/MIR，就必须让它们可见。

要求：
	- HIR 能看出语义绑定结果
	- MIR 能看出 lowering 后的控制流与状态机
	- async/generator 必须能直接看到状态切分点

例如在 async 函数上，至少能看到：
	- 状态结构体字段
	- 每个 await 对应的状态号
	- 恢复点
	- 错误路径

在 generator 上，至少能看到：
	- 每个 yield 对应的状态号
	- 持久化局部变量
	- next/resume 路径


4.6.9 C 代码必须保留反向映射信息
-------------------------------
生成的 C 代码不能只是“能编译”。

必须保留反向映射：
	- 源文件
	- 源行号
	- AST/HIR/MIR 节点 ID
	- 所属函数 ID

建议至少通过以下方式保留：
	- 注释
	- `#line`
	- 调试辅助表

这样未来在 tcc 编译错误、运行时崩溃、native 映射出错时，才能反查到源语言层。


4.6.10 建议输出统一的编译追踪文件
--------------------------------
第五版建议支持输出一个完整的追踪文件，例如：
	- `build.trace.json`
	- `module.trace.json`

内容包括：
	- 阶段记录
	- 所有表快照
	- 关键决议 trace
	- 诊断
	- HIR / MIR 摘要
	- 生成 C 代码映射

这会成为以后理解编译器行为的核心资产。


4.6.11 可跟踪性要进入工程结构，而不是散落日志
----------------------------------------------
不建议把这些能力做成一堆临时 `printf`。

建议正式建立：
	- `src/trace/`
	- `src/dump/`
	- `src/view/`

其中：
	- `trace/` 负责阶段记录与决议记录
	- `dump/` 负责各种表与 IR 的序列化
	- `view/` 负责 CLI 展示格式


4.6.12 第五版在可跟踪性上的最终要求
----------------------------------
第五版必须做到：
	- 所有关键编译阶段可见
	- 所有关键表结构可查看
	- 所有关键决议可解释
	- 所有 IR 可导出
	- 最终 C 代码可反查来源

只有这样，xlang 的编译器才不会变成黑盒。
这不仅是调试体验问题，而是语言机制可持续演化的前提。



================================================================================
五、第五版的功能恢复策略
================================================================================

第四版砍掉很多功能，不是因为这些功能不该有，而是当时没有足够基础设施。
现在基础设施变化了，第五版应恢复以下能力。


5.1 必须恢复的功能
------------------
	- 异常系统
	- async / await
	- yield / 生成器
	- 任务编排
	- 模块系统
	- native 标准库绑定


5.2 可以继续延后的功能
----------------------
	- class / custom / object
	- 闭包与匿名函数的完整形态
	- 元编程
	- 泛型
	- 优化器


5.3 恢复顺序建议
----------------
建议恢复顺序不是“按语法章节”，而是按后端可实现性：
	1. 异常
	2. 模块
	3. async / await
	4. yield / generator
	5. task / channel / orchestration

原因：
	- 这些能力都直接依赖 xrt 已有运行时
	- 一旦语义明确，就能通过 C 状态机方式稳定生成



================================================================================
六、后端路线：C 是 demo5 的正式后端
================================================================================

6.1 为什么坚持 C 后端
---------------------
第五版和后续正式版本都采用这一思路的理由很充分：
	- C 是跨平台最稳定的中间后端
	- tcc 可以提供内存编译与即时运行能力
	- xrt 本身就是 C 运行时，ABI 对接最自然
	- 以后接 GCC/Clang/LLVM，也不需要推翻前端


6.2 demo5 对 tcc 的定位
-----------------------
tcc 在第五版中的定位不是“语义执行器”，而是：
	- 一个快速可嵌入的 C 编译执行引擎

也就是说：
	- xlang 的语义必须在前端与 lowering 阶段就确定
	- tcc 只负责把生成的 C 编译并执行


6.3 第五版建议加入中间 Lowering 层
----------------------------------
不建议 AST 直接生成 C。

建议结构：
	AST
	-> 语义绑定后的 HIR
	-> 控制流 / async / generator 降级后的 MIR
	-> C 代码

HIR 的职责：
	- 保留源语言结构
	- 已经绑定符号与类型

MIR 的职责：
	- 消除高层语法糖
	- 明确临时变量
	- 明确跳转结构
	- 为 C 后端生成状态机与函数框架



================================================================================
七、第五版的关键语义设计
================================================================================

7.1 `for` 语句统一收敛
----------------------
第五版正式取消：
	for i = 1 to 10
	for i = 0 to 100 step 5

统一改为：
	for i in range(1, 10)
	for i in range(0, 100, 5)

原因：
	- 根目录问题列表已经指出 `to` 与 `range` 有歧义
	- `range` 是更稳定、更统一的运行时模型
	- 统一之后，编译器只需处理一种范围循环 lowering
	- parser 与语义层都不再为 `for ... = ... to ...` 保留兼容路径


7.2 `await` 是编译期识别的语义节点
----------------------------------
`await` 不是普通函数调用，也不是简单库糖。

编译期必须完成：
	- 只允许出现在 async 上下文
	- 确认目标表达式是否为 Awaitable
	- 生成挂起点与恢复点
	- 把后续代码切分到状态机的下一个状态


7.3 `yield` 是状态机切分点
-------------------------
`yield` 也不是普通函数调用。

编译期必须完成：
	- 确认当前函数是 generator 上下文
	- 为局部变量生成持久化状态结构
	- 生成 resume 点
	- 把 `for in generator` 统一转到迭代协议


7.4 `async` 与 `yield` 要明确区分
--------------------------------
第五版建议保留两套语义：
	- `async func`：返回 future/task
	- 普通 `func` 中出现 `yield`：返回 generator

不建议第五版首发支持：
	- 同一个函数同时既是 async 又是 generator

原因：
	- 这会显著提高 lowering 与状态机复杂度
	- 先把两条语义链跑通更重要


7.5 任务编排属于标准库能力，但需要编译器协助
--------------------------------------------
例如：
	task.all(...)
	task.race(...)
	task.spawn(...)

这些 API 本质属于标准库，但编译器需要支持：
	- async 上下文检查
	- future 类型识别
	- await 结果类型传播



================================================================================
八、异步与协程的 C 后端降级方案
================================================================================

这是第五版最关键的新增设计点。


8.1 async 函数的生成模型
------------------------
xlang：
	async func fetch(url) as string
		var resp = await net.get(url)
		return await resp.text()
	end

建议生成思路：
	- 生成一个异步状态结构体
		- 当前状态号
		- 局部变量快照
		- 当前等待的 future
		- 输出 future
		- 错误状态

	- 生成一个 step 函数
		- `switch(state)` 恢复执行
		- 遇到 await 时保存状态并返回
		- 等 future 完成后再次进入 step

	- 对外暴露一个入口函数
		- 创建状态对象
		- 创建输出 future
		- 调度第一次执行
		- 返回 future

底层依托：
	- xrt coroutine
	- xrt future / task
	- xrt 网络与异步文件能力


8.2 generator 的生成模型
------------------------
xlang：
	func count(n)
		for i in range(0, n)
			yield i
		end
	end

建议生成思路：
	- 生成 generator 状态结构体
	- 生成 `next/resume` 函数
	- 每个 yield 对应一个状态编号
	- 局部变量存入状态结构体，而不是 C 栈


8.3 为什么必须做状态机 Lowering
-------------------------------
因为：
	- C 本身没有原生 `await`
	- C 本身没有原生 `yield`
	- tcc 只会编译 C，不会替你理解 xlang 协程语义

结论：
	async / yield 的“语言难度”全部落在 xlang 编译器自己身上，而不是 tcc 身上。



================================================================================
九、异常系统的后端方案
================================================================================

9.1 异常系统必须进入第五版核心
------------------------------
原因：
	- 没有异常，async 错误无法完整传播
	- 没有异常，native 绑定错误只能退化成返回码
	- 没有异常，try/catch/finally 无法验证模块初始化与清理路径


9.2 同步路径建议
----------------
同步函数可继续沿用：
	- `XL_ExecCtx`
	- jump frame / setjmp
	- 当前错误对象


9.3 异步路径建议
----------------
异步状态机路径不建议依赖跨挂起点 longjmp。

建议做法：
	- await 恢复点统一检查当前错误状态
	- 如果 step 执行中发生错误：
		- 把错误写入 output future
		- 标记 reject
		- 结束状态机

这样可以保证：
	- 同步函数异常模型与异步函数异常模型对用户一致
	- 但底层实现可以不同



================================================================================
十、模块系统与标准库绑定
================================================================================

10.1 模块系统必须恢复
---------------------
第五版建议正式纳入：
	- import
	- export

暂不建议把 include 放入核心路线。


10.2 模块职责
-------------
模块系统在第五版中承担三类职责：
	- 组织 xlang 源模块
	- 组织标准库模块
	- 组织 native xrt 绑定模块


10.3 建议的标准模块分层
----------------------
	core
		- print / println / type / len / str / int / float / bool 等

	task
		- spawn / all / race / delay / cancel

	sync
		- channel / mutex / rwmutex / semaphore / atomic

	fs
		- 文件读写
		- 优先暴露 async 版本

	net
		- http / tcp / udp / socket 等 xrt 包装

	time
		- now / sleep / parse / format

	json/xson
		- parse / stringify

	os
		- env / argv / cwd / pid


10.4 native 模块绑定思路
-----------------------
建议每个 native 模块都有一份编译期描述：
	- 模块名
	- 导出函数列表
	- 参数签名
	- 返回值签名
	- 是否 async

编译器用途：
	- import 时完成签名绑定
	- 生成调用包装 C 代码
	- 做最基本的参数检查


10.5 外部扩展单元格式
--------------------
第五版需要正式承认 xrt 的外部扩展方式：
	元信息 + 可接入代码/库

建议编译器支持的分发单元：
	1. 共享库扩展包
		- xpack 包，扩展名 `.xle`
		- 内含 dll/so + 元信息文件

	2. 静态库扩展包
		- xpack 包，扩展名 `.xle`
		- 内含 `.a` + 元信息文件

	3. 分享库扩展包
		- xpack 包，扩展名 `.xle`
		- 内含 `.c` + 元信息文件
		- 可选附带 `.h`

这意味着：
	- 编译器导入外部模块时，优先读取元信息，而不是先猜测二进制符号
	- 元信息决定：
		- 导出函数
		- 重载映射
		- 调用约定
		- 类型桥接
		- 后续 custom/class 能力映射

结论：
	外部扩展的最小单元不是某个库文件，而是“元信息 + 实现载体”。


10.6 多版本依赖与版本绑定 ABI
---------------------------
第五版建议正式支持同名依赖多版本共存。

例如：
	- 库 A 依赖 库 C 1.0
	- 库 B 依赖 库 C 2.0

则最终编译时：
	- 库 C 1.0 与 2.0 都进入最终依赖图
	- A 继续绑定 C 1.0 的 ABI
	- B 继续绑定 C 2.0 的 ABI

为了实现这一点，编译器必须：
	- 读取 `.xle` 中的依赖项表
	- 为每条依赖边解析具体版本与 ABI
	- 在符号生成、模块导出、链接单元组织中保留版本信息
	- 把调用点绑定到“声明 -> 依赖边 -> ABI -> 目标符号”，而不是只绑定逻辑库名

结论：
	第五版不采用“全局只允许一个同名依赖版本”的策略。



================================================================================
十一、执行上下文与运行时 ABI
================================================================================

第五版需要一个正式的执行上下文 `XL_ExecCtx`。

它至少需要包含：
	- 全局变量表
	- 模块缓存表
	- 当前错误
	- 调用栈
	- 调度器句柄
	- 当前线程上下文
	- xrt runtime 句柄


所有生成函数建议统一形态：
	- 第一个参数都是 `XL_ExecCtx*`
	- 再跟业务参数

这样做的好处：
	- 异常传播路径统一
	- 模块访问统一
	- async / generator / native 都能共享同一 ABI 约定

================================================================================
十四、第五版的最终结论
================================================================================

第五版的核心不是“比第四版多一些语法”。

第五版的核心是三件事：
	1. 正式确认 xlang 的实现路线是“编译到 C，再交给 tcc 运行”
	2. 正式确认类型系统走“编译期查表 / 注册构建”路线
	3. 正式把第四版因基础设施不足而砍掉的异步、协程、任务编排等能力加回来


因此，第五版应被定义为：
	- 第一版真正沿着正式路线推进的 xlang demo
	- 第一版真正像“C 编译器前端”那样工作的 xlang demo
	- 第一版把 xrt 运行时能力系统性接入语言的 xlang demo


建议结论：
	- 不做解释器主路线回摆
	- 继续用 C 作为 demo 阶段统一后端
	- 继续深化第四版的类型注册系统
	- 以 lowering + 状态机生成方式落地 async / yield
	- 以模块系统承载标准库与 xrt native 绑定


如果第五版按这个方向推进，xlang 的状态就会从：
	“一个可运行的语法 demo”

转成：
	“一个真正开始具备正式编译器形态的语言实现”。
