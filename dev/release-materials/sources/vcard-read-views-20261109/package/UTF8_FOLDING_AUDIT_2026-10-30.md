# UTF-8 折行读取审查

## 问题与修复

原来对整个物理输入先检查 UTF-8，再移除折行。输入在多字节序列中间
折行时，即使展开后的字段完全有效也会被拒绝。
[RFC 6350 §3.2](https://www.rfc-editor.org/rfc/rfc6350.html#section-3.2)
要求先展开再解码，并建议读取端正确恢复被不当折行拆开的 UTF-8 序列；
发送端仍必须保持多字节字符连续。本库写出器原有完整字符折行不变。

修复只在 `vcard_parse.c` 将 UTF-8 检查移动到非空的完整逻辑行，连同
未知属性/参数和分组字段一起检查。3.0/4.0 的版本/包络规则、4 MiB
限制、NUL/CR 检查、映射、错误类别与资源归属均未改变。诊断文字相应
改为输入或 UTF-8 错误；没有新的模式、兼容别名或运行时包装。

没有新正文副本或缓冲，仍复用原来的逻辑行 xbuffer。原先整段的一次
UTF-8 调用变为逐非空逻辑行调用，总扫描保持线性，但调用次数改变；
本轮没有吞吐/体积测量，不承诺零性能影响。API、ABI、XRT 与主线未改。

## 独立防回归

- C 夹具分别验证 3.0/4.0 的 FN、NOTE、N、ORG、item1.EMAIL、未知属性、
  带引号的未知参数及重复 NOTE。336 个合法场景覆盖 SP/HTAB、2/3/4
  字节字符各切点与逐字节连续折行；解析后立即释放原输入，再检查
  独立字段、重复数组、规范写回与重解析。
- 352 个非法场景覆盖孤立续字节、过长编码、代理区、超范围、截断、
  非法字节、CR/DEL 和内嵌 NUL；折行和未知字段不能绕过检查。每次
  都核对 VALUE 和清理后的活动分配数/字节数、非法/重复释放/UAF 计数。
- 两种版本/八位置共 224 个实际 OOM 点必须保留 MEMORY、释放半成品，
  并在取消注入后用同一输入恢复，活动内存和错误状态保持平衡。
- C 回归在 GCC、TCC JIT/AOT 执行；Linux 原生 GCC 启用 ASan/UBSan。
  同一最终 C 测试重放旧解析器，两平台均有 208 条断言失败，修复后
  为零；这是一个顺序问题的多个场景，不是 208 个独立 BUG。
- XLang 源字面量仍必须是有效 UTF-8。`test/utf8_folding.c` 通过普通
  C 借用字符串提供真实折行字节，`utf8_folding.xl` 验证两版本、三种
  字符宽度、非法未知字段与 OOM，JIT/AOT 均通过。不为测试放宽语言
  规则，也没有把测试辅助函数加入包的公开接口。
- 用真实 cgen 的两个公开 extern 原型与 C 头对照；错误的 parse 返回
  类型必须以类型冲突拒绝，不能把任意编译失败都当作负例通过。

## 范例与门禁

新增 `examples/folded_contact.xl` / `folded_contact_c.c` 展示姓名、分组
邮箱和备注的读取、TEXT 恢复与规范写回。五条语言/引擎路径核对相同
三行输出和独立固定的完整 `.vcf` 黄金字节；两平台各五份正常 AOT
程序通过。原 C 范例还核对 GCC/JIT/AOT 字节及写入目录失败无输出。

Windows 默认门禁 44 项中前 43 项符合预期，其中包含一个错误原型与
两个失败写入的必拒绝负例；55 个输入/工具指纹在运行期间不变。
最后的原 `test/cases/extlib_vcard.xl` 因语言字典 build 的 M1 失败。
Linux 原生文件系统的前置矩阵通过后也在同一中央正例失败；52 个复制
源及 GCC/cc1/Python 三工具前后不变。两平台独立最小源的 JIT/AOT
均先通过原生对象写回，然后在语言字典处 ValueError。

因此 **M1 未关闭，整包仍不能签收发布级**。没有删改、跳过、改为
预期失败或用原生对象替代原语言字典正例，后续原语言用例/完整原
范例的阶段没有执行，不扩大为全包运行通过。

门禁有界执行并保留失败现场，Windows 另保存独立 stdout/stderr、状态、
预期/原始码的 JSON；Linux 保存合并日志、首错和真实命令。
真实 Windows 入口 silentCC raw37/outer1、Linux raw37/127 控制通过。
初写 PS5 脚本的无 BOM 中文注释、夹具重复宏和外层 xtrace 污染静默
输出断言均在工具层修正/分流后重验，不计为库 BUG。

  门禁 raw1 为真实 M1；外层确认前置、旧源、M1 和故障控制后退出 0，
