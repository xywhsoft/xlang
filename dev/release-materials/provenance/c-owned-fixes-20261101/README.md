# C-owned match / callback 修复验收

源码修复覆盖四项审计发现：`match` 方法组缺少期望签名、混合字符串/二进制分支依赖顺序、绑定回调丢失转换成本，以及 Windows CLI 门禁的 AOT 路径不一致。扩展回归另修复了回调类型别名在普通返回 ABI 适配时的编译器崩溃。每项修复有独立阶段提交；测试子门总预算修复另行提交。

使用规则见 [extern-owned-match.md](../../../../docs/extern-owned-match.md)。完整机器回执为同目录 `report.json`。历史构建/测试 JSON 按原字节归档到 `artifacts/`，保留内部记录的原始绝对路径；主线合入结果见 `integration/after.json`。

独立子门使用真实 GCC 翻译单元与生成的公开头文件，执行 O0/O2、分配失败、损坏 IR 拒绝等控制。新增正常程序分别扫描 512、384、512 个 XRT 分配失败前缀，检查外部分配器平衡、XRT 存活分配和原生句柄回收。两个新增编译反例验证泛型约束和私有成员。测试登记检查通过：3796 个自动文件、1 个手工探针、53 个前缀。

## 实际成本与边界

`@owned string` 方法回调的调用区间保留生产者原始指针，JIT/AOT、隐式 match 绑定与逐分支显式转换都只有生产者的一次 XRT 分配，没有 calloc/realloc/memdup 或调用结束前的 free；同一生产者的手写 C 对照也为一次分配。计数从回调构造之后开始，不能用它声称整个 OOP 调用与手写 C 等速。

C 释放器路径继续使用现有的 owner 记录，cstring 接管仍须确定 NUL 结尾字符串的长度。方法绑定仍有既有的闭包、接收者引用和代码生命周期成本。

**混合 bytes/cbytes 的普通 bytes 分支会多分配一个 owner 记录，转换本身不复制缓冲区。** 双端实测：单独 bytes 字面量一次 XRT 分配，混合 match 的两种分支顺序及既有条件表达式均为两次。普通 string 转入该载体不需要这个记录，单独 bytes 路径也不增加成本。消除这个二进制混合路径的记录分配需要另行调整载体或生命周期设计，本轮没有擅自扩大设计。

没有改变 xrt 或普通字符串的运行时布局，没有增加普通字符串读取分支，也没有增加回调转发层。显式请求普通返回 ABI 的语言 cstring/cbytes 回调仍按照既定规则复制；类型别名不改变该规则。原生 `@owned string` 继续要求真正兼容 xrtMalloc/xrtFree 的分配器。

## 构建与暂存记录

编译器源码包含主线 `0a12a07b0` 的 XRT 更新；后续 IDE 发布守卫同步不改变任何编译输入。Windows 候选按正式源码驱动脚本构建。Linux 所有 1396 单元从源码编译，并使用实际 TCC 配置与发布 TCC core；不把这个验收表述为正式发布库/VFS 重新认证。

Linux 早期尝试因暂存漏带两个示例文件中断；补齐后另一个尝试在独立 C 子门的 300 秒总预算内未完成。对象、头文件和驱动的 4362 个文件经哈希核对后制作原生文件系统镜像。再次运行确认总预算应与单阶段预算分开，测试工具已把独立子门总预算改为 1800 秒，各子命令保留原有超时。最终验收使用全新的输出目录，失败尝试不计入通过项。

额外源码快照和测量输入位于 `dev/release-materials/sources/c-owned-fixes-20261101/`。按 `manifest.json` 的 order 顺序解包可重建暂存输入；验证工具补丁单独记录。正式 `current-delivery.json` 沿用其他线程的已验收产品，本轮仅合入源码和测试，产品重建后才具有本轮行为。
