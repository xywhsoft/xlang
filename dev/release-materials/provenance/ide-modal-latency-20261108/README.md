# IDE 关于／MsgBox 打开卡顿根因（2026-11-08）

已确认根因：XGE 的窗口类型查询重复注册已有样式属性，每个注册又触发一次同步全界面样式重算；IDE 的关于窗口和消息框没有合并这批变更。发布程序未修改。

## 发布版实测

使用发布目录的原始 xge.dll 和匹配的 108 单元 GUI 构建，只在隔离诊断程序中添加阶段计时；窗口运行在私有桌面。每组创建独立进程，分别打开、关闭三轮，四次进程均正常退出。

| 操作 | 原路径首次打开 | 诊断中合并样式提交 | 原路径样式代数增量 | 合并后 |
|---|---:|---:|---:|---:|
| 关于 | 6,748.64 ms | 270.46 ms | 23 | 1 |
| MsgBox | 9,604.92 ms | 258.73 ms | 35 | 1 |
| 文件对话框 | 219.92 ms | 207.58 ms | 1 | 1 |

独立复测分别得到约 7.08 秒、9.85 秒、0.21 秒，结果一致。窗口打开后的稳定帧中位数约 0.8–1.4 ms；关于窗口复用打开约 2 ms，消息框后续创建约 4–6 ms。

## 因果链

1. `D:/GIT/xge/src/xui/controls/xui_window.c:1909`：`xuiWindowGetType` 在类型已经存在时仍调用 `__xuiWindowRegisterStyleProperties`。其注册助手不像 Button 等常用控件那样先检查属性存在性，因此重新登记全部 23 项属性。
2. `src/xui/core/xui_widget.c:3746`：`xuiStyleRegisterProperty` 对相同定义也执行替换，再调用 `__xuiStyleCommitChange`。
3. `src/xui/core/xui_widget.c:2926`：没有事务时，每次提交立即增加全局样式代数并调用 `xuiStyleRefresh`。
4. `src/xui/core/xui_widget.c:3554`：刷新遍历工作区根树与覆盖层；`xuiWidgetResolveStyle`（7945）重新构造并替换各控件的属性数组。所有工作发生在调用弹窗的 UI 线程上。
5. 首次 MsgBox 的 `__xuiMsgBoxEnsureType`（`src/xui/controls/xui_msgbox.c:122`）还注册 12 项自身属性，所以累计 23 + 12 = 35 次。

进一步隔离掉窗口创建、文字测量和绘制后，查询已经存在的窗口类型仍可复现：`xuiWidgetFindType(context,"window")` 约 0.0004 ms、0 次代数变化；`xuiWindowGetType(context)` 约 4,069.97 ms、23 次变化。后者包在同一事务内约 171.22 ms、1 次变化。这直接确认了类型查询／样式提交链路的影响。

## 为什么文件窗口比较流畅

`ide/src/ui/file_dialog.c:65` 在创建原生文件对话框时已有 `xuiStyleBeginUpdate/EndUpdate`。整批注册合并成一次提交。关于路径（`about_view.c` → `dialog.c:55`）及 `message_box.c:61` 没有等价的构建事务。文件窗口构造更复杂，但不会为每个样式属性重复重算整棵工作区。

## 建议修复顺序

- **XGE 公共机制优先**：已有类型查询返回稳定类型，不重复注册；属性注册对完全相同的定义应保持幂等，保留显式更新定义的合同。检查 Window 的缺失保护；IconPicker 源码也有未保护的同类形态，但本轮没有把它当作 IDE 已测触发点。
- **合并首次注册**：控件类型的首次属性初始化在原生层统一提交一次，嵌套事务及失败／回滚都需正确退出。源码扫描的 41 处同形调用中，39 处已有属性存在检查，不能机械地都认定为故障。
- **IDE 统一弹窗构建事务**：关于、消息框、更新提示等共享同一构建约束，与文件对话框一致。
- **继续压低单次刷新成本**：一轮全界面样式重算仍有约 0.2–0.3 秒开销。后续应限制到实际受影响的类型／继承子树，并保护未变更控件的解析结果，不能将合并提交的实验值视为最终性能目标。
