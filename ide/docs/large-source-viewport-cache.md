# 超长行可见范围缓存实验

2026-10-10，本轮继续优化大文件编辑。独立 SDK 增加了一次遍历计算可见范围，以及当前读取缓冲区的单结果缓存。八组真实编辑器检查全部通过，16 MiB 单行帧时间有所降低，仍有数秒延迟，性能尚未验收。当前应用核心、编译器和发布 SDK 没有替换，长期任务保持进行中。

前一轮结果见 [大源文件性能记录](large-source-performance.md)。本轮 SDK11 基于 SDK9，只修改一个源码材料：src/xui_code_edit.c。其余 236 个材料和公开头相同，两者均使用 GCC 16.2.0。原始发布 SDK 与 SDK9 的比较还涉及编译器版本变化，本轮没有混用这两种比较。

## 修改依据

对自己创建的 SDK9 C 16 MiB 单行进程进行了一次 GDB 栈采样。采样落在可见字节范围计算，经水平滚动模型进入字素遍历。旧代码分别从行首寻找视口起点和终点，重复查询也重复扫描。

新实现用一次遍历找出两端，保留旧的严格“下一视觉列大于目标列”规则。每个 CodeEdit 只缓存一个结果，键包含文档身份、文档版本、读取范围、起止视觉列和 Tab 设置，只对自己的完整当前读取缓冲区命中。缓冲区复制前先失效，覆盖分配或复制失败路径；行布局清理也使它失效。它没有增加字形或文本副本，也没有改写 Unicode、整形、语法、撤销或绘制裁剪规则。

采样进程实际完成 43 项检查并退出 0，但 GDB 会影响时间，所以该次时间不作为性能对照。第二次采样尝试被进程身份核对拒绝，未执行附加，随后原生运行确认终态；这次拒绝不计入通过项，也不说明 SDK 故障。实际性能表使用未附加 GDB 的八次新运行。

## 验证结果

使用新旧实际静态函数片段、真实 Unicode 字素函数和 SDK9 文档模型做等价检查，完成 461,674 项断言。覆盖中文、组合字符、ZWJ、区域指示符、Hangul、Indic、Tab、部分范围、非法 UTF-8 片段、视口变化、文档更新、缓冲区复用及读取失败。相同窗口的缓存重复查询没有再次调用字素遍历。首次夹具为空输入生成了无效 C 数组，严格链接退出 1；保留失败，修正夹具后实际严格链接和测试均退出 0。

SDK11 完整冷构建实际退出 0，237 个输入构建前后相同。构建沿用 -O2、-Wall、-Wextra 及原来的警告排除，不是整个 SDK 的 -Werror 构建。修改的 CodeEdit 编译单元另外以 -Werror 编译成功；这仅证明该单元的严格编译，不代表应用核心或整个 SDK 重新严格构建。新 SDK 的原始 Unicode、Emoji 两项测试也实际通过。

原生矩阵仍为 C / xlang × 2 / 16 MiB × 多行 / 单行，每例 43 项断言，共 344 项，八例实际退出码均为 0。每例在自己的 2 GiB 进程私有提交限制中运行，使用从未切换到前台的私有 Windows 桌面、1600 × 1000 窗口及 1.25 DPI 覆盖；操作为打开、绘制、定位、插入、撤销和空闲帧。语言服务未配置，检查不代表实体键盘或 IME。

两者最大的操作后采样私有内存分别约 964.3 / 965.8 MiB，Windows 峰值工作集分别约 1407.4 / 1401.0 MiB。操作后采样不是进程真正的峰值提交。这些是同一主机的单次观察，后台主机负载未完全隔离，没有统计稳定性或预先约定的性能通过阈值。

SDK9 与 SDK11 的八组最终窗口截图中，六组像素完全相同；两组 xlang 单行截图各仅有光标位置的 20 个像素不同，其余像素相同。人工查看了新的 xlang 16 MiB 截图，定版 Dock 布局、中央帮助、中文、Emoji、组合字符和语法状态保持正确。有限截图比较不证明完整字体越界、SVG 溢出或 DPI 裁剪正确。
