# canonical 类型文本存储实验（未采用）

本轮试验将原生类型索引中的逐字符串所有权改为一个索引持有的 XRT 字符缓冲区。类型文本仍在检查阶段完整生成、验证并参与声明身份构造；没有把工作移到首次悬停或文档大纲请求。完整语义、IR 转换和 verifier 保留。

**候选未采用，默认源码已恢复，根 `release/` 未安装。** 全新候选构建及正确性回归通过，但未满足预先约定的全部性能条件。九项候选差异文件及其精确摘要归档于 [开发源码覆盖](../../dev/release-materials/sources/lsp-canonical-arena-experiment-20261102/README.md)，不进入默认构建。

本次组合使用已审核的统一前端；当前仓库随后加入的 C 记录、类型化指针等变化不能凭本实验直接准入。长期目标、最新编译器／SDK／GUI 对齐及真正的有类型函数和最终 IR 局部生产继续保留。

## 数据和生命周期

- 复用原 canonical visitor、别名规则和字节／深度／访问次数限制，在私有 builder 中增加 XRT `xstrbuf` 输出目标。没有另写一套类型格式化规则。
- 只在空间不足时调用 `xrtStrBufReserve`，将原格式化片段写入共享缓冲区；每条文本保留独立 NUL，XRT 的末尾 NUL 另计。输入 AST 及其文本不可与输出缓冲区别名。
- 收集期间只保存偏移；全部收集成功后才转为只读指针，随后不再追加。偏移与最终指针共用原字段，宽度和对齐由编译断言保护，x64 fact 大小保持 56 字节。
- `xlsFrontendIndexDestroy` 释放共享缓冲区一次。失败时仍销毁整个未发布索引，恢复原有的 typed-build TLS 和新增的 arena TLS；不会逐项释放仍为偏移的字段。
- `xlsFrontendTypeCanonicalAppend` 失败时恢复原 Size 和前缀终止符，清零输出偏移／长度；容量可能已增长。此契约不承诺失败时恢复原地址或容量。
- 原生查询接口及其公开头文件不变，查询不触发延迟生成。Legacy JSON 继续使用原来逐字符串分配与释放的路径。

原生索引继续使用 32 MiB 的逻辑预算、每节点 64 字节的文本余量及原 `6 * length` 计量，数组容量按实际元素大小收费；新增缓冲区对象计入索引对象大小。共享缓冲区还检查成功时的实际容量。XRT 几何扩容可能复制既有内容，也可能在一次失败尝试中先增大容量；这些限制不是全局 RSS、内部内存池或瞬时峰值上限，不构成零拷贝或零开销声明。

四套现有精确 parser/XRT 组合均保持原摘要守卫。额外核对了 `xrtStrBufInit`、`xrtStrBufReserve`、`xrtStrBufFree`、`__xrtStrBufGrowth` 和 `xrtStrBufValid`：移除 API 宏及归一化换行后，其函数体在这四套 XRT 中一致。上游源码保持不变，构建器只从通过守卫的源生成私有 TU。

## 正确性证据

本轮资料位于 `ide/build/Release/lsp-index-arena-20261102/`。此前延迟生成实验位于 `ide/build/Release/lsp-index-display-20261101/`，完整保留，不作为默认实现。

最终共享缓冲区原型 `prototype-v4` 已完成：

- `native-v4`：126 项既有原生回归通过，包括完整导航对照和读者生命周期。
- `fixtures-v9`：15,632 项专项断言，覆盖原格式化输出对照、空文本、Unicode、8191／8192／8193 字节边界、深度／访问次数限制、多片段部分失败、前缀回滚、重试以及 3,000 个偏移经过扩容后的正确性。
- 3,000 个有类型节点的受控构造，可见 Calloc／Realloc 入口从 3,010 次降至 10 次，另有 13 次共享缓冲区增长操作。发布后的重复查询没有触发这些入口。原所有权实现被相同断言拒绝；此计数不等于 XRT 内部的全部分配次数。
- 32 节点构造的六个实际可见分配／增长拒绝点逐项失败后均清理并可重试。测试按实际地址跟踪公共分配和 XRT 缓冲区所有权；Release 的内存统计不可用，未把恒为零的统计当成堆无泄漏证明。
- 重新编译的真实 collector storage 夹具通过 12,651 项断言、26 个原对象／fact／来源分配故障点，保留 Legacy JSON、深度、实体歧义及 TLS 检查。新增 arena TLS 哨兵也覆盖成功、失败和重试。
- `negatives-v4`、`storage-tls-v4`：四种实际 C 遗漏分别移除缓冲区释放、指针封存、字符串 NUL 和 TLS 恢复，均被原断言拒绝。
- `wire-v4`：62 个真实服务进程，增量与全新检查、悬停、定义及补全对照通过；退出、stderr 和清理记录正常。

专项发现并修复过空文本在全新缓冲区中写入空指针的问题；失败原型、编译／链接错误和早期不充分的内存统计尝试均保留。最终证据只采用修正后的地址／缓冲区所有权跟踪，不扩大为所有 CRT、XRT 内部池或编译器 OOM 的证明。

恢复资源后的正式源构建 `product-full-v2` 全新完成 224 次编译和 127 项原生回归，记录 775 项输入及 129 项产物。永久专项复现 15,632 项断言；collector storage 的 12,651 项及导航的 132,357 项对照均通过。`product-omissions-v1` 使用该构建重编译四种真实 C 遗漏，全部被原断言拒绝；`product-wire-v1` 的 62 进程对照和 `product-validation-v1` 的 56 套既有协议回归均通过。

原对照构建的 772 项输入和 128 项产物也完成核对：五项本轮修改过的输入保留修改前的精确字节，存于 `original-product-inputs`，并与原报告摘要一致；其余输入及全部产物仍一致。原报告的字节和记录路径没有重写。公开索引头文件未修改，正式源构建仍将全部消费者一起重新编译。

## 性能与资源状态

两对进程、512 函数的小样本测试保留原门槛及全部慢样本：A/A 失败 2/96 项，候选导航链失败 4/96 项，文档大纲镜像失败 20/96 项。后者包含 12 项相对门槛和 8 项绝对延迟门槛。这些结果不能表述为无退化或正式准入。

首轮正式 32／512 函数、八对进程测试在完成 1,692 个请求后，系统可用提交额度跌破运行中 3 GiB 的原底线而中止；114 个已启动服务进程均正常退出，未执行剩余导航任务。随后全新构建在第 14 个对象的编译中发生 `cc1.exe: out of memory`。原报告和失败状态保留，未把部分采样或部分对象当作完成的性能验收或完整构建。

用户暂停其他大内存任务后已恢复工作，从新的 `product-full-v2` 目录完整重建。正式测试仍要求启动时至少 5 GiB、运行中至少 3 GiB 的系统可用内存和提交额度；不修改原门槛，不筛除成功但缓慢的请求。计时期间不并行运行本任务的编译、回归或大规模摘要检查。

## 复现入口

以下为候选验证时的入口。先按 [归档说明](../../dev/release-materials/sources/lsp-canonical-arena-experiment-20261102/README.md) 在完整源码副本中恢复九项差异；当前默认源码已移除实验工具，不能直接把这些命令当作活动版本的新增功能。输出目录须尚不存在。这里使用冻结前端做版本对照和故障注入，是为保护尚未对齐的根工作发行版。

```powershell
python -X utf8 -B ide/tools/build_lsp_core.py --frontend-root ide/build/Release/lsp-frontend-alignment-20261101/frontend --output ide/build/Release/lsp-index-arena-20261102/product-full-v2 --server
python -X utf8 -B ide/tools/check_lsp_index_arena.py --build ide/build/Release/lsp-index-arena-20261102/product-full-v2 --output ide/build/Release/lsp-index-arena-20261102/product-omissions-v1
```

故障工具要求完整、通过且输入／产物摘要仍一致的正常构建。每个变体只替换一个私有 include，重新编译真实 owner 或 collector 夹具，再链接匹配的 archive；正常构建和断言体保持不变。协议对照、GUI 接入、整体性能和全局资源验收仍分别需要相应范围的证据。
