# 重命名的配置范围与跨工程引用收集

本阶段在现有工程引用 actor 上建立重命名的工作区范围，沿用原检查器的声明身份、完整成员覆盖、输入守卫和后台缓存。它不是最终的重命名事务，仍未注册 `renameProvider`。

`analysis_catalog` 继续服务普通查询的工程选择；新增的全归属查询复用同一个已排序原生路径索引，返回所有明确登记该文件的工程。选择 A 工程不会让共享文件的 B 工程归属消失。准备好的原生键查询没有分配、磁盘访问或目录扫描，复杂度为二分查找加最多 64 个匹配归属。目录包含关系、同名文件和导入成功都不能补出成员资格。

`rename_scope` 用 XRT 管理不可变对象，保留完整 catalog 和明确打开的独立 xlang 文件上下文，总计最多 64 个分析范围。工程顺序沿用 catalog，之后是独立文件。独立文件只贡献自身入口；其导入文件和所在目录不因此获得成员资格。所有分析配置原样保留，位图的位置只能与同一个范围快照一起使用。默认及最大 128 MiB 预算计入完整保留的 catalog、原分配的成员容量、上下文、文件键和对象，即使另一个调用者也共享它们；这不是进程 RSS、临时路径转换或分配器元数据的预算。

`xideProjectReferencesSubmitRenameScope` 接收原生目标和一个准确配置范围，使用原目标独立拥有的声明来源、完整文本和字节区间，在该范围的全部成员中收集引用。该工程不必拥有或导入最初的查询文件；无关工程也要完成检查后才能返回空结果。使用原有后台队列、成员覆盖、原生 shard、缓存、取消和最终输入守卫，不创建第二个编译器或主机层名称搜索。

声明必须位于明确配置的 `.xl` 源文件。每个实际引用也必须属于整个范围快照中明确配置的源文件；隐式依赖里的引用不能被悄悄跳过。未登记的声明或引用、检查失败、声明完整来源变化、输入变化、基础设施错误及取消都不能给出部分成功。结果始终带现有的来源证明，并包含声明。调用者仍须对每个 ScopeAt 收集结果，按来源区间去重，核验当前配置、输入和发布 epoch。

队列保留目标、配置范围及输入文本，调用者释放自己的引用不影响已提交任务。队列上限仍为 8；若每个请求使用不同的最大范围快照，仅这些保留快照的上界可达 8 × 128 MiB，另有原有检查、缓存、守卫和结果成本。这里没有把共享引用计为零成本，也没有声称最终内存或性能准入已经完成。

这一阶段证明的是明确成员资格和准确声明的逐范围引用收集。物理别名、操作系统可写性、库和外部符号的完整访问策略、继承和重载族、冲突及改名后的绑定证明、精确标识符编辑范围、版本化 WorkspaceEdit 和 IDE 原子事务仍须完成。不能据此直接写文件或宣称完整重命名已支持。

验证通过 167 个原生夹具、10 套协议与 27 个 IDE 夹具。新增范围检查 1121 项、跨范围原生引用检查 116 项；四个实际 C 变体分别遗漏共享归属、放开独立文件边界、遗漏未登记引用或忽略声明来源失配，均被拒绝。资格检查绑定 275 个实际消费者、168 个程序及 core 的所有成员，故障注入的工程调度副本也从当前源码重新生成。IDE 完整重编译 116 个对象，配对同一语言服务和匹配 SDK，覆盖 C/xlang 输入、删除、撤销、Unicode/IME、焦点和语言功能，浅色与深色截图已复核。默认六个发行程序/DLL 保持，未进行新的正式性能准入或线上发布。可恢复材料入口为 `dev/release-materials/provenance/lsp-rename-scope-20261110.json`。

后续的[全工作区收集](lsp-rename-workspace.md)在同一 actor 上合并各范围的原生行，并在完成最后一个范围后重新核验所有输入守卫。
