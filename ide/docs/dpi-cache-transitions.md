# DPI 与窗口视口变化时的绘制缓存与内存

IDE 在实际 DPI 比例变化时，先通过固定 SDK 的缓存清理接口释放可重建位图，再事务更新字体与目标表面。XUI 随当前布局重建绘制缓存；Dock、代码编辑器和其他控件的缓存策略继续启用。正文、撤销、选区、文档版本与语言模式保留。DPI 比例与逻辑视口尺寸均不变时，不触发这次清理。

旧流程会把上一布局的全部目标表面按新比例重新分配，之后视口和布局变化又使许多缓存失效。本轮对真实原生窗口进行逐次资源记录：125% → 200% 时，清理前有 63 个管理表面，清理后只余主目标；后续绘制按新布局创建有用缓存。此改动位于应用帧入口，独立 DPI 代理的事务更新与失败回滚保持原合同。

## 实际比较

私有观察构建复制当前源码，只加入内存／尺寸记录及可选的 Windows Job 进程提交上限。比较构建仅增加上述缓存清理操作。程序运行在从未切换的独立桌面，使用同一固定 XGE DLL、同一 CodeEdit 场景和真实 Win32/XUI。系统设置和其他进程保持原状态。

| 场景 | 旧流程 | 清理后流程 |
| --- | --- | --- |
| 普通原生场景 | 94 项检查通过；观测峰值 722,092,032 字节，约 689 MiB | 94 项检查通过；观测峰值 498,610,176 字节，约 476 MiB |
| 正常启动提交量 + 128 MiB | DPI 表面分配返回 -5，程序退出 1 | 全部 94 项检查通过，程序退出 0 |
| 正常启动提交量 + 16／64 MiB | DPI 表面分配失败，程序退出 1 | DPI 更新提交成功，后续捕获复合断言失败，程序退出 1；没有计为通过 |

峰值取实际 PROCESS_MEMORY_COUNTERS_EX.PeakPagefileUsage 计数；记录也保留 PrivateUsage 和当时系统可用提交量。代理 RGBA 字节为其管理表面的估算，并不包含全部字体、驱动或 GPU 内存。约 31% 的峰值下降是本机这对私有观察场景的结果，不能推作所有机器或工程的保证。进程上限只限制指定子进程；没有通过耗尽系统内存制造失败。

最初控制器仍预期原夹具的 93 条断言，新增一条内存上限设置检查后实际为 94，导致控制器拒绝；当次原生程序确实退出 0。原脚本、记录及日志继续保留，后续三个受限观察复用同一严格构建的私有可执行文件。观察构建与生产程序分开；生产程序使用普通夹具，仍是既有 93 条跳转断言。

## 生产验收

## 尚未证明的事项

原始 DPI GPU 错误 -9 和独立 4K 最大化错误 -5 没有逐次分配记录。本轮解决已测到的 DPI 缓存重建重叠，不据此认定那两次历史失败根因。纯窗口尺寸变化、其他驱动、真实系统低内存、实体混合显示器／IME、干净 Windows 与完整 C 输入图／ABI 等事项继续核对。长期目标保持进行中。

## 纯窗口尺寸变化（2026-10-10）

窗口逻辑尺寸变化时，IDE 同样先释放可重建 XUI 缓存，再分配新主目标。主目标仍先创建成功再替换；既有 DPI 代理事务保持。所有缓存策略继续启用，布局按新的视口重建。DPI 已先清理时，随后这次清理可为空操作。

真实 Win32 窗口固定 100% DPI，依次使用 3840×2100、1920×1080、1000×650、3840×2100、1400×900 客户区。每次 SetWindowPos 后返回 XGE 事件循环，确认原生客户区和 XGE 尺寸精确一致，再执行实际帧。两种顺序各通过 48 条检查，验证 C/xlang 正文版本、脏状态、选区、撤销、字体实例及中央底栏／右侧上下 Dock。基准 C 和比较 C/xlang 的三张原生图已查看。

| 本机私有观察场景 | 旧尺寸更新顺序 | 提前清理旧缓存 |
| --- | --- | --- |
| 普通五次尺寸变化 | 48 项检查通过；峰值 889,925,632 字节，约 849 MiB | 48 项检查通过；峰值 861,798,400 字节，约 822 MiB |
| 正常启动提交量 + 448 MiB | 退出 1，实际缓存表面分配 -5 | 退出 1，实际缓存表面分配 -5 |
| 正常启动提交量 + 464 MiB | 退出 1，实际缓存表面分配 -5 | 48 项检查通过，退出 0 |
| 正常启动提交量 + 512 MiB | 48 项检查通过，退出 0 | 48 项检查通过，退出 0 |

约 3% 的峰值下降仅来自本机这一对私有程序；进程上限相对于各自正常启动的 PrivateUsage，实际绝对上限记录于原始日志。不是全机低内存压力，也不保证其他工程或驱动获得相同比例。448 MiB 两次失败未计为通过；464 MiB 的旧流程失败也未计为通过。

前两次观察夹具失败继续保留。第一次在同一 XGE 回调内要求尺寸已更新，第二次请求 3840×2160 客户区实际受到原生窗口约束变为 3840×2141。第三版返回事件循环并使用能精确实现的 3840×2100，保留严格尺寸断言。两个早期过程不计为成功比较；不能据此断言 IDE 渲染失败。

生产严格 Release 的 83 个实际对象另行链接基于同一窗口夹具并补充首次 3840×2100 实际像素截图的测试，未替换生产 DPI 或应用对象，50 条真实窗口检查通过；12 项邻近检查和完整 90 类运行回归通过。源码只增加窗口尺寸变化前的缓存清理，编译器及固定 SDK 未改。[纯尺寸比较](../build/viewport-memory-comparison-v1.json)、[受限原生观察](../build/viewport-memory-caps-v1-run.json)、[生产对象验收](../build/viewport-memory-production-v1-run.json)、[完整回归](../build/viewport-memory-full-v1-run.json)与[最终核验](../build/viewport-memory-final-v1-verification.json)记录准确范围。此前 4K 最大化 -5／DPI GPU -9 的故障没有本次逐项记录，仍不认定历史根因已经证明；实体输入／混合 DPI、干净 Windows、完整 C 输入图／ABI 和正式发布继续。
