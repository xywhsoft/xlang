# 单次整形中的字形度量复用实验

2026-10-10，SDK19 的数值度量复用通过了语义、绘制和应用回归，但本轮原生测量没有证明交互性能改善。该版保留为可复现实验，不选作安装候选。长期任务继续，当前应用与便携候选保持原样。

上一版见[字形查找复用](large-source-shape-lookup.md)。SDK19 相对 SDK17 的 237 个源材料只改变 `src/xge_text_run.c`，公开头相同。比较程序与原生矩阵分别使用匹配的新旧源码或 DLL，没有混用两个版本的查找表。

## 实验内容

至少 256 字节的单次整形使用 64 槽的调用内查找表，在复用实际字体与字形编号的同时，保存整形消费的两个数值：前进宽度 `fAdvanceX` 和右侧边界 `fX1`。每槽由 16 字节增加到 32 字节，槽数由 128 减至 64，总表大小仍为 2,048 字节。散列冲突重新解析并替换条目；度量失败不缓存，保留原来的失败、输出与重试规则。

表返回即失效，没有新增跨调用字体状态、正文、逐字符或字形数组。整段结果分配、字体引用、字距、Emoji 匹配、UTF-8 扫描和行度量仍使用原规则。比较编译的静态栈使用记录新整形函数为 2,432 字节，SDK17 比较函数为 2,448 字节；这不是整个调用链的峰值栈用量或跨平台保证。

源码准备第一版因过宽的检查误把合法的 `tEmojiMatch.tMetrics` 当成应移除的局部度量变量而退出 1。该版已复制的独立源目录保留，尚未写入新整形代码或启动构建。第二版仅修正准备器的检查并复用已冻结的基线，使用新的实验目录。后续构建、比较和回归对应第二版目录；没有把准备失败算作通过的构建。

## 实际验证

整套 SDK 严格冷构建使用 `-O2 -Wall -Wextra -Werror` 和既有三项警告排除，实际退出 0，耗时 146.312 秒。237 个输入前后相同；DLL、导入库与资源对象成套保存。SDK17／SDK19 的 5,949 个导出名称与序号一致，这不等于完整 ABI 验收。

真实比较在一个引擎程序中包含 SDK19 实现和 SDK17 的原始查找表、解析辅助函数及整形函数。SDK17 表仍为原来的 128 槽。程序是唯一 XRT 所有者，不链接 SDK DLL，也不向 SDK 添加诊断钩子。

原始夹具与落盘的独立入口各实际通过：

- 14,809,718 项断言，2,822 组完整整形。
- 3,365,718 项标量查找，6,672,384 次实际新旧数值度量对照。
- 108 组新旧像素对照，其中 12 组明确非空的 ASCII 控制。
- 三组受控的无效字形度量，确认失败不缓存、数值输出不被改写并能重试。

两次原生运行分别耗时 1.859／1.735 秒，严格编译和运行均退出 0。使用本机 Consolas 与仓库 Noto 字体，覆盖四个字号、三种回退顺序、Unicode 标量、重复与冲突查找、缓存启用边界、中文、组合字符、非 BMP、Emoji／ZWJ、不同标志、缺字、换行、Tab、嵌入 NUL、非法 UTF-8、1 MiB 重复文字和无后端回退循环。完整字形结构、簇、行度量、字体顺序及引用恢复匹配。有限字体、像素和策略不构成完整复杂 Bidi、所有字体、GPU 故障、并发字体修改或分配失败验收。

三个原始 SDK 测试和六个现有 IDE 程序均退出 0，后者为 `document`、`editor_view`、`goto_view`、`find_view`、`input`、`reading`。应用程序没有重新编译，在独立目录加载 SDK19 DLL；本轮没有执行新 SDK 的完整标准回归或便携验收。输入事件测试不等于实体 IME 验收。

## 下一处耗时与复现入口

本轮另对 SDK17 的 C 16 MiB 单行做了一次独立调用栈观察，所有进程均自行创建，调试器附加前核对 PID、创建时间、可执行路径和仍有效的自有进程句柄。两次 GDB 附加、采集和分离均退出 0，应用最终退出 0 并完成 43 项检查。该运行带调试器，明确排除在上述性能矩阵之外。

两个栈都处于 `__xuiUnicodeDecode`／`xuiInternalTextGraphemeNextRead` → `__xuiCodeEditVisibleByteRange` → `__xuiCodeEditCacheRender` → `xuiRender`。这是当前候选在绘制时进行可见范围字素遍历的直接证据，不能仅凭两次采样断言其占总耗时比例。源码已有可见范围缓存和超过视口末端即停止的扫描；下一步检查滚动到长行末端时的前缀遍历、缓存有效条件与调用间复用，不盲目扩大字形缓存或改变 Unicode 边界规则。
