# SDK48 长行编辑路径耗时诊断

2026-10-11，已在当前 SDK48 上测量读取、可见范围、列计算、布局和绘制五条编辑器路径。16 MiB 长行的读取复制约需 1–3 ms；可见范围和列计算仍从行首遍历，重新绘制仍遍历整段文本。现有的布局前缀复用在输入和撤销时约需 33 ms。结果将下一项实现指向重复的行遍历及整段绘制。

当前可运行 IDE 候选继续使用 SDK48，详见[集成候选验收](integrated-editor-sdk.md)。此次 SDK50 是私有诊断版，没有安装到产品，没有发布新的 SDK 补丁包，也没有把极长行性能标记为通过。

## 诊断方法与行为核对

诊断版从已选择的 SDK48 的 241 份源材料生成，只修改编辑器实现及布局内部文件。五个函数的原有函数体保留；添加计时包装、可见范围分支标记、读取分支标记和已计算的公共前缀长度记录。计时与输出保存 Windows 错误状态和 errno。公开头文件不变，整个 SDK 的 O2/Werror 编译实际退出 0；5,954 个导出名称及序号与 SDK48 相同。这不能代替完整 ABI 验收。

原生测试程序复用 SDK48 测试程序的 83 个应用对象，只增加操作阶段标记并链接诊断 SDK。C 与 xlang 分别测试 2 MiB 和 16 MiB 长行，执行打开、Ctrl+End、输入、撤销、Ctrl+Home、再次定位和空闲帧。四个进程均正常退出，共完成 180 条检查；与对应 SDK48 原生截图的四组逐像素比较均为零差异。进程只在从未切换的自有 Windows 桌面运行，输入文件和既有候选保留原字节。

计时使用 QueryPerformanceCounter，仅记录至少 64 KiB 的调用。下表是同一操作阶段内各函数调用的包含式时间，包含其嵌套调用及部分日志开销。各列不能相加为总耗时，也不能换算成互斥的时间占比。每个用例只有一次观测，背景负载未隔离，诊断结果不计作无插桩性能验收。

## 16 MiB 长行编辑

| 语法 | 操作 | 读取复制 ms | 可见范围扫描次数 / 合计 ms | 列计算 ms | 布局前缀复用 ms | 绘制 ms |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| c | 输入一个字符 | 2.294 | 3 / 318.420 | 106.728 | 33.800 | 584.485 |
| xlang | 输入一个字符 | 2.312 | 3 / 317.197 | 106.540 | 33.800 | 579.551 |
| c | 撤销 | 1.240 | 3 / 317.679 | 107.450 | 32.586 | 575.123 |
| xlang | 撤销 | 0.955 | 3 / 318.817 | 106.601 | 33.103 | 585.640 |

输入与撤销的布局调用均核对到 16,777,216 字节的公共前缀。可见范围函数在这两个阶段各重新扫描三次；已命中的可见范围结果几乎不耗时。单次未命中扫描及列计算均约需 106 ms。读取复制规模与长行一致，但耗时很小，不能据此前的缓存失效现象把复制本身视为主要成本。

首次打开还需要建立完整布局；该布局调用包含在首次绘制中：

| 语法 | 首次完整布局 ms | 首次绘制 ms |
| --- | ---: | ---: |
| c | 675.193 | 1253.956 |
| xlang | 641.167 | 1223.729 |

## 下一项实现

先处理同一文档版本下可见范围和列计算的重复行遍历，再处理编辑或滚动后仍需完整遍历的绘制。行级索引或检查点应直接服务于定位，避免只给某一种查询再叠加局部缓存。文档替换、读取失败、版本变化、制表宽度变化和非完整 UTF-8／文本簇边界必须保留正确结果。

绘制改动还需保持最终升部与行高、画笔浮点相加顺序、字偶调整、活跃字体和图集状态、Emoji／SVG 裁剪及失败回退。诊断时间不能代替同批实际窗口对照、逐像素比较和功能回归；上述成本也不证明任意一种索引或绘制复用方案已经有效。
