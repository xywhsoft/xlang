## 测量方式

工具运行真实外部原生服务，经 stdio 发送配置、未保存正文及 `xlang/check`。支持 32／512 辅助函数、独立文件／导入模块、单函数字面量／双函数声明编辑。每个进程对同时保留两边服务，每代按 AB／BA 交替查询；进程启动顺序也按进程对交替。源码生成不在请求时钟内。

每次响应核对版本、配置 epoch、成功语义结果及独立工作线程，并比较除分析工作统计和服务耗时外的全部标准结果。完整分析统计、所有成功慢样本、stderr 和协议 transcript 均保留。首次、第一次改动、后续热请求和相同请求重复分别汇总。

启动前保存不可变计划及程序、已知 xlang 运行库、工具、辅助脚本和占位文件的 SHA-256；完整运行后再次核对。每次启动／请求前检查物理内存和可用提交额度。资源、协议或输入验证失败会使整轮无效，仍回收全部已启动服务并保留失败记录；不从部分样本计算门槛。

Windows 后端记录请求墙钟、进程 CPU、`QueryProcessCycleTime` 周期计数和内存。周期计数仅供诊断，不替换原 CPU 门槛。进程 CPU 可能约为 15.625 ms 粒度；请求后的内存快照不是瞬时峰值，另保留 OS 生命周期峰值工作集。

配对模式会同时保留两个服务的内存，其环境与此前顺序运行进程的筛选不同，不能直接合并为同一验收样本。工具没有自动功能准入：即便全部门槛通过，`accepted` 仍为 false。它也不代表 GUI 绘制、完整工程或完整 LSP 验收。

## 三种运行模式

- 默认比较模式要求两个程序，保留原 5% P50／P95／CPU 非退化门槛、0.5 ms 墙钟绝对容差、10 ms 缓存请求 P50 和 192 MiB 额外私有内存界限。可以预先指定双函数编辑的收益比例。
- `--calibrate` 要求两边程序逐字节相同，并核对已知运行库，默认两边运行同一路径。相对门槛失败可以暴露本轮测量波动；绝对预算失败也可能说明基线本身慢，应分别判断。校准不构成候选验收。
- `--functional-only` 只验证传输、结果、计数器、输入保护和进程回收，不计算性能门槛，不支持性能结论。只有该模式允许使用低于正式性能下限的资源设置。

正式比较／校准至少要求起始 5 GiB 余量、逐请求 3 GiB 下限，不能通过参数降低；资源不足后不得把中止结果解释为通过。新输出目录必须不存在，计划和历史结果不覆盖。

在仓库根目录，以下命令使用已保留的原生开发程序；默认发布的 CLI 后端服务不作为本工具的原生性能目标：

```powershell
$before = '.\ide\build\lsp-m75-20261030-1fa6d284\matched-control-v1\xlang-ls.exe'
$after = '.\ide\build\lsp-m74-20261030-72a4b519\qualification-v1\native-v2\xlang-ls.exe'
python -X utf8 -B .\ide\tools\benchmark_lsp_analysis.py --baseline $before --calibrate --edits literal --output .\ide\build\analysis-calibration-new
python -X utf8 -B .\ide\tools\benchmark_lsp_analysis.py --baseline $before --candidate $after --declaration-ratio-32 0.90 --declaration-ratio-512 0.85 --output .\ide\build\analysis-comparison-new
```

这组同宿主比较示例不会替换 M74 原对照及其 11 项失败；正式准入仍需完整的正确性、原门槛和目标范围证据。默认每场景四对进程，属于筛选规模，不是尾部分布的充分验收。

## 本轮验证

先建立同一完整运行时／宿主的对照：64 个核心成员逐文件核对，保留完整构建的 63 个成员，仅用原 0.99 的语法成员替换候选语法；19 个宿主对象不变。原语法源码与当前根工作树一致。三个原生 fixture 重新链接并通过。首次二进制绑定检查误用 Windows `ar p` stdout，发生换行转换；保留失败，随后在新目录提取并逐文件验证原始载荷，没有用错误的字节流支持绑定结论。

四个普通程序组成两组诊断：原 0.99／仅替换语法成员的候选，以及同宿主对照／完整候选。432 次请求、48 个进程全部标准结果一致，并核对实际语法工作；它是诊断，不是 M74 正式补验。

| 场景 | 原 0.99 → 语法候选 P50 ms | 同宿主对照 → 完整候选 P50 ms |
| --- | ---: | ---: |
| 32 独立字面量 | 18.758 → 19.102 | 18.717 → 19.240 |
| 512 独立字面量 | 457.360 → 450.630 | 485.726 → 456.541 |
| 512 导入字面量 | 641.398 → 617.971 | 568.128 → 540.854 |
| 512 导入双函数声明 | 882.300 → 576.417 | 911.999 → 589.203 |

没有复现稳定的普通编辑热 P50 退化，但尾部仍有上升，例如同宿主 512 独立字面量 P95 为 651.932 → 684.876 ms。不能据此将 M74 的原失败改判为通过。

新工具的 A/A 校准计划为 480 请求／32 进程；在第 460 个请求前发现可用提交额度约 2.898 GiB，低于 3 GiB，整轮无效。459 个成功请求及全部 32 个正常退出记录保留，没有计算数值门槛，也没有进行同一轮重启。尚不能确认该主机当前能稳定分辨 5% 差异。

工具自身另外完成以下验证，均不作为低资源性能验收：

- 回放 M74 原完整 960 请求，64 项实际值、界限及通过／失败标志逐项一致，原 11 项失败全部重现。
- 拒绝不同程序作为 A/A 目标，并在创建输出目录前拒绝降低正式资源下限。
- 两组功能模式共 160 次真实请求、32 个进程通过：一组同程序，一组同宿主旧语法与候选。候选的实际两个片段与对照的全量解析均被保留，标准结果一致，不计算性能门槛。
- 真实发布 CLI 后端在编译器不可用时返回协议错误，工具失败并正常回收两个服务；首次外围验证脚本预期另一条错误文本的失败也保留，未通过重跑替代真实记录。
