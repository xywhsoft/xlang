# 当前语义键、拥有型事实与编号重绑定

2026-10-30，M7a2b79a。接续固定提交 `9192a99f96ecd83bd57ca6e53df6dfcdda7d2f15` 的 AST、语法和索引适配。本阶段补齐当前 AST 元数据在语义缓存内部的编码、拥有型复制、预算、销毁、证明与原子重放。完整当前语义适配仍未准入；开发基线保持 0.99，根 `release/` 保留。

## 缓存表示

当前布局的语义键增加接收者编号、编译包错误／根标量和链接文本，递归覆盖普通子节点、推导类型及声明类型。NULL 与空链接分别编码。旧布局保留原来的字段集合。

IR AST 输入键同步保留这些值。只有已由原词法声明证明的接收者编号才可编码为函数内槽位，且槽位／原生编号／稳定实体各有独立标签；事实类型树中的编号保留原分类。执行区域的原归一化字段位置没有移动。实体编码仍要求调用方另外证明相同 store、上下文和模块，编码结果自身不是复用准入。

当前布局的平面语义 fact 保存三项标量及拥有型链接，字符串由 XRT 独立复制。捕获发生在类型树已取得独立所有权后；共享类型森林的 unit 仍单独拥有平面 fact 的字符串。销毁两种 unit 时都释放链接，不把它混入类型森林的所有权。

重放先在私有暂存中复制字符串与类型。失败时清除仍借用旧 unit 的指针，只释放本次构造；通过全部范围、来源和编号检查后，才把字符串移交给目标 AST。旧缓存及失败目标保持不变。

平面链接占用从类型复制预算中扣除。余量为零时不调用“零代表默认预算”的 AST 克隆入口，避免意外放大额度。完整事实证明和延迟正文证明同时计入平面／类型链接，并分类接收者编号。跨函数或未证明的动态编号拒绝重绑定。

## 接口与验证边界

当前前端的签名排序函数、泛型 callable 构造的上下文参数、三态路径比较已适配编译；旧布局继续调用原接口。本阶段不宣称完成签名捕获的运行验证。

新增 `tools/build_lsp_semantic_facts.py`。它核对上一阶段完整基础库的输入／输出摘要和编译器，复用该库，分别新编译 7 个专用对象。测试 TU 使用原语义适配器的实际私有函数，不维护第二套 fact 或键实现。普通 namespace、raw-body scope、词法符号及实体查询使用真实代码；未安装的签名／补全池捕获有明确的终止护栏，不能模拟成功。

工具仅显式请求 `_current_unit_probe`；正常服务构建没有这个入口参数，当前语义守卫依旧拒绝。当前主 TU 的 71 处类型查询只是本次单元派生时核对的数量，不是完整读取覆盖声明。

尤其需要继续审查当前新增包含文件 `xl6_sem_c_owned.c`、`xl6_sem_special_collection.c` 和 `xl6_sem_constructor.inc`。例如 `xl6SemCOwnedSpecialize` 会通过 `declarations` 向模块或类正文追加私有特化声明；这种副作用不能由字段复制、相同计数或一次普通函数复用替代证明。完整读取族、声明变动、注册表及跨结果重放尚待准入审核。

## 已验证的单元

当前前端 341 项检查、旧前端 108 项检查通过，覆盖：

- 四种树位置的新键属性与 NULL／空链接；真实已检查函数的词法编号移动、原生数字碰撞、类型树保守分类、稳定实体映射和标签分离。实体映射由真实索引 TU 私有布局及 XRT 数组构造，只验证编码规则，不替代加载器／全局域证明。
- 独立／共享类型 fact 捕获，来源 AST 提前销毁、字符串独立所有权、成功重绑定、非法编号拒绝与目标完整键保持不变，以及仅够平面字符串的不足预算。
- 证明中的接收者移位资格，捕获／借用暂存的 6 处定向 `xrtStrDupN` 失败及逐点成功重试、逻辑分配平衡和旧来源保护；这不是全部 allocator 位置的 OOM 验收。
- 原检查器真实执行两个函数的连续版本，一处正文改动重新检查、另一处函数实际复用；与同一原检查器的无 memo 完整路径比较完整 AST。这个用例不覆盖所有新语言规则或外部副作用。

旧布局的派生语义 C 与原生 0.99 相同，使用原参数新编译的 `xl6_sem.o` 也逐字节一致。首次旧布局对象比较发现共享收尾写法带来代码差异，已把新增操作限定到当前字段布局后重新验证；原差异记录保留。未据此宣称当前服务或整体 IDE 更快。

两个负向对照分别移除平面接收者重放和包链接键，均由对应断言以退出码 1 拒绝。8 项守卫检查覆盖正常当前语义／IR 构建拒绝、语义或 AST 改动、注册表／XRT 混搭及新旧语法与语义混搭。

最终构建器把完整前端 cohort 核对应用到新旧两种显式 probe。此收紧发生在上述二进制编译后；已存档测试时的构建器 `build_lsp_core.tested-v4.py`，其余输入与最终源码一致。最终构建器派生的新旧 C 均与已测试 C 逐字节一致。这个控制器核验没有重跑不变的 C 编译，也没有开放正常服务构建。

## 复现与后续

以仓库根目录为当前目录，提供保留的 M78 基础库与一个不存在的新输出目录：

```powershell
python -X utf8 -B .\ide\tools\build_lsp_semantic_facts.py --base .\ide\build\lsp-m78-20261030-76b0f0ca\current-final-v1 --output .\ide\build\semantic-facts-new --base-source-revision 32e4f242d
```

历史 Python 构建器与当前工具不同时，工具只接受摘要匹配的已存档字节或指定提交；C／头文件变动会拒绝复用。基础库复用不等于重新全编译基础运行时。本轮实测 Windows x64／GCC 16.2，其他平台尚未验收。

证据保存在 `ide/build/lsp-m79-20261030-db089541/`：当前／旧单元为 `facts-current-v4`／`facts-legacy-v2`，负向对照为 `negative-v1`，最终守卫为 `guards-v1`，旧对象对照为 `legacy-object-v2`，统一输入与输出摘要复核为 `review-v1.json`。

本轮没有完整原生服务、协议、GUI 或性能验收，也没有发布新服务。下一步继续当前检查器的真实读写／特化声明副作用和注册表准入，然后完成 IR、来源／加载器／报告／XRT 契约，以及全部协议、IDE 与性能验收；长期目标保持 active。
